## 一、功能目标与用户场景

### 目标
回答两类问题：
- **个案**：「这起事故到底怎么回事、依据是什么」→ 详情页
- **总体**：「这类事故的致因结构是什么、哪几个因素总一起出现」→ 致因分析页

### 三条用户路径

| 路径 | 动作 | 系统行为 |
|---|---|---|
| **看个案** | 从列表点某行 | 详情页：48 字段分档 + 致因树 + 每条编码的证据与推断原文 |
| **看结构** | 打开致因分析页 | 5 层 19 类金字塔 + 分布图 + 共现矩阵 |
| **做交叉** | 在致因分析页加筛选（类型/地区/年代） | 全部分析图服务端重算，展示该子集的致因结构 |

### 设计约束
CAICS 的类名**必须来自数据库**（`caics_causes.code` + `caics_causes.name`），不得在模板里硬编码。旧 web 的 `/api/causes/framework` 端点 500 崩溃，根因正是 `hfacs.py:58` 的默认路径指向不存在的 taxonomy JSON 且 `load()` 静默失败——**新方案从表里取类名，这个失败模式从根上消除**。

### 2.3 计数口径：两个数字都成立（2026-09-30 裁决）

`caics_causes` 对 `(accident_id, code)` **没有唯一约束**（建表脚本里的约束从未在真实库生效，见蓝图 03）。实测：

| 口径 | 值 | 含义 | 用在哪 |
|---|---:|---|---|
| **行数** `COUNT(*)` | **16,323** | 致因**标注**条数。同一事故的同一编码可有多条，各带独立证据原文 | 概览统计卡、§2.2 类目分布、§2.6 证据等级表、论文（措辞「16,323 条致因标注」） |
| **去重** `COUNT(DISTINCT accident_id, code)` | **15,985** | 事故×类别**覆盖**数。一条事故在一个类别上只算一次 | §2.4 每事故编码数、§2.5 共现矩阵——凡「事故级」陈述都用它 |

差的 338 = 616 行重复 − 278 组。重复分布：**219 组 2 行、58 组 3 行、1 组 4 行**，涉及 **68 条事故**。

**这 278 组不是写入错误，也不是重复数据**：抽查文山州模架坍塌事故的 M1 三行，证据文本分别是「监理单位发现违规后未采取有效措施进一步制止其施工…」「…未按规定进行高支模施工专项方案论证…」「无视和拒绝执行…停工指令通知…」——是同一类别下的**三条不同原文引用**。全库 278 组中，**0 组**在「证据 + 推断 + 证据等级」三项上完全一致，即没有一组是无信息增量的重复。

> ⚠️ **实现红线**：共现矩阵与「每事故几个致因类别」若照抄行数用法，会把「同一事故同一编码标了 3 次」算成 3 次共现——文山州那类事故（所有编码都 ×3）会把整个矩阵整体抬高。

> **注意措辞边界**：共现是**关联**，不是因果关系。页面文案写「常同时出现」，**不写**「导致」「引起」。项目既定禁用措辞含「因果机制」，此处尤其要守。

**服务端职责**（与 `detail.py` 一一对应）：

- `work_task_label` 等枚举中文名由编码查 `enum_definitions` 得到（`ENUM_COLUMNS` 五列），**前端不硬编码编码表**；查不到的编码原样回显，不写兜底词
- `layer` / `layer_label` 由 `code` 首字母映射（M/F/T/H/C → 管理因素/设施设备/技术工艺/人因/合规），层序按 M→F→T→H→C 固定
- `quality_label` 由 `evidence_quality` 映射固定文案
- `tiers` 把「分档定义 + 各档实际有值数」一并下发。分档表**只在 `detail.py` 定义一次**，服务端算数、前端按同一个定义渲染，两边不会漂移
- **同一编码多条标注**：按 `code` 合并为一条，多条证据并列进 `citations`（不是去重丢弃）；该编码的 `evidence_quality` 取多条中**最强**的一条——「原文有直引」不因并存一条弱推断而降级
- **证据文本兜底**：`caics_causes.evidence` 实测 **8 条空串**、`inference` **11 条空串**（两列均无 NULL）。不能假定「有编码就有证据文本」；缺失时给 `null`、页面显示「未提供证据文本」，**不得用 `code` 的类名去冒充证据**——那会把"无证据"伪装成"有证据"，直接损害证据三级分层的可信度
- **不提供 `cause_chain` / `primary_cause`**：`accidents` 表实测**没有这两列**，`caics_causes` 也没有编码间顺序字段（`sort_order` 是展示排序，不是因果推进）。链条形式的「致因链」在本库无数据支撑，**不编造**；详情页只呈现并列的类别集合
- **找不到时返回 404**（而非 200 + 空对象）：「没有这条」与「这条什么都没有」是两件事，前端要能分开处理

### `GET /api/causes/framework`
CAICS 体系定义（19 类 + 层归属），页面初始化时取一次。

```json
{ "ok": true, "data": {
  "version": "caics_v1.0",
  "layers": [
    { "key":"M", "label":"管理因素", "count":7077, "categories":[
        {"code":"M1","name":"现场监管缺失","count":2208,"accidents":2166},
        {"code":"M2","name":"隐患排查失效","count":1784,"accidents":1755},
        {"code":"M4","name":"制度规程漏洞","count":1390,"accidents":1361},
        {"code":"M3","name":"安全培训不足","count":1200,"accidents":1170},
        {"code":"M5","name":"市场行为违规","count":495,"accidents":468} ] },
    … 其余四层 F / T / H / C，结构同上 ],
  "total": 16323,
  "covered_accidents": 2618,
  "evidence_quality": [
    {"key":"direct_quote","label":"直接引用","count":14784},
    {"key":"indirect_infer","label":"间接推断","count":1117},
    {"key":"weak_infer","label":"弱推断","count":422} ]
} }
```

> **层序固定为 M → F → T → H → C，不是按计数排**（`LAYER_ORDER`）。五层全给，即使某层计数为 0——缺层会让页面少一行，读者无从分辨「这层没有」与「这层没返回」。

> `code` 与 `name` **取自 `caics_causes` 表的 `GROUP BY code, name`**，不是常量。若表中出现体系外的 code，`framework` 会如实列出——**不静默丢弃**。
>
> **这份计数是全库的，不随筛选变化**，命中时也**不重排**。前端拿它的顺序当 19 类明细的骨架：改筛选条件时条长变、位置不变。若按筛选后的计数重排，每改一次条件整个列表就洗一次牌，反而看不出「改条件后哪一类掉得最多」——而后者正是这张图要回答的（`causes.framework()` docstring）。
>
> `categories[].accidents` 是**含该编码的事故数**（与 `count` 的编码行数口径并列，见 §2.3）。`evidence_quality` 与概览页同源——`framework()` 直接复用 `overview.build()` 的结果，不另算一遍。

### `GET /api/causes/distribution`
带筛选的致因分布，供致因分析页的交叉分析。

| 参数 | 说明 |
|---|---|
| `accident_type` / `severity` / `province` / `project_type` / `construction_phase` | 与列表页同口径的下推筛选 |
| `year_from` / `year_to` | 年份区间 |
| `q` / `has_causes` | 关键词、有无编码，同列表页 |

> **蓝图原定的 `by` 参数（`layer` · `code` · `year` · …）没有实现，也不该实现**：一次请求就返回了 `by_layer` / `by_category` / `evidence_quality` 三块，页面同屏渲染。按 `by` 分次请求要把同一批筛选跑三遍，三块之间的数字还可能因为请求间数据变动而对不上——本项目反复强调的「同一批数字不在多处各算一遍」在这里直接由「一次给全」落实。**蓝图此处已按实现更正**。

`scope` 与 `filter` **平铺在 `ok` 平级**，不进 `data`（即蓝图 00 §4.1 里第 2 类形状）。理由是这两个块回答「我现在在看哪个子集」，要跟 `data` 一起在页面顶部常显；塞进 `data` 会让「是结果还是元信息」在模板里分不清。

```json
// 实测：?accident_type=坍塌
{ "ok": true,
  "scope": { "accidents": 1092, "causes": 6352, "covered": 1092,
             "pairs": 6174, "without_causes": 0, "filtered": true },
  "filter": { "q": "", "province": [], "severity": [], "accident_type": ["坍塌"],
              "project_type": [], "construction_phase": [],
              "year_from": null, "year_to": null, "has_causes": null,
              "sort": "date_desc", "page": 1, "size": 50 },
  "data": {
    "by_layer": [ {"key":"M","label":"管理因素","count":2801,"accidents":1078},
                  {"key":"F","label":"设施设备","count":1150,"accidents":1073},
                  {"key":"T","label":"技术工艺","count":630,"accidents":559},
                  {"key":"H","label":"人因","count":1700,"accidents":1039},
                  {"key":"C","label":"合规","count":71,"accidents":66} ],
    "by_category": [ {"code":"M1","name":"现场监管缺失","layer":"M",
                      "layer_label":"管理因素","count":857,"accidents":834,
                      "share":0.1349}, … ],
    "evidence_quality": [ {"key":"direct_quote","label":"直接引用",
                           "count":5455,"accidents":1083}, … ],
    "evidence_unknown": 0,
    "total_causes": 6352
} }
```

> **口径**：`count` = 编码行数，`accidents` = 覆盖事故数，**两个指标含义不同，页面上要分开标注**。`share` = `count / total_causes`（编码占比），至于「含该类编码的事故占子集事故的比例」，前端拿 `accidents / scope.accidents` 现算即可——**响应里不给现成的比率**，免得同一批数字在服务端与前端各算一遍（`causes.py` 的既定做法：能复用就复用，不在多处重复计算）。
>
> `by_category` **按 `(层序, 计数降序)` 排**（层序取 `LAYER_ORDER`，同 `framework`），与 `framework` 那份**全库**顺序不同——这里是**当前筛选子集**的计数。两处各自服务于自己的图，别混用。
>
> `scope.pairs` 是 `DISTINCT (accident_id, code)` 的条数（见 §2.3 去重口径），`scope.causes` 是编码行数，二者在坍塌子集里差了 178，正是重复编码的量。`without_causes` 报出子集里**一条编码都没有**的事故数——不报的话读者会拿它去减 `accidents` 然后找不到差额（`scope()` docstring）。
>
> `filter` 回显的是列表页那套 `ListParams.normalized()`，所以**带着 `page` / `size` / `sort`**——这三个对本接口无意义（这里不分页、不排序）。共用同一个归一化出口换来的是「筛选器口径与列表页必然一致」，代价是回显多了三个字段。**前端不得读这三个键**（`check_field_alignment.py` 会报出无人读的字段，仅供排查）。
>
> `evidence_unknown` 是落三级之外的取值计数。实测为 `0`，但**不并进任何一档**——吞掉就再也发现不了（`distribution()` docstring）。

### `GET /api/causes/cooccurrence`
编码共现。

| 参数 | 说明 |
|---|---|
| `top` | 返回前 N 对，默认 20，上限 100 |
| 其余筛选参数 | 同 `distribution` |

```json
{ "ok": true, "data": {
  "codes": ["M1","M2","M4","M3","M5","F2", … ],     // 19 个，顺序同 framework
  "names": ["现场监管缺失","隐患排查失效","制度规程漏洞", … ],
  "layers": ["M","M","M","M","M","F", … ],          // 与 codes 逐位对齐
  "pairs": [ {"a":"H1","a_name":"违反操作规程","b":"M1","b_name":"现场监管缺失",
              "count":1821, "joint_share":0.6956, "lift":1.085}, … ],
  "pair_total": 171,
  "scope": { "accidents": 2618 },
  "matrix": [ [0, 1386, 1083, 1024, …], … ],        // 19×19，全量
  "sort": "count",
  "filter": { "min_count": 10 } } }
```

> **`codes` / `names` / `layers` 是矩阵的坐标轴**，前端不该自己按字母排序去对位——`matrix` 的行列下标就是这三个数组的下标。三者的顺序**来自 `framework` 那份全库骨架**（层内按全库计数降序），所以矩阵的行序**不随筛选变化**：切条件时格子里的数变、行列位置不变，热力图的「形状变化」才看得出来。
>
> `pair_total` = 门槛前的**全部**对数（实测 171），`pairs` 是过了 `filter.min_count = 10` 再取前 `top` 的那几条。报出总量是为了让读者知道「当前显示 20 对，条件范围内共有 171 对」，而不是以为世界上只有 20 对。
>
> `scope.accidents` 在这里**不是**主库全部事故数，是**有编码的事故数**（实测 2,618）——`lift` 的分母。拿全部 2,623 当分母会把所有 `lift` 整体压低，且压得没有意义（`cooccurrence()` docstring）。

> **两条实现红线**：
> 1. **必须先去重再自连接**——`FROM (SELECT DISTINCT accident_id, code FROM caics_causes) a JOIN (…) b ON a.accident_id = b.accident_id`。直接 join 原表会把「同一事故同一编码标了 3 次」算成 3 次共现（见 §2.3）。按行数算 H1+M1 是 1,968，去重后 1,821，**页面用后者**。
> 2. `count` 是**事故数**，不是编码出现次数——文案写「1,821 条事故中同时出现」，不写「共现 1,821 次」。
>
> `lift` = 实际共现率 / 独立期望率，用于剔除「因为 M1 本身出现得多所以共现多」的伪相关。**页面默认按 `count` 排序，`lift` 作为可切换的第二种排法**（实现后修订，理由见下）——实测按 `lift` 排的榜首是 `C1 + H4`（仅 24 条事故支撑，lift 6.42），首屏给不出数据的主线；按 `count` 排的榜首 `H1 + M1`（1,821 条，lift 1.08）才是。lift 的价值在**筛选到具体子集之后**看（如限定「坍塌」后榜首换成 `H2 + H4`，10 条，lift 2.93），那时它才能提示偏离基线，默认位让给它并不合适。

### `GET /api/causes/timeline`
编码随年代的变化（供年代交叉图）。

**粒度是「每年 × 每层」，不是「每年 × 每个编码」**。19 类各画一条线，49 个年份里有数据的只占一半，图会碎成一片——层这一级才看得出趋势。

```json
{ "ok": true, "data": {
  "years": ["1978", … "2026"],                     // 连续补零，共 49 个
  "accidents": [4, 1, 4, 6, 6, …],                 // 每年总事故数，作分母
  "by_layer": [ {"key":"M","label":"管理因素","counts":[4,1,4,6,6,…]},
                {"key":"F","label":"设施设备","counts":[…]},
                {"key":"T","label":"技术工艺","counts":[…]},
                {"key":"H","label":"人因","counts":[…]},
                {"key":"C","label":"合规","counts":[…]} ],
  "without_date": 30 } }
```

> **`years` 是连续补零的**（实测 1978–2026 共 49 个），1991–2004 那十四年`counts` 全是 0。**折线必须在缺口处断开**（见蓝图 04）——若只返回有数据的年份，折线会从前一点直接连到后一点，读者看不出中间空了十四年，而那正是数据来源的历史特征。
>
> `counts` 是**覆盖事故数**（`COUNT(DISTINCT accident_id)`）而非编码行数：趋势图回答的是「这一年有多少条事故涉及管理类致因」，不是「标注了多少行」。`accidents` 是同年全部事故数，**一并给出作分母**——1980 年代那几个点的占比波动到底是结构还是样本量，读者要能自己判断（`timeline()` docstring）。
>
> `without_date` 是**没有日期、落不到任何年份**的事故数（实测 30 条，NULL 与空串都有）。不报出来，读者会拿它去和口径条上的事故总数相减，然后找不到差额。

**关键交互**（已实现于 `static/accident.js` + `static/app.css` ⑪ 节）：

- **层分组而非平铺**：致因树按 M/F/T/H/C 五层分组（层序固定，不随计数变化），各层内按 `sort_order` 排。19 类平铺成一长列读者无法理解，分层才对应 CAICS 的体系结构。
- **证据两级折叠**：默认只显示「编码 + 类名 + 证据等级徽章」；点开才展开 `evidence` 与 `inference` 两段原文。均值 6.1 类 × 2 段文本默认全展开会让页面过长。
- **多标注显示 `×N` 角标**：同一编码在本事故下有 N 条标注时，角标提示 N，展开后 **N 条证据并列**（见 §2.3——它们是同一类别下的不同原文引用，不合并、不丢弃）。
- **无 `cause_chain` 区块**：库里没有这个数据，不渲染空壳（见 §三 的接口说明）。
- **未提及字段**：显示为虚线下的「—」并可 hover 提示「原报告未提及」——**空值与"没有"要能区分**（`deaths=0` 显示为 `0`，不是「—」）。
- **四档始终渲染**：A 档默认展开、B/C/D 默认折叠，但**不隐藏**。D 档 `weather` 只有 7.9%、`trapped_count` 10.3%——它们的存在与否本身反映采集源的信息丰富度，隐藏掉就把「原始报道提供了什么」这一层信息也丢了。
- **返回列表保持状态**：列表的筛选条件与页码带在 URL hash 里（蓝图 04 已设计），详情页的「返回列表」走 `history.back()`，浏览器原样恢复；直接进详情页（无历史）时退回首页。

## 五、技术选型与理由

| 选择 | 理由 |
|---|---|
| **类名查表，不硬编码** | `caics_causes` 自带 `code` + `name`（19 类实测齐全）。旧 web 因依赖缺失的 taxonomy JSON 而 500，此方案从根上消除该失败模式 |
| **层归属由 code 首字母推导** | `substr(code,1,1)` → M/F/T/H/C。已有数据严格符合（实测 19 类 5 前缀齐全），无需额外映射表 |
| **聚合查询下推 SQL** | `GROUP BY code` / 自连接做共现 / `substr(date,1,4)` 做年代——都在 SQLite 内完成。2,623 条 × 16,323 行的规模下毫秒级 |
| **共现提供 lift 而非只有 count** | 高频编码（M1 出现 2,208 次）天然与所有编码共现多，`count` 排序会误导。lift 校正后才能真正看出关联强度 |
| **图表用内联 SVG / CSS** | 与蓝图 04 一致，**不引 CDN**，保证离线可用。金字塔与条形图用 CSS 宽度百分比；共现热力图用内联 SVG 网格 |
| **致因树按层分组** | 对应 CAICS 的体系结构；平铺 19 类不可读 |
| **详情页一次请求返回全部** | 6.2 条编码 × 2 段文本 + 48 字段，单次响应约 20–40 KB，远小于旧版 `/api/dataset` 的 21.5 MB |

## 七、验收标准

1. `GET /api/causes/framework` 返回 **19 类**，各层计数为 M 7,077 / H 4,723 / F 2,799 / T 1,533 / C 191，`total = 16323`
2. 19 类的 `code` + `name` 与 `SELECT code, name, COUNT(*) FROM caics_causes GROUP BY code` **逐项一致**
3. `GET /api/accidents/<id>` 对每条记录返回的 `causes.items` 条数 = 该 `accident_id` 在 `caics_causes` 的实际行数
4. 12 列 A 档字段在 100% 的记录上都有返回键（值可为 `null`，但键必须存在）
5. `GET /api/causes/cooccurrence` 的 Top 1 为 `H1 + M1 = 1821`（去重口径，**不是** 1,968）
6. `GET /api/causes/distribution`（无筛选）的 `by_layer` 五项 `count` 与 `framework` 的层计数逐项一致（M 7,077 / F 2,799 / T 1,533 / H 4,723 / C 191）
7. 加 `accident_type=坍塌` 筛选后，`scope.accidents = 1092`，且 `scope.causes` = `SELECT COUNT(*) FROM caics_causes WHERE accident_id IN (SELECT id FROM accidents WHERE accident_type='坍塌')`
8. 证据等级分布：`direct_quote` 14,784 / `indirect_infer` 1,117 / `weak_infer` 422（无筛选时）
9. 每条编码的 `evidence_quality` 落在三级之内，且页面按三级三色正确渲染
10. 含 29 条编码的事故（最大值）详情页正常渲染，无截断、无卡顿
11. **`causes.items` 为空的事故（5 条）**：详情页显示「该事故暂无致因编码」而非空白区域
12. 构造 `code` 不在 19 类内的数据，`framework` 如实列出而非丢弃（用测试库验证）
13. 无任何 CDN 引用（`grep -r "http://" templates/ static/` 只应命中 `source_url` 之类的数据字段）
