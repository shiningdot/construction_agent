## 一、查什么

「对齐」落到代码上有四件不能有的事，**本节脚本**（`check_web_alignment.py`）覆盖
其中前两个维度。渲染、字段名、交互三个维度各有自己的脚本，见 §六 / §七 / §八。

**路由维度**（静态分析，不需要数据库）

| 缺口 | 形态 | 后果 |
|---|---|---|
| **孤儿端点** | 后端实现了、前端从不调用 | 数据层有、展示层缺。功能上「有」，用户够不到 |
| **幽灵调用** | 前端在请求、后端没有这条路由 | 点下去就是 404 |

核查范围是四个 API 蓝图（`api` / `collect` / `extract` / `review`）的全部路由，与
`static/*.js`、`templates/*.html` 里全部 `/api/...` 调用点。

**页面维度**（起 app 打真实请求）

| 缺口 | 形态 | 后果 |
|---|---|---|
| **打不开的页面** | 路由在、请求报 500 | 蓝图 07 验收第 1 条直接不过 |
| **没有入口的页面** | 能打开，但从任何页面都点不到 | 只能手敲 URL 进，等于不存在 |

## 二、判据：为什么第一版是错的

第一版脚本用的是**静态段顺序查找**——把路由的静态段按序在前端源码里找，
段落在别处偶然出现过就算「有调用」。它给 42 条路由报了 **0 条孤儿**。

这个结论是假的。`/start`、`/cancel`、`/rerun` 这几个后缀在前端源码里到处都是
（按钮文字「取消」、状态映射 `cancelling: '取消中'`、`// 启动` 注释、模板里的
`id="rerunBtn"`），判据只看「字符串出现过」，自然全部命中。真有一条孤儿，
是手工 grep 调用路径才挖出来的。

改用**路径形状匹配**：把两侧的变量段与 query string 都归一成 `<>`，再做集合运算。
难点在前端拼接——`'/api/extract/tasks/' + t.task_id + '/start'` 在源码里是三个字面量
夹两个表达式，所以从 `/api` 那串起贪心地吃后续的 `+ expr + '...'` 片段。

两个起初踩到的坑，一并记下来免得重蹈：

1. **蓝图前缀**：装饰器里写的是蓝图内相对路径（`/tasks`），完整路径要加上
   `Blueprint(url_prefix=...)` 的前缀（`/api/collect/tasks`）。漏了这步，
   41 条路由会全部对不上，报出一大片假孤儿。
2. **正则捕获的是 `api_bp` 不是 `api`**：前缀映射的键必须带 `_bp` 后缀。

## 三、结果

### 3.1 路由维度

```
后端 API 路由 41 条（36 种路径形状）
前端调用点   44 处（36 种路径形状）

✓ 后端每条路由都有前端调用点
✓ 前端每个调用点都有后端路由
```

44 > 41 是正常的：同一端点被多处调用（如 `/api/health` 在 3 处），且部分调用
共享同一路径形状（query 参数不同）。

### 3.2 页面维度

```
✓ 200  /                              ✓  5 个入口  /
✓ 200  /accident/<accident_id>        ✓  1 个入口  /accident/<accident_id>
✓ 200  /causes                        ✓  5 个入口  /causes
✓ 200  /collect                       ✓  5 个入口  /collect
✓ 200  /extract                       ✓  5 个入口  /extract
✓ 200  /review                        ✓  5 个入口  /review
```

（左右两栏是脚本两块输出的合并排版——真实输出先列全部状态码、再列全部入口数。）

6 个页面全部 200（蓝图 07 验收第 1 条），全部有入口。四个主页面互为 5 个入口
（顶部导航的 5 个链接），详情页的 1 个入口来自概览列表——它是叶子页，1 个入口
是它应有的形态。

页面维度有两个必须真跑起来才判得了的地方，都是这次踩出来的：

1. **导航不在源码里**。导航写的是 `url_for('views.xxx_page')`，`templates/` 与
   `static/` 里没有 `/collect` 这样的字面量——拿字面量去源码里找，6 个页面的
   入口数全是 0。只能起 app、打真实请求、解析**渲染后**的 HTML。
2. **入口要算两路**。列表页的详情链接是 JS 拼的（`overview.js:470`
   `href: '/accident/' + encodeURIComponent(it.id)`），服务端 HTML 里没有。
   只数渲染后 HTML 的 href，详情页会被误判成「谁也链不到」——它其实正是唯一
   那个叶子页，1 个入口恰恰说明结构是对的。所以入口 = 渲染后 href ∪ 该页加载的
   JS 里的路径字面量。

## 四、处理掉的那一条孤儿

`GET /api/accidents/<id>/images`（原 `api.py:80`）— **已删除**。

它是**真孤儿**：前端 0 个调用方，详情接口已经内联了 `images` 数组。删它有两条依据：

1. **它自己的定位不成立**。蓝图 06 §4 写的是「既然详情接口已返回 `images` 数组，
   此端点供画廊单独刷新或分页使用」——「刷新」靠 F5 就能做到，「分页」则被数据
   否掉：实测单事故最多 **7 张**，≥10 张的 **0 个**（559 个有图事故的完整分布见
   `check_web_alignment.py` 同期的 `img_dist` 查询）。
2. **它的实际成本是双份逻辑**。这段取数（取清单 → 取可疑哈希 → 逐条打 `shared`
   标记）在 `api.py` 与 `detail.py` 里是**逐字重复**的两份，一旦漂移，同一事故经
   两条路拿到的标记就不一样。

取数已收敛到单一出口 `images.for_accident_marked()`，`detail.py` 改调它，测试的
5 处断言改走**详情接口**——测的正是前端真正走的那条路。

顺带清掉的过时内容：

- `api.py` 里 `GET /api/images/stats` 的 docstring 还写着「覆盖率只有 7.4%」（单版口径），
  已改为三版合并口径 21.3% 并说明 `accidents_with_images_legacy_only` 的含义
- `detail.py` 的注释还在说「`image_files` 的 `local_path` 三版混存，按它拼 URL 会大面积
  404」——这条论断已被 08 的复核推翻，改为「旧登记与磁盘真源差 123 张 / 83 个事故」

## 五、代码领先于数据：两类不对齐

路由与调用都对上，不等于系统就是对的——两侧代码都「对」，中间的**数据与 schema**
却可能停在旧版本。本次撞见两类，共同点是不会报「字段不存在」，而是页面照常渲染、
只是少了东西，或者直接 500。

### 5.1 `image_manifest` 口径落后

核查路由时发现工作库的 `image_manifest` 停在**旧口径**：226 行 / 193 事故，
版本分布只有 `v3`。

代码已经把取材范围放开到三版，库里却还是单版——**代码对了、数据没跟上**，
这同样是端到端断裂：页面上会照常显示图片，只是少了 725 张、少了 366 个有图事故，
而且不报任何错。

重建后的实际值与代码口径一致：

| | 旧（库内） | 新（重建后） |
|---|---|---|
| 行数 | 226 | **951** |
| 有图事故 | 193 | **559** |
| 版本分布 | v3: 226 | **v1: 263 / v2: 462 / v3: 226** |
| 内容非图片被剔除 | — | **2**（`imageV2/` 下两个 `.webp`，内容是 HTML 与 MP4） |

重建命令（图片在主仓库、工作库在 worktree，所以要显式给 `--data-dir`）：

```bash
/home/suntianhao/construction_agent/.venv/bin/python3 scripts/build_image_manifest.py \
  --data-dir /home/suntianhao/construction_agent/data \
  --report /tmp/img_report.json
```

> 不加 `--data-dir` 时脚本会用 worktree 自己的 `data/`，那里**没有图片目录**
> （`.gitignore` 忽略了），结果会是「扫描到 0 张」——不是数据没了，是找错了地方。

### 5.2 工作库 schema 落后：审核页两处 500

同一趟探测还撞见 `/api/review/queue` 与 `/api/review/stats` **双双 500**：

```
sqlite3.OperationalError: no such table: promote_log
```

工作库的 schema 停在 `staging_v1.0`（现为 `v1.1`），缺 `promote_plans` 与
`promote_log` 两张表——它们是 `staging_schema.py` 后来才加的，而库是更早建的。
`review.py` 在 rollback / history 等入口写了 `_has_table("promote_log")` 检查，
但 `queue` 与 `funnel_payload` 没有；`promote.py` 里读这张表的两处
（`history()`、`promoted_accident_ids()`）自身也不容错。**缺一张空表就把审核页
整块打成 500**，违反蓝图 07 验收第 1 条「全部页面返回 200 无 500」。

两处都修了：

- `promote.py`：`history()` 与 `promoted_accident_ids()` 在表不存在时返回空集——
  缺表 ≡ 从没并入过任何东西，语义上正确。顺带补上 `if not ids` 防御：空列表会
  拼出 `IN ()`，而 SQLite 不接受空集合
- 工作库补表：跑 `scripts/create_staging_db.py`（幂等，DDL 是
  `CREATE TABLE IF NOT EXISTS`，不动既有数据——`image_manifest` 的 951 行原样保留）

回归测试 `test_工作库缺_promote_log_时审核端点不崩` 覆盖这条路径。

### 6.0 详情页差点从核查里消失

上面这张表早先有一行「详情 1,085 字 7 图」——**那时详情页是截得到的**，样本从
工作库的 `image_manifest` 里挑「图最多且有 CAICS 编码」的事故。后来主仓库的工作库
退回成空壳（一张表都没有），`pick_sample()` 挑不出来就整个跳过详情页，于是这一页
**静默地从核查里消失了**——不报错、不提示，只是表里少一行，而当时详情页恰恰改过
三列展示（`project_type` / `construction_phase` / `collapse_subtype`）。

修法是两级挑选：有图更好（覆盖图片区），没图也必须截。**详情页不依赖工作库也能
渲染**——图片区给空清单 + `images_available=false`，文字区、致因树、四档折叠照常。
退回主库直选时的条件是「有编码 + 有摘要 + 有伤亡 + `collapse_subtype` 非哨兵」，正好
让新增的三列都落在有值的路径上。

这一改立刻看出两个只有看图才知道的问题：

1. **长文本格把三列网格撑爆**。字段明细是 `repeat(auto-fill, minmax(320px, 1fr))`
   网格，摘要塞进单格里把那一行撑到十几行高，同行的短字段右边留一大片空白，后面
   的字段被挤下去（网格行高由该行最高的一格决定）。修法：正文级长文本（摘要 /
   直接原因 / 检索增强文本）`grid-column: 1 / -1` 独占一行，短字段重新排整齐。
   **摘要与直接原因在首屏专卡里已展示过，字段明细里仍保留**——那一区的语义是
   「接口返回了什么」的完整对照表，不能因为别处展示过就漏列。
2. **没有图的空态是「说明」不是「空白」**。工作库不可用时详情页的图片区写着
   「图片索引未重建 / 图片登记表与磁盘对不上，需要先跑 `scripts/build_image_manifest.py`」，
   而不是留白或报错——与采集 / 提取 / 审核三页的空态同一个做法。

这几页还顺带确认了几处只有看图才知道的事：

- **空态是空态，不是错误页**。采集 / 提取 / 审核三页的工作库部分都是 0 行，页面
  照常给出「还没有采集任务。」「先去『在线采集』把相关记录标出来。」这类**指路**
  文案，而不是报错或留白——这正是蓝图里「空态要说明下一步做什么」的落地。
- **脏值没有冒充标准省份**。概览页的省按钮区把「境外及港澳台 46 / 未归一 4 /
  未标注 14」与标准省份分列，底部数据质量区另注「32 个省单位 · 3 个脏值」。
- **页脚会自己报缺索引**。采集、提取、详情三页的页脚都写着「⚠ 缺 3 个索引，
  列表筛选会明显变慢（scripts/add_indexes.py）」——第 4 步还没跑，系统就把该跑
  什么说了出来。（概览页页脚走的是另一套文案：2,623 条事故 · 16,323 条编码。）
- **详情页把「图可能是别的事故的」摆在了明面上**。样本 7 张图，页面自己标出
  「7 张 · 2 张有多模态分析」；其中 2 张带**「多事故共用」红标**（同一图床图被
  多起事故引用），6 张带**「历史版本」**角标（来自早期目录 `images/`、`imageV2/`，
  未必是最终采纳的版本），并写明「最终版（imageV3）排在最前」。
- **字段四档折叠是实装的**：A 必显 11/11、B 有则显示 6/7、C 折叠 0/5、D 高级
  折叠 1/6，右上角注明「按有值率分档，折叠的不隐藏」。这条正是 §五 5.1
  字段填充率两极化在界面上的落法——必显档全是 100% 的字段，C 档 0/5 说明该
  事故这五个字段一个都没有，页面对空档的处理是收起而不是留一排空行。

### 6.1 途中挖出的缺口：图片根没有覆盖开关

第一次跑探针时详情页 **7 张图全部 404**。根因不是代码写错，是**配置不对称**：

| 路径 | 默认值 | 可用环境变量覆盖 |
|---|---|---|
| 最终库 | `settings.DATA_DIR / caiems_v2.db` | `CAIEMS_DB` |
| 工作库 | `settings.DATA_DIR / caiems_staging.db` | `CAIEMS_STAGING_DB` |
| **图片根** | `settings.DATA_DIR` | **（无）** |

三者的默认值都从 `settings.DATA_DIR` 派生，而它跟着**被导入的包**走——在
worktree 下运行时指向 worktree 自己的 `data/`，那里没有图片目录（`.gitignore`
忽略了，图留在主仓库），于是 `/media/...` 全部 404。库路径早就用一个环境变量
解决了同一类问题，图片根漏了这一环。

已补 `CAIEMS_DATA_DIR`（`images.py`），与另两个对称。这不是给 worktree 开的
后门——图片放在别处、或 `data/` 挂到别的挂载点时，此前没有任何办法指定。

## 七、字段级：前端读的名字 ↔ 后端返回的字段

到这里还剩一类错配看不见：**后端返回 `death_count`、前端读 `deaths`**。页面不
报错、控制台干净、数字对账也全对，只是那一格永远显示「—」。出错的不是值，是
**名字**。

`scripts/check_field_alignment.py` 把两侧的名字对账：起 app 打真实请求，把 JSON
递归展平成字段路径；再读 `static/*.js` 与 `templates/*.html`，抽出全部 `.属性`
读取。前端读的每个名字落到四层之一就放过：

| 层 | 个数 | 是什么 |
|---|---|---|
| 后端运行时返回过 | 117 | 名字确实在 JSON 里——最强证据 |
| JS/DOM 白名单 | 24 | `.length`、`.classList`、`.dataset`，以及 `dom.js` 导出的 `el` / `num` / `blank` |
| 前端自己构造 | 4 | `on` / `accent` / `color` / `dev_pct`，每个都在代码里注明了出处 |
| 后端源码里出现过 | 126 | 兜底：库空时端点上没有元素可展 |

264 个读取全部有归属，**未归类 0 个**。

### 7.1 判据是怎么定下来的

第一版把 JSON 展开成字段路径、与前端 `.属性` 直接做差集，报了 156 个候选，绝大
多数是噪音——前端内部工具函数的属性（`add` / `clear` / `createElement`）跟后端
字段名混在一起。这次逐个查清了两类假信号：

1. **注释里的文件名**。`/* … overview.js 里还有一份… */` 会被当成 `.js` 属性读取。
   先剥注释。
2. **赋全局那几行**。`global.num = num` 里的 `.num` 是**定义**，不是读取。排除
   「点号后面跟单个等号」的位置（`==` 不算，那是比较）。

修完这两处，候选从 156 降到 4，而那 4 个也都查清了：`on` / `accent` / `color` 是
前端配置对象的键（`opts.on` 是事件表、`c.accent` 决定要不要加样式、`cfg.color(r)`
是取色回调），`dev_pct` 是 `usage()` 给后端的 `deviation_pct` 起的别名——查过后端
`extract.py:207`，那个字段确实返回，链路是通的。

同一批里还验过一次**反向**的：`/api/extract/tasks` 返回的 `usage` 对象，前端读
`tokens` / `est_tokens_so_far` / `deviation_pct` 三个名字，后端的 `extract.py:202-208`
逐个对得上。这类字段最容易在改名时单边漂移——后端改了 `deviation_pct`，前端还读
旧名，两边都不报错。

### 7.2 这一维的边界

**没被兜住的部分**：18 个端点的数组是空的，元素字段核不到。脚本会把它们连同空
数组的位置一起打出来，例如：

```
/api/review/queue            data
/api/collect/tasks           data
/api/accidents/<id>          data.images
/api/collect/stats           data.by_source data.funnel
```

这些字段能过四层里的一层，**是因为别处见过，不是因为在元素上核过**。这与 §五 的
空工作库是同一条边界：采集 / 提取 / 审核三组的表是 0 行，只在这三处出现的字段，
静态判据认不出、运行时也展不出。第 45 项全链路验证（起真实任务跑一遍）覆盖的正是
这一段，但那次是一次性的，没有固化成可复跑脚本——**库里灌了数据后重跑本脚本才算数**。

### 7.3 同一条脚本的反方向：`accidents` 的列 ↔ 详情页四档

上面这一半只查「前端读了什么」。缺口还有另一种形态，它天生查不出来：**后端表里
有值、页面上从未出现**。前端不会去读一个后端没下发的名字——它读不出来，也就永远
不会出现在「前端读取」那个集合里。7.1 里那套判据再准也看不见它。

所以同一条脚本又做了一件事：把 `accidents` 的**每一列**拿去对
`detail.CONTENT_TIERS` ∪ `META_FIELDS`，两边都不在的必须进 `DETAIL_NOT_SHOWN`
并写明理由（目前两项：`raw_text` 在响应顶层单独下发、`work_task_enum` 是 1.0 残留列）。

一查就查出三列：

```
── 不在任何档里：5 列 ──
  project_type               有值  2623 / 2623
  construction_phase         有值  2623 / 2623
  collapse_subtype           有值  2623 / 2623   ← 其中 1320 行是哨兵「不适用」
  raw_text                   有值  2623 / 2623   （单独下发，前端读了 ✓）
  work_task_enum             有值  1538 / 2623   （1.0 残留列，有意排除 ✓）
```

`project_type`（工程类型）与 `construction_phase`（施工阶段）**有值率 100%**、
在 `accidents` 里排第 7/8 位，列表页有「工程类型」列、概览页有这两维筛选，**唯独
详情页看不到**。`collapse_subtype` 同理。

**根因在文档，不在代码**：蓝图 05 §2.1 的分档表只列了 43 个列名，而顶层标题写着
「48 列实测分档」——五列的去向没人交代（其中两列还是 100% 有值的核心分类）。实现
忠实照抄表格，缺口就从文档进了代码。这与 §8.2 是同一种病：**蓝图里的表格比声称
的范围少了几项，实现照着表格做，文档的漏项变成了代码的漏项**。

三列的处置：前两列进 A 档（与 `accident_type` 同类），`collapse_subtype` 进 C 档。
后者还带出一个数据侧的问题——`step1_basic_extractor.py` 给「仅某类事故才填」的
字段约定了一个字面量**「不适用」**做哨兵（「仅坍塌/土方坍塌类填写，非坍塌类填
'不适用'」）。列里 2,623 行全部非空，但 **1,320 行就是这个哨兵**。不归一的话，
1,320 条非坍塌事故会各显示一行「坍塌子类：不适用」，C 档的 `available` 也会被顶成
满值。`detail.py` 读它时归一成缺失，真实有值 1,303 / 49.68%。

**这条判据反向验证过**：在内存里把 `project_type` 从 A 档挖掉，脚本报
`['project_type']`；再挖 `collapse_subtype`，报两列。挖一列报一列，不是恒过。

**这一维的边界**：它只认 `accidents` 的列，`caics_causes` / `enum_definitions` 等
其余八张表不查——那几张表的值进页面要走聚合与查表，列名与展示名不是一对一，
「没展示」与「不该展示」分不开。另外它判的是**列有没有归宿**，不判**归宿对不对**：
`trapped_count` 进 D 档而它有值率 100%（值几乎全是 0），档位是否合适由 §2.1 的分档
理由说了算，脚本管不着。

## 八、交互：点下去之后页面对不对

前四个维度验的全是**首屏**——路由通不通、页面开不开、渲染坏没坏、名字对不对。
用户在页面上做的事——勾筛选、翻页、粘贴链接、重置——一层都没验过。接口对账
（`e2e_verify_main.py` 那 45 项）验的是 API 层，也管不到「按钮绑没绑上」。

`scripts/check_web_interaction.py` 用无头浏览器真点一遍，看**页面自己说的话**
跟**点完之后的结果**对不对得上。十一条：

| 断言 | 观察到的 |
|---|---|
| 初始加载 | 分页器有总数，且是多页 |
| **概览页维度齐全** | chips 的 `data-key` 集合 == `/api/filters` 的五维（见 8.3） |
| **致因页维度齐全** | 同一判据，同一份 `/api/filters` |
| 勾一个省份 chip | 总数 == 该 chip 自己标的条数 |
| 列表真的只剩该省 | 首行确属该省 |
| 再点一次取消 | 总数回到初始，hash 里 `province` 已清空 |
| 翻到第 2 页 | 页码变了、首行换了、总数不变 |
| 粘贴链接能复原 | 新开页与当前页首行一致、chip 无残留选中 |
| **过期链接自愈** | 过期的省份值被清掉，列表回到全部 |
| 关键词搜索 | 总数变小，且首行标题确实含该词 |
| 重置 | 回到初始总数与首行 |

**断言为什么能自洽、不写死数字**：概览页每个 chip 的 `title` 里就写着
「辽宁省：137 条」——那是后端 `/api/filters` 算的计数。点下去之后分页器的
「共 N 条」应当**等于**它。两个数出自不同代码路径（筛选器计数 vs 列表查询），
相等才算对齐。所以脚本里没有 `2623` 这种常量，数据变了照样跑。

### 8.1 途中挖出的缺口：`meta.filters` 回显的是假话

第 9 条「过期链接自愈」是在前八条之后补的，起因是实测：

```
GET /api/accidents?province=北京        （库里只有「北京市」，没有「北京」）
  → total = 2,623     全部条数，没筛
  → meta.filters.province = ["北京"]    声称筛了
```

`province.filter_clause` 对未识别的键是**静默忽略**的（刻意的：前端传了过期的
键不该让页面崩），但 `ListParams.normalized()` 把传入值原样回显。于是响应一半
在说「我按北京筛了」、另一半返回全部——前端拿到的是假话，也无从知道筛选没生效。

修法是**一份判断的两半**，放在同一个文件里共用 `raw_values`，避免分头实现漂移：

- 后端 `province.effective_keys()`（`province.py`）——回答「最后到底筛了什么」，
  `normalized()` 改用它。空值桶 `__empty__` 总生效（它筛的是 `IS NULL OR
  TRIM = ''`，与库里有几条无关，`raw_values` 对它返回空列表，不能拿它当判据）。
- 前端 `pruneUnknown()`（`overview.js`）——拿到 `/api/filters` 后，把 state 里
  库中已不存在的值摘掉、`writeHash()` 重写 URL、重查列表。用户看到的是自洽的
  状态，而不是「URL 说筛了、列表却是全部」。

其余多值字段（`severity` / `accident_type` …）不需要这一步：它们直接进
`IN (...)`，未知值筛出 0 条——条件确实生效了，回显原值是对的。

配套测试三条（`tests/test_web_m1.py`）：剔除库外省份、空值桶总生效、以及
**「生效键与过滤条件不漂」**——对五种键组合断言
`bool(filter_clause(keys)[0]) == bool(effective_keys(keys))`。这条是防漂移的锁：
两半各自演化时，它先红。

### 8.2 后端给了五维筛选，概览页只画了三维

这一轮做界面审美核查（截图探针只能看出「破图 / 空白 / 报错」，看不出「少了一组筛选」）
时，对着致因页的筛选区读数，读到两件事：

**第一件：标签串了维度。** 致因页把 `construction_phase` 标成「**施工工序**」，值却是
地基与基础 / 主体结构 / 装饰装修 / 拆除——那是**施工阶段**。`step1_basic_extractor.py`
里这个字段的描述原文就写着「或**施工阶段**(主体结构/装饰装修)」。而真正的「施工工序」
在库里是另一列：`work_task`（WT01–WT99，施工作业类型 11 类 LLM 枚举，蓝图 05 §57 定名
「**作业任务**」）。两个独立维度撞了同一个中文名，且取值还有个刻意的近似
（「主体结构」vs「主体结构工程」），串了名读起来完全通顺。

实测坐实了这一点：致因页筛选区的计数（主体结构 1,064 / 装饰装修 363 / 地基与基础 290）
与 `construction_phase` 分组**逐项一致**，而 `work_task` 分组（WT02 主体结构 397）对不上。

三处标签原本各叫各的：

| 文件 | 字段 | 原名 | 改后 | 依据 |
|---|---|---|---|---|
| `causes.js` | `construction_phase` | 施工工序 | **施工阶段** | `step1` 字段描述、`review.js` 已用此名 |
| `accident.js` | `work_task` | 施工工序 | **作业任务** | 蓝图 05 §57、`review.js` 已用此名 |
| `review.js` | 两个 | 施工阶段 / 作业任务 | 不动 | 本来就对 |

蓝图 04 §256 的筛选条线框里也写着「[工序▾]」——误名是从蓝图抄进代码的，一并更正为
「[施工阶段▾]」，并在 04 §4.2 写明两个维度不得互串。

**第二件是个更大的缺口：`/api/filters` 返回五维，概览页只渲染三维。** 后端给的
`province` / `severity` / `accident_type` / `project_type` / `construction_phase` 里，
`overview.js` 的 `MULTI_KEYS` 只列了前三个，`renderFilters()` 里还**另外字面重写了一遍**
同一个三元数组——`project_type`（工程类型）与 `construction_phase`（施工阶段）的值就
在接口里躺着，用户筛不到。而蓝图的筛选条线框（§256）明确画了「[工程类型▾]」。

这类缺口**没有任何症状**：不报错、不空白、控制台干净。原先的交互核查也测不出来，
因为 `check_web_interaction.py` 用 `#filterChips label.chip` 的 `.first` 定位——永远打
第一组，chips 区有几组它根本不知道。

修法与防复发：

1. `renderFilters()` 里那句字面副本删掉，直接用 `MULTI_KEYS`（原先是两处各写一遍，
   改一处漏一处）。
2. chips 容器加 `data-key` 属性，让核查脚本能**按维度**取集合而不是按位置。
3. 交互核查加两条断言（概览页 + 致因页）：`chips 的 data-key 集合 == /api/filters
   里非空列表键的集合`。两页共用一套判据函数，避免各写一遍再漂移。
4. **反向验证过**：把 `MULTI_KEYS` 临时改回三维，脚本如期报
   「后端给了 [...] 这几维可筛，页面只画了 [...]」并以退出码 1 结束——不是一条
   恒真的假断言。

### 8.3 这一维的边界

- **本脚本只覆盖概览页**。中段三页另有脚本，而且是自带数据的：

  | 页面 | 第三层（headless 真点击） |
  |---|---|
  | 提取页 | `scripts/e2e/e2e_click_m3.py`——从勾选到成本弹层到抽屉证据链 |
  | 审核页 | `scripts/e2e/e2e_click_review.py`——专验三处「前端先行拦截 + 后端兜底」的前半 |
  | 采集页 | `scripts/e2e/e2e_click_collect.py`——13 段，勾源 → 任务自己走完 → 表格自己刷出 → 裁决 → 筛选 → 翻页 |

  三页都造假采集器 / 假 pipeline，但落库、闸门、幂等、进度回填全是真的，库是临时库。
  所以此前记的「中段三页交互待数据具备」是**错的**——**能自己造出的条件，不该记成
  待办**。采集页这个脚本补齐后，三页的第三层齐了。
- **不做视觉回归**。断言的是文本与计数，不比对像素；样式改坏了这十一条不会响。
- **维度齐全只在概览页与致因页有断言**。中段三页（采集 / 提取 / 审核）的筛选是另一套
  形状，没有 `/api/filters` 那种「可选值接口」可比，这条判据套不上。
- **时序靠 `wait_for_timeout`**。900–1500ms 的等待在慢机器上可能不够——失败时
  先怀疑这里，再怀疑功能。
- **端口要各占一个**（约定见 `scripts/e2e/README.md`）。本脚本默认 **5100**，
  第一版写的是 5098——那个端口是「主库对账」的，两套脚本同时跑会撞。

## 九、蓝图 ↔ 实现：文档规定的接口，实现了吗

前面几维比的是**代码内部**两边（路由 ↔ 调用、名字 ↔ 字段）。这一维比的是
**文档 ↔ 代码**，问一个更靠前的问题：蓝图写下的接口规格，实现跟上了吗？实现了
的接口，写回蓝图了吗？

`scripts/check_blueprint_alignment.py` 对账两侧：蓝图（`docs/web/00`–`08`）里
的接口与 `construction_agent/web/*.py` 真正注册的路由。

### 9.1 判据：只有标题算「规定」

蓝图里出现 `/api/xxx` 有两种语义，混在一起判会立刻出错：

1. **接口设计章节的标题**（`### `GET /api/collect/sources``）——这是**规格**
2. **正文里的一笔带过**——可能是举的例子，也可能是**在说旧实现怎么错**。蓝图 02
   写「旧实现 `POST /api/process`（`web/app.py:326-350`）同步调用，40 秒的请求
   必然超时」，是在陈述**已废弃**的东西；蓝图 06 写「原有一个
   `GET /api/accidents/<id>/images`，2026-10-01 删除」，是在记录**删掉了什么**

把正文也算规定，这两条就会被报成幽灵接口——而它们恰恰是文档最该有的交代。所以
只取标题行；正文提及单独列出，并用否定词（删除 / 旧实现 / 原有 / 已废弃 / 移除 /
不再）把「对照提及」与「漏写」分开。

**踩过的坑**：第一版把每行 `[:90]` 截断后再存，`/api/process` 那行的「旧实现」
正好落在 90 字之外，否定词过滤看不见它，一条正常的对照提及被报成了缺口。改成
**存完整行、显示才截断**。

反向也要求为 0：实现了却没写进蓝图的端点，下一轮就可能被当成冗余删掉——蓝图是
后续会话唯一的施工依据。

### 9.2 结果：6 条全部是「蓝图漏写」

第一版报幽灵 **0** 条、未写进蓝图 **6** 条。逐条读实现核实，**没有一条是实现
多写的**，全是蓝图只给了正文描述或 JSON 样例、没立接口标题：

| 端点 | 蓝图里的原貌 | 补在哪 |
|---|---|---|
| `GET /api/extract/pending` | 只有「待提取队列」的正文描述 | 02 §四 |
| `GET /api/extract/estimate` | 只有一段 `estimate` JSON 样例 | 02 §四 |
| `GET /api/review/history` | 03 只有 `stats`，没有 history | 03 §四 |
| `GET /api/filters` | 04 §2.4 讲了筛选语义，没立接口 | 04 §三 |
| `GET /api/health` | 00 完全没有 | 00 §4.5 |
| `GET /api/province/audit` | 04 正文提了一次（未立标题） | 04 §三 |

补写时逐条读了实现，照实描述参数与响应，**没有照抄旧文档**。补完双向清零：
蓝图标题规定 **36** 条 == 代码注册 **36** 条。

### 9.3 这一维的边界

- **只管 `/api/*`**。页面路由（`views_bp`）不在此列——它们的对齐由 §三 3.2 的
  页面维度管（打不开 / 没入口）
- **不管语义**。脚本比的是路径形状，蓝图说返回 A、实现返回 B 它看不出来。字段级
  的那部分由 §七 管，但 §七 是拿前端做参照的——**蓝图描述的响应字段与实现是否
  一致，目前仍无人核**（蓝图里的 JSON 样例是给人看的）
- **补蓝图是人工动作**。脚本报出的缺口不会自己消失，读实现、写回文档这一步没法
  自动化——这也正是它值得单独跑一遍的原因

## 十、响应契约：蓝图画的样例 ↔ 实现真的给的字段

§九 的脚本只比到**路径**这一层：蓝图写了 `GET /api/images/stats`、代码也注册了
`/api/images/stats`，就算对上——至于文档样例里画的 `by_ext`、`analyzed` 实现给
不给，它看不见。§七 的字段核查也管不着，那个比的是**前端代码**读的名字与后端
返回的名字，两边都在代码里，文档根本没进场。

中间这一格由 `scripts/check_api_contract.py` 补上（第七维）。

### 10.1 判据

**文档侧**：`### `GET /api/…`` 标题下的 ```json 块，块内含 `"ok"` 的算**响应
样例**。只认标题行——正文里提接口名是在说「旧实现怎么错」，那不算规定（同一个
坑 `check_blueprint_alignment.py` 踩过）。块里画着 `<载荷>` 这类占位符的算
**规范示意**，本就不属于某个接口，分开列不混进「归属不明」。

**实现侧**：不起服务，`app.test_client()` 直接打真实 GET，把响应里出现的
**键名**递归收成集合。用名字不用路径：文档样例的嵌套靠缩进表达，还原成路径
要么写缩进解析器、要么先清洗 `//` 注释和 `…` 占位，两条路都脆。

### 10.3 过程中修掉的两个「吞缺口」的 bug

这两处都是**判据写错**，会把真缺口咽下去，比不查还坏：

1. **`available` 用 `not v` 判**。`available` 这个名字在同一个响应里有两层意思：
   详情接口的 `tiers[].available` 是**该档有几个字段有值**（整数，某条事故上为
   0 很正常），`images_available` 才是「清单建没建」的布尔。用 `not v`，只要碰上
   一条某档有值数为 0 的事故，整个接口就被判「数据没准备好」——实测踩过：
   `images` 明明有 4 张图，却被标成「未判定」。改成 `v is False` 修好。
2. **多次采样用 `or` 合并**。`blocked = blocked or blocking_flag(body)` 让「五条
   里一条没数据」升级成「整个接口没数据」，于是真缺口不报。改成收集 `blocks`
   列表、**每次采样都不可用**才算「展不开」。

还有一处是**采样太窄**：`/api/accidents/<id>` 原判据只认参数名 `id`，而实现用的
是 `accident_id`，导致只打 1 条（76 个键名）。条件字段（天气、坠落高度、被困
人数）单条覆盖不全，会把它们误报成缺口。修好后打 5 条，93 个键名。

### 10.4 未判定为什么不算缺口

「未判定」有两种，都不该记成实现的问题：

- **整个接口展不开**：工作库未建，或本次响应的列表**全空**。空表时元素字段一个
  也展不出来，比下去全是假缺口
- **字段住在空数组里**：文档把 `token`、`backup_path` 画在 `promote_history` 里，
  而这次 `promote_history` 返回 `[]`。脚本把样例里的**数组键 → 数组内键名**解
  出来（括号配对，不引 `json.loads`——样例里有 `//` 注释和 `…` 占位，解析器会
  直接抛），再看该字段归属的数组**是不是全空**。只要有一个非空，元素结构就摆在
  那儿，照记硬缺口

第二条是本维度最费劲的一处：`/api/review/stats` 曾有 10 个字段被判硬缺口
（`token`、`stage_ids`、`promoted`…），其实它们只是住在两个空数组里。

### 10.5 这一维仍然比不出来的

- **层级归属**。只比键名不比路径：文档把 `data` 里的键平铺写在顶层，脚本照样判
  「文档写了」。`data` 只装查询结果这条约定得靠人核（`00` §4.1 那张表就是人
  核出来的，脚本护不住）
- **值与类型**。`"size": 50` 与 `"size": "50"` 在这层看着一样
- **POST 接口**。它们写库，只读核查不打，如实列在「未比对」里。这批的错误只能
  靠人核——下面 10.6 里 `03` 那段 `promote` 响应样例就是这么找出来的：脚本连
  碰都没碰

### 10.6 附带发现

§九 9.3 说的「蓝图 JSON 样例 ↔ 实际响应字段」这条已于本次补上。同一轮里还核出
并改掉了文档侧的四类错（都不影响运行，但会误导下一轮读文档的人）：

- `00` §4.1 原写「统一结构 + 两条例外」——实测 23 个 GET 里只有 7 个是教科书式的
  `{ok, data}`，整节重写为四类形状 + 三条共用约定 + 三种失败形状
- `distribution` 样例里有个**不存在的 `by` 参数**；`timeline` 样例画的 `series`
  实测是 `by_layer`
- `cooccurrence` 的 `lift` 写成 1.28，实测是 **1.085**（`joint_share` 0.6956）
- `03` 与 `07` 共 5 处写过 `rollback_token` 这个**不存在的字段**，且把无参的
  `POST /api/review/rollback` 写成了收参。它真正指的是两段式里的
  **`confirm_token`**（预演发、确认用，一次性、绑定选择集），与回滚无关——
  两者被混成了一个东西。`03` 的 `promote` 响应样例也据此重写（原样把预演的
  请求与执行的响应拼在一起，两边的字段都是真的，拼起来的那个响应体不是）

### 10.7 顺带复核的 07 验收条目

`07` §四 的验收标准写于实现之前，实现定型后有两处描述的机制跟代码不一样——
都不是 bug，是实现选了更好的做法，但条目留着会误导下一个读它的人：

- **M2「24 个源在 `collect_sources` 表中一一对应」**。实现是**代码为原件、表为
  投影**：24 个源在 `collector/registry.py` 的 `SOURCES` 里，首次起采集任务时才
  由 `sync_to_db()` upsert 进表。新工作库里这张表 **0 行是正常的**，拿它当
  「缺源」会白追一场
- **M3「`staging_accidents` 列名与最终库 `accidents` 一致」**。实现是**暂存表
  忠实保留 S3 输出原名、转换集中在并入映射层**：`location`／`relevance_verdict`／
  `s3_ms`／`s4_ms` 四处刻意不同名。拿「列名一致」去改会毁掉这层设计

已实测可静态验证的条目（不依赖网络与 LLM）：主库孤儿 **0**、`raw_accidents`
的 `UNIQUE(url_hash)` 在、工作库 12 张表与最终库物理分离、并入映射 47 列各有
出处（无一处靠名字猜）。需要真跑才判得了的（`limit=20` 任务 5 min 内完成、
成本预估偏差 < 30%、中断续跑不重复）留给实跑，不在本轮范围。

## 十一、已知未覆盖的对齐维度

本次核查覆盖**路由 ↔ 调用**（§三 3.1）、**页面可访问性 / 可达性**（§三 3.2）、
**渲染质量**（§六）、**字段名**（§七）、**交互行为**（§八）、**蓝图 ↔ 实现**
（§九）与**响应契约**（§十）七个维度。§八 8.2 补的「后端给了几维筛选 ↔ 页面画了
几维」是**第八个**——它不属于前七个里的任何一个：路由在、页面开、名字对、响应也有
那些字段，缺的只是「前端愿不愿意渲染」。§7.3 补的「`accidents` 的列 ↔ 详情页四档」
是**第九个**，与第八个同族但走反方向：前七维都从「页面上有什么」出发，这一维从
「库里有什么」出发，找的是**后端有值而页面从未显示**的那一类。以下维度尚未做机器化核查：

- **元素字段的运行时核对**：§七 7.2 说的那 18 个空数组——不是方法不成立，是
  **当前库里没数据**。属「待条件具备」，不属「待做方法」
- **概览页之外的页面交互**（列表页的深度筛选、详情页的图片灯箱、暂存页的并入
  二次确认）：中段三页现在各有第三层脚本（§八 8.3），但覆盖的是主路径；边角交互
  仍只到第二层
- **层级归属**：§十 10.5 说的那一条，只比键名不比路径，脚本护不住
- **中段三页的「能力 ↔ 使用」**：§八 8.2 那条判据要求「有个接口告诉前端可筛哪几维」，
  概览页与致因页有（`/api/filters`），中段三页没有这种接口，套不上。要靠人对着
  蓝图 01–03 逐个核
- **其余八张表的「有值 ↔ 有展示」**：§7.3 的判据只认 `accidents` 一张表。`caics_causes`
  / `enum_definitions` / `image_analyses` 等表的值进页面要经聚合与查表，列名与展示名
  不是一对一，「没展示」与「不该展示」分不开。另外 §7.3 判的是**列有没有归宿**、
  不判**归宿对不对**（`trapped_count` 有值率 100% 却进 D 档，档位合不合适是分档理由
  的事，脚本管不着）
