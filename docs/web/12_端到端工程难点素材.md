## 零、这份文档是什么、不是什么

### 0.1 先回答两个被问过的问题

**问：§2.5 章节居然有 101 个小节？这是论文中的内容吗？**

不是。`docs/web/01_在线采集.md` 是本项目的**工程过程记录**，1,179,036 B / 17,891 行 /
§2.5.1–§2.5.101 逐节记录「某一轮做了什么核查、查出什么、怎么处置、还剩什么没定」。
它服务于**系统自己**（让下一个人知道某件事查过没有、结论是什么），**不是论文内容**，
也不会以现有形态进论文。

论文里的是它的**蒸馏物**——本文档第二节就是把 101 节压成 10 条的那道工序。
压完之后剩下来的**复用率**（约 40 节 → 10 条）本身就是这个判断的证据。

**问：这些任务对论文有帮助吗，还是只是让系统更 robust、相当于测试维护循环？**

**两部分都有，必须分开说**，混在一起谈就是自欺：

| 成分 | 规模 | 能不能进论文 |
|---|---|---|
| **A 类：生产链路上真实存在的、可迁移的工程难点** | 源出约 40 节 | ✅ 能，是 Methods/Discussion 的骨料 |
| **B 类：核查基础设施本身**（判据设计方法论） | 约 35 节 | ⚠️ 部分能，作为「质量保障流程」一节 |
| **C 类：纯 web 工程质量**（对比度、键盘可达性、DOM 注入面…） | 约 30 节 | ❌ 不能，与论文主题无关 |
| **D 类：对论文自身的核验**（九项） | 15 脚本 / 4,650 行 | ❌ 不产生论文内容，但它**改写了论文的事实**（见第五节） |

**诚实说法**：C 类那 30 节若单独看，确实接近"测试维护循环"。但它们**共同暴露了 A2**
（同一语义在多处各写一遍）——**没有这些看起来很远的核查，那个模式看不出来**。
它们不是论文内容，**但其中一节产出了论文内容**。

### 0.2 准入标准

一条素材要进 A 档，必须同时满足三条，缺一不收：

1. **可迁移**——别的团队做类似系统时会撞上同一个坑，而不是"我们这里某个函数写错了"；
2. **有实测数字**——现象被量化过（丢了多少、差了几条、占比多少），不是"感觉上容易错"；
3. **能支撑论点**——它要能在论文里回答一个读者会问的问题（数据怎么来的？可信吗？代价是什么？）。

### 0.3 分档与阅读方式

- **★ 必进**（6 条）：论文三个必须回答的问题——系统有多难建（A1/A2/A3/A6）、
  数据是什么（A5）、数据语义可信吗（A4）；
- **☆ 可选**（4 条）：Methods 细节层面，篇幅允许时各占半节；
- **环节标签**：①采集 ②清洗与提取 ③暂存与入库 ④展示，**横切**＝不属单一环节。

### ★ A1. 论文对自身实现的描述与实现不一致，而九项自动核验全部抓不到

**环节：横切（论文 ↔ 代码）**

**现象** — 论文 §3.2.2 描述采集器架构，五个数字/枚举里**三处与实现不符**：

| 论文写法 | 实测 | 差 |
|---|---|---|
| "Twenty-five collectors" | **24** | 多 1 |
| "nineteen provincial" | **18** | 多 1 |
| "two national (MEM + MOHURD)" | 2 | ✅ |
| "three auxiliary importers" | 数目对、**成员错** | — |
| "...covering ... two published academic accident datasets" | `academic_import.py` **从未注册进 registry** | 描述了**不存在的源** |
| —（架构描述里没有） | `esafety` 389 条（14.8%）+ `safehoo` 1,247 条（47.5%）= **62.3% 的数据** | 贡献最大的两个源**没被描述** |

第三处（第 97 行）：论文写 "whitelist of 15 news domains"，实测 `NEWS_DOMAINS = 19`，
剔除与 `.gov.cn` 分支冗余的 mem/mohurd 后净 **17**；按任一算法都不是 15。

**证据链**（可执行）：`registry.py` 的 docstring 自称 24；`GROUP_LABELS` 明写
literature/academic「未启用」；commit `43b4924`；`academic_import.py` 来自 `cb5397f`、
此后从未登记。

**为什么它是一类问题（而不是"打错一个字")** — 论文散文里有 **412 个数字 token**、
其中 **100 种只出现一次**，而数字对账清单只覆盖 **55 项** ⇒ 结构性排除了"只在这一句里
出现的描述性数字"。而且 LHF（大语言模型辅助写作）会按**合理的方式**组织分类法——
"一个聚合器 + 一批省级 + 一批国家级 + 几个辅助导入器"读起来**非常自然**，
但这些分类**没有跟代码注册表对齐**。**不是幻觉，是描述与实际运行集合的错位**。

**处置** — ★必修，见第五节 D1。

**可迁移性** — 任何"论文描述自己造的系统"的场景都会遇到：**散文里的数量词是核验的盲区**，
因为核验脚本通常只登记"全文统一值"（同一个数出现多次才登记），而一次性描述词天然被漏掉。

**论文落点** — Limitations 新增一条"描述—实现一致性"。可写成一条正面贡献：
把散文里的集合描述也纳入核验射程（论文可展示 `registry.all_sources()` 与散文数字的
自动对账，作为"论文自检"的一个可复用做法）。

**锚点** — `docs/paper_v2/eswa_paper_v2.md` 第 93、97 行；`construction_agent/collector/registry.py`。

### ★ A2. 「同一语义在多处各写一遍」——本项目最主要的腐蚀模式（17 次独立发作）

**环节：横切**

**现象** — 同一条事实（一个上限、一个颜色、一个路径、一个类名、一份清单）在系统里
出现**第二份副本**，两份**各自局部正确、全局不一致**，且**从不自行收敛**。

| # | 语义 | 第二份副本长什么样 | 实测后果 | 来源 |
|---|---|---|---|---|

| 2 | 配置文件 | worktree vs 主仓库 `config.py` | 字段数 **13 vs 17**（主仓库独有 4 个字段） | §2.5.66 |

| 5 | 前端工具 | 两份 `el()`（`dom.js` 认 `{id,cls,text,attrs}`、`overview.js` 认 `{cls,text,attrs,on}`） | **双向分叉**，合并必须**取并集** | §2.5.89 |

| 11 | 请求封装 | 四个封装挂了什么各不相同 | `fetchJson` 挂 status+body、`jsonGet` 只挂 body、`send` 两样都缺 | §2.5.87 |
| 12 | 库路径解析 | 脚本走 `_common.main_db_path()`、web 走 `settings.DATA_DIR` | 一边读 A 库一边读 B 库，无任何东西会吭声 | §2.5.94 |

| 15 | 筛选键 | `overview.js` 里同一批 12 维键**写了五处** | `readHash`/`writeHash`/`toQuery`/`const state`/后端各一遍 | §2.5.99 |
| 16 | **同名函数** | `collect.api_list_tasks` vs `extract.api_list_tasks` | 前者 `limit` **缺下界夹紧**（`?limit=-1` → SQLite `LIMIT -1` = **吐全表**） | §2.5.100 |
| 17 | 死配置 | `needs_ocr` 全仓零消费方；`min_text_length = 30` 从未生效 | 配置项存在、读不到 | §2.5.11/12/17 |

**第 5 条最能说明"这不是版本漂移"**：按"谁新用谁"合并**必然再丢一半**，因为两份是**互补**的
（`id` 是事故之后补的、`on` 是 `overview.js` 自带的）。**判断"是不是版本漂移"是有实际价值的**：
漂移取新、分叉取并集——判错方向就丢功能。

**为什么它是一类问题** — 不是泛泛的"代码重复"，是**有具体机制的**：LLM 在 B 处生成代码时
**不知道 A 处已有一份**。危险在于**腐蚀是单调的、不会自收敛**——项目里没有任何一个时刻会
自动发现"这两份已经不一样了"。

**第 1 条最刺痛**：唯一算对的那一处（`gd_em` 的 40000）**把警告留在了自己那个文件里**，
另外四个源永远不知道。

**处置** —
- 运行时读 CSS 变量（第二份副本整体删除，`LAYER_COLOR` 对象删掉）；
- `ResizeObserver` 量真实高度写回 CSS 变量（`layout.js`），CSS 里那个 55px 降级为**首帧初值**；
- 判据按**规则块**取声明体（`_decls()` 大括号配平），不裸搜子串；
- 跨副本分叉建**会过期的登记表**（分叉了却没登记 ⇒ 红；登记了却已同源 ⇒ 红；
  登记着但任一侧 md5 变了 ⇒ 红）；
- 死配置做**读取点审计**（`--self-test` 里先重新发现已知的死字段，脚本才被采信）。

**可迁移性** — 任何 LLM 辅助构建的系统都有这个模式。可迁移的处置是**给每个"同一语义"
指定唯一来源**，并让"第二份"在编译期/测试期就报错。

**论文落点** — Discussion 新增一节 **"Consistency under LLM-assisted construction"**，
与"词汇门控效应"并列。

**英文论点（拟）** —
> *"In a system built with substantial LLM assistance, the dominant maintenance cost was not
> defects but divergence: the same fact — a colour, a layout constant, a truncation limit, a
> taxonomy, a database path — acquires a second copy that is locally correct but globally
> inconsistent, and the copies never reconverge on their own. We counted seventeen independent
> instances across four layers of the stack."*

**锚点** — §2.5.34 / 66 / 73 / 74 / 75 / 87 / 88 / 89 / 91 / 94 / 97 / 98 / 99 / 100。

### ★ A3. 静默失败：缺陷没有任何症状，且「没报」与「没能力报」在输出上同形

**环节：横切**

六个独立实例，前两个最锋利。

**① 搜索增强 97.4% 从未生效，而两个错误列全空**

- `search_logs` 1,636 行里 `total_results = 0` 有 **1,594** 行；
  `search_enriched_text == raw_text` **也** 1,594 行 ⇒ 只有 **42 条**真被增强，
  **1,594 + 42 = 1,636 严丝合缝**（两处独立字段互证是结论能站住的原因）；
- 机制：**把事故正文前 80 字当检索词**——LCP = 80 占 **1,594/1,594（100%）**，
  且保留了 `\n\n`（`== raw_text[:80].replace('\n',' ')` 命中 0），是旧版 fallback 的指纹；
- **两处错误列全空**：`processing_log.error_message` **45/45 NULL**、
  `search_logs.error` **1,636/1,636 NULL**——而这不是"没出错"，是**结构上就写不进去**：
  三条写入路径殊途同归（一条列清单**含**该列但实参是**字面量 `None`**、一条列清单**不含**、
  一条**不写该表**）。

> *"An error column that is empty across all 1,636 rows is evidence of an uninstrumented failure
> path, not of a failure-free system: the enhancement stage that produced those rows succeeded in
> 42 cases out of 1,636."*

**② 一整轮采集归零，而日志报成功**

`trs_cms_base.collect()` 的批写条件是 `len(results) % 5 == 0`，而结尾的 `self.raw_store._save()`
**不产生记录、不 append、不碰 sink** ⇒ 余数那几条**从未进 `_data`**。实测：

| 输入条数 | store | sink |
|---|---|---|
| 3 | 0 | 0（**全丢**） |
| 5 | 5 | 5 |
| 6 | 5 | 5（丢 1） |
| 7 | 5 | 5（丢 2） |

日志照写「采集完成: 列表7 → 初筛过滤0 → 分类过滤0 → 收录3 + 审核0 (0.3s)」。
**这是本项目唯一一个能让整轮采集归零而日志全绿的缺陷类。**

**③ 契约变更后旧判据恒假** — `1922bd7`（10-01 00:33）落盘 e2e 时 503 的 `message`
就是建库提示；13 小时后 `ca41bc4` 新增 `dberr.py` 拆成 `{error, message, hint}`、
**把下一步动作移到 `hint`**，改了五个实现文件、**没改 e2e** ⇒ 断言**恒 False 却永不报错**
（`e2e_collect.py` 96/1、`e2e_extract.py` 126/1）。

**④ 健康检查数字连续多轮不动** — 清单第八轮 16/24「第三到第八轮一次都没动过」；
`jx_em` 清单记"没连上（SSL 老式重协商）"而实测**站点活着、列表解析 0 条**
⇒ "是判据对不上页面，不是断连"。抓到/没抓到是**二值**，把断连 / 选择器失效 / 限流 / 空
**压成同一个 0**。

**⑤ 核查在空数据集上恒真** — 工作库 12 表里 **9 张 0 行** ⇒ 28 条只读 GET 里 **5 条**打不出
真响应、449 条键路径里 **76 条从未进比对**；`check_2578` 的 46 条差异**100% 归因到空容器**。

**⑥ 多层故障叠加，每层都给"通了"的假信号** — `jx_em` 三层：列表页 200 且 271,906 字节
但 7 个 `<a>` 全是 `javascript:void(0)`；转 JSONP 接口 200 返回 15 条而 `page` 自带
`articleCount = 49`；详情页拿到 `{{#each data}}` **模板源码 467 字**，四条不同事故提取到
**完全相同的 467 字**。

**为什么它是一类问题** — 因为「**判据没报**」与「**判据没能力报**」长得一模一样。
②最锋利：不是"某个函数写错了"，是**批量写入的刷新节律与最终部分批次从设计上就不匹配**。

**处置** —
- 覆盖率须由**产出侧与失败侧两个独立字段互证**（1,594 vs 1,594 严丝合缝）；

**论文落点** — Results + Limitations。

**英文论点（拟）** —
> *"Automated pipelines fail most dangerously without symptoms: a batch writer whose flush cadence
> never matched its final partial batch discarded an entire round's records while its own log

### ★ A4. 「不知道」与「确定为零」在许多层上不可区分

**环节：②清洗与提取 · ③暂存与入库 · ④展示**

四层各有一次**同形**发作。

**① 存储层：四种缺失表示并存**

| 表示 | 分布 | 例 |
|---|---|---|
| `NULL` | `accidents` **21 列**纯 NULL 型 | — |
| 空串 `''` | **5 列**纯空串型，全表空串单元 **922** | — |
| 字符串哨兵 | `不适用` 1,320 / `未知` 399 / `其他/未知` 201 / `未提及` 48… | — |
| **数值哨兵 `0`** | `deaths` 343 / `injuries` **1,396** / `trapped_count` **2,354** | 与"真的 0 人伤亡"**不可区分** |

**列级干净、表级不干净**：实测**混合列 = 0**（无一列同时用 NULL 与空串），
但 `accidents` 一张表内是 **纯 NULL 21 + 纯空串 5 + 无缺失 22 = 48 列**。

**后果**：同一个"填充率"算出**三个数**——
`publish_date` 的 `IS NOT NULL` 算 **100%**、去空串算 **65.4%**（差 **907 条**，全部来自
5 个本地书源）；`weather` 的 7.9% 里含「未提及」46 条，真实记录只有 **6.2%**；
`fall_height` 的 13.0% 是**「>0 率」不是「非空率」**（实测非空率 14.2%）。

**② 监控层** — `net_failed=1` 一格压三种故障（`hub_em` HTTP 412 / `jl_em` DNS 失败 /
`jx_em` TLS 握手失败）；重跑得 17/24 与上次**同一个数**，但七个空源的**定性构成变了三处**
——同一个数字、不同的世界。

**③ 判定层** — `_median([])` 返回 **0**，三源都显示中位数 0，差点据此**改错基类**。

**④ 展示层** — `images_available = false` 有**四条来路**（文件不存在 / 0 字节空壳 /
12,288 B 0 张表 / 16,384 B 表在 0 行），详情页只有**两句文案** ⇒ 前三条被统一说成
"先跑 `build_image_manifest.py`"，照做后那个脚本自己退 3 说"先跑 `create_staging_db.py`"。

**必须保留的区分（不是缺陷，别去"修"）** — `不适用` 与 `未知` 的**差异化处理是有意的**：
`detail.py:229-231` 把 `不适用` **归一成缺失**（否则 1,320 条非坍塌事故每条都显示
"坍塌子类型：不适用"，是噪声）；而 `未知` **保留显示**——"问过但原文没答"与"根本不该问"
是两件事，后者信息量为零、前者有信息量。数值哨兵同理（`overview.py` 用 `deaths > 0` 另计
"有死亡记载的事故数"）。

**处置** — 状态判据从**布尔改三态**（`classify_response() -> "results"|"blocked"|"unknown"`、
`availability() -> "ready"|"empty"|"unavailable"`）；统一 `_empty_clause() = (col IS NULL OR
TRIM(col) = '')`，但**调用面只收拢一半**（1 处已用、另 5 处仍手写）。**未改数据**
（数值哨兵 `0` 换 `NULL` 属作者裁决，牵动全部下游统计与论文数字）。

**可迁移性** — LLM 抽取型数据库的缺失值**不是二值的**。提示词里一句
"未提及填 0"就制造出一批**与实测零值不可区分**的数据。

**论文落点** — Methods + Limitations 第 6 条。

**英文论点（拟）** —
> *"Missing values in an LLM-extracted database are not binary: four distinct encodings coexist
> across 133 columns, and a prompt-level convention ('fill 0 when not mentioned') yields values
> indistinguishable from measured zeros."*

另可：
> *"The first engineering risk in multi-source collection is not failing to collect but being
> unable to tell a failed collection from an empty one."*

**锚点** — §2.5.65 / 74 / 94。

### ★ A6. 「有名无实」四层：名字在、语义在，数据或实现不在

**环节：横切（存储 → 结果集 → 响应 的整条链）**

**现象** — 同一个病在**四个抽象层次**上各发作一次，且**相邻两层之间的落差是相邻两节查出来的**：

| 层 | 名字在 | 实际 | 数字 |
|---|---|---|---|
| **① 数据库列** | 133 列（9 表） | 全空 **2** + 单值 **14** + 低区分度（2–3 值）**10** + 其余 107 | 14 个单值列逐个定性：结构必然 5 / 写死常量 4 / 缺失表示 2 / 样本必然 1 / **疑似缺陷 2** |
| **② 配置项** | 五层：registry→构造器参数错配 **0** / `TrsSiteConfig` **零读取点死字段 4 个** / 读在**但分支恒不可达** / **同名不同物**（`enable_classify` 真生效 vs `enable_classify_v2` 全仓零赋值）/ 跨副本分叉 | `base_url` **12 个源全填了值**、基类注释明写"不能拿它拼 URL"——**有意废弃但没收拾** | §2.5.66 |
| **③ 查询结果集** | 主库 133 列 | `read` 26 / 仅因 `SELECT *` 带回 `star` 32 / 只做筛选 `filter` 4 / **零出口 `zero` 67** / 值全空 `empty` 4 | 零出口的**每一条都配了可证伪判据** |
| **④ HTTP 响应** | 结果集 58 对（表.列） | 名字面出口 **56** 对、**失守 2 对**；响应键面 256 个键（201 个是派生字段） | `pipeline_metadata.value` 是**设计**（解析后派发）；`accidents.work_task_enum` 两层都不成立（**有意不下发**，运行时印证） |

**自证要求（这一条的方法论价值）** — 这个体检脚本**先重新发现已知的三项**
（§2.5.64 查出的两个全空列 + `pipeline_version` 单值）**才被采信**——
**一个体检脚本若报不出已知的两处缺陷，它报的"其余 107 列正常"一文不值。**

**为什么它是一类问题** — 与 A2（同一语义写两遍）**方向相反、同属一致性家族**：A2 是
"写了两份"，这一条是"**只有一个名字，后面什么都没有**"。信息从存储走到用户眼前是一条链，
而**每一段都有"到了这一段就没了"的位置**，且**没有任何一段会主动报告自己把东西丢了**。

**附带的口径陷阱三连**（同一个"填充率"三种算法）——见 ★A4，此处不重复。

**处置** — 零出口列**逐条**配可证伪判据（物化链 / 前端零命中 / 上游归并未发生 / 主键白名单），
另加三条**元判据**（登记表与实测面不重不漏、`web/` 里没有模块绕过代理补丁直接读入口、
判据覆盖面自证）。

**可迁移性** — 任何"schema 先写、数据后填"的系统都会长出一批有名无实的列；可迁移的做法是
**把"进没进结果集"和"发没发出去"分成两道判据**，而不是靠读 SQL 文本 grep。

**论文落点** — Methods 的"数据层"一小节 + Limitations。

**英文论点（拟）** —
> *"A field name is not a field. Across four layers of one pipeline — database columns,
> configuration keys, result-set columns, and HTTP response keys — we measured how many named
> entities carry no value forward, and found the same pattern at every layer: 2 of 133 columns are
> entirely empty and 14 hold a single value; 67 never appear in any result set; 2 of the 58
> result-set columns never reach the client."*

**锚点** — §2.5.65 / 66 / 76 / 77。

### ☆ A8. LLM 输出的取值域越界：声明的枚举与落库的值分了家

**环节：②③**

**现象** — `report_type` 声明值 **`教材/案例`**（`step1_basic_extractor.py:260`），

改＝篡改既成事实，且各 1–6 条不构成统计影响），判据列进 `KNOWN_OUT_OF_DOMAIN` **双向**核

①895 条是既成事实（改数据要动 34%）；②`docs/enums/work_task_llm_enum.md` 的自然语言写的就是
"教材案例"；③斜杠只是"教材或案例"的口语转写，**改声明不改变任何语义**。**风险为 0**
（该值从未被 step1 产出过）。改后越界 **895 → 0**。

**判据的已知盲区（如实登记）** — 软判据只抓"整词与全部 2-gram 都零命中"的凭空概念，
**抓不到用真词拼凑的伪词**（自证用例「外星人施工」被高频「施工」救活，退出码仍 0）。
**不收紧阈值来骗过自测**——那会误伤「提升机故障」这类合法概括词。

**英文论点（拟）** —
> *"Enumeration constraints declared in an extraction prompt constrain the model, not the
> database: a second write path bypassed the prompt and populated a differently-spelled value for
> 34% of records, splitting one semantic category into two for any downstream GROUP BY."*

**锚点** — §2.5.74。

### ☆ A10. 指向性断言没有到期机制：「交给某脚本」与「挂到某时刻」都不会自己过期

**环节：横切（工程管理）**

**现象** — 仓里到处写着两类**指向性断言**：横向「交给某脚本做」、纵向「挂到某时刻做」，
外加 `TODO` 这类显式欠账。它们读起来像"有人管"，但**从来没有人回头核过那句话今天还算不算数**。

**首跑抓到的** — 纵向那一类当时有 **12 处把两份 `el()` 的合并挂到里程碑 M1 的句子**，
而 M1 **早在 2026-09-30 收尾** ⇒ **12 处全部逾期**。另：待决项账本实测 **73 条**

**处置** — **不是删声明**（债是真的），而是**把债改挂 backlog**（蓝图 07 的 `U1`）——
**里程碑会做完、做完那一刻挂在上面的声明集体到期；backlog 不会自己到期**，
**两类触发点因此需要两种判据**。另**兑现两条空头支票**（项目文档称某前端链归交互核查脚本管，
而该脚本里此前并没有这条判据 ⇒ 补上第 18 条）、撤掉一个**还了债没销的标记**。

**为什么它是一类问题** — 技术债的**记账方式**决定了它会不会被遗忘。用里程碑当挂点，
系统会在里程碑收尾那天**静默制造一批假承诺**。

**可迁移性** — 建议：backlog 项要有**稳定 ID 与状态字段**；指向性断言要能被脚本扫出
（否则它是散文，不是账）。

**论文落点** — Limitations（工程过程的可复现性）+ Methods 的"质量控制"一小节可选。

**英文论点（拟）** —
> *"Work deferred to a milestone expires when the milestone does: twelve deferral statements in
> this repository pointed at a milestone that had already closed, and 61% of the outstanding
> decision items had no expiry mechanism at all. Deferrals must be anchored to a backlog, not to a

## 三、B 档：方法论贡献——「判据的设计」本身

这一档回答的是"你们怎么知道系统是对的"。它的价值**不在系统，在方法**——
可写成论文的一小节（"Quality assurance protocol"），也可作为**独立的方法论贡献**。

### B1. 核查基础设施的规模与形态

- 系统核查脚本 **51 个 / 33,876 行**（≈ 业务代码 35,852 行）；
- **27 个带 `--self-test`、38 个带注入式自证、23 个带机器可读 `MARKS` 出口**；
- 一轮 40 脚本全量复跑约 **19.5 分钟**（91% 花在 7 个脚本上）。

### B2. 判据设计的元规矩（本项目最可迁移的产出）

**价值主张**：不是"我们写了很多测试"，而是"**写测试本身有十几种会骗过自己的方式**"。

| # | 规矩 | 出处 |
|---|---|---|
| 1 | **判据的宽度决定结论的强度**——裸子串判据会在混合语料里制造假阳性 | §2.5.63 |
| 2 | **判据必须收窄接收者**——同名不同物（`.base_url` 属别的类、`filter` 是键还是方法） | §2.5.66 |
| 3 | **白名单只写理由不验证 = 永久豁免**——每条例外须配可证伪判据 + 一条元判据（防"加例外忘配判据"） | §2.5.67 |
| 4 | **宿主取不到要判红，不能降级成空集合**——"取不到"与"确实为空"必须分开 | §2.5.73 |
| 5 | **`退出码 0` 只有在脚本有能力报 1 时才可信**——没有失败路径的判据只是一句自述 | §2.5.64 |
| 6 | **注入式自证要断言"红的恰好是哪几条"**——只断言"退出码非 0"太弱，归因不唯一 | §2.5.68 |
| 7 | **两个注入面都要测**——文档面被改坏了，只测源码面的用例不会有任何一条转红 | §2.5.68 |

| 9 | **写死的固定值本身可能就是响应式的**（`HEAD~1` 会随提交前进失效；字面量锚点会过期） | §2.5.75 |
| 10 | **改完必须立刻复跑**——"上一次跑绿了"不是"今天还是绿的" | §2.5.90 |
| 11 | **两条判据方向相同则归因不唯一**——互为充要条件的两个等式必同时红 | §2.5.93 |
| 12 | **引述旧声明一律描述、不复述**——逐字引述会被判据扫成新声明 | §2.5.96 |
| 13 | **判据自己算错 = 报假红 = 让人去改本来正确的正文，比漏报更糟**（浮点 `round(0.9965*100,1)` 实测 99.7 而断言写 99.6） | 第三十六节 |
| 14 | **用例条数 ≠ 判据覆盖的格数**——多出来的用例是空话 | §2.5.64 |
| 15 | **设计前提会过期**——"文件名 = 文档角色"这类前提破了，判据会静默失效 | §2.5.90 |
| 16 | **判据的遍历深度不足会让它静默失效**——Tab 遍历缺了"先滚动"这一真实动作，焦点遮挡判据恒绿 | §2.5.75 |

### B3. 真值面的构造方法

**核心原则**：**真值面是一条运行路径、静态面是全部分支**，两者**互有盲区**
（真值面看不见"表不存在时才走的那条分支"、静态面看不见"这次真实数据长什么样"），
**所以判红必须收窄成"两面都说没有"**。实测把首次报出的 **5 条假缺陷收敛到 0**。

**接口契约的四格矩阵**（本阶段最系统的一件方法论产出）：
- **写·入参**：13 条写路由 × 14 处前端调用点；
- **写·出参**：13 条路由，返回结构**解出 12 / 解不出 1**（解不出的**如实列出、不当通过**）；
- **读·入参**：36 条 GET 路由（读 query 的 11 条）× 29 处前端调用点；
- **读·出参**：真值面真打 **28 条**路由得 **449 条**键路径；唯一真缺陷是 `/api/images/stats`
  的层级错位 ⇒ 「现场图片」卡**从未出现过**；
- **四格全程不发一个请求**（契约两端都在磁盘上），是静态解析；**再加一层真值面**独立复核。

**错误分支要真打**：读侧 **280 格**（九场景 × 28 路由）、写侧 **43 格**错误输入 +
三条安全措施（副本用 SQLite `backup()` API 复制、只打错误输入、打前打后逻辑摘要）。
**关键教训**：**文件字节哈希会把"打开了"报成"写了"**——`PRAGMA journal_mode = WAL`
在每次建连接时执行，库一被打开文件头就变 ⇒ 判据必须用**逻辑摘要**
（`sqlite_master` schema + 每表逐行 `repr`），且**不能用 `immutable=1`**（它会忽略 `-wal`、
把真写入读成没写）。

### B4. 观测工具本身也是被测对象

- **日志 69/69 = 100% 归错**；AST 数出日志调用 **306 条、仅 16 条带源名前缀**；
- `pytest` 输出带 ANSI 颜色码 ⇒ 反改验证脚本"新变红 0 条"（**判定脚本被输出格式骗了**）；
- **文件字节哈希会把"打开了"报成"写了"**（见 B3）。

### B5. 破坏性操作的安全边界

**不敢打的必须显式登记**：写路由错误分支实验里登记跳过 **9 条快乐路径**，每条带原因
（`executor.submit_task()` 真起采集线程发网络 / `run_one` 真调 DeepSeek / `pm.execute()`
把暂存**并入主库** / `/api/review/rollback` **无参数无令牌**直接回滚主库）。
**"跳过"与"通过"必须分开说**——否则覆盖面缺口会被读成"核过了"。
