## 一、功能目标与用户场景

### 目标
让研究者**不写一行 SQL** 就能回答一类问题：「某地区近五年高处坠落事故的致因分布是什么」。

### 三条用户路径

| 路径 | 动作 | 系统行为 |
|---|---|---|
| **摸底** | 打开首页 | 一屏看完语料全貌：规模、伤亡、类型/等级/年代/来源构成 |
| **定位** | 设筛选条件 → 翻页 | 服务端 SQL 筛选分页，返回命中集合 |
| **深入** | 点某行 | 跳详情页（蓝图 05） |

### 设计约束
概览页必须在**没有任何点击**的情况下说清"这份数据是什么、有多大、缺口在哪"。项目历史上有过多个口径不一致（JSON 41 字段 / DB 48 列 / tool schema 30 属性 / docstring 23），**本页是口径的对外唯一出口**，数字须与 `修订对账记录.md` 一致。

## 二、数据来源

### 2.1 概览统计（全部为 SQL 聚合，不取全量记录）

| 展示项 | 实测值 | SQL 来源 |
|---|---:|---|
| 事故总数 | **2,623** | `SELECT COUNT(*) FROM accidents` |
| 死亡总数 | **5,894** | `SELECT SUM(deaths) FROM accidents` |
| 受伤总数 | **5,796** | `SELECT SUM(injuries) FROM accidents` |
| 致因编码总数 | **16,323** | `SELECT COUNT(*) FROM caics_causes` |
| 覆盖事故数 | **2,618**（5 条无编码） | `SELECT COUNT(DISTINCT accident_id) FROM caics_causes` |
| 证据等级分布 | **14,784 / 1,117 / 422** | `GROUP BY evidence_quality` |
| 年代跨度 | 1978–2026（35 个年份，1991–2004 断档） | `GROUP BY substr(date,1,4)` |
| 来源构成 | 网络 1,728（65.9%）+ 文献 895（34.1%） | `GROUP BY source_name` |

> **口径澄清（2026-09-30 实测修正）**：`deaths` / `injuries` **无空值**——两列均 `NOT NULL DEFAULT 0`，填充率 **100%**。实测 0 值的含义是「原文未提及伤亡」（S3 的 prompt 规则为「未提及填0，不编造」），而非数据缺失。因此：
>
> - `SUM(deaths)=5,894` / `SUM(injuries)=5,796` 是**全部 2,623 条的完整总和**，无需「基于有记录的 N 条」这类限定
> - 但**确有死亡记录**的事故只有 **2,280** 条（86.9%）、**确有受伤记录**的 **1,227** 条（46.8%）、两者至少其一非零的 **2,474** 条（94.3%）
> - 页面标注应写成「2,623 条中 2,280 条有死亡记录」，**不能**暗示其余 343 条是数据缺失

### 2.4 `province` 的处理（79 个取值）

**不能直接 `SELECT DISTINCT province` 当筛选选项**。实测分布：

| 组 | 数量 | 处置 |
|---|---:|---|
| 标准省级单位 | 31 个 / **2,544 条**（四川 191 · 浙江 161 · 黑龙江 156 …） | 正常列出 |
| 可归一的地址级脏值 | 15 条（`鄂州市五里墩建设工地`→湖北省 · `太原市`→山西省 · `西藏`→西藏自治区 · `深圳市福田区笋岗路深圳市体育中心`→广东省 …） | **计入所属省份**，原始值在「数据质量」区单列 |
| 境外 / 港澳台 | 28 个取值 / **46 条**（印度 11 · 香港 7 = 特别行政区 4 + 香港 2 + 特区 1 · 韩国 2 · 美国 2 · 西班牙 2 · 海地 2 · 台湾 2 …）**全部来自 safehoo** | 归入「境外及港澳台」，单独计数 |
| 认不出来的值 | 4 条（`中国` · `黄浦区南浦社区…` · `甘州区滨河新区…` · `宁波世纪大道和北外环交界处`） | 归入「未归一」 |
| 空值 | 14 条 | 归入「未标注」 |

合计 2,544 + 15 + 46 + 4 + 14 = **2,623**。

> **2026-09-30 实测修正**：本节初稿写「境外 45 条 / 脏值约 20 条」，实为 **46 / 19**。
> 更要紧的是那 19 条脏值里有 **15 条能被 `utils/location.py` 的 `extract_province()` 认出来**。
> 初稿计划把它们一律丢进「未归一」桶——那样按「四川省」筛选只会返回 191 条，
> 而库里确实有 192 条，筛选结果与概览卡片的计数对不上。
> 因此归一结果**计入所属省份**，脏值本身在「数据质量」区逐条可查，两者不冲突。

**筛选器呈现**：省份下拉共 **34 项** = `内地省份`（31 个，计数含已归一的脏值）+ 三个独立桶
（`境外及港澳台` / `未归一` / `未标注`）。**四组计数之和恒等于 `accidents` 总行数**，
这个不变量由 `province.selfcheck()` 在每次 `/api/overview` 返回前断言，写进响应的
`data_quality.province` 字段——对不上就是归一层漏了取值，前端会直接看到。

`/api/province/audit` 把全部 47 个非标准原始值按三类列出（`renormalized` 15 · `overseas` 28 · `unanchored` 4），
含原始值、条数、归一去向。

> 这正是 CLAUDE.md 所记"约 17 条地址级错误"的实测全貌：19 条地址级脏值（15 条可归一、4 条认不出），
> 加上境外 46 条与空值 14 条，非标准记录合计 **79 条（3.0%）**。**显性呈现而非掩盖**——
> 这些数字本身是论文"数据质量"章节的素材。

    "buckets":  [ {"value":"__overseas__","label":"境外及港澳台","group":"overseas","count":46},

> **这个接口不套 `{ok, data}` 外壳**——统计块直接摊在顶层，元信息挂在 `meta`。
> `/api/accidents` 同理（`{items, meta}`），`/api/filters`、`/api/province/audit`
> 同属这一类。四个都是整页一次取全的「大盘接口」，外面再包一层 `data` 只是多一层
> 剥壳。同类接口的完整清单与判断标准见 §00 4.1 那张表。

**`deaths_recorded` / `injuries_recorded` / `casualty_any` 必须返回**——语义是「**有**伤亡记录的事故条数」（`deaths > 0` 等），不是「非空」。见第 2.1 节的口径澄清。

### `GET /api/accidents`

| 参数 | 类型 | 说明 |
|---|---|---|
| `q` | string | 关键词，匹配 `title` + `summary` + `direct_cause` |
| `province` | string | 标准省级值；或特殊值 `__overseas__` / `__unnormalized__` / `__empty__` |
| `severity` | string | 四值之一 |
| `accident_type` | string | 13 种之一 |
| `project_type` | string | 9 种之一 |
| `construction_phase` | string | 9 种之一 |
| `year_from` / `year_to` | int | 年份区间 |
| `has_causes` | bool | 只看已编码 / 未编码 |
| `sort` | string | `date`（默认降序）· `deaths` · `title` |
| `page` / `size` | int | 默认 1 / 50，上限 200 |

**响应**：

```json

      "deaths":3, "injuries":1, "trapped_count":0,

            "sort": "date",
            "filters": { "q":"", "province":[], "severity":[], "accident_type":[],
                         "project_type":[], "construction_phase":[],
                         "year_from":null, "year_to":null, "has_causes":null,
                         "sort":"date", "page":1, "size":50 },

```

> 同 `/api/overview`：**不套 `{ok, data}` 外壳**，`items` + `meta` 直接是顶层。
> `meta.filters` 把**实际生效**的筛选条件原样回显（前端据此判断 URL 与结果是否
> 同源），`has_more` 免去「翻到最后一页才知道没了」。
>

> 查 `enum_definitions` 得到中文名，**前端不硬编码编码表**。

### `GET /api/filters`

筛选器各字段的可选值（带计数）：`province`（31 省 + 三个桶）、`severity`、
`accident_type`、`project_type`、`construction_phase`、`sort`。

取值一律来自数据本身——新增一个枚举值后重新加载页面即可筛选，**不需要改代码**。
空值若存在则作为 `__empty__` 选项列出（`NULL` 与空串在 SQL 里是两组、对用户是同一
件事「没填」，服务端先把两者并成同一个键再计数，否则前端拼出的 `?severity=` 会被
解析成「不筛选」，筛选器直接失效）。

页面加载时取一次。**前端拿到后要拿它对一遍 URL 里带来的筛选值**：库里已不存在的
键（数据更新后省份改名等）要就地清掉并重写 hash，否则用户会停在「URL 说筛了、
列表却是全部」的自相矛盾状态——后端对未知省份键是刻意静默忽略的（见 §2.4）。

### `GET /api/province/audit`

省份归一的**逐条明细**：把 79 个原始取值里非标准省级全称的 47 个，按归一去向分
三类列出——`renormalized`（地址级脏值，已归入某省）· `overseas`（境外及港澳台）·
`unanchored`（认不出来，落进未归一桶）。

这是「**不掩盖问题**」的落点：那些被成功归一的脏值在筛选时计入所属省份，但仍然
完整出现在这里，可以逐条追查。筛选器只负责不掩盖，**清理是独立任务**（见 §七 风险表 C）。

### SQL 生成要点

```sql
SELECT a.id, a.date, a.title, a.accident_type, a.severity,
       a.deaths, a.injuries, a.province, a.city, a.work_task,
       (SELECT COUNT(*) FROM caics_causes c WHERE c.accident_id = a.id) AS cause_count
FROM accidents a
WHERE 1=1
  /* 动态拼接，全部用参数占位符，禁止字符串插值 */
  AND a.province = ?                      -- 标准值走精确匹配
  AND a.severity = ?
  AND a.accident_type = ?
  AND substr(a.date,1,4) BETWEEN ? AND ?
  AND (a.title LIKE ? OR a.summary LIKE ? OR a.direct_cause LIKE ?)
ORDER BY a.date DESC
LIMIT ? OFFSET ?
```

**必须配 `COUNT(*)` 独立查询**取 total（不要 `SELECT` 全量再在 Python 里数）。

`__overseas__` 等特殊值展开为 `a.province IN (...)` 的子句，境外清单由服务端内置的常量集合提供。

### 4.2 交互逻辑

**服务端筛选（与旧版的关键差别）**

旧版 `dataset.html` 把全部记录塞进页面，筛选靠前端 `JSON.stringify(r).includes(q)` 遍历，且**首屏有 3 处 None 崩溃点**（`:372` title、`:374` severity、`:381` location）——而其 JS 重渲染路径反而有 `|| ''` 兜底，于是出现"首屏 500、但一点筛选就正常"的诡异行为。

新版：
- 筛选条**任何变化都触发 `GET /api/accidents`**（含 300 ms 防抖），不再全量下发
- 列表由 **JS 渲染**（表格 9 列结构固定，服务端只给数据），避免 Jinja 与 JS 两套渲染逻辑并存
- 每次响应携带 `meta.total`，结果摘要与分页控件据此更新
- **URL 同步**：筛选状态写入 `location.hash`（如 `#province=浙江省&severity=较大事故&page=2`），便于分享与回退

**空值兜底**：服务端出口统一把 `null` 保留为 `null`，前端渲染一律 `v ?? '—'`。**不再出现"某条记录某字段为空就整页崩"的情况。**

**列头排序**：日期 / 死亡数 / 标题三列可点，切换 `sort` 参数并重查。

**五组 chip 必须与 `/api/filters` 一一对应**（实现后修订）

筛选条上那五组多选 chip——地区 / 等级 / 类型 / 工程类型 / **施工阶段**——的取值与计数全部来自
`/api/filters`，前端不硬编码任何一张码表。由此推出一条硬约定：**后端给了几维，页面就得画几维**。
少画一维不会有任何症状——那一维的值在接口里躺着，用户只是筛不到，既不报错也不空白，
正是最难发现的一类缺口。核查脚本 `check_web_interaction.py` 因此对**概览页与致因页**各断言一次
「chips 容器的 `data-key` 集合 == `/api/filters` 里非空列表键的集合」，chips 容器上的
`data-key` 属性就是为这条断言留的锚点（原先只能按「第几个」定位，测不出漏渲染）。
（该脚本 2026-10-05 起共 **17 条**，其中第 12–15 条转到详情页的真实点击——折叠 / 展开全文 /
灯箱 / 列表↔详情往返（`01_在线采集.md` §2.5.69、`09_端到端对齐核查.md` §8.4），第 16–17 条
转到**键盘路径**——Tab 真实遍历 + Enter/Space 开合、灯箱焦点陷阱与 Esc 后焦点归还
（`01_在线采集.md` §2.5.70、`09_端到端对齐核查.md` §8.5）。）

**别把「施工阶段」写成「工序」。** `construction_phase`（施工阶段：地基与基础 / 主体结构 /
装饰装修 / 拆除…，`step1_basic_extractor.py` 的字段描述明写「施工阶段」）与 `work_task`
（作业任务：WT01–WT99，施工作业类型 11 类 LLM 枚举，蓝图 05 §57 定名「作业任务」）是**两个
独立维度**，中文名不得互串。两者的取值名还有意长得像（「主体结构」vs「主体结构工程」），
串了名读起来完全通顺，只有对着数据才能发现。

**标题可点进详情页**：用 `<a href="/accident/<id>">` 而不是点击事件——中键新开、右键复制链接、浏览器前进后退都跟着能用。详情页的「返回列表」依赖 `history.back()` 回到带筛选状态的这一页，这条路径要成立，列表就必须是真正的链接。

**表头吸顶与横向滚动不能并存**（实现后修订）

`.grid thead th` 是 `position: sticky; top: 57px`（57px = 顶栏高度，改顶栏要一起改），滚动长列表时列名留在顶栏下方。

踩过的坑：`.table-wrap` 一开始写了 `overflow-x: auto`。**一个方向设了非 `visible`，另一个方向的计算值也会变成 `auto`**——`.table-wrap` 于是成了滚动容器，而 sticky 是相对**最近的滚动容器**定位的。后果是表头既不跟随视口滚动（sticky 白设），又被 `top:57px` 从容器顶再往下推 57px，压在首行数据上：实测表头落在 938–977、首行落在 920–983，标题的中心点被表头吃掉，**列表里的标题点不进详情页**。

处置：宽屏下不加 `overflow`——表格最小只需 738px，装得下。窄屏在 `@media (max-width: 790px)` 里才切回横向滚动容器，并同时把表头改回 `position: static`。两条约定都有断言守着（`tests/test_web_m1.py::TestStaticAssets`），因为浏览器布局行为在 pytest 里跑不出来。

## 五、技术选型与理由

| 选择 | 理由 |
|---|---|
| **服务端筛选分页** | 2,623 条虽可全量下发，但详情页的编码与证据链不可；统一走 API 才能复用同一套查询层。旧版 `/api/dataset` 一次吐 21.5 MB 是反例 |
| **JS 渲染列表 + Jinja 只出壳** | 避免旧版"两套渲染逻辑行为不一致"的坑。首屏数据由 `GET /api/overview` + `GET /api/accidents` 拉取 |
| **图表用 CSS 横条 / 内联 SVG** | 旧 `causes.html` 的 `.level-bar` / `.cat-bar` 已证明可行；**不引 CDN**，保证离线。若需环形图（严重程度），用内联 SVG 弧线 |
| **`enum_definitions` 查表出中文名** | 编码含义只在库里存一份，前端不维护副本 |
| **省份三分组用内置常量** | 34 个省级单位是稳定知识，写进后端常量模块（复用 `utils/location.py:14-61` 已有的 34 个省级单位清单与 `:77` 的 70 条别名映射） |

**可复用的现成资产**：`construction_agent/utils/location.py` 已有 34 个省级单位、70 条别名、151 条城市→省份映射——**省份归一与分组直接复用它，不重写**。

## 七、验收标准

1. `GET /api/overview` 的 `totals` 与直接 SQL 查询逐项一致；`evidence_quality` 三项为 **14,784 / 1,117 / 422**
2. `GET /api/accidents` 无参数时返回 2,623 条中的前 50 条，`meta.total = 2623`、`meta.pages = 53`
3. 各筛选参数单独与组合生效，结果条数与 `SELECT COUNT(*)` 的等价查询一致
4. `q=塔吊` 命中数正确；含空格/中文/特殊字符不报错（全程参数化查询）
5. `province=__overseas__` 命中 **46** 条；`__unnormalized__` 命中 **4** 条；`__empty__` 命中 **14** 条；`province=四川省` 命中 **192** 条（含 1 条由地址归一）；四组之和 = 2,623
6. `has_causes=false` 命中 **5** 条
7. 页码越界（`page=9999`）返回空列表而非报错
8. 响应时间：无筛选列表页 < 300 ms（索引生效后）
9. 首屏无 500；**构造 `date` 为 NULL / `province` 为 NULL / `title` 为 NULL 的记录，页面正常显示占位符**
10. 「工序」列读 `work_task`（**不是 `work_task_enum`**）：中文名由服务端查 `enum_definitions` 得到；无值的 **421** 条显示 `—`（不写「未标注」）；编码查不到名字时**回退显示编码本身**。主库实测 11 类、2,202 条有值、**零异常编码**
