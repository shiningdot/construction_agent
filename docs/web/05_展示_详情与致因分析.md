## 一、功能目标与用户场景

### 目标
回答两类问题：
- **个案**：「这起事故到底怎么回事、依据是什么」→ 详情页
- **总体**：「这类事故的致因结构是什么、哪几个因素总一起出现」→ 致因分析页

### 三条用户路径

| 路径 | 动作 | 系统行为 |
|---|---|---|
| **看个案** | 从列表点某行 | 详情页：48 字段分档 + 致因树 + 每条编码的证据与推断原文 |
| **看结构** | 打开致因分析页 | 5 层 19 类金字塔 + 分布图 + 共现矩阵 |
| **做交叉** | 在致因分析页加筛选（类型/地区/年代） | 全部分析图服务端重算，展示该子集的致因结构 |

### 设计约束
CAICS 的类名**必须来自数据库**（`caics_causes.code` + `caics_causes.name`），不得在模板里硬编码。旧 web 的 `/api/causes/framework` 端点 500 崩溃，根因正是 `hfacs.py:58` 的默认路径指向不存在的 taxonomy JSON 且 `load()` 静默失败——**新方案从表里取类名，这个失败模式从根上消除**。

## 二、数据来源

### 2.1 详情页字段：48 列实测分档

按**有值率**（= 非 NULL 且非空串，分母 2,623）分为**内容四档 + 过程元数据一区**，页面据此决定「必显 / 有则显示 / 折叠 / 高级折叠」。**口径定义与三种算法的区别详见蓝图 00 第 3.5 节**——不要用「非零率」（会把 `deaths=0` 误判为缺失），也不要用 `COUNT(col)`（会把空串计为有值）。

**A 档 · 必显（有值率 ≥ 90%，12 列）**

| 字段 | 有值率 | 缺失构成 | 展示形式 |
|---|---:|---|---|
| `title` | 100% | — | 页面标题 |
| `accident_type` | 99.77% | 6 条空串 | badge（12 种取值 + 6 条空 → `—`） |
| `severity` | 99.96% | 1 条空串 | 四色 badge（空值 → 灰色「未定级」） |
| `deaths` / `injuries` | 100% | — | 醒目数字（**0 表示原文未提及，非缺失**） |
| `summary` | 99.81% | 5 条空串 | 摘要段 |
| `direct_cause` | 99.89% | 3 条空串 | 直接原因段 |
| `province` | 99.47% | 14 条 NULL | 地区（含三分组处置，见蓝图 04） |
| `date` | 98.86% | 30 条 NULL | 日期 |
| `city` | 96.07% | 103 条 NULL | 地区 |
| `accident_location_detail` | 91.88% | 213 条 NULL | 地点补充 |

### 2.4 编码共现（实测 Top 15）

同一事故内同时出现的编码对：

| 编码对 | 共现次数 | | 编码对 | 共现次数 |
|---|---:|---|---|---:|
| **H1 + M1** | **1,968** | | F2 + M1 | 1,274 |
| **H3 + M1** | **1,778** | | H1 + M4 | 1,231 |
| **H1 + H3** | **1,639** | | H1 + M3 | 1,187 |
| **M1 + M2** | **1,490** | | M1 + M4 | 1,182 |
| **H3 + M2** | **1,477** | | F2 + H1 | 1,161 |
| H1 + M2 | 1,383 | | M1 + M3 | 1,130 |
| | | | F2 + M2 | 1,129 |
| | | | H3 + M4 | 1,117 |
| | | | F2 + H3 | 1,098 |

**读法**：排名前列的共现对集中在两组之间——**{H1 违反操作规程, H3 风险辨识失败}（人因）× {M1 现场监管缺失, M2 隐患排查失效, M4 制度规程漏洞}（管理）**。这是数据里最稳定的结构，也是致因分析页首先要呈现的内容。

> **注意措辞边界**：共现是**关联**，不是因果关系。页面文案写「常同时出现」，**不写**「导致」「引起」。项目既定禁用措辞含「因果机制」，此处尤其要守。

## 三、接口设计

### `GET /api/accidents/<id>`
单事故详情，一次返回全部内容。

```json
{ "ok": true, "data": {
  "id":"5cd6ec7f8873",
  "fields": {
    "title":"…", "date":"2024-03-15", "province":"黑龙江省", "city":"齐齐哈尔市",
    "district":"龙沙区", "accident_type":"坍塌", "severity":"重大事故",
    "deaths":11, "injuries":4, "trapped_count":0,
    "summary":"…", "direct_cause":"…", "project_name":"…", "project_type":"房屋建筑",
    "construction_phase":"装饰装修", "building_structure":null,
    "work_task":"WT04", "work_task_label":"装饰装修",
    "equipment_involved":null, "material_involved":"MAT07", "worker_type":null,
    "collapse_subtype":"建筑结构坍塌", "fall_height":null, "weather":null,
    "contractor":"…", "contractor_type":"无资质/挂靠",
    "developer":null, "supervision_company":null,
    "direct_economic_loss":null, "accident_time":"14:30",
    "accident_location_detail":"…", "report_type":"新闻报道", "raw_text":"…"
  },
  "causes": {
    "primary_cause":"…",
    "cause_chain":"M2→F1→H3→H1",
    "items": [
      { "code":"M2", "name":"隐患排查失效", "layer":"M", "layer_label":"管理",
        "evidence":"…", "inference":"…", "evidence_quality":"weak_infer",
        "quality_label":"原文未直接提及", "sort_order":1 } ]
  },
  "meta": {
    "source_name":"safehoo", "source_url":"http://…", "crawl_date":"…",
    "publish_date":"…", "text_type":"single",
    "classification_verdict":"batch_direct", "classification_confidence":"high",
    "pipeline_version":"caics_v1.0",
    "step1_duration_ms":17200, "step2_duration_ms":24600, "created_at":"…"
  },
  "images": [ {"local_path":"imageV3/…/1.jpg","phase1_scene_type":"…"} ],
  "available": { "A": 12, "B": 7, "C": 6, "D": 5 }
} }
```

**服务端职责**：
- `work_task_label` 由 `work_task` 查 `enum_definitions` 得到中文名——**前端不硬编码编码表**
- `layer` / `layer_label` 由 `code` 首字母映射（M/F/T/H/C → 管理/设施/技术/人因/合规）
- `quality_label` 由 `evidence_quality` 映射固定文案
- `available` 返回各档实际有值的字段数，前端据此决定是否渲染折叠面板
- **证据文本兜底**：`caics_causes.evidence` 实测 **8 条空串**、`inference` **11 条空串**（两列均无 NULL）。不能假定「有编码就有证据文本」；缺失时显示「未提供证据文本」，**不得用 `code` 的类名去冒充证据**——那会把"无证据"伪装成"有证据"，直接损害证据三级分层的可信度

### `GET /api/causes/framework`
CAICS 体系定义（19 类 + 层归属），页面初始化时取一次。

```json
{ "ok": true, "data": {
  "version": "caics_v1.0",
  "layers": [
    { "key":"M", "label":"管理", "count":7077, "categories":[
        {"code":"M1","name":"现场监管缺失","count":2208},
        {"code":"M2","name":"隐患排查失效","count":1784},
        {"code":"M4","name":"制度规程漏洞","count":1390},
        {"code":"M3","name":"安全培训不足","count":1200},
        {"code":"M5","name":"市场行为违规","count":495} ] } ],
  "total": 16323,
  "covered_accidents": 2618
} }
```

> `code` 与 `name` **取自 `caics_causes` 表的 `GROUP BY code, name`**，不是常量。若表中出现体系外的 code，`framework` 会如实列出——**不静默丢弃**。

### `GET /api/causes/distribution`
带筛选的致因分布，供致因分析页的交叉分析。

| 参数 | 说明 |
|---|---|
| `accident_type` / `severity` / `province` / `project_type` / `construction_phase` | 与列表页同口径的下推筛选 |
| `year_from` / `year_to` | 年份区间 |
| `by` | `layer`（默认）· `code` · `year` · `province` · `accident_type` |

```json
// by=code 时
{ "ok": true, "data": {
  "scope": { "accidents": 1092, "causes": 7104, "filter_desc":"事故类型 = 坍塌" },
  "items": [ {"code":"M1","name":"现场监管缺失","layer":"M","count":1103,
              "share":0.155, "accident_share":0.934}, … ],
  "by_layer": [ {"key":"M","label":"管理","count":3201,"share":0.451}, … ],
  "evidence_quality": [ {"key":"direct_quote","count":6402}, … ] } }
```

> `share` = 该类编码数 / 该子集编码总数；`accident_share` = 含该类编码的事故数 / 该子集事故数。**两个指标含义不同，页面上要分开标注**，避免读者混淆「编码占比」与「事故覆盖率」。

### `GET /api/causes/cooccurrence`
编码共现。

| 参数 | 说明 |
|---|---|
| `top` | 返回前 N 对，默认 20，上限 100 |
| 其余筛选参数 | 同 `distribution` |

```json
{ "ok": true, "data": {
  "scope": { "accidents": 2623 },
  "pairs": [ {"a":"H1","a_name":"违反操作规程","b":"M1","b_name":"现场监管缺失",
              "count":1968, "joint_share":0.751,
              "lift":1.28} ],
  "matrix": [ [0, 1639, 1968, …], … ] } }
```

> `lift` = 实际共现率 / 独立期望率，用于剔除「因为 M1 本身出现得多所以共现多」的伪相关。**页面默认按 `lift` 而非 `count` 排序**，并在文案中说明理由。

### `GET /api/causes/timeline`
编码随年代的变化（供年代交叉图）。

```json
{ "ok": true, "data": {
  "years": ["1978", …],
  "series": [ {"code":"M1","name":"现场监管缺失","values":[0,2,5,…]}, … ] } }
```
> 年份有断档（1991–2004 无记录，见蓝图 04），**折线必须断在缺口处**，不能用插值连起来。

## 四、页面结构与交互逻辑

### 4.1 详情页 `/accident/<id>`

```
┌─ 顶栏（base.html）────────────────────────────────────┐
├─ ① 头部：标题 + 类型/等级 badge + 日期 + 地区 ─────────┤
│   齐齐哈尔市第三十四中学体育馆屋顶坍塌事故             │
│   [坍塌] [重大事故]  2024-03-15  黑龙江省 齐齐哈尔市    │
│   死亡 11 · 受伤 4 · 被困 0                            │
├─ ② 摘要 + 直接原因（两段文字）───────────────────────┤
├─ ③ 致因树（本页主体）────────────────────────────────┤
│   ┌ 管理 5 类 ────────────────────────────────────┐  │
│   │ M2 隐患排查失效  [原文未直接提及]               │  │
│   │    证据：原文未直接提及，但从防护栏杆缺失可推断  │  │
│   │    推断：防护栏杆缺失是显性隐患……               │  │
│   │ M4 制度规程漏洞  [原文直接表述]                 │  │
│   │    …                                            │  │
│   └─────────────────────────────────────────────────┘  │
│   ┌ 人因 3 类 ─┐ ┌ 设施 2 类 ─┐ ┌ 技术 1 类 ─┐      │
│   │ …           │ │ …           │ │ …           │      │
│   └─────────────┘ └─────────────┘ └─────────────┘      │
├─ ④ 字段明细（A 档必显 / B 档 / C 档折叠 / D 档高级折叠）┤
├─ ⑤ 图片画廊（见蓝图 06）─────────────────────────────┤
├─ ⑥ 处理信息（折叠：来源、时间、模型耗时、判定路径）──┤
├─ ⑦ 原文全文（折叠）─────────────────────────────────┤
└──────────────────────────────────────────────────────┘
```

**关键交互**：
- **层分组而非平铺**：致因树按 M/H/F/T/C 五层分组，各层内按 `sort_order` 排。19 类平铺成一长列读者无法理解，分层才对应 CAICS 的体系结构。
- **证据两级折叠**：默认只显示「编码 + 类名 + 证据等级徽章」；点开才展开 `evidence` 与 `inference` 两段原文。6.2 条编码 × 2 段文本默认全展开会让页面过长。
- **`cause_chain` 单独呈现**：`M2→F1→H3→H1` 形式的链条用箭头串联显示在主致因下方，它表达的是编码间的推进顺序，**不等于因果关系**，文案写「致因链」。
- **未提及字段**：显示为「—」并可 hover 提示「原报告未提及」——**空值与"没有"要能区分**。
- **返回列表保持状态**：从列表点入时列表的筛选条件与页码带在 URL hash 里（蓝图 04 已设计），详情页放一条「返回列表」保持原状态。

## 五、技术选型与理由

| 选择 | 理由 |
|---|---|
| **类名查表，不硬编码** | `caics_causes` 自带 `code` + `name`（19 类实测齐全）。旧 web 因依赖缺失的 taxonomy JSON 而 500，此方案从根上消除该失败模式 |
| **层归属由 code 首字母推导** | `substr(code,1,1)` → M/F/T/H/C。已有数据严格符合（实测 19 类 5 前缀齐全），无需额外映射表 |
| **聚合查询下推 SQL** | `GROUP BY code` / 自连接做共现 / `substr(date,1,4)` 做年代——都在 SQLite 内完成。2,623 条 × 16,323 行的规模下毫秒级 |
| **共现提供 lift 而非只有 count** | 高频编码（M1 出现 2,208 次）天然与所有编码共现多，`count` 排序会误导。lift 校正后才能真正看出关联强度 |
| **图表用内联 SVG / CSS** | 与蓝图 04 一致，**不引 CDN**，保证离线可用。金字塔与条形图用 CSS 宽度百分比；共现热力图用内联 SVG 网格 |
| **致因树按层分组** | 对应 CAICS 的体系结构；平铺 19 类不可读 |
| **详情页一次请求返回全部** | 6.2 条编码 × 2 段文本 + 48 字段，单次响应约 20–40 KB，远小于旧版 `/api/dataset` 的 21.5 MB |

## 七、验收标准

1. `GET /api/causes/framework` 返回 **19 类**，各层计数为 M 7,077 / H 4,723 / F 2,799 / T 1,533 / C 191，`total = 16323`
2. 19 类的 `code` + `name` 与 `SELECT code, name, COUNT(*) FROM caics_causes GROUP BY code` **逐项一致**
3. `GET /api/accidents/<id>` 对每条记录返回的 `causes.items` 条数 = 该 `accident_id` 在 `caics_causes` 的实际行数
4. 12 列 A 档字段在 100% 的记录上都有返回键（值可为 `null`，但键必须存在）
5. `GET /api/causes/cooccurrence` 的 Top 1 为 `H1 + M1 = 1968`
6. `GET /api/causes/distribution?by=layer` 的 `by_layer` 五项与 framework 的层计数一致（无筛选时）
7. 加 `accident_type=坍塌` 筛选后，`scope.accidents = 1092`，且 `scope.causes` = `SELECT COUNT(*) FROM caics_causes WHERE accident_id IN (SELECT id FROM accidents WHERE accident_type='坍塌')`
8. 证据等级分布：`direct_quote` 14,784 / `indirect_infer` 1,117 / `weak_infer` 422（无筛选时）
9. 每条编码的 `evidence_quality` 落在三级之内，且页面按三级三色正确渲染
10. 含 29 条编码的事故（最大值）详情页正常渲染，无截断、无卡顿
11. **`causes.items` 为空的事故（5 条）**：详情页显示「该事故暂无致因编码」而非空白区域
12. 构造 `code` 不在 19 类内的数据，`framework` 如实列出而非丢弃（用测试库验证）
13. 无任何 CDN 引用（`grep -r "http://" templates/ static/` 只应命中 `source_url` 之类的数据字段）
