## 一、功能目标与用户场景

### 目标
在「机器产出的结构化数据」与「正式数据集」之间，放一道**看得见、可回退、可追溯**的人工关口。

### 三条用户路径

| 路径 | 动作 | 系统行为 |
|---|---|---|
| **逐条审** | 打开一条暂存结果 | 左侧原文、右侧 33 字段与致因树，逐字段可改，改完通过/退回 |
| **批量过** | 勾选多条 → 批量通过 | 只对「无告警」的条目开放批量；有告警的必须逐条看 |
| **并入** | 点「并入最终库」 | 单事务写 `accidents` + `caics_causes`，写失败整体回滚 |

### 设计约束
并入是**唯一会写最终库的操作**。最终库里有 2,623 条已发表的论文数据，一次错误的并入会直接污染论文口径。因此本蓝图的全部设计围绕一件事：**并入要么完整成功，要么完全不影响现有数据**。

## 二、现状诊断：这一环目前不存在

### 2.1 没有暂存层——只有"直接写最终库"

实测 `accidents` 表的写入路径全部在 `scripts/` 下的批处理脚本里，**从原始文本到最终库一竿子到底**，中间没有人工确认点。这是 1,041 行孤儿外键与 338 行重复编码得以产生并长期潜伏的结构性原因：**没有人有机会在看到数据之后再决定收不收**。

### 2.2 写入方式不统一，是孤儿与重复的直接来源

| 脚本 | `accidents` 写法 | `caics_causes` 写法 |
|---|---|---|
| `scripts/batch_runner.py` | `INSERT OR REPLACE` | `INSERT OR REPLACE` |
| `scripts/process_ebook800.py` | `INSERT OR REPLACE` | `INSERT OR REPLACE` |
| `scripts/run_batch.py` | `INSERT OR REPLACE` | **裸 `INSERT`**（`:102-108` 附近）|
| `scripts/run_batch_pipeline.py` | `INSERT OR REPLACE` | **裸 `INSERT`**（`:92-96` 附近）|

主表用 `INSERT OR REPLACE` 而子表用裸 `INSERT` 的组合最危险：`INSERT OR REPLACE` 在 SQLite 上是 **DELETE + INSERT**，若 `PRAGMA foreign_keys` 未开，级联删除不触发，子表旧行留下成为**孤儿**；重跑时同一事故的子表又追加一遍，于是**重复**。这正是 2026-09-23 清理的 1,041 行孤儿（109 个失效 `accident_id`）与本次核查发现的 338 行重复（278 组 `(accident_id, code)`）的共同成因。

### 2.3 建表脚本与真实库已经漂移

| 检查 | 结果 |
|---|---|
| `scripts/create_db_v2.py:10` 注释 | 「事故主表 **(55列)**」 |
| 同文件 `SCHEMA` 实际列数 | **52 列**（注释本身就错） |
| 真实库 `accidents` | **48 列** |
| 差额 | 少了 `lighting` / `day_of_week` / `season` / `time_period` / `is_night_shift` **5 个派生时间字段**，多了 `work_task_enum` |
| `caics_causes` 索引声明（`create_db_v2.py:84-85`） | `idx_cause_acc` / `idx_cause_code` |
| 真实库 `caics_causes` 索引 | **0 个**（`PRAGMA index_list` 返回空）|
| `accidents` 索引声明（`create_db_v2.py:66-70`） | 5 个（类型/等级/日期/城市/死亡） |
| 真实库 `accidents` 索引 | **仅主键**，5 个全无 |

原因就在脚本自身：`create_db_v2.py:165-167`

```python
if os.path.exists(db_path):
    os.remove(db_path)      # ← 会删除现有数据库
```

**该脚本从未在真实库上执行过**（否则库早没了）。当前库是另一条途径建的，于是脚本里声明的索引与约束一个都没生效。所有 SQL 查询（`caics_causes` 16,323 行、`accidents` 2,623 行）都在**全表扫描**。

### 2.4 外键声明了但从不强制

三张子表（`caics_causes` / `search_logs` / `image_analyses`）都声明了 `REFERENCES accidents(id) ON DELETE CASCADE`，`create_db_v2.py:171` 也写了 `PRAGMA foreign_keys=ON`——**但那只是建库那一个连接**。SQLite 的 `foreign_keys` 是**连接级**开关，默认 OFF。任何没显式打开的连接写数据，外键形同虚设。这就是 1,041 行孤儿能够存在的技术条件。

## 三、暂存层设计

### 3.1 位置

暂存表（`staging_accidents` / `staging_causes` / `extract_tasks`）定义在**工作库 `data/caiems_staging.db`** 中，见 [`02_审核与提取.md`](02_审核与提取.md) 第 3.2 节。本蓝图不再重复列定义，只补充审核相关列的使用语义：

| 列 | 取值 | 含义 |
|---|---|---|
| `review_status` | `pending` | 待审（默认） |
| | `approved` | 审核通过，可并入 |
| | `edited` | 人工修改过，可并入（保留 `review_note` 记录改了什么） |
| | `rejected` | 退回，不并入 |
| `reviewer` | 文本 | 审核人（本轮为单人，字段先留着） |
| `reviewed_at` | ISO | 审核时间 |
| `review_note` | 文本 | 修改说明或退回理由 |

### 3.2 告警：让该看的条目浮出来

暂存层在审核时**自动计算告警**（不存表，读时算），把需要人眼判断的条目标出来：

| 告警 | 触发条件 | 为什么重要 |
|---|---|---|
| `empty_title` | `title` 为空或 < 4 字 | 最终库 `title` 是 `NOT NULL`，空标题入库后无法检索 |
| `no_death` | `deaths = 0` 且 `injuries = 0` | 可能原文确实无人伤亡，也可能抽取失败 |
| `type_mismatch` | `accident_type` ≠ `text_type` 隐含类型 | 类型与文本体裁矛盾 |
| `no_causes` | `staging_causes` 无行 | 无致因编码，与主库 5 条无编码的记录同类 |
| `quality_shift` | `evidence_quality_llm` 与生效值不一致的条数 > 半数 | 判定方式存疑（见蓝图 02 待决项 A） |
| `cause_not_in_taxonomy` | `code` 不在 CAICS 19 类内 | S4 产出了未知编码 |
| `short_text` | `raw_text` < 100 字 | 信息量可能不足 |

**批量通过只对零告警条目开放**。有告警的必须逐条打开确认——这是"人工审核"四个字的实际落点。

### 3.3 为什么暂存层要在工作库而非最终库

| 理由 | 说明 |
|---|---|
| 隔断风险 | 暂存表与待审数据不进最终库文件，备份、发布、外发都不受污染 |
| 可丢弃 | 工作库可整库删除重建，最终库不行 |
| 连接权限不同 | 展示层对最终库只读（`mode=ro`），暂存层需要读写，物理分离最干净 |
| 与用户的分层表述一致 | 用户原话即「临时数据库 → 人工审核 → 最终数据库」，本设计是它的直接实现 |

### 5.2 幂等键：`raw_id` 就是 `accidents.id`

最终库 `accidents.id` 实测为 12 位十六进制字符串，与 `RawAccidentStore._hash_url`（`stores/__init__.py:87-90`）和 `RawAccidentText.generate_url_hash()`（`base.py:54-58`）的算法一致：`md5(source_url)[:12]`。

**因此 `raw_accidents.raw_id` 可直接作为 `accidents.id`**，同一条 URL 无论并入多少次都命中同一主键——**幂等性由主键天然保证**，不需要额外的查重逻辑。

> ⚠️ **文献轨例外**：樊锡仁《800例》703 条、住建部三卷 192 条等**没有 URL**，其 `accidents.id` 来自别的算法（待确认）。新管道若纳入文献轨，需要为无 URL 的条目定义 id 生成规则。**列为待决项 B。**

### 5.3 并入事务模板

```python
# 伪代码：一个 stage_id = 一个事务
conn.execute("PRAGMA foreign_keys=ON")      # ← 每个连接都必须开
conn.execute("BEGIN IMMEDIATE")             # 立即取写锁，避免并发并入相互等待
try:
    # ① 主表：REPLACE 语义（同 id 则覆盖）
    conn.execute("INSERT OR REPLACE INTO accidents (%s) VALUES (%s)" % (COLS, PLACEHOLDERS),
                 values_from_staging)

    # ② 子表：先清后写（关键——不要裸 INSERT）
    conn.execute("DELETE FROM caics_causes WHERE accident_id = ?", (accident_id,))
    conn.executemany(
        "INSERT INTO caics_causes (accident_id, code, name, evidence, inference,"
        " evidence_quality, sort_order) VALUES (?,?,?,?,?,?,?)",
        cause_rows)

    conn.execute("COMMIT")
except Exception:
    conn.execute("ROLLBACK")
    raise
```

**三条不可协商的规则**：
1. **主表与子表在同一事务**——避免出现"主表已更新、子表还是旧的"中间态
2. **子表先 `DELETE` 再 `INSERT`**——这是消除 338 行重复的直接手段（不依赖 `UNIQUE` 约束，因为现有库上无法加约束而不影响历史数据）
3. **写入连接显式 `PRAGMA foreign_keys=ON`**——这是消除未来孤儿的唯一手段

### 5.4 并入前置检查（`promote` 执行前强制）

| 检查 | 不通过时 |
|---|---|
| 最终库可写（非 `mode=ro`） | 中止 |
| `PRAGMA foreign_keys` 已开 | 中止 |
| 索引已补（见第六节） | 中止（全表扫描下的写入会显著变慢，且可能超时） |
| 所有 `stage_id` 的 `review_status ∈ {approved, edited}` | 中止，列出不合规项 |
| `dry_run` 已跑过且无 `conflicts` | 中止 |
| 最终库备份已生成 | 中止 |

**强制先 `dry_run` 再执行**：`promote` 请求必须携带上一次 `dry_run` 返回的 `confirm_token`，token 与 `stage_ids` 集合绑定。这防止"用户改了选择但沿用了旧确认"。

### 5.5 回滚

| 方式 | 适用 | 做法 |
|---|---|---|
| `rollback_token` | 并入后立即发现错误 | 从本次备份恢复最终库文件（需确保无其他连接持有） |
| 手工恢复 | 隔天后发现 | 从 `data/db_backups/` 取对应时间戳备份 |
| 逆操作 | 只需删掉误入的几条 | 按 `stage_id` 反查 `accidents.id`，事务内删主表+子表 |

> 备份文件按 `caiems_v2.db.bak.before_promote_<时间戳>` 命名，与既有 `caiems_v2.db.bak.before_orphan_cleanup_20260923_155533` 的命名约定保持一致。

## 六、并入前必须完成的库修复（阻塞项）

**这三项不在 web 范围内解决，但 web 的并入功能依赖它们完成。**

### 6.1 补索引

当前 `caics_causes` 零索引、`accidents` 仅主键。`create_db_v2.py:66-70` 与 `:84-85` 声明的 7 个索引全部不存在。需补：

```sql
CREATE INDEX IF NOT EXISTS idx_acc_type     ON accidents(accident_type);
CREATE INDEX IF NOT EXISTS idx_acc_severity ON accidents(severity);
CREATE INDEX IF NOT EXISTS idx_acc_date     ON accidents(date);
CREATE INDEX IF NOT EXISTS idx_acc_city     ON accidents(city);
CREATE INDEX IF NOT EXISTS idx_acc_deaths   ON accidents(deaths);
CREATE INDEX IF NOT EXISTS idx_cause_acc    ON caics_causes(accident_id);
CREATE INDEX IF NOT EXISTS idx_cause_code   ON caics_causes(code);
```

### 7.3 交互逻辑

**左右联动**：点右侧某字段，左侧原文中相关句段高亮（若 S3 记录了来源句段；未记录则跳正文顶部）。**这是审核效率的关键**——没有它，审核员要在长文里手找每个数字。

**告警驱动**：抽屉打开时告警条置顶。`quality_shift` 类告警直接在致因树每条上标出「LLM 判为 X」与「生效值 Y」的差异。

**批量通过的限制要显式**：按钮在选中集合含告警条目时禁用，并提示「12 条中有 3 条含告警，已从批量中排除，请逐条确认」——**不是静默跳过**。

**并入两步走**：`dry_run` 结果用弹层展示（新增/覆盖/冲突三栏），用户确认后才点亮「确认并入」。确认 token 绑定当前选择集。

**空值**：33 字段大量可为空，一律 `v ?? '—'`；编辑时空值可提交，但 `NOT NULL` 列（`title`/`project_type`/`construction_phase`/`accident_type`/`severity`/`report_type`/`summary`）在保存时校验。

## 八、验收标准

1. `GET /api/review/queue` 的 `counts` 与直接 SQL 聚合逐项一致
2. 对一条含 `quality_shift` 告警的记录执行批量通过 → 被 `skipped` 并返回原因，**不被静默通过**
3. `POST /api/review/promote` 带 `dry_run:true` 时**不产生任何写操作**（前后对比最终库文件哈希不变）
4. 不带 `dry_run` 的 `promote` 请求缺少 `confirm_token` → 拒绝
5. 完整并入 10 条后：
   - `accidents` 恰好 +10 行（或按幂等键覆盖，不产生重复 id）
   - `caics_causes` 的行数等于 `staging_causes` 中对应条数之和
   - `SELECT COUNT(*) FROM caics_causes WHERE accident_id NOT IN (SELECT id FROM accidents)` = **0**（无孤儿）
   - `SELECT COUNT(*) FROM accidents WHERE id NOT IN (SELECT DISTINCT accident_id FROM caics_causes)` 仅在无编码条目上非 0
6. **重复并入同一批**：第二次并入后 `accidents` 与 `caics_causes` 行数**不变**（幂等性验证）
7. **中途失败回滚**：人为在子表写入时抛异常，验证主表也未变更（事务完整性）
8. 并入前自动生成的备份文件存在且可打开；`rollback_token` 能撤销最近一次并入
9. 字段映射逐列核对：`province` ← `staging.location`、`classification_verdict` ← `staging.relevance_verdict`、`step1_duration_ms` ← `staging.s3_ms`、`step2_duration_ms` ← `staging.s4_ms` 四处**映射正确**（构造已知值验证）
10. 索引补齐后，`EXPLAIN QUERY PLAN` 显示列表查询走索引而非 `SCAN`；`caics_causes` 按 `accident_id` 查询不再全表扫描
11. `reject` 操作要求 `note` 必填，缺失时返回 400
