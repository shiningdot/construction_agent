# Section 5.2-5.4: Prompt 策略对比实验分析

> 本章对标 Liu et al. (ESWA 2025) Table 3 "Performance comparison of six prompts"，在建筑施工事故致因提取任务上系统比较6种 Prompt 策略的效果。实验使用100条专家多数投票构建的 Ground Truth（5层19类 CAICS 致因框架），在 DeepSeek V4 Pro（temperature=0.0）上运行。

---

## 5.2 实验设计

6种策略按 Liu et al. 的分类框架设计：S0（Basic Zero-Shot）仅提供 CAICS 分类体系与输出格式；S1（Basic Few-Shot）在 S0 基础上增加3个真实专家标注案例；S2（Auto-CoT）要求 LLM 自组织推理链；S3（Plan-and-Solve）要求 LLM 先制定计划后执行；S4（CAICS-CoT，本文提出）将 CAICS 领域知识嵌入 CoT 设计，每个编码附带线索关键词并以"两步判断"（显性匹配 + 隐性推断）引导推理；S5（CAICS-CoT+，本文提出）采用5次独立 API 调用的逐层串行架构。

详细 Prompt 文本与编码指南见附录A，完整实验结果见表2。

## 5.3 逐策略分析

### 5.3.1 S0 Zero-Shot：仅有分类清单时，LLM 能做什么

S0 只提供 CAICS 的19个编码名称和 JSON 输出格式，不作任何推理引导。结果呈现一个明显的精度-召回不对称：Precision（0.759）显著高于 Recall（0.551）。这意味着 LLM 在没有引导的情况下，能较准确地判断"某个编码是否适用于这段文本"，但大量应该输出的编码被遗漏了。

具体而言，M3（安全培训不足，Recall=0.333）和 H3（风险辨识失败，Recall=0.386）是最严重的漏检项。这两类的共同特征是：它们通常不在事故新闻中被显式陈述。建筑施工事故报道倾向于描述"发生了什么"（坍塌、坠落）和"违反了哪个具体规程"，但很少明确叙述"工人未经培训"或"未意识到危险"——这些是隐性致因，需要从事故性质推断而非从表面文本提取。

相比之下，accident_type（0.680）和 severity（0.950）的准确率远高于致因编码。这两个字段是事故新闻的"标题级"信息——文本几乎总是显式陈述"某地发生坍塌事故""造成N人死亡"。LLM 对这一类表面级提取任务已经足够可靠，无需任何 prompt 工程。

S0 的96%编码成功率说明：即使没有推理引导，DeepSeek V4 也能理解 JSON 格式要求。这为所有后续策略提供了可靠的格式基线。

**与 Liu et al. 的对比**：Liu et al. 在 GPT-4o 上的 Basic Zero-Shot 呈现相似模式——Precision 高于 Recall，但两者的绝对值均高于本研究。差异可能来自两个因素：一是 Liu et al. 的 HFACS 编码任务（11个 yes/no 问题）比 CAICS 的19类分类任务粒度更粗、歧义更小；二是 GPT-4o 的零样本推理能力可能略优于 DeepSeek V4。

### 5.3.2 S1 Few-Shot：三个示例为何压倒领域知识

S1 在所有策略中取得最高 F1（0.737），且编码密度（5.0/条）与 GT（5.0/条）完美匹配。这一结果发生在我们预期 CAICS-CoT（S4）——嵌入了完整领域知识的 CoT 策略——将成为最优策略的背景下，构成了本实验最大的"意外"。

**为什么3个示例的效果如此显著？**

首先，Few-Shot 示例提供了 Liu et al. 所称的"格式-内容联合校准"（joint format-content calibration）。三个示例不仅展示了输出格式（JSON 结构、字段名称），更展示了编码密度（5-7个/条）、编码组合模式（M 层几乎总出现、H 层常伴随 M 层出现）和推理深度。LLM 通过 in-context learning 内化了这些隐式规范，而非仅仅记住格式。

其次，示例中的推理模式展示比显式的领域知识引导更"可执行"。S4 的 prompt 说"根据事故类型和严重程度推断隐性致因"，这是一个需要 LLM 自行转化为操作步骤的抽象指令。而示例直接展示了这一推断过程：给定"升降机未经检验合格即投入使用"，输出 `["M1","M3","M4","F2","T1","H1","H2"]`——LLM 只需模仿这一映射模式，而不需要理解"为什么 M3 需要被推断出来"。

**为什么 Few-Shot 优于领域知识引导的 CoT？**

这个结果在 Liu et al. 的 GPT-4o 实验中恰恰相反——HFACS-CoT 优于 Basic Few-Shot。我们提出一个模型特异性的解释：

DeepSeek V4 的预训练目标中包含大量代码和结构化数据，它被优化为从"输入-输出对"中高效学习映射模式。Few-Shot 的3个示例恰好利用了这种模式匹配能力。而 GPT-4o 在指令遵循（instruction following）方面经过更多对齐训练，对结构化推理指令的响应更好。

这一差异的学术意义在于：它挑战了"领域知识嵌入 CoT 是普适最优策略"的隐含假设。Prompt 策略的效果至少部分取决于底层模型的能力剖面（capability profile），需要针对具体模型进行校准——这是 Liu et al. 的单模型实验未能揭示的。

**为何编码密度完美匹配？**

一个值得注意的细节是 S1 不仅 F1 最高，而且编码密度与 GT 完全一致（5.0 vs 5.0）。其他策略均偏离 GT 密度：S0 偏低（3.6，保守），S4 偏高（6.5，激进）。Few-Shot 示例中的编码密度恰好充当了隐式的"输出长度校准器"，这是纯文本指令难以实现的控制效果。

### 5.3.3 S2 Auto-CoT：自组织推理的能与不能

S2 要求 LLM 按 M→F→T→H→C 因果链自行组织推理过程，不提供领域知识线索。初始版本的 F1 仅为 0.046，但这完全是格式兼容问题——96/100 的输出采用了 `{M:["M1","M2"], F:["F2"], ...}` 的分层 JSON 格式，而非 prompt 要求的 `{codes:[...]}` 统一格式。我们的后处理脚本从这些分层键中成功聚合出 421 个有效编码，修复后 F1=0.630，与 Zero-Shot（0.628）几乎持平。

**这个持平意味着什么？**

Auto-CoT 没有提供领域知识，也没有提供推理示例。LLM 完全依靠自身对"M→F→T→H→C 因果链"这一概念的理解来组织推理。它与 Zero-Shot 持平的事实说明：对于 LLM 已经具备基础知识（建筑施工事故致因）的领域，"自组织推理"这一步本身并不增加分类能力——它只是把同一套知识用更结构化的方式表达出来。

但 Auto-CoT 的推理质量并非毫无价值。我们在分析分层输出时发现，LLM 产出的推理文本（如"M1：文本明确指出建设单位未取得施工许可证、未委托监理，现场监管缺失严重"）对于安全分析人员理解编码依据具有实质帮助。Auto-CoT 的价值可能不在于提升分类精度，而在于提供可解释性。

**格式漂移的深层原因**

S2 的格式漂移（从 `{codes:[...]}` 漂移到 `{M:{...}, F:{...}}`）并非偶然。Prompt 要求"按 M→F→T→H→C 因果链推理"，这在 LLM 的语义空间中激活了"分层组织"的期望——按层输出自然比平铺 codes 列表更"合理"。这揭示了 Auto-CoT 的一个内在矛盾：推理结构越接近人类的思维模式（分层分析），输出格式越容易偏离机器的解析预期（统一 JSON）。在应用 Auto-CoT 时，需要在 prompt 中显式桥接这两个范式——明确说明"推理可以分层，但最终编码必须合并到 codes 字段"。

### 5.3.4 S3 Plan-and-Solve：规划的边际增益

S3 的 F1（0.643）仅比 S0（0.628）高 0.015，提升极其有限。这与 Liu et al. 的发现一致：Plan-and-Solve 在他们的实验中同样位于中等位置，增益不明显。

更值得注意的是，S3 的 TypeAcc（0.560）反而是所有策略中最低的（不含 S2/S5 的格式问题）。分析发现，部分 LLM 在"制定分析计划"时过度聚焦于致因层面的检查，将事故类型和严重程度判断推迟到"执行"步骤，而执行步骤的 JSON 输出中又遗漏了这些字段。规划步骤在此处产生了意外的注意力转移效应——LLM 将规划与执行视为两个独立任务，而非一个统一的分析流程。

**为什么规划没有带来显著增益？**

建筑施工事故致因分析的认知负荷主要不在于"不知道该检查什么"，而在于"理解文本中的隐式信息"。规划对于需要多步逻辑推导的任务（如数学证明）有帮助，因为每一步的逻辑依赖关系需要显式组织；但致因分类的任务结构是扁平的一一对应（文本片段→编码），规划无法为这种映射关系增加信息。

### 5.3.5 S4 CAICS-CoT：领域知识嵌入 CoT 的设计与迭代 ⭐

S4 是本文提出的核心策略，将 CAICS 领域知识嵌入思维链设计。我们在实验过程中经历了一次关键迭代，这一迭代本身提供了关于 CoT prompt 设计的重要方法论启示。

**v1 的失败与诊断**

S4 初版 prompt 采用"条件检查"格式：对每个编码，以疑问句形式呈现判断线索——"M1现场监管缺失: 文本提到'无人监管''监理失职'？"这种设计在语义空间中将编码判断建模为一个二值门控（gate）：如果关键词存在则输出编码，如果不存在则输出"无"。初版 prompt 还包含了"不要编造"的保守指令。

结果是灾难性的：F1=0.425，Recall=0.319，30% 的样本无任何编码输出，M1（现场监管缺失）的 Recall 仅为 0.143。GT 中 M1 是最常见的编码（出现在 85/100 条中），但 LLM 在"条件检查"模式下几乎对其失明——因为大多数事故新闻不会精确使用"无人监管"或"监理失职"这些措辞，而是用"安全管理不到位""未及时发现制止"等变体表述。

**问题不在领域知识本身，而在知识的呈现方式**

我们修正了 v1 的两个核心设计缺陷。第一，将"条件检查"改为"两步判断"：（1）显性匹配：文中有直接相关的表述吗？（2）隐性推断：根据事故性质和施工安全常识，该致因是否必然存在？第二，将"不要编造"的保守指令替换为"安全分析宁可多标不漏标"的全覆盖偏好。

修正后的效果令人震惊：F1 从 0.425 跃升至 0.676（+0.251），Recall 从 0.319 跃升至 0.772（+0.453），M1 的 Recall 从 0.143 恢复至 0.941。解析错误从 9 条降至 1 条，空编码率从 30% 降至 1%。

**这一迭代对 Prompt 工程的方法论启示**

CoT prompt 的"指令语法"（imperative syntax）对 LLM 行为的影响远超预期。"文本提到 X 吗？"这种疑问式引导激活的是"精确模式匹配"——LLM 在字面上寻找 X。而"X 的线索包括 a, b, c，即使没有这些词，根据事故性质合理推断"激活的是"推理模式"——LLM 将关键词视为线索而非门控。

这一发现与 Liu et al. 的 HFACS-CoT 设计哲学一致——他们的 prompt 同样采用了引导式而非检查式的表述。但这一"设计惯例"在他们的论文中并未被显式讨论。本研究通过 v1→v2 的对照实验，为这一设计原则提供了因果证据。

**S4 在致因推断上的独特优势**

尽管 S4 的总体 F1（0.676）不及 S1（0.737），但它在特定维度上展现出独特优势。S4 的 TypeAcc（0.880）和 SevAcc（0.970）是所有策略中最高的——领域知识嵌入帮助 LLM 更准确地识别事故的表面特征。在 T 层（触发条件），S4 的 F1（0.753）也超过了 S1（0.708）。T 层编码（设备故障、物料异常、地质突变、气象触发）是 CAICS 中最"客观"的一层——它们描述物理世界的因果事件，而非组织或行为的缺陷。领域知识引导在这一层最有效，因为客体性因果关系的判断受益于明确的关键词线索。

S4 的 Precision（0.628）低于 S1（0.750），但 Recall（0.772）高于 S1（0.739）。这反映了我们在 v2 中有意选择的"安全优先"策略——宁可误报不可漏报——在安全分析领域具有实际价值：漏掉一个致因比多报一个致因的成本更高。

### 5.3.6 S5 CAICS-CoT+：逐层串行的理论预期与现实落差

S5 将 CAICS 的5层分析分解为5次独立 API 调用，每次由一个"层专家"（M层=安全管理专家，F层=安全防护专家，等）完成单层编码。前层分析结果以摘要形式注入后层。这一设计对标 Liu et al. 的 HFACS-CoT+（逐问题独立输入），其理论预期是：每层独立推理可以避免跨层注意力稀释，提升每层的分类质量。

**现实与理论相反**

S5 的 F1（0.488）不仅远低于 S4（0.676），甚至低于 S0（0.628）。6次 API 调用（5层+1次汇总）的总成本是单次调用的6倍，但产出反而更低。这不是工程实现的缺陷——我们在 v2 中修复了 v1 的字段遗漏问题（TypeAcc 从0恢复到0.770）——而是架构层面的问题。

**为何逐层串行反而不如单次调用？**

逐层调用在每个"层专家"看到的输入是不完整的：H 层（人的行为）分析时，LLM 收到的不是完整的因果链上下文，而是"前层分析结果：M层=M1,M2；F层=F2；T层=T2"的摘要。这个摘要丢失了推理过程——它告诉 H 层分析者"前面发现了 M1、M2、F2、T2"，但没有告诉它"为什么发现这些"以及"这些发现之间有什么因果联系"。

更关键的是，CAICS 的因果链是双向的。M→F→T→H→C 的序列暗示了自上而下的因果关系，但在实际事故分析中，往往是某个触发事件（T）暴露了防线失效（F），而防线失效又追溯到管理缺陷（M）。这种循环因果关系需要 LLM 在同一推理过程中反复上下追溯——单次调用可以做到这一点（在 reasoning tokens 中自由跳转），而逐层串行架构在每一层做了硬性截断。

**与 Liu et al. 的差异**

Liu et al. 在 GPT-4o 上发现 HFACS-CoT+（逐问题输入）与 HFACS-CoT（同时输入）效果相近甚至略优。我们的实验在 DeepSeek V4 上发现了相反的结果。这可能与两个模型在处理"部分信息"时的策略差异有关：GPT-4o 在信息不完整时倾向于保守推断（与上下文窗口较大时行为一致），而 DeepSeek V4 在上下文受限时倾向于做出更不稳定的推断。但这一假说需要进一步的控制实验验证。

**串行架构是否在致因分析中根本不可行？**

我们的结果不应被解读为"逐层串行架构在所有领域都无效"。Liu et al. 的成功案例说明在 HFACS 航空事故分析中，逐层推理可能是可行的。两个领域的关键差异可能在于因果链的密度：航空事故的 HFACS 编码之间相对独立（飞行员的不安全行为与组织因素之间的联系已有成熟的映射规则），而建筑施工事故的 CAICS 编码之间关联更紧密，需要更多跨层推理。逐层架构的适用性可能取决于领域因果结构的耦合度。

## 5.4 讨论：Prompt 策略效果的模型依赖性

### 5.4.1 与 Liu et al. 的核心差异

表3将本研究的6策略排名与 Liu et al. 的结果进行并排对比。

**表3: 策略排名的跨研究对比**

| 策略 | Liu et al. (GPT-4o) | 本研究 (DeepSeek V4) |
|------|---------------------|----------------------|
| Zero-Shot | 中等 | 第5（F1=0.628） |
| Few-Shot | 低于 CoT | **第1（F1=0.737）** |
| Auto-CoT | 低于 Few-Shot | 第4（F1=0.630） |
| Plan-and-Solve | 中等 | 第3（F1=0.643） |
| Domain-CoT | **第1-2** | 第2（F1=0.676） |
| Domain-CoT+ | **第1-2** | 第6（F1=0.488） |

最显著的差异是 Few-Shot 与 Domain-CoT 的相对排位完全反转。在 Liu et al. 的实验中，领域知识引导的 CoT 优于 Few-Shot；在本实验中，Few-Shot 以 0.061 的 F1 优势领先于最优的 CoT 策略。

**这一反转不应被简单解读为"哪个模型更好"的证据，而应被理解为一个方法论发现：Prompt 策略效果是 model-dependent 的。**

### 5.4.2 为什么 Prompt 策略效果是模型依赖的？

我们提出一个分析框架：模型对 Prompt 策略的响应取决于两个因素——（1）模型的 in-context learning 效率，和（2）模型的指令遵循对齐程度。

DeepSeek V4 在预训练中处理了大量代码和结构化数据对，其 in-context pattern matching 能力可能强于指令分解能力。Few-Shot prompt 恰好利用了这种"输入→输出"的模式匹配——它不需要 LLM 将抽象的分析指南（"根据事故性质推断隐性致因"）转化为具体操作步骤，只需要从示例中学习隐式映射。GPT-4o 经过更多的 RLHF 对齐训练，其"遵循复杂指令"的能力更强，因此能更好地执行结构化 CoT 中的多步推理指令。

这一解释如果成立，其推论是：对于开源或半开源模型（如 DeepSeek、Qwen、LLaMA 系列），Few-Shot 可能是比复杂 CoT 更可靠的高性能策略；对于经过高强度指令对齐的商业模型（如 GPT-4o、Claude），领域知识 CoT 才可能达到或超越 Few-Shot。这一假说可通过多模型对比实验进行检验。

### 5.4.3 CoT Prompt 设计的质量门槛

S4 的 v1→v2 迭代揭示了 CoT 的一个非对称特性：一个差的设计不仅不能帮助，反而会显著损害性能（v1 F1=0.425 vs Zero-Shot F1=0.628）。这与 Few-Shot 和 Zero-Shot 不同——它们的 prompt 相对简短，出错空间小。

CoT 的"指令语法"对 LLM 行为有放大效应。"文本提到'无人监管'吗？"这种疑问句表面上是引导，实际上在 transformer 的语义空间中激活了精确匹配的操作模式。LLM 不会"理解"这是一个建议性线索——它会在 attention 机制中给包含这些精确关键词的文本片段赋予高权重，并给不包含的片段赋予低权重。

相反，"线索词：无人监管、监理失职、安全管理混乱。即使没有这些词，几乎所有建筑施工事故都存在现场监管缺失，请合理推断"——这种陈述句激活了推理模式。LLM 将关键词理解为一个开放的语义族（semantic family），并自主判断文本中的哪些表述属于这一族。

这一发现的操作建议是：**在安全分析、医疗诊断等需要"宁可多报不可漏报"的领域，CoT prompt 中的条件表述应采用"线索引导"而非"条件检查"**。"条件检查"模式更适合于需要零误报的场景（如法律条文引用）。

### 5.4.4 串行 vs 集成推理：因果链分析的设计准则

S5（F1=0.488）与 S4（F1=0.676）的对比提供了关于因果链分析中"集成推理 vs 串行推理"的因果证据。虽然 S5 的每层分析由"专家"完成，且前层结果被注入后层，但摘要式的信息传递无法替代在同一个 reasoning context 中自由追溯因果链的能力。

对于需要使用 CAICS 或其他分层致因框架的实践者，我们的实验结果表明：**在单次 LLM 调用中进行完整的因果链分析，优于将分析拆分为多个子任务。** 如果计算资源允许，更好的做法可能是在单次调用中增加推理 token 预算（max_tokens），让 LLM 有充分的 reasoning 空间在因果链上来回追溯，而非将因果链硬性切分为独立调用的瀑布。

### 5.4.5 实验局限

本实验存在几个需要注意的局限。第一，样本量为100条，虽然覆盖了全部12种事故类型和19类编码，但对低频编码（C1=1次，C2=4次）的评估不可靠。第二，仅使用单一模型（DeepSeek V4），5.4.2 节提出的"模型差异性假说"尚未经过多模型验证——这一验证将在第6章的多模型实验中完成。第三，S2 的编码指标通过后处理修复，且事故类型/严重程度无法评估，其0.630的 F1 应视为下界估计。第四，温度设为0.0，结果反映了模型在确定性模式下的行为，对于生成式任务的随机性未作探索。
