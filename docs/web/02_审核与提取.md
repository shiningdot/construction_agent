# 蓝图 02 · 审核与提取

> 对应阶段②「采集的原始事故文本输入到在线分析管道，原始数据审核（单个事故、多事故、通报），符合要求的进入特征提取 + 致因分析」
> 依赖：[`00_总体架构与数据层.md`](00_总体架构与数据层.md)（工作库、CAICS 唯一口径）、[`01_在线采集.md`](01_在线采集.md)（输入 = `raw_accidents` 中 `gate_verdict='confirmed'` 的记录）
> 下游：[`03_暂存与人工审核.md`](03_暂存与人工审核.md)（本阶段产出的 `staging_*` 记录是其审核对象）

## 一、功能目标与用户场景

### 目标
把「一段原文」变成「一张可审核的结构化事故卡片 + 一棵 CAICS 致因树」，全程在线、可中断、可看到每一步为什么这么判。

### 三条用户路径

| 路径 | 动作 | 系统行为 |
|---|---|---|
| **送审** | 从采集页选一批已确认相关的原始记录 → 送提取 | 建提取任务，先给**成本预估**待确认，再异步执行 |
| **看过程** | 打开任务详情 | 逐条显示走到第几步（类型闸门 / 相关性 / 字段 / 编码）、耗时、token |
| **看产出** | 打开某条结果 | 33 字段卡片 + 致因树 + 每条编码的证据与推断文本，可整条退回重跑 |

### 设计约束
单条全链路耗时 **40–50 秒**（实测：字段提取 16–19 s + 致因编码 21–30 s）。这不是可以塞进 HTTP 请求的量级——**必须异步任务 + 轮询**。旧实现 `POST /api/process`（`web/app.py:326-350`）同步调用，40 秒的请求在生产里必然超时，这是本蓝图最硬的技术约束。

## 二、现状诊断

### 2.1 四个处理步骤已存在，但编号冲突

链路组件全部齐备且质量不低，问题出在**命名**：

| 实际执行顺序 | 代码位置 | 该文件内的自称 | 产出 |
|---|---|---|---|
| ① 文本类型判断 | `collector/llm_classifier.py:335 classify_text_type()` | 该文件注释写 **"Step 0"**（`:332`） | 6 类文本类型 |
| ② 事故相关性判断 | `collector/llm_classifier.py:406 classify()` | 该文件注释写 **"Step 1"**（`:403`） | 是否施工事故 |
| ③ 基础字段提取 | `extraction/step1_basic_extractor.py` | 文件名即 **"step1"** | 33 字段 |
| ④ CAICS 致因编码 | `extraction/step2_caics_encoder.py` | 文件名即 **"step2"** | 19 类编码 |

**同一个"Step 1"指两件不同的事**：`llm_classifier` 里指相关性判断，`extraction/` 里指字段提取。日志、checkpoint 文件名、论文描述全部受此影响。

**统一编号（本蓝图确立，后续所有文档与代码一律遵循）**：

| 新编号 | 名称 | 实现 |
|---|---|---|
| **S1** | 类型闸门 | `llm_classifier.classify_text_type()` |
| **S2** | 相关性闸门 | `llm_classifier.classify()` → `classifier.classify_v2()` |
| **S3** | 字段提取 | `step1_basic_extractor.Step1BasicExtractor.extract()` |
| **S4** | 致因编码 | `step2_caics_encoder.Step2CaicsEncoder.encode()` |

### 2.2 S1 类型闸门：设计正确，直接沿用

`TextType`（`llm_classifier.py:43-58`）六值，**与用户说的「单个事故、多事故、通报」精确对应**：

| 用户说法 | 枚举值 | 处置 |
|---|---|---|
| 单个事故 | `SINGLE` | 进入 S3 |
| 多事故 | `MULTI` | LLM 拆分后逐条进入 S3 |
| 通报 / 政策 / 督察 | `REGULATORY` | 归档 |
| 统计 / 趋势综述 | `AGGREGATE` | 归档 |
| 培训教材 / 案例教学 | `TRAINING` | 归档 |
| 无法归类 | `OTHER` | 归档 |

两个设计细节值得保留：
- **不做规则预判**（`:338-339` 明写「每条文本均通过 LLM + Few-Shot Prompt 判断类型，不做规则预判」），理由注释为「避免 1.7% 误杀率」——这是实测得出的取舍，不要"优化"
- **LLM 调用失败判为 `OTHER` 而非 `SINGLE`**（`:346-353`，注释「避免噪音污染DB」）——失败时宁可丢弃不可污染，方向正确

主库 `accidents.text_type` 实测 `single` 2,622 + `multi` 1，说明该闸门在真实数据上几乎全放行 `single`——**符合预期**（采集源多为单事故通报），不是失效。

### 2.3 S2 相关性闸门：规则先判 + LLM 仲裁

`classify()`（`:406-443`）的顺序是：

```
非中文为主 / 正文过短 → INFO_INSUFFICIENT（直接返回，不调 LLM）
     ↓
规则判定 classify_v2(title, text)
     ↓
规则 high 且 is_construction → 直接通过，跳过 LLM（:430-440）
     ↓
否则 → LLM 仲裁 _call_llm_with_retry + _merge_results（:442-443）
```

规则词表在 `collector/classifier.py`：`SPECIFIC_CONSTRUCTION`(34) / `STRONG_CONSTRUCTION`(32) / `INDUSTRIAL_COMPANY_KW`(61) / `STRONG_EXCLUDE`(26) 四组。

### 2.4 `evidence_quality` 在 6 处重复计算

`evidence_quality`（三级证据）是 CAICS 体系的组成部分，但**不产生于编码器**——`CauseItem`（`step2_caics_encoder.py:176-188`）只有 4 个字段：

```python
@dataclass
class CauseItem:
    code: str = ""        # CAICS 码，如 "H1"
    name: str = ""        # 中文类名，如 "违反操作规程"
    evidence: str = ""    # 证据文本
    inference: str = ""   # 推断文本
```

`evidence_quality` 与 `sort_order` 是**入库时现算**的，且同一段字符串匹配逻辑被复制在 **6 个生产脚本**里：

```
scripts/batch_runner.py:79-81
scripts/run_batch.py:102-104
scripts/run_batch_pipeline.py:92-96
scripts/process_pdf.py:73-75
scripts/process_pdf3.py:55-57
scripts/process_ebook800.py:63-65
```

六份逻辑逐字相同：

```python
eq = "direct_quote"
if "推断" in c2.inference or "表明" in c2.inference: eq = "indirect_infer"
if "原文未直接" in c2.evidence or "原文未直接" in c2.inference: eq = "weak_infer"
```

（worktree 下同名副本已与主仓库**行号漂移**：`run_batch.py` 在主仓库是 `:102-104`，在 worktree 是 `:106-108`——六份副本已经开始分叉。）

**风险**：这是**靠关键词猜测 LLM 的措辞**。S4 的 prompt（`step2_caics_encoder.py:166-169`）恰恰示范了 `"原文未直接提及，但从…可推断"` 这种写法，于是 `weak_infer` 由「LLM 有没有写"原文未直接"这五个字」决定。实测分布 `direct_quote` 14,784 / `indirect_infer` 1,117 / `weak_infer` 422 中，前档占 90.6%——分层能力的实际效果受限。

> **处置原则**：本蓝图**不改变现算规则的行为**（论文数字基于它），只做两件事：
> ① 把六份复制品上收为**一个共享函数** `compute_evidence_quality(cause) -> str`，六处脚本改为 import——行为完全不变，重复消除；
> ② 让 S4 的输出**增加 `evidence_quality` 字段由 LLM 自报**，作为**对照列**存入暂存表（不覆盖现算值），供未来评估是否切换。切换与否是独立决策，不在本蓝图。

### 2.5 旧 web 的在线提取走的是旧链路

```python
# construction_agent/web/app.py:326-350
@app.route("/api/process", methods=["POST"])
def api_process():
    ...
    accident = pipeline.process(text)   # ← ExtractionPipeline，即 claude_extractor.py（HFACS 链路）
    ...
    db.add(accident)                    # ← DatasetManager → JSON 快照
```

`pipeline` 是模块级全局单例（`app.py:31`）。该端点：走旧理论、落 JSON、**同步阻塞**、无超时、无限流、无成本控制、有并发竞态。

**新 web 必须切到 S1→S2→S3→S4，落工作库。**

### 2.6 其他实测事实

| 项 | 事实 | 影响 |
|---|---|---|
| 单条耗时 | S3 16–19 s + S4 21–30 s ≈ **40–50 s** | 必须异步 |
| `response.usage` | `Step1Result` / `Step2Result` **均未保存** | token 计量需新写 |
| S3 tool schema | 30 属性 / 9 必填（`step1_basic_extractor.py:277-281`） | 落库字段以它为准 |
| 建表 SQL | 在 `scripts/create_db_v2.py`，**不在 `construction_agent/database/`** | 数据层由脚本管，ORM 不参与 |
| DeepSeek 输出预算 | 思考块吃 token，`max_tokens` 需 ≥16384 | 否则返回空文本（CLAUDE.md 已记） |

### 2.7 实测发现的缺口：`direct_cause` 无人产出

把最终库 48 列逐列溯源，**只有一列找不到出处**：

| 事实 | 证据 |
|---|---|
| 旧链路产 `direct_cause` | `claude_extractor.py:114` 的 tool schema 里有它 |
| S1–S4 **完全不产**它 | `step1_basic_extractor.py` 的 30 个字段里没有；`step2_caics_encoder.py` 也不产 |
| 而它是详情页 A 档必显字段 | 有值率 **99.89%**（2,620 / 2,623） |
| `search_enhancer.py:75` 已在读它 | `step1_result.get('direct_cause', '')` —— 因 S3 不产，**恒为空串**，静默失效 |

**算术验证**：48 列中，S3 覆盖 30 列、S1/S2 覆盖 3 列（`text_type` + `classification_*`）、
`raw_accidents` 提供 5 列（`id` / `source_url` / `source_name` / `crawl_date` / `publish_date`）、
常量与过程元数据 9 列、`raw_text` 1 列 —— 合计 **47**。差的那 1 列正是 `direct_cause`。

**处理方式**：在 P0-1（管线统一）中给 `step1_basic_extractor.py` 的 tool schema 补上
`direct_cause`，使其成为第 31 个 S3 字段。否则新管道并入的数据在这一列全部为 NULL，
新老数据不同构，详情页的「直接原因」段对新数据永远空白。

> 这一列也解释了为什么 `versions/`、`evaluation/` 不能简单删除——它们是产出既有
> 2,623 条数据的实际代码，是消融实验的对照物。生产链路切到 S1–S4 时，旧链路原地
> 保留并标注「已归档、勿用于生产」，而非移走。

## 三、目标架构

### 3.1 四段流水线与两道闸门

```
raw_accidents (gate_verdict='confirmed')
        │
        ▼
┌─ S1 类型闸门 ──────────────────────────┐
│  SINGLE ────────────────┐              │
│  MULTI ─→ LLM 拆分 ─────┤              │
│  REGULATORY/AGGREGATE/  │              │
│  TRAINING/OTHER ─→ 归档 │              │
└─────────────────────────┼──────────────┘
                          ▼
              ┌─ S2 相关性闸门 ─────────┐
              │  规则 high + 施工 → 通过 │
              │  否则 LLM 仲裁          │
              │  不相关 → 归档          │
              └────────────┬────────────┘
                           ▼
              ┌─ S3 字段提取（33 字段）─┐
              └────────────┬────────────┘
                           ▼
              ┌─ S4 致因编码（19 类）───┐
              └────────────┬────────────┘
                           ▼
                 staging_accidents + staging_causes
```

**两道闸门的分工**：S1 判「这段文本是什么体裁」，S2 判「这段文本讲的是不是建筑施工事故」。两者都通过才进入提取。用户说的「原始数据审核」在实现上是这两道自动闸门 + 阶段③的人工复核，共三层。

### 3.2 工作库新增表

```sql
-- ① 提取任务
CREATE TABLE extract_tasks (
    task_id        TEXT PRIMARY KEY,        -- uuid4 hex[:12]
    raw_ids        TEXT NOT NULL,           -- JSON 数组
    stages         TEXT NOT NULL,           -- JSON: ["S1","S2","S3","S4"]
    enable_split   INTEGER DEFAULT 1,       -- MULTI 是否拆分
    status         TEXT NOT NULL,           -- pending|running|done|failed|cancelled
    created_at     TEXT NOT NULL,
    started_at     TEXT, finished_at TEXT,
    concurrency    INTEGER DEFAULT 3,
    est_tokens     INTEGER,                 -- 建任务时的预估
    est_cost_cny   REAL,
    actual_tokens_in  INTEGER DEFAULT 0,    -- 来自 response.usage（现被丢弃）
    actual_tokens_out INTEGER DEFAULT 0,
    stats          TEXT,                    -- JSON: {s1:{...},s2:{...},s3:{...},s4:{...}}
    error          TEXT
);

-- ② 暂存事故（阶段③的临时数据库主表）
CREATE TABLE staging_accidents (
    stage_id       TEXT PRIMARY KEY,        -- uuid4 hex[:12]
    raw_id         TEXT REFERENCES raw_accidents(raw_id),
    task_id        TEXT REFERENCES extract_tasks(task_id),
    origin_segment TEXT,                    -- MULTI 拆分时的原文片段；single 为 NULL

    -- S1 产出
    text_type          TEXT,                -- single|multi|regulatory|aggregate|training|other
    text_type_reason   TEXT,
    text_type_confidence TEXT,
    split_index        INTEGER,             -- MULTI 拆分序号，从 1 起

    -- S2 产出
    relevance_verdict  TEXT,                -- construction | non_construction | insufficient
    relevance_reason   TEXT,
    relevance_stage    TEXT,                -- rule | llm
    relevance_confidence TEXT,

    -- S3 产出（31 字段；列名保留 S3 原样输出，改名集中在并入映射层）
    --   实测校准：step1_basic_extractor.py 的 tool schema 是 **30** 字段
    --   （CLAUDE.md 与本文早前写的「33」均不准）。这 30 个字段全部映射到
    --   accidents 列，其中 `location` 在并入时改名为 `province`。
    --   另补 `direct_cause` 一列——它是唯一一个现有 S3 覆盖不到的内容字段，
    --   详见第 2.7 节。
    title TEXT, date TEXT, accident_time TEXT, location TEXT, city TEXT, district TEXT,
    accident_location_detail TEXT,
    project_name TEXT, project_type TEXT, construction_phase TEXT,
    building_structure TEXT, accident_type TEXT, severity TEXT,
    deaths INTEGER, injuries INTEGER, trapped_count INTEGER,
    collapse_subtype TEXT, fall_height REAL,
    work_task TEXT, equipment_involved TEXT, material_involved TEXT, worker_type TEXT,
    weather TEXT, contractor TEXT, contractor_type TEXT,
    developer TEXT, supervision_company TEXT, direct_economic_loss REAL,
    direct_cause TEXT, summary TEXT, report_type TEXT,
    -- 不设 source / source_url：来源信息在 raw_accidents 中是唯一出处，
    -- 此处冗余存储只会引入不一致（并入映射本就从 raw_accidents 取）

    -- 过程元数据（可溯源）
    s3_model TEXT, s3_ms INTEGER, s3_tokens_in INTEGER, s3_tokens_out INTEGER,
    s4_model TEXT, s4_ms INTEGER, s4_tokens_in INTEGER, s4_tokens_out INTEGER,
    -- 不设 s4_primary_cause / s4_cause_chain：主库 accidents 表实测没有对应列，
    -- step1/step2 也不产出这两个值。建出来就是两列恒 NULL，并入映射时无处可取
    -- （详见蓝图 05 §三 的说明）

    -- 阶段③审核（本蓝图只建列，逻辑在蓝图 03）
    review_status   TEXT NOT NULL DEFAULT 'pending',  -- pending|approved|edited|rejected
    review_note     TEXT,
    reviewer        TEXT,
    reviewed_at     TEXT,

    created_at     TEXT NOT NULL,
    UNIQUE(raw_id, split_index)
);
CREATE INDEX idx_stage_review ON staging_accidents(review_status, created_at DESC);
CREATE INDEX idx_stage_task   ON staging_accidents(task_id);

-- ③ 暂存致因编码
CREATE TABLE staging_causes (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    stage_id     TEXT NOT NULL REFERENCES staging_accidents(stage_id) ON DELETE CASCADE,
    code         TEXT NOT NULL,             -- CAICS 码，如 "H1"
    name         TEXT NOT NULL,             -- 中文类名，来自 S4 输出
    evidence     TEXT,
    inference    TEXT,
    evidence_quality       TEXT,            -- 现算规则结果（与论文口径一致）
    evidence_quality_rule  TEXT,            -- 同上，显式记录来源
    evidence_quality_llm   TEXT,            -- S4 自报，对照列，可为 NULL
    sort_order   INTEGER
);
CREATE INDEX idx_scause_stage ON staging_causes(stage_id, sort_order);
```

> **`evidence_quality` 三列并存**：`evidence_quality` 是生效值（当前 = 现算规则），两个 `_rule` / `_llm` 列是审计留痕。这样切换判定方式时不丢历史，也不破坏与论文数字的对齐。

### 3.3 统一证据等级计算

新增 `construction_agent/extraction/evidence_quality.py`：

```python
def compute_evidence_quality(evidence: str, inference: str) -> str:
    """现算三级证据等级。

    行为与 scripts/ 下 6 处既有复制品完全一致，勿改判定顺序。
    """
    eq = "direct_quote"
    if "推断" in inference or "表明" in inference:
        eq = "indirect_infer"
    if "原文未直接" in evidence or "原文未直接" in inference:
        eq = "weak_infer"
    return eq
```

6 处脚本改为 `from construction_agent.extraction.evidence_quality import compute_evidence_quality`。**这是纯重构，输出逐字节不变**（可用既有数据回归验证）。

### 3.4 异步执行与成本控制

| 项 | 方案 |
|---|---|
| 执行模型 | 后台线程池，默认并发 3（与采集共用池，避免叠加过载），`max_concurrency` 可配 |
| 落库时机 | **每条完成即写 `staging_accidents`**，不等整批——任务中断时已完成的不丢失 |
| 断点续跑 | 任务重跑时跳过已有 `stage_id` 的 `raw_id`（`UNIQUE(raw_id, split_index)` 保证不重复） |
| 超时 | 单条 S3/S4 各 120 s；超时记错误并跳过该条，任务继续 |
| 重试 | 单条单步最多 3 次，指数退避（沿用 `llm_classifier` 既有重试风格） |
| 取消 | 协作式：每条开始前检查任务状态 |
| **成本预估** | 建任务时按 `条数 × (S1 0.5k + S2 1k + S3 8k + S4 16k)` 估算 token，返回给前端确认。**用户确认后才执行** |
| **用量记账** | 从 `response.usage.input_tokens / output_tokens` 取实际值，累计到 `extract_tasks.actual_*` 并写入每条的 `s3_tokens_*` / `s4_tokens_*` |

> 用量记账是**新增能力**——现有 `Step1Result` / `Step2Result` 丢弃了 `response.usage`，导致历史批次的实际 token 消耗无法回溯。新管道必须接上。

### 3.5 理论口径的单一出口

S3/S4 的 prompt 内硬编码了 CAICS 体系与枚举（如 `step1_basic_extractor.py:290-314` 的 work_task 决策规则、`:277-281` 的必填字段）。为避免 prompt 与数据库口径漂移，新增：

- `GET /api/extract/taxonomy` — 返回**当前生效**的 CAICS 19 类（从 `caics_causes` 的 `code`+`name` 反查，或从 `enum_definitions` 取）与 5 个 MECE 枚举的版本号（`pipeline_metadata` 登记的 `work_task 2.0-llm` 等）
- 页面在提取工作台上显示当前理论版本号，**让研究者一眼确认自己在用哪一版**

{ "ok": true, "data": {

### 5.2 交互逻辑

**成本确认是一道硬闸门**：第③步弹层显示预估金额，未点「确认执行」不产生任何 API 调用。这直接回应旧 `/api/process` 的缺陷——它没有任何限流或成本控制。

**进度轮询**：仅 `running` 时启动 2 s 递归 `setTimeout`；展示 `current` 字段让用户看到"正在跑第几条的哪一步"，而不是只有百分比。

**失败可见**：`errors` 数组在任务详情里列出每条失败原因（哪一步、什么错），可单条重跑。**失败不能静默**——旧管道多处 `except: continue`（如 `pipeline.py:246-248`）把失败埋在日志里。

**结果查看**：整条卡片式展示，致因树按 `sort_order` 排列，每条编码下并列「证据」与「推断」两段文本 + 证据等级徽章（三级三色，与展示页共用同一套配色）。

**空值兜底**：33 字段中大量可为空（`weather` 有值率 7.93%、`supervision_company` 10.22%、`fall_height` 14.22%）。渲染一律 `v ?? '—'`，**真 NULL 与空字符串**统一显示为「—」。注意两者是**不同的存储形态**：`IS NULL` 查不到空串（如 `publish_date` 有 907 条空串却零 NULL、`accident_type` 有 6 条空串却零 NULL），**过滤与统计时两个条件都要写**。口径定义见蓝图 00 第 3.5 节。

## 六、技术选型与理由

| 选择 | 理由 |
|---|---|
| **沿用 S1–S4 既有实现，不改 prompt** | 论文的消融实验与主库数据均基于当前 prompt。改 prompt 等于更换理论版本，属于独立决策 |
| **异步任务 + 逐条落库** | 40–50 s/条 × 128 条 = 1.5–1.8 h。逐条落库让中断不丢已完成部分 |
| **线程池而非队列服务** | LLM 调用是 IO 等待型，线程足够；不引入 Redis/Celery 依赖 |
| **`evidence_quality` 上收为共享函数** | 纯重构，行为不变，消除 6 处复制品（含已漂移的 worktree 副本） |
| **三列并存（生效/规则/LLM）** | 切换判定方式时不破坏与论文数字的对齐，且保留审计留痕 |
| **模型名统一写 "DeepSeek V4"** | 项目既定决策（CLAUDE.md），`auto` 档位路由，不写 Pro/Flash |
| **不缓存 LLM 响应** | 同一条文本重跑可能得到不同编码，缓存会掩盖这一点；改为保留历史版本 |

**必须遵守的环境约束**：`max_tokens ≥ 16384`（思考块吃预算，否则返回空文本）；解释器用 `/home/suntianhao/construction_agent/.venv/bin/python3`。

## 八、验收标准

1. 送 10 条 `raw_accidents`（`gate_verdict='confirmed'`）走完整 S1→S2→S3→S4，`staging_accidents` 恰好新增 ≤10 条（MULTI 拆分时按拆分段数）
2. 每条的 33 字段**列名与最终库 `accidents` 完全一致**，可直接 `INSERT INTO accidents SELECT ...` 并入（端到端对齐的核心判据）
3. `staging_causes` 的 `code` 全部落在 CAICS 19 类内（`M/F/T/H/C` 前缀，无未知码）
4. `evidence_quality` 三列：生效值与原 6 处脚本的输出**逐条一致**（回归验证）；`_llm` 列允许为 NULL
5. 任务运行中杀进程，重启后已完成条目的 `staging_accidents` **不丢不坏**；任务状态转 `failed`，可续跑且不重复（`UNIQUE(raw_id, split_index)`）
6. `REGULATORY` / `AGGREGATE` / `TRAINING` / `OTHER` 四类文本**不产生** `staging_accidents` 行，只在任务统计的 `by_type` 中计数
7. `MULTI` 文本按 `split_index` 拆成多条，`origin_segment` 记录原文片段，可回溯到拆分依据
8. 成本预估与实际用量偏差 < 30%；`actual_tokens_in/out` 与 `response.usage` 逐条对得上
9. 未点「确认执行」的任务不产生任何 LLM 调用（用 API 侧计数或日志验证）
10. 构造 S3 返回空文本（`max_tokens` 不足的已知失败模式）的用例，该条记为失败并在 `errors` 中可见，**任务继续**而非整批中止
11. `GET /api/extract/taxonomy` 返回的 19 类与 `caics_causes` 表中实际出现的 code+name 一一对应
