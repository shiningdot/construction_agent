## 一、功能目标与用户场景

### 目标
两件事：
1. **让事故现场图片可见**——详情页里图文对应，而不是只有一个崩溃的占位框
2. **让全站图表风格统一**——四份蓝图里出现了金字塔、条形图、热力图、折线、漏斗、徽章，需要有统一的规范与实现方式

### 两条用户路径

| 路径 | 动作 | 系统行为 |
|---|---|---|
| **看现场** | 打开事故详情页 | 图片画廊（缩略图网格）+ 灯箱放大 + VLM 分析结论 |
| **看趋势** | 打开致因分析页 / 概览页 | 统一的图表渲染（同一套配色、字号、刻度规则） |

### 设计约束
图片资产经过**三轮迭代**（`images/` → `imageV2/` → `imageV3/`），最终版是 `imageV3/`。数据库登记表 `image_files` 却把三版的路径**混在一起存**，且**没有指向最终版的完整映射**。本蓝图要解决的是「以最终版为唯一真源，重建登记」，而不是修补旧路径。

## 二、现状诊断

### 2.1 图片登记表与磁盘实际状态

**`image_files` 表（1,037 行，涉及 476 个事故，11 列）**：

| 一级目录 | 条数 | 说明 |
|---|---:|---|
| `imageV2/` | **550** | 中间版 |
| `images/` | **276** | 初版 |
| `imageV3/` | **211** | **最终版** |
| 合计 | **1,037** | |

全部记录的 `download_status` 都是 `'downloaded'`——**该字段不可信**：三条路径指向的目录内容并不一致，标注"已下载"不等于文件真的在那。

**磁盘实际状态**：

| 目录 | 目录数 | 文件数 | 说明 |
|---|---:|---:|---|
| `data/images/` | — | 263 | 初版 |
| `data/imageV2/` | — | 464 | 二版 |

| `data/clip_test/` | — | 317 | CLIP 阈值判读样本（非数据） |

### 2.2 「少注册 15 条」的确切含义

CLAUDE.md 记载的「imageV3 少注册 15 条」实测确认：

```
imageV3 实际文件数                    : 226
image_files 中指向 imageV3/ 的记录数  : 211
                                差值  : 15
```

**这 15 个文件存在于磁盘但不在登记表里**，因此永远不会被前端展示。这正是需要重建登记的直接理由。

### 2.3 目录与事故的对应关系（实测）

`imageV3/` 的目录名 = `accident_id`（12 位十六进制，与 `accidents.id` 格式一致），实测 **427 个目录全部能在 `accidents` 表中找到对应**——**目录命名规则是可靠的**。

| 关系 | 数量 |
|---|---:|
| `imageV3` 目录总数 | 427 |
| 其中**非空**目录 | **193** |
| 其中**空**目录 | **234** |
| `image_files` 涉及的事故数 | 476 |
| `imageV3` 与 `image_files` 两边都有 | 229 |
| **仅 `image_files` 有（无目录）** | **247** |
| **仅 `imageV3` 有目录** | **198** |
| `imageV3` 非空目录 ∩ `image_files` | **178** |

**读法**：三个数字说明现状不可修补——247 条登记找不到目录，198 个目录不在登记里，只有 178 个非空目录是两边都能对上的。**任何"按 local_path 直接取图"的展示方案都会大面积 404。**

### 2.4 VLM 分析结果

`image_analyses` 表 **282 行**，记录了多模态分析结论（阶段一场景观察 + 阶段二上下文融合）：

```sql
id, accident_id, local_path, source_url,
phase1_scene_type, phase1_objects, phase1_people, phase1_damage, phase1_weather,
phase1_raw_response,
phase2_consistency, phase2_confidence, phase2_new_info, phase2_raw_response,
vlm_model, duration_ms, created_at
```

- 建表 SQL 的 `vlm_model` 默认值是 `'qwen-vl-max'`（`create_db_v2.py:116`）
- **实测该列 282 行全部是 `glm-5v-turbo`**，没有一行取到过默认值——表里的数据是对的，只是 DDL 的默认值写旧了（待决项 C 已结案）
- `image_analyses` 与 `image_files` 通过 `local_path` 关联——**同样受 2.1 的路径混存问题影响**

重建后 `image_manifest` 里的 VLM 字段填充率（226 条）：

| 列 | 有值 | 说明 |
|---|---|---|
| `analyzed` | **204 / 226**（90.3%） | 其余 22 条在图库里但没有分析结论 |
| `vlm_model` | 204 / 226 | 全部 `glm-5v-turbo` |
| `phase1_scene_type` | **202 / 226** | 有 2 条 `analyzed=1` 但场景为空——是「分析过但没给出判定」，与「没分析过」不同 |
| `source_url` / `source_page_url` | **205 / 226**（90.7%） | 回填自旧登记，对不上的 21 条留空不猜 |
| `phase2_consistency` | **0 / 226** | 整列为空 |
| `phase2_confidence` | **0 / 226** | 整列为空 |
| `width` / `height` | **0 / 226** | 整列为空 |

> **`phase2_*` 与宽高四列整列为空，是本节最该记住的一条。** 展示层因此**不渲染**这四项：摆出来就是四行「—」，而页面上一行「—」既可能读成「模型没判」、也可能读成「这张图没分析过」，把两种不同的状态糊成一种。灯箱只展示 `phase1_scene_type` 与 `vlm_model`，`analyzed=1` 而场景为空时给「已做多模态分析，但未给出场景判定」。同理，画廊布局**不能用宽高**做占位（`width/height` 全空），改用 `aspect-ratio` + `object-fit: cover`。

### 2.5 跨事故重复图片（实测 23 组 / 70 条）

`sha1` 一列原本是为「同一文件被重复下载」准备的，重建时却查出一件更值得记的事：

```
跨事故重复的图片 : 23 组 / 70 条记录（占全部 226 条的 31.0%）
  其中覆盖 ≥3 个事故的 8 组 / 40 条
```

**读法**：70 条图片的内容（`sha1`）出现在**不止一个事故的目录**里。逐组看下来，覆盖 ≥3 个事故的那 8 组呈现同一个模式——同一张图配给 8～10 条事故，而那些事故**按地域聚成堆**（武汉一批、广州一批、沈阳一批），来源 URL 里带 `n.sinaimg.cn/default/`。

这是**图床返回的默认占位图**：原网页的配图已经 404，图床把请求重定向到一张通用图，采集端照单收下，于是同一张「默认图」被记到了几十条互不相干的事故名下。它**不是**现场照片。

只剩 2 个事故共用的那 15 组不定性——同一工程的分支事故、或转载媒体配同一张图，都是合理的，数据里也确实有这种情形。所以阈值取 **3**：

```python
# build_image_manifest.py
# 同一张图覆盖多少个事故目录，就判定为「疑似通用图」。取 3 而不是 2：
# 实测 23 组重复里 15 组只有 2 条，那可能真的是两条事故共用一张图（同一
# 工程的分支事故、转载配图）；而覆盖 ≥3 条的有 8 组，事故还按地域聚成一
# 堆，那种模式不可能是巧合。
SUSPECT_GENERIC_MIN = 3
```

**处置：打标，不隐藏。** 展示层给这些图一个「多事故共用」角标，灯箱里补一句说明。理由有两条——一是数据里就是这样，藏起来会让人以为每条事故都有独立的现场照片，那是**更严重**的误导；二是这 40 条（占图片总量 17.7%）本身就是「图片采集完整性」的证据，与 7.4% 的覆盖率一起构成了图片这条线的真实状态，是可以写进论文的观察。

## 三、路径对齐方案

### 3.1 原则：以文件系统为真源，重建登记

**不做**的事：
- ❌ 不修改最终库的 `image_files` 表（会污染论文数据，且改动无法验证）
- ❌ 不按 `local_path` 做字符串替换（三版混存，替换规则无法统一）
- ❌ 不删除 `images/` 与 `imageV2/`（属可清理项，需作者确认，见文件地图第十一节）

**做**的事：
- ✅ 扫描 `imageV3/` 生成**新的登记表**，放在**工作库**（`data/caiems_staging.db`）
- ✅ 从旧 `image_files` / `image_analyses` **尽力回填** `source_url` 与 VLM 结论（能对上就填，对不上留空）
- ✅ 最终库的 `image_files` 保持原样，作为历史审计留痕

### 3.2 新表：`image_manifest`（工作库）

```sql
CREATE TABLE image_manifest (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    accident_id  TEXT NOT NULL,              -- 目录名，= accidents.id
    rel_path     TEXT NOT NULL,              -- 相对 data/ 的路径，如 'imageV3/<acc_id>/5eb976418594.png'
    filename     TEXT NOT NULL,
    ext          TEXT NOT NULL,              -- jpg | png | webp
    bytes        INTEGER,
    sha1         TEXT,                       -- 内容哈希，用于识别跨目录重复
    -- 尽力回填（来自旧登记，可为 NULL）；width/height 实测回填到 0 条
    source_url   TEXT,
    source_page_url TEXT,
    width        INTEGER, height INTEGER,
    -- 尽力回填（来自 image_analyses）；phase2_* 实测回填到 0 条
    phase1_scene_type TEXT, phase2_consistency TEXT,
    phase2_confidence TEXT, vlm_model TEXT,
    analyzed     INTEGER DEFAULT 0,
    -- 溯源
    version      TEXT NOT NULL DEFAULT 'v3',
    manifest_at  TEXT NOT NULL,
    UNIQUE(rel_path)
);
CREATE INDEX idx_manifest_acc ON image_manifest(accident_id);
```

### 3.3 重建脚本 `scripts/build_image_manifest.py`

处理步骤：

1. **扫描** `data/imageV3/` 下全部文件（`226` 个），每个文件记录 `accident_id`（父目录名）、`filename`、`bytes`、`ext`
2. **校验** `accident_id` 是否存在于 `accidents` 表——实测 **427/427 全部存在**，不在表里的 0 个
3. **算内容哈希** `sha1`，识别同一张图出现在多个事故目录的情况（→ §2.5）
4. **回填 `source_url`**：用 `(accident_id, filename)` 去 `image_files` 匹配
5. **回填 VLM 结论**：同上，用 `local_path` 与 `image_analyses` 匹配
6. **生成报告**：文件数、目录数、空目录数、回填成功率、无法归属的事故 id、疑似通用图分组
7. **写工作库**

**实测输出**（`--data-dir` 指主仓库 `data/`）：

```
  图片文件 : 226
  扩展名   : [('jpg', 168), ('png', 55), ('webp', 3)]
  空目录   : 234
  归属校验 : 427 个事故目录（含 234 个空目录），不在 accidents 表的 0 个
  来源链接 : 205/226  (90.7%)
  VLM 结论 : 204/226  (90.3%)
  跨事故重复的图片 : 23 组 / 70 条记录（占全部 226 条的 31.0%）
    其中覆盖 ≥3 个事故的 8 组 / 40 条：疑似图床占位图
  已写入 226 行
```

**归属校验要连空目录一起算**：`records`（有文件的事故）∪ `empty_dirs`。只算前者会报出 193 个目录、把 234 个空目录当成「归属不明」——它们其实都是合法的事故目录，只是没配到图。这一条是补上之后才得到 427/427 的。

**空目录处理**：`imageV3/` 有 **234 个空目录**。扫描时忽略，但报告里列出来——它们代表"曾计划为这些事故配图但最终没有可用图片"，是有价值的过程信息。

**幂等靠「先删同版本、再整批插入」，不是 `INSERT OR REPLACE`**：

```python
# 磁盘是唯一真源。删掉一张图，表里那一行就必须跟着消失——
# INSERT OR REPLACE 只能覆盖同 rel_path 的行，删不掉已经不在磁盘上的。
con.execute("DELETE FROM image_manifest WHERE version = ?", (version,))
con.executemany(INSERT_SQL, rows)
```

删除与插入在同一个 `sdb.write_tx()` 事务里，中途失败不会留下半张表。版本维度带上是为了将来并存 `v4` 时能各自重建、互不牵连。复跑验证：行数仍是 226。

### 3.4 展示层用法

详情页请求 `/api/accidents/<id>` 时，服务端**从工作库**读：

```sql
SELECT rel_path, filename, ext, bytes, sha1, source_url, source_page_url,
       phase1_scene_type, vlm_model, analyzed
FROM image_manifest WHERE accident_id = ? ORDER BY filename
```

三种状态，页面上必须**分别可辨**：

| 状态 | 判据 | 页面表现 |
|---|---|---|
| 有图 | `images` 非空 | 画廊 + 灯箱 |
| 该事故无图 | `images` 空 且 `images_available=true` | 「该事故无现场图片」（427 个事故有目录，只有 193 个非空，"有目录无图"是常态） |
| 索引未重建 | `images` 空 且 `images_available=false` | 「图片索引未重建，需要先跑 `scripts/build_image_manifest.py`」 |

> 后两种都表现为「没图」，但成因完全不同：一个是数据事实，一个是环境没配好。合成一句「无现场图片」会让运维拿着数据问题去查数据。

图片文件由 Flask 的静态路由按 `rel_path` 提供，**必须校验路径在 `imageV3/` 之内**（防目录穿越）。

## 四、接口设计

### `GET /api/accidents/<id>/images`
既然详情接口已返回 `images` 数组（见蓝图 05），此端点供画廊单独刷新或分页使用。

```json
{ "ok": true, "data": {
  "accident_id":"b7d2d036d638",
  "count": 4,
  "available": true,
  "items": [
    { "rel_path":"imageV3/b7d2d036d638/28198fe84c04.jpg",
      "url":"/media/imageV3/b7d2d036d638/28198fe84c04.jpg",
      "filename":"28198fe84c04.jpg", "ext":"jpg", "bytes":28881,
      "sha1":"…", "shared": false,
      "analyzed": true,
      "phase1_scene_type":"高处坠落（或疑似高处坠落/坠物事故）…",
      "vlm_model":"glm-5v-turbo",
      "source_url":"https://img.caixin.com/…",
      "source_page_url":"…" } ] } }
```

- `shared`：该图的 `sha1` 被 ≥3 个事故共用（→ §2.5），**服务端算好下发**，前端不重复实现判据
- `phase1_scene_type` 已剥掉 VLM 返回里的 Markdown 强调标记（实测形如 `**坍塌 / 土方坍塌**`）；只剥标记，题注里的补充说明原样保留
- `available` 与详情接口同义（索引是否已重建）

### `GET /media/<path>`
图片静态服务。

- 白名单根目录：`data/imageV3/`（仅最终版）
- 两道关：`rel_path` 必须以 `imageV3/` 开头（挡绝对路径、`..`、其它版本目录）；`realpath` 之后必须仍落在 `imageV3/` 之内（挡符号链接）
- 不通过、或文件不存在，统一返回 **404**（不是 403——对外不必区分"没权限"与"没有这张图"）
- 缓存头：`Cache-Control: public, max-age=86400`（图片改了就是换文件；不用 `immutable`，留出同名替换的回源余地）
- **不提供 `images/` 与 `imageV2/`**，也不提供 `data/clip_test/`——前者不是最终版，展示旧版会让同一事故出现重复图片；后者是 CLIP 阈值判读样本，不是事故图片

### `GET /api/images/stats`
图片覆盖统计（供概览页）。

```json
{ "ok": true, "data": {
  "files": 226, "accidents_with_images": 193,
  "accidents_total": 2623, "coverage": 0.07358,
  "by_ext": [ {"ext":"jpg","count":168}, {"ext":"png","count":55}, {"ext":"webp","count":3} ],
  "analyzed": 204, "generated_at": "2026-09-30 23:38:27",
  "available": true } }
```

> 图片覆盖率仅 **7.4%**（193/2,623）。这个数字**必须显式呈现**——它是采集完整性的真实反映，不是缺陷。
>
> `coverage` 在服务端算好（内部查一次 `accidents` 行数），不是留 0 让前端补——同一张表两处算比值，迟早会有一处忘了改。

## 五、页面结构

### 5.1 详情页图片画廊

```
┌─ 现场图片                    4 张 · 4 张有多模态分析 ┐
│  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐        │
│  │ 缩略图  │ │ 缩略图  │ │ 缩略图  │ │ 缩略图  │      │
│  │ ▣已分析 │ │ ▣已分析 │ │ ▣已分析 │ │ 多事故共用│    │
│  └────────┘ └────────┘ └────────┘ └────────┘        │
│  点击图片查看大图与多模态分析结论。图片来自最终版目录   │
│  imageV3，早期版本（images/、imageV2/）不参与展示。    │
└─────────────────────────────────────────────────────┘
（点击缩略图 → 灯箱：大图 + 左右切换 + 来源链接 + VLM 结论）
```

**交互**：
- 缩略图按需加载（`loading="lazy"`）——226 个文件里有 4096×3072 的大图，画廊一屏放不下
- 网格自适应列数（`auto-fill` + `minmax(150px, 1fr)`），**不用宽高做占位**（`width/height` 整列为空，见 §2.4），改用 `aspect-ratio: 4/3` + `object-fit: cover`
- 灯箱支持键盘（`←`/`→`/`Esc`）与点击遮罩关闭；两端循环
- 点**大图本身不关闭**——用户正要在那里看来源链接，误关会很难受
- 灯箱为**单例**：一次建好，开关只切类名。每次点击重建 DOM 会让几百 KB 的图重新解码，也留不住键盘焦点
- 打开时锁 `body` 滚动
- VLM 分析结论**只在灯箱内展示**，不占画廊空间
- 角标：`已分析`；共享图另加 `多事故共用`（红底，hover 说明来由）——**打标不隐藏**（→ §2.5）
- 无图时：显示「该事故无现场图片」+ 覆盖率数字，**不留空白区**
- 索引未重建时：显示「图片索引未重建」+ 要跑的脚本名，**与"无图"分开**
- **不显示 `clip_test/` 的内容**（那是阈值判读样本，不是事故图片）

**灯箱宽度跟着图片走**：面板用 `width: fit-content`，图片是内容、说明文字用 `width: 0; min-width: 100%` 限制在图片宽度内换行（经典的最小宽度技巧）。实测——财新转载的配图只有 **145×97**，若面板固定 1000px，灯箱里就是「一张小邮票 + 两侧 400px 黑带」，看着像加载失败。`min-width: min(560px, 88vw)` 兜住下限，免得小图把说明文字挤成一列。小图（145×97）面板宽 560px，大图（4096×3072）面板宽 816px（受 `max-height: 68vh` 约束）。

### 必须重写
- **图片来源**：`image_files.local_path`（三版混存，大面积 404）→ `image_manifest`（扫描 `imageV3/` 重建）
- **图片路由**：旧 `app.py:1177` 导入即 `mkdir` 的副作用 → 显式静态路由 + 路径校验
- **无图时的表现**：旧版无图即空白/崩溃 → 显式占位文案，且区分「无图」与「索引未重建」
- **VLM 结论展示**：旧版未展示 `image_analyses` 内容 → 灯箱内结构化呈现，且**只呈现真有值的列**（`phase2_*` 与宽高整列为空，见 §2.4）
- **深色模式**：旧模板有两段重复 `.dark` 定义 → 统一为 CSS 变量
- **跨事故重复图**：旧版无从发现（没有内容哈希）→ 重建时算 `sha1`，打标不隐藏（§2.5）
