## 0. 为什么要重设计

在把策略维度补齐成「模型 × 策略」交叉矩阵时，发现实验二的三个策略不适合直接复用：

| 策略 | 实验二原版的问题 |
|---|---|
| **S3′** | 原版 = S0 + 一句 `Let's first make a plan`，与 S0 差异过薄（设计文档自记 F1 0.598、平均 3.2 编码、13/100 空输出）。它不是真正的 Plan-and-Solve，作为「模型自主规划」这一档的代表不成立。 |
| **S4′** | 原版是"一次长提示词 + 逐层关键词与推断规则"，缺结构。对标论文 HFACS-CoT 的价值在其**两阶段与约束**，原版没有体现。 |
| **S5′** | 原版是"5 层调用 + 汇总"，但层级提示词里**没有程序化逻辑**，与对标论文 HFACS-CoT+ 的核心差异（把文字指令下沉为代码控制流）没有对上。 |

重设计遵循一条总原则，来自实验二的旗舰发现：

> **对标论文用疑问式条件检查（"文本提到'无人监管'吗？"），你们自己的实验二已证明该形式会触发
> 「词汇门控效应」——模型把关键词当成必须跨过的门槛，而事故叙述极少用这些精确措辞，
> 导致 M1 召回掉到 0.141、21% 样本输出空编码。**
>
> 因此本轮重设计的口径是：**采用对标论文的结构（分阶段、逐步喂入、程序化逻辑、依赖与互斥约束），
> 但措辞一律用陈述式的两步判断（线索路径 / 推断路径），不复刻疑问式门槛。**

### 共享底座（三策略一致的输出口径）

- CAICS 分类体系全文注入（19 类，含操作定义与典型关键词）——六个策略都有，含 S0′
- 统一的 31 个基础特征字段规格 + `codes`（CAICS 编码），由 `prompt_build.build_output_block()` 提供
- `temperature=0`、`max_tokens=16384`、原文整段送入
- 输出要求：**只输出一个 JSON 对象**；末尾追加以免与"先写推理"冲突

## 1. S3′ 计划与求解（真 Plan-and-Solve）

### 1.1 设计理由

「模型自主规划」这一档的对照价值在于**拆解方式由谁决定**：

- S2′：人工给定固定因果链 M→F→T→H→C
- **S3′：模型自主决定从哪些角度拆解、按什么顺序检查**

原版只有一句口号，模型实际不会规划。重设计把它落成**强制的三步**：先写计划（且计划必须交代
拆解角度、顺序、每处要找什么证据），再按自己写的计划执行，最后输出 JSON。
并明确禁止套用固定模板——否则它会退化成 S2′。

### 1.2 完整正文

正文 = **S0 的正文**（CAICS 分类体系 + 空 codes 说明）＋ 下面这段：

```text
## 分析方式：先规划，再执行

这起事故的致因结构不由固定的层级顺序决定，而由你在通读文本之后自行判断。请严格按下面三步作答。

**第一步 · 制定计划。**
先通读事故文本，用两三句话概括：事故类型、涉事的作业环节与工艺、伤亡后果、以及你注意到的异常之处。
然后**自行决定**分析方案，写成一份明确的计划。计划中必须交代清楚三件事：
1. 你准备从哪几个方面拆解这起事故的致因（例如按因果链分层逐层排查、按责任主体划分、按事故演进的时间顺序推进，或其它你认为更贴合本案的角度）；
2. 这几个方面按什么顺序检查，以及为什么这个顺序适合本案；
3. 每一个方面上，你准备在文本里寻找什么样的证据。
分析角度与检查顺序必须由你根据本案特点自行决定，**不要套用任何固定的层级顺序模板**——不同的事故应当有不同的计划。计划写完之后不要再改动。

**第二步 · 按计划执行。**
严格按第一步写下的计划逐条推进。每推进一条，写明：
- 你查了什么；
- 文本中相应的表述是什么（若文本未提供，明确写"文本未提供"）；
- 据此得到哪些 CAICS 编码。
若执行过程中发现计划有遗漏，可以追加检查项，但要写明追加的理由。

**第三步 · 输出 JSON。**
计划与执行过程写完之后，在全文最后一行输出最终的 JSON。
```

**末尾追加（覆盖前面的"只输出 JSON"）**：

```text
注意：上面的「只输出 JSON」指的是最终答案有且只有一个 JSON 对象。你仍然必须先写出第一步的
计划与第二步的执行过程，然后把这个 JSON 放在全文的最后一行，其后不要再有任何文字。
除该 JSON 之外的行文中不要使用大括号。
```

> 「不要使用大括号」这句是**工程必要**：JSON 提取器取的是全文**最后一个 `{`** 起的配对对象，
> 行文中若出现大括号会破坏定位。

### 1.3 与原版的差异

| | 原版 | 重设计 |
|---|---|---|
| 规划指令 | 一句 `Let's first make a plan ... then solve it step by step` | 三步强制，计划须交代角度/顺序/证据类型 |
| 是否禁止固定顺序 | 未提 | 明确禁止 |
| 实测「JSON 前"行文长度」 | — | **1271 字符**（glm5.2）/ 1807（flash）/ 1075（hy3）/ 945（pro） |
| 对照：S0′/S1′/S2′ 同指标 | — | 0 / 0 / 0（S2′ flash 为 64） |

也就是说，重设计后 S3′ **确实产生了实质的计划与执行行文**，不再是口号。

## 2. S4′ CAICS-CoT（两阶段 + 推断授权）

### 2.1 设计理由

**保留实验二 S4 的轴 C（推断授权）不动**——即那 12 处「推断→……」允许脱离字面证据的规则，
以便与历史 S4 可比。**叠加**对标论文 HFACS-CoT 的结构要素：

1. **两阶段划分**：阶段一判直接致因（T→F→H），阶段二判系统背景与后果（M→C）
2. **顺序约束**：`1.1 → 1.2 → 1.3 → 2.1 → 2.2` 不得跳项、不得颠倒
3. **依赖约束**：由阶段一的结论决定哪些防线**必须检查**（坍塌涉混凝土/模板→F2；
   高处坠落→F1 与 F4；特种设备→F3；基坑/沟槽/隧道/边坡→F2）
4. **互斥约束**：⚠ 见第 4 节——这条**首次实现是错的**，已更正

对标论文的 HFACS-CoT 一次性喂入全部问题 + 文本指令（其附录 C）；本策略同样是单次调用，
但把它的疑问式问题串改写成陈述式的逐项判定。

### 2.2 完整正文

```text
你是建筑施工安全事故分析专家。使用 CAICS 框架分析这起事故。分析分两个阶段，按 触发条件→防线失效→人的行为→管理根基→后果放大 的因果方向推进。

**核心原则：** 对每一个编码，同时运用显性证据匹配与隐性领域推断两条路径——
- **线索路径**：文本中以任何同义表述出现了相关证据 → 该编码成立，记为 `explicit`
- **推断路径**：依据事故性质与建筑施工安全常识，该致因即使文本没有显式措辞也必然存在 → 该编码同样成立，记为 `inferred`

推断路径允许脱离字面证据。宁可多标不漏标。

## 阶段一：直接致因（触发条件 → 防线失效 → 人的行为）

### 1.1 触发条件 T —— 先判定事故的物理机制：是什么物质或环境条件直接引发了这起事故

- **T1 设备机具故障**：线索→设备故障/钢丝绳断裂/机械失灵/制动失效/升降机故障
- **T2 物料状态异常**：线索→堆载超限/荷载过大/材料缺陷/珍珠岩浸水/瓦斯积聚。**推断→坍塌事故而文本未给出明确触发物 → T2[inferred]**
- **T3 地质环境突变**：线索→涌水/边坡失稳/地基沉降/流沙/突泥。**推断→基坑、沟槽或隧道类事故 → T3[inferred]**
- **T4 气象水文触发**：线索→暴雨/大风/冰雪/雷电/连日降雨/高温/台风
- ⚠ 若上述线索在文本中均不成立，且本案不属于坍塌、基坑、沟槽、隧道类，则 T 层记为空，并写明"文本未提供触发机制"。

### 1.2 防线失效 F —— 事故意味着至少一道防线被突破；由 1.1 判定的机制与事故类型反推被突破的是哪一道

- **F1 临边洞口防护缺失**：线索→无防护/无护栏/临边未设防/洞口未盖/未设安全网。**推断→高处坠落事故 → F1[inferred]**
- **F2 支撑体系失稳**：线索→模板坍塌/脚手架失稳/支撑不足/支架倒塌/未按方案搭设/扣件松动。**推断→坍塌事故且涉及混凝土、模板或支撑 → F2[inferred]**
- **F3 设备安全装置失效**：线索→限位器被屏蔽/防坠器失效/安全装置损坏/力矩限制器缺失
- **F4 个体防护未使用**：线索→未系安全带/未戴安全帽/无防护用品/安全带未挂点。**推断→高处坠落或物体打击造成伤亡 → F4[inferred]**
- ⚠ **依赖约束（由 1.1 的结论决定，命中即必检，不得跳过）**：
  - 判定为坍塌、且涉及混凝土或模板支撑体系 → **必须检查 F2**
  - 判定为高处坠落 → **必须检查 F1 与 F4**
  - 涉及塔吊、施工升降机、物料提升机等特种设备 → **必须检查 F3**
  - 判定为基坑、沟槽或隧道类事故 → **必须检查 F2**

### 1.3 人的行为 H —— 判定直接导致事故的人为行为

- **H1 违反操作规程**：线索→未按方案放坡/违反操作规程/擅自变更施工方案/违规拆除/未按规范搭设。**推断→作业行为违背基本安全常识 → H1[inferred]**
- **H2 违规指挥决策**：线索→强令冒险作业/违章指挥/明知风险仍要求继续施工。**推断→多人同时作业且工期紧张 → H2[inferred]**
- **H3 风险辨识失败**：线索→未意识到危险/安全意识薄弱/未检查确认/疏忽大意/低估了风险。**推断→人员进入本应避开的危险区域 → H3[inferred]**
- **H4 应急行为失当**：线索→盲目施救/未及时撤离/救援方法错误导致伤亡扩大/二次坍塌时仍在施救
- ⚠ **H1 与 H3 不是互斥选项**：二者刻画同一行为的不同侧面——有没有违反规程（H1）、有没有低估风险（H3）。它们可以同时成立，也可以只成立其一。请**各自独立**依据线索与推断来判断，不要用其中一个的结论去否定另一个；也不要因为一个成立就默认另一个也成立。

## 阶段二：系统性背景与后果放大（管理根基 → 后果放大）

### 2.1 管理根基 M

- **M1 现场监管缺失**：线索→无人监管/监理失职/安全管理混乱/未及时发现制止/现场无安全员。**推断→发生死亡事故本身即说明现场监管缺失，即使文本未提也应输出 M1[inferred]**
- **M2 隐患排查失效**：线索→未排查/未整改/隐患长期存在/未进行风险评估/检查走过场。**推断→事故涉及的结构缺陷或设备问题此前未被发现 → M2[inferred]**
- **M3 安全培训不足**：线索→未经培训/安全交底不到位/交底走过场/三级教育不足。**推断→工人明显违章而文本未提培训 → M3[inferred]**
- **M4 制度规程漏洞**：线索→无安全方案/应急预案缺失/制度不健全/未编制专项方案
- **M5 市场行为违规**：线索→违法分包/转包/无资质/挂靠/抢工期/未办理报建
- ⚠ **依赖约束**：阶段一判出 H 层编码后，必须回头检查 M1–M5 中哪些构成了这些行为得以发生的条件。

### 2.2 后果放大 C

- **C1 救援响应迟缓**：线索→救援不及时/无预案/延误抢救/救援力量不足/救援设备缺乏。**推断→死亡≥3人且文本未提救援细节 → C1[inferred]**
- **C2 信息迟报瞒报**：线索→未及时上报/瞒报/迟报/漏报/未按规定报告

---

## 作答方式

必须严格按 **1.1 → 1.2 → 1.3 → 2.1 → 2.2** 的顺序逐项判定，不得跳项、不得颠倒。每一项都要写出：
1. 判定结论；
2. 依据（文本原文，或推断所依据的事故性质与安全常识）；
3. 由该项得到的编码，并标注 `explicit` 或 `inferred`。
某项判定为空时，写明"本项无编码"，不要略过。

最终 JSON 中的 `codes` 必须是去掉 `[explicit]`/`[inferred]` 标记的纯编码列表，如 `["M1","F2","H1"]`。
```

**末尾追加**：同 S3′（JSON 必须放最后一行、行文中不要用大括号）。

### 2.3 与原版的差异

| | 实验二原版 S4 | S4′ |
|---|---|---|

| 轴 C 推断授权 | 12 处 | **保留同样 12 处**（与历史 S4 可比） |

## 3. S5′ CAICS-CoT+（逐步独立调用 + 程序化逻辑 + 领域知识）

### 3.1 设计理由

对标论文 HFACS-CoT+ 相对 HFACS-CoT 的三处差异，逐条落地：

1. **逐步独立调用**：论文把每个问题连同它自己的定义、以及叙述**逐个、顺序**喂入
   （原文 "steps (questions) are fed into the LLM individually and sequentially"），
   而不是一次性全灌。我们照此把 5 个因果层各做一次独立调用，**前层结论注入后层**。
2. **程序化逻辑语句**：论文用 `if/elif/else` 取代提示词里的文字指令
   （"replaces textual instructions with structured programming logic statements"），
   以消除"指令说互斥、模型却同时判是"的逻辑不一致。我们的对应实现是
   `apply_programmatic_rules()`——**层级白名单、依赖必检、互斥裁定全部由代码裁定，不写在提示词里**。
3. **领域知识注入**：每层的判定要点里写入建筑施工安全的具体工艺与规范知识
   （模板支撑体系构造与浇筑超载、扣件式钢管脚手架连墙件与拧紧力矩、
   有限空间"先通风再检测后作业"与氧含量 19.5%–23.5%、临边栏杆 1.2m 与洞口 500mm 判据、
   防坠安全器年度标定、事故 1 小时上报时限、三级配电两级保护等）。

与论文的差异（有意为之）：论文用疑问式问题串，我们用陈述式判定要点，理由同第 0 节。

### 3.2 结构：5 层调用 + 1 次汇总 = 每条 6 次调用

层序按因果方向 **T → F → H → M → C**。每层调用：

```text
System: 你是建筑施工安全事故分析专家。<该层的 intro>

        <该层的领域知识要点>

        ## 本层编码定义
        <该层的编码 + 操作定义>

        <该层的判定要点（如 H 层强调 H1 与 H3 不互斥）>

        [前序层级已判定的结论]        ← 第 2 层起注入

        ## 输出
        只输出一个 JSON 对象：
        {"codes": [...], "mechanism": "一句话机制或结论", "reasoning": "判定依据"}
        `codes` 只能取自本层 <该层编码>；本层若无编码则输出空数组 []。

User:   事故文本：<原文>
```

第 6 次为**汇总调用**：给出全部 5 层的编码与理由，要求产出 31 个基础特征字段。
`codes` 由程序化规则裁定后**覆写**汇总调用的输出，保证可复现。

### 3.3 程序化逻辑（代码级，不在提示词里）

`apply_programmatic_rules()` 依次做三件事：

**① 层内白名单**：本层只接受本层编码，越界码一律丢弃。

**② 依赖必检**（`MECH_FORCE_RULES`）——由 T 层判定的物理机制反推必检防线：

| 机制关键词 | 强制补入 | 说明 |
|---|---|---|
| 坍塌 / 模板 / 混凝土 / 支撑 / 脚手架 / 支架 / 浇 | `F2` | 涉模板混凝土支撑 → F2 必检 |
| 坠落 / 高处 | `F1`, `F4` | 高处坠落 → F1 与 F4 必检 |
| 塔吊 / 塔式起重机 / 升降机 / 物料提升机 / 起重机 / 起重 / 吊装 | `F3` | 涉起重机械 → F3 必检 |
| 基坑 / 沟槽 / 隧道 / 边坡 | `F2` | 基坑沟槽隧道边坡类 → F2 必检 |

> 实测：300 条中 **229 条触发了强制规则**（F2 必检 171 次、F1 55 次、F4 47 次、F3 59 次），
> 说明程序化这一层确实在起作用，而不是摆设。

## 4. ⚠ 一处设计错误的发现与更正（必须记录）

**这是本轮最值得写进论文方法学讨论的一件事。**

### 4.1 错误的引入

对标论文 HFACS-CoT 有一条硬约束：**error（无意的差错）与 known deviation（故意的偏离）互斥**，
其附录 C 甚至把这条写成控制流（`if Q2 == no and Q3 == no: answer Q4; else: skip Q4`）。
我们把它搬成 CAICS 的对应物，写进了 **S4′ 与 S5′**：

> 「互斥约束：H1（违反操作规程）与 H3（风险辨识失败）性质互斥，同一个行为不能同时判为两者。」

### 4.2 症状

- **S4′×glm5.2** 跑满 300 条后 Ave+-F1 只有 **0.736**，全矩阵最低
- 逐类拆开：**H3 召回 0.19**（GT 201 条只命中 43）、H2 召回 0.44
- **S5′×glm5.2** 更差：**H3 召回 0.05**（GT 201 条只预测 11 条）

### 4.3 根因：与人工 GT 直接冲突

查 300 条人工 GT（`gt_manual/cause_gt.jsonl`）：

| 统计 | 数值 |
|---|---:|
| 含 H1 的事故 | 288 / 300（96.0%） |
| 含 H3 的事故 | 201 / 300（67.0%） |
| **H1 与 H3 同时出现** | **191 / 300（63.7%）** |
| H1+H3 在 GT 共现对中的排名 | **第 8 位** |

**这条约束逼模型在二者中二选一，与真值直接冲突。**

语义上的原因：HFACS 里"无意的差错"与"故意的偏离"确实是同一维度的两端，一个行为只能落在某一侧；
而 CAICS 的 H1（有没有违反规程）与 H3（有没有低估风险）是**两个不同侧面**，一个行为
完全可以既违反规程、又低估了风险——这正是施工事故中最常见的情形。

### 4.4 更正与验证

**S4′**（1 处）改为："H1 与 H3 **不是互斥选项**……请各自独立依据线索与推断来判断，
不要用其中一个的结论去否定另一个；也不要因为一个成立就默认另一个也成立。"

**S5′**（**3 处**，这也是 S5′ 崩得更彻底的原因，第 3 处模型无从绕过）：
1. `DOMAIN["H"]` 的领域知识文本："二者性质不同，不可同时成立" → 改为"不是互斥选项"
2. H 层层级提示词的 `extra`："性质互斥，同一个行为不能同时判为两者" → 改为"不是互斥选项"
3. **`apply_programmatic_rules()` 的 `MUTEX` 规则**（代码级强制删除 H3）→ **置空**

`MUTEX` 置空时写明：CAICS 的 19 类里**目前没有找到语义上真正互斥的编码对**；
S5′ 的程序化逻辑改由**依赖约束**（`MECH_FORCE_RULES`）承担，那部分实测是站得住的。

**完整 300 条上的 A/B（S4′×glm5.2）**：

| | Ave+-F1 | 宏召回 | 宏精确 | H3-F1 | H2-F1 | 编码/条 |
|---|---:|---:|---:|---:|---:|---:|
| 互斥版 | 0.736 | 0.829 | 0.773 | 0.32 | 0.59 | 8.17 |
| 更正版 | **0.766** | 0.897 | 0.740 | **0.81** | **0.80** | 9.51 |

### 4.5 方法学教训

> **从别的框架移植结构时，不能连约束一起照搬。移植的是结构，约束必须逐条按本地分类体系
> 与真值验证。** HFACS 的"差错/偏离互斥"成立是因为那两个类在语义上真互斥；
> 到了 CAICS 的"违规/风险辨识"就完全不是一回事。照搬的代价是召回崩塌（0.57 → 0.19 → 0.05）。

旧版提示词跑出的数据未丢弃，全部归档在 `strategies/_pilots/`（见第 6 节索引），可复核。

### 6.4 需要注意的取数口径

`results.jsonl` 是**追加写**的：重跑补齐会在同 id 后追加新行，**旧失败行仍留在文件里**，
所以**行数不等于条数**。正确取法是**按 `id` 去重、同 id 取最后一条成功行**
（`verify_matrix.py` 与 `eval_matrix.py` 都已按此实现）。
