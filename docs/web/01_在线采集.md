## 一、功能目标与用户场景

### 目标
让研究者**在浏览器里**完成从前只能敲命令做的事：选站点 → 起采集 → 看进度 → 逐条审阅原始文本 → 决定哪些进入提取管道。

### 三条用户路径

| 路径 | 动作 | 系统行为 |
|---|---|---|
| **起任务** | 勾选数据源 + 设时间范围 → 点「开始采集」 | 建任务记录，后台异步跑，页面轮询进度 |
| **看产出** | 进「原始数据」列表 | 分页浏览本次抓到的原文，看自动分类结论与理由 |
| **人工裁决** | 勾选若干条 → 标记「相关 / 不相关」 | 写回 `gate_verdict`，相关者进入阶段② |

### 设计约束
采集是**唯一会写工作库的阶段**，因此它必须满足三件事：可中断续跑（爬虫会断）、可溯源（每条原文留着 URL 与抓取时间）、可审计（谁在什么时候起了什么任务、抓到多少、留了多少）。旧实现的 22 个落盘目录、`_collect_tasks` 内存字典、`sessionStorage` 进度都做不到这三点。

### 2.2 为什么产出会消失：设计层面的三个不可维持点

**① 落盘路径散在 `DATA_DIR` 根目录**
每个适配器把 `settings.DATA_DIR / "<源名>"` 当自己的私有目录（`safehoo.py:178`、`sh_em.py:45`、`beijing_em.py:95`、`mohurd.py:73`、`open_gov.py:108`、`news_aggregator.py:90`…）。22 个源 = `data/` 根下 22 个目录，与 `datasets/`、`imageV3/`、`db_backups/` 混在一起，无法区分「程序产出」与「人工资产」。

**② 每个适配器自建缓存与状态机**
`grep '"review"' sources/*.py` 命中 **18 个文件**——审核状态机的写入被复制了 18 遍：

```python
# 出现在 tj_em.py:95、sh_em.py:94、js_em.py:94、sx_em.py:92、hub_em.py:72、
# sc_em.py:72、cq_em.py:72、jl_em.py:72、jx_em.py:72、gz_em.py:72、
# shaanxi_em.py:72、hain_em.py:72 …（代码逐字相同，系复制粘贴）
else: cls, cr, cf, st = "pending_review", r["reason"], "low", "review"
```

而 `RawAccidentStore` 类本身**没有任何方法把 `status` 写成 `review`**（`stores/__init__.py:219` 只读不写）。所以「待人工审核队列」在库层面是个空集合，在 18 个适配器里各有各的实现。

**③ 存储层有并发与原子性缺陷**
`RawAccidentStore._save()`（`stores/__init__.py:80-85`）：

```python
def _save(self):
    self.filepath.write_text(json.dumps(self._data, ...))   # 全量覆盖，无锁、无 tmp+rename、无 fsync
```

- `add()`（`:96-135`）只 append 到内存，**不落盘**；只有 `add_batch()`（`:165-167`）才 `_save()` → 单条采集的进程崩溃即丢数据
- 21 个采集器各持一份实例、各自 `_save()` 全量重写 → **后写的覆盖先写的**
- 状态机语义冲突：`classify()` 把确认通过的记录 `r["status"] = "new"`（`:244`）——「已确认」变回「未处理」，与「已处理」的语义直接矛盾

### 2.3 协议其实是统一的（本节实测修订）

**初稿写的「只有 4 个真正继承 `BaseCollector`，其余 21 个是鸭子类型、`collect()` 返回 dict」是错的。**用 AST + `importlib` 逐文件跑了一遍 24 个源（`sources/*.py` 去掉 `__init__` 与基类），实测：

| 实测项 | 结果 |
|---|---|
| 适配器数量 | **24 个**（蓝图初稿写 25，含了基类 `trs_cms_base.py`） |
| 全部 `import` 成功 | **24/24**，无缺依赖 |
| **直接**继承 `BaseCollector` | **12 个** |
| 经 `TrsCmsCollector` **间接**继承 | **12 个** |
| `collect()` 返回 `list[RawAccidentText]` | **24/24** |
| 调 `RawAccidentStore` 落盘 | **21 个**（9 个源直接调 + 12 个经 `TrsCmsCollector`） |
| 引用 `settings.DATA_DIR` | 22 个文件 |
| 源码里出现 `'review'` 字面量 | **6 个文件**（初稿写 18） |

`TrsCmsCollector(BaseCollector)`（`trs_cms_base.py:107`）是把 12 个省级应急管理厅源收拢成一个基类，子类只提供 `TrsSiteConfig`。所以：

- **24/24 都符合 `BaseCollector` 契约**，不存在"鸭子类型"那一类；
- `TrsCmsCollector.collect()` 的签名与返回类型完全合规（`trs_cms_base.py:148`），它**额外**做了两件事——每 5 条调一次 `self.raw_store.add_batch(...)` + `_save()`（`:253-267`），以及 `__init__` 里 `self.data_dir.mkdir(parents=True, exist_ok=True)`（`:127`）；
- 初稿的「21 个」数字对应的是**调 `RawAccidentStore` 的源数**，不是鸭子类型数——两件事被混成一件了；
- 初稿「18 个文件有 `'review'` 字面量」对应的真实情况是：**1 个基类（`trs_cms_base.py`，3 处）覆盖 12 个源**，另有 5 个源各写一遍。18 = 12 + 5 + 1，把"覆盖"数当成了"文件"数。

**这个修正的后果是实施变简单了，不是变复杂了**：既然 24/24 统一契约，§3.4 就不再需要 `LegacyAdapter` 的「字段名映射表」与「拦截各自内部落盘」那套兜底——只要在 `BaseCollector` 契约上包一层，再**统一掐掉 `RawAccidentStore` 这一条落盘通路**即可（见 §3.4）。

适配器的抓取逻辑本身仍然是有价值的资产——24 个站点各自的解析规则（分页、PDF 抽取、正则定位）是长期积累的，且 `RawAccidentText`（`base.py:13-114`）设计得很好：URL 哈希（`generate_url_hash`）、事故指纹（`generate_fingerprint`，基于「年月+城市+伤亡+类型」容忍多源报道）、标题哈希（`generate_title_hash`）三层去重键齐备。

**结论：保留抓取逻辑，重建存储、状态与调度。**

#### 2.5.3 第三次跑：两个源一条都抓不到（根因在解析之前），另修一处日期恒空

2.5.2 里 `js_em` 与 `sc_em` 都是 0.2–0.3s 就返回，当时归为「未细查」。
逐源拆开才发现两者都不是站点失效——**列表页 HTTP 200、体积正常、
`<a>` 也不少**，断点在拿到 HTML 之后、进入 DOM 之前。

**`js_em`：列表条目藏在一个 `<script type="text/xml">` 数据岛里。**

那个站的列表页形如：

```html
<div id="397082"><script type="text/xml"><datastore>
<recordset><record><![CDATA[
<li class="cf"><a title="…" href="/art/2026/4/22/art_81395_11761062.html">…</a><span>2026-04-22</span></li>
]]></record></recordset></script></div>
```

两道坎叠在一起，**缺一不可**：

1. `html.parser` 对 `<script>` 的内容**一律当文本**（script 是 CDATA 元素），
   里面的 `<a>` 不会成为标签节点；
2. 那条 `CDATA` 声明本身也不被识别，整段仍然是文本。

只拆其中一道没有用——实测先只剥 `CDATA` 声明，命中仍是 0，因为 `<a>` 还
关在 `<script>` 里。最后连 `<script type="text/xml">` 外壳一起剥掉，
`find_all("a")` 才看见那 45 条。修法是 `trs_cms_base.py` 新增
`_unwrap_data_islands()`，`_parse_list()` 一进来先过一遍；**只对真含这种数据岛
的页面动手**（正则匹配不上时原样返回），其余 11 个 TRS 源的结构不受影响。

修完 `_parse_list(_fetch(list_url))` 从 0 条变 45 条，初筛后 3 条，
实抓 1 条、正文 2,993 字。

**`sc_em`：`list_link_pattern` 抄的是另一种 CMS 的格式。**

原值 `r"/\d{6}/t\d{8}_\d+\.html"`，在本页一条都不匹配。实测该站详情页形如
`/scyjt/dcbg/2023/8/14/<32 位 hex>.shtml`。改正则后解析出 4 条，
**经 `is_construction_candidate` 初筛全部不通过**（水电站透水、道路交通、
食品厂中毒窒息），reason 一律是「无建筑关键词」。

这 4 条**确实都不是建筑事故**，所以 `sc_em` 的「0 条」是**正确结果**，不是缺陷。
改正则的价值不在多出这几条，而在于：它把「正则一行不匹配」这种**沉默失效**
换成了「条目进来了、被初筛判掉」这种**有日志的排除**——两者在健康检查里都
显示 0 条，但一个坏了、一个没坏。

> **顺带记一条差点下错的结论。** 看到 `js_em` 那 45 条里有 6 条标题含
> 「坍塌 / 坠落 / 工地」却没通过初筛，我一度判定「分类器过严、疑似误筛」。
> 直接打印 reason 才看到是 `非事故记录: 挂牌督办`——`classifier.py` 的
> `NON_ACCIDENT_PATTERNS` 把「挂牌督办」「管理办法」「培训班」这类**文件类
> 通知**明确排除，是刻意设计。**下「误筛」结论前必须先看 reason，不能只看
> 标题里的关键词**：标题像事故，未必是事故通报。

**顺带撞出来的第三处：列表页日期恒为空。**

`_parse_list` 从 URL 里抠日期用的是 `(\d{4})[/-](\d{2})[/-](\d{2})`，
`\d{2}` 要求月、日补零；而这两个站的 URL 写的是 `/art/2019/4/18/…`、
`/scyjt/dcbg/2023/8/14/…`——**一条都匹配不上**，`date` 恒为空串。
两个分支（有/无 `list_link_pattern`）的日期正则本来还不一样，两处都空。

这不是本轮要找的「0 条」类缺陷，是补数据岛测试时撞出来的：测试断言
`records[0]["date"] == "2019-04-18"`，实跑却是空串，而 URL 里明摆着
`2019/4/18`。**空串不报错，看起来就像「这个站列表页不写日期」——又一条
恒空的判据。**

修法：抽 `_date_from_url()` 统一两个分支，斜杠分段与连续八位都认，
抠出来的三组数做范围校验（`1234/56/78` 不返回）。真页面复核：
`js_em` **45/45**、`sc_em` **4/4** 都抠出了日期（修复前是 **0/49**）。

**第三次全量结果：16/24 有数据、0 出错、0 超时。** `js_em` 由空转有数据
（1 条 / 2,993 字）；`sc_em` 仍显示 0 条，但性质已从「未知」变成「已知且正确」。

**这几处缺陷现在有测试守着。** 新增 `tests/test_collector_parsing.py`
（28 条，**不发任何网络请求**）：数据岛四种写法、两个源的链接正则、
从 URL 抠日期的六种形状，外加两组静态契约——`RawAccidentText` 的关键字
必须在字段表里、`_extract_pdf_text` 的调用名必须在模块内绑得上。
后两组正是「真跑才炸、真跑又会被 `except Exception` 吞掉」的那类，
**静态查反而查得到**。它替代不了 `check_collector_health.py`（站点活没活、
选择器还匹不匹配，只能真发请求），两者管的不是同一件事。

#### 2.5.4 第四次跑：四个「能列条目、正文 0 字」的源全部恢复

第三轮把「空源」分成了两类，并判定**先修第二类**（第一类至少诚实报 0，
第二类报的是「有数据」）。那个分类和尚未修复的清单都在 2.5.5——它写的是
**第三轮的判断**，只是位置排在后面。这一轮做的就是第二类。

**根因是一处 URL 拼接，一路长成了四种不同的假象。**

`_parse_list` 把列表页里的链接拼成绝对地址时写的是

```python
base_url.rstrip("/") + "/" + href.lstrip("/")
```

而 TRS 的链接写作**相对当前目录**的 `./202609/t20260918_16096386.html`。
`lstrip("/")` **不去掉开头的 `./`**，拼出来是 `https://yjj.cq.gov.cn/./202609/…`
——服务器对 `/./` 一律返回 404。实测三种拼法（`cq_em` 第一条）：

| 拼法 | 结果 |
|---|---|
| 旧拼法（含 `/./`） | **404** |
| `urljoin(列表页, href)` | **200，49,969 字符** |
| `base_url` + href 去掉 `./` | **404** |

第三行说明它也**不是相对于站点根**：`./202609/…` 相对的是列表页所在目录
`/zwgk_230/…/dcbg/`，所以**只能拿列表页自己的 URL 去 join**。改用
`urljoin` 后顺带还修好了三种旧拼法处理不了的写法：`../x`、`//host/x`
（会被 `lstrip("/")` 啃掉两个斜杠）、已是绝对 URL 的 href。

于是这四个源呈现出本项目里**最容易被放过的一种样子**：列表页正常、条目正常
解析出十几条、每条都有标题、健康检查里全部显示「有数据」——只有正文是空的。

**第二现场：同一个 bug 也吃掉了 PDF 附件。** `_crawl_detail` 拼 PDF 链接用的是
同一段逻辑，而附件同样写作 `./P020240905567173081196.pdf`，拼出来是
`https://yjt.shanxi.gov.cn/P020240905567173081196.pdf`——**整条路径都丢了**。
这一处更要命，因为**省级源的正文常常只存在于附件里**：`sx_em` 的详情页 HTML
里一个字正文都没有，只剩导航和页脚。

**而那个页脚里写着「国家矿山安全监察局」。** PDF 取不到时，`body.get_text()`
剩下的 715 字就是这堆机构链接，`classify_v2` 从中读到「矿山」这个强排除词，
**高置信度判成「非建筑施工事故」并静默排除**。一处 URL 拼接错误，一级级传导
下来，最后长成的是「这个源没有建筑事故」——**而它每一步单看都正常。**

修复后同一页 15 条走完整流程的结果：初筛排除 7、收录 2、审核 3、排除 3、
**无正文 0 条**（修复前「无正文」是全部 15 条）。

**第四次全量：16/24 有数据——数字与第三次一模一样。**

但内容完全不同：

#### 2.5.6 第五次跑：两个带分页的源，一直只抓了第一页

24 个源里只有两个配了分页（`sh_em`、`shaanxi_em`），**两个都从头到尾只抓了第一页**。
这里是四层截断叠在一起，每一层单独看都正常，合起来的结果是「这个站只有一页」。

| 层 | 位置 | 表现 |
|---|---|---|
| ① | `_build_page_url` | 返回**裸文件名** `index_2.html`——没有协议头的相对路径 |
| ② | `_discover_pages` | 用 HEAD 判存在性，而 `shaanxi_em` **整站拒 HEAD**（403），GET 才 200 |
| ③ | `sh_em` / `shaanxi_em` 配置 | `list_page_start=2` → 第 2 页**从未被探过** |
| ④ | 同上 | `list_page_max_probe=20` 把 `shaanxi_em` 的 21–24 页截掉 |

**第①层是一处分支顺序事故**。原写法：

```python
if "{n}" in pattern:
    return pattern.format(n=page_num)     # ← `index_{n}.html` 命中这里
if "index_" in pattern:                    # ← 这个分支从没执行过
    return f"{list_url.rstrip('/')}/{pattern.format(n=page_num)}"
```

`index_{n}.html` **同时**含 `{n}` 和 `index_`，而第一个分支在前面，于是返回的是
`pattern.format(n=2)` 本身——一个裸字符串。`httpx` 对没有协议的 URL 抛
`UnsupportedProtocol`，落进 `_discover_pages` 的 `except Exception: break`，
**静默地只剩第一页**；返回「1 页」与「这个站确实只有一页」表现完全一致。
改成 `urljoin(self.cfg.list_url, pattern.format(n=page_num))` 后，`list_url`
是**目录**（`…/sgdcbg/`）还是**文件**（`…/sgdc/index_1.html`）都能拼对——
而字符串拼接只对前者成立。

**第②层是又一条「恒真的判据」**。修完①立刻看到：`shaanxi_em` 第 2、3、4 页
HEAD **全部 403**，GET **全部 200**，每页 38,000 字符内容完整。这个站只是
不响应 HEAD 请求。拿 HEAD 的状态码判「还有没有下一页」，它的结论是
「只有一页」——**403 被读成了「页面不存在」，但 403 只说明「不给你 HEAD」**。
改成 GET 探测（GET 200 继续、非 200 停止），并把探测到的正文存进
`_page_cache` 供 `_fetch` 复用，列表页不会因为探测而请求两遍。

**第③层是配置字段的语义**。`list_page_start` 的定义是「`list_url` 对应的页码」
（默认 1），`_discover_pages` 从 `start + 1` 起探。两个源都写了 2，
于是**第 2 页从来没被探过**。这两行配置此前无从证伪：分页整个没跑起来，
写几都一样。

**第④层只有实测才能发现**：修完前三层，`shaanxi_em` 探到第 20 页仍然全 200，
而 `max_probe` 就是 20。往后探——第 21、22、23、24 页全 200，第 25 页才 404。
**真实末页在第 24 页**，`max_probe=20` 截掉约 80 条。该值只是保险上限
（非 200 即停、能自然收敛），放宽到 30。

实测结果（列表条目数，`sh_em` 第 8 页 404、`shaanxi_em` 第 25 页 404）：

| 源 | 修复前 | 修复后 | 倍率 |
|---|---|---|---|
| `shaanxi_em` | 1 页 / 20 条 | **24 页 / 472 条** | 23.6× |
| `sh_em` | 1 页 / 15 条 | **7 页 / 94 条** | 6.3× |

> **为什么四轮健康检查都没报出来。** 这两个源在第四轮的成绩是
> `shaanxi_em 1/17232`、`sh_em 3/4898`——正文中位是全 24 源里最高的两个，
> 「有数据」判绿，正文质量没问题。它们唯一不对的是**条数少**，
> 而「这个站建站晚、事故通报本来就少」是一个完全合理的解释。
> 这与 2.5.4 那类（条数正常、正文为空）正好相反，也是同一族：
> **判据里少一维，缺失的那一维就不会报警**——2.5.4 缺的是「正文中位」，
> 这一轮缺的是「列表条目数 vs 详情页实际条数」的对照。
> 健康检查默认 `--limit 3` 加早停，本就看不见列表总长；
> 分页是否生效要用 `_total_listed` 核，已记入第十节待办。

测试新增第六组 5 条（`tests/test_collector_parsing.py`）：分页 URL 必须带协议、
文件型与目录型 `list_url` 都拼得对、**扫全部源文件**的分页绝对地址校验、
`_discover_pages` 不许出现 `.head(`、探测过的列表页不再重复请求。

#### 2.5.7 第六次跑：「单页」是一句没查过的注释

第五轮给健康检查加了「列表条目数」一栏，加完**当场**就报出来：`cq_em` 的列表
恰好 **15 条**——而 `sh_em` 每页正是 15 条。`cq_em` 的配置里写着 `list_page_pattern=""`
加一句注释「无分页」。**那句注释是断言，不是结论。**

顺着这一栏查下去，**又有 6 个源在丢整页数据**，而且它们连分页字段都没配过：

| 源 | 修复前 | 修复后 | 分页形态 |
|---|---|---|---|
| `cq_em` | 15 | **42** | 零基，`index_{n}.html`，3 页 |
| `gz_em` | 15 | **33** | 零基，3 页 |
| `hain_em` | 19 | **37** | 零基，2 页 |
| `henan_em` | 16 | **193** | 零基，13 页 |
| `sx_em` | 15 | **29** | 零基，**`.shtml` 后缀**，2 页 |
| `tj_em` | 8 | **15** | 零基，2 页 |
| _（第五轮）_ `sh_em` | 15 | 94 | 一基，7 页 |
| _（第五轮）_ `shaanxi_em` | 20 | 472 | 一基，24 页 |

**八个数加起来 123 → 915，7.4 倍。** 而本轮开始之前，健康检查对全部八个源
报的都是「有数据」。

##### 两套页码约定，别把其中一套当成普遍规律

| 站点 | 第 1 页 | 第 2 页 | `list_page_start` |
|---|---|---|---|
| `sh_em` `shaanxi_em` | `index_1.html` | `index_2.html` | 1 |
| `cq_em` `gz_em` `hain_em` `sx_em` `tj_em` `henan_em` | `list_url` 那个目录本身 | `index_1.html` | 0 |

零基站的第 1 页就是目录，编号从 0 起而 0 号没有独立文件，所以「第 2 页」写作
`index_1.html`。`henan_em` 的 `_discover_pages` 原先从 `index_2.html` 起探，
**`index_1.html` 从未被访问过**——而它正是第 2 页；同时又用了 HEAD（见下）。
两处叠加，这个源一直只抓 16 条，实际 193 条。

`sx_em` 还要再拐一道：**后缀是 `.shtml` 不是 `.html`**。页面脚本里写着
`"index"+"_"+(countPage-1)+"."+"shtml"`。我最初试 `index_1.html` / `index_2.html`
全是 404，差一点就得出「确实只有一页」——**404 只说明我猜错了文件名**。

##### 核查方法：三种证据，从弱到强

| 证据 | 强度 | 实例 |
|---|---|---|
| 页面上有「下一页」三个字 | **最弱，可能是模板固定文案** | 一开始就是这么扫的，四个源「命中」，但 `cq_em` 的控件 href 是 JS 拼的 `' + prePage + '`，一个字面 URL 都没有 |
| 分页控件的 **href** 或**脚本参数** | 强 | `gz_em` 的「下一页」href 直接是 `index_1.html`；`hain_em` 写着 `createPageHTML(38, 2, 0, "index", "html")`——总数 38、**共 2 页**、当前索引 0、文件名 `index` |
| **日期接缝** | 最强 | 列表按时间倒序，真第 2 页应紧接第 1 页最旧的那条。`cq_em`：第 1 页最旧 2025-08-07 → `index_1.html` 最新 2025-08-05，**隔两天接上**；`tj_em`：2021-12-24 → 2021-12-17；`hain_em`：2021-04-20 → 2020-09-03 |

##### 一条恒真的判据：`?page=2`

查的过程中试过 `?page=2` 这个候选，**7 个源全部返回 HTTP 200 且「条数正常」**。
差点当成「有分页但参数不对」。实际做的是**比对两页的条目 URL 集合**：

> `?page=2` 的链接集合与第 1 页**逐个相同**——服务器把查询参数整个忽略了，
> 返回的就是第一页。

条数一样不足以说明是同一页（不同页恰好条数相同很常见），但**集合逐个相同**只能
是同一个响应。这条判据的教训与 `16/24` 同源：**一个对所有输入都返回相同答案的
判据，不含任何信息**。

##### 判据的覆盖范围本身也要查

健康检查的「列表」一栏读的是 `_total_listed`——那是 TRS 基类的属性名。
六个独立实现的源各写各的（`henan_em` 用 `_total_list`、`beijing_em` 用
`_total_records`），于是**它们的「列表」栏一直是 `—`**。而 `—` 与「这个源没有
列表」看起来一样，判据对它们静默失灵。改成按优先级依次尝试三个属性名
（`_total_listed` → `_total_list` → `_total_records`）后，六个源全部读出：
`beijing_em` 84、`gd_em` 53、`hebei_em` 110、`henan_em` 193、`ln_em` 20、`nmg_em` 8。

**加一栏判据之后，还要问一句「这栏对哪些源是空的，为什么空」。**

#### 2.5.8 第七次跑：四个「待查」逐一有答案，其中一个源根本跑不起来

第六轮末尾留了四个源「待查」。查完的结果是：**三个不用改，一个改完才第一次跑通**。

| 源 | 列表条目数 | 结论 | 依据 |
|---|---|---|---|
| `ln_em` | 20 | 确为单页，不改 | 页面自证「共 1 页」；分页模板 `f88f5849-%1.shtml`，实测 `-1` 与 `index.shtml` 逐条相同、`-3` 起 404 |

| `hebei_em` | 110 | 确为正常，不改 | 中途误判过一次，原委见下——**问题出在测法，不在这个源** |

##### `ln_em`：`-2.shtml` 是一条岔路，不是第 2 页

页面自己渲染出 `当前1页 | 共1页`，且脚本参数写着
`jumpToPage(event,this,'1','1','/yjgl/…/f88f5849-%1.shtml')`——两个来源一致。
上一轮的教训是「页面上有『下一页』三个字最弱」，但**这里两个独立来源互相印证**，
性质不同。

顺着模板往下探，出现岔路：`f88f5849-2.shtml` 返回 **200、39,304 字符**，
而页面声称只有一页。三个特征把它和「第 2 页」区分开：

1. **日期不接缝而是落在区间内**：它那 3 条是 2020-08-07、2021-08-30、2021-12-21，
   而第 1 页覆盖 2026-07-10 ～ 2012-12-05——真正的第 2 页应当**全部早于**末条；
2. **条目两两不相交**（`P1∩P2 = 0`）：说明确实是别的内容，不是重复渲染；
3. **标题不是事故报告**：「…评估暂行办法」「…公告（2021年第15号）」
   「较大生产安全事故查处挂牌督办通知书〔2021〕7号」——是规范性文件，不是调查报告。

判定：它是该栏目下的**旁支/残留页**，且那 3 条都不是本项目要采的对象。
`ln_em` 维持单页 20 条。

> 副产品：`-1.shtml` 与 `index.shtml` **逐条相同**，说明这套编号是一基的；
> `-3` 起 404。**一基站的编号与目录本身不是同一个东西**——`cq_em` 那一批是零基，
> 目录就是第 1 页。两套约定在同一批源里并存。

##### `beijing_em`：JS 分页不是分页，是显示分屏

这个源页面里**没有任何可 GET 的翻页 URL**——分页完全由客户端脚本完成：

```js
var pagecount = 15;
var totalpage = Math.ceil(i / pagecount);
… <a onclick="javascript:showNews_38622(0)">首页</a>
… <a onclick="javascript:showNews_38622((totalpage-1)*pagecount)">尾页</a>
```

`i` 是**内联数组的长度**。四组数组各赋值多少次：

```
urls[…]=  84 次      headers[…]= 84 次
xkxm[…]=  84 次      xkrq[…]=    84 次
```

四组同为 84，与采集器解出的 84 条一致。**数据全量内联在这一次响应里**，
`showNews_N(offset)` 只决定把数组的哪一段渲染出来，翻页不产生任何新请求。

探它的 `?page=2` 会得到与第 1 页**逐字节相同**的响应（37,924 字符）——恒真
判据的又一例，与上一轮的 7 个源同源。

##### `gd_em`：控件自己写了「最后一页」

`<div class="pages">` 的末位是
`<a class="last" href="…/sgdcbg/index_3.html">最后一页</a>`——站点自证 3 页。
另两条独立证据同向：

- **集合两两互斥**：`|P1−P2| = 20`、`|P2−P3| = 13`，交集均为 0；
- **日期首尾相接**：P1 最旧 2022-10-24 ← P2 最新 2022-09-30；
  P2 最旧 2021-04-17 ← P3 最新 2021-04-14。

三条证据一致，53 条为全量。

> 顺带一处陷阱：它的 `index_4.html` 返回的不是 404，而是
> **`RemoteProtocolError`（服务器直接重置连接）**。这意味着
> **「用状态码判断有没有下一页」在这类站点上失效**——404 判不了，
> 200 也判不了（`hain_em` 会给空模板）。能用的只有「这一页解析出几条」。

##### `hebei_em`：一个我自己造出来的「bug」

这一节记的是一次**查错方向**的过程，结论与前面三个源都不同：**这个源没有问题，
是我的测法有问题。**

事情的经过是这样的。分页查到这里，顺手想看看它的列表接口长什么样，于是直接调：

```python
c = HebeiEMCollector()
c._fetch_all_pages()        # ← 绕过 collect()，直接调内部方法
```

得到 `UnicodeDecodeError: 'utf-8' codec can't decode byte 0xb7 in position 388`。
顺着一看，响应体确实是坏的：

```
列表接口返回：b'??????4\xb713?????????'
详情页标题  ：'秦皇岛卢龙“4·13”事故整改评估报告'
```

**字符数一一对应**（6 个 `?` ↔「秦皇岛卢龙“」，`4·13` 原样，9 个 `?` ↔
「”事故整改评估报告」）。看起来是汉字在服务端被逐字替换成了 `?`。

于是判定「这个源从来没跑通过」，动了代码：加了个 `_json_body()` 用 latin-1
兜底解码，又把 `collect()` 改成「先抓详情、再用详情标题初筛」——因为拿那份
`??????` 去做关键词初筛，通过数是 **0 / 110**。

**但健康检查一直显示它有数据。**

当时的处理是把它记成「矛盾」——「列表栏显示 110，实际却崩，说明这栏不可靠」。
这个判断是错的。真相是：**健康检查走的是 `collect()`，它一直是对的；**
**我直接调 `_fetch_all_pages()`，绕过了 `collect()` 开头那句**

```python
self._session.get(HBEM_LIST_PAGE)      # 拿 JSESSIONID
```

**这个接口对匿名请求返回的是另一份东西。** 同一时刻，两条路径：

| 请求方式 | content-type | 响应体 | 首条标题 |
|---|---|---|---|
| 带 `JSESSIONID`（`collect()` 的路径） | `application/json;charset=UTF-8` | 6,499 字节 | `'秦皇岛卢龙“4·13”事故整改评估报告'` |
| 不带 cookie（我直接调的那条） | `text/plain;charset=ISO-8859-1` | 5,460 字节 | `'??????4·13?????????'` |

连打 6 次裸请求，6 次都是 5,460 字节 / `0xb7`；旧代码的 `collect()` 连打 2 次，
2 次都成功、`total_records=110`。**cookie 决定服务器返回哪一份**，不是随机，
也不是时间相关。

**教训不在于这个源，在于「怎么测」。** `_fetch_all_pages()` 依赖一个由调用方
建立的前置状态（cookie），我却把它当成了可以独立调用的纯函数。测出来的东西
在真实路径里并不存在，而据此改的生产代码——「先抓详情再初筛」——把开销从
18 次详情请求抬高到 110 次，**换来的是修一个不存在的 bug**。

更值得记的是当时那个「矛盾」信号：**健康检查说没事，我的手动测试说有事。**
两者不一致时，我默认了手动测试是对的。而这一整轮的核查反复验证过同一件事——
判据要在真实路径上取值。健康检查走的就是真实路径。

**最后留下的改动只有一处**，而且是朝着「更容易发现」的方向：

```python
def _decode_json(resp) -> dict:
    ...  # UTF-8 解不出来时，抛一句说明「这通常意味着 cookie 预热失败」的错误
```

原来 `resp.json()` 在这里抛的是 `codec can't decode byte 0xb7 in position 388`，
指不到「cookie 没了」。**没有做静默降级**（用 latin-1 硬解能出 JSON，但拿到的
是那份汉字全是 `?` 的降级响应，接着初筛把 110 条全判为无关——与「这个栏目本来
就没有建筑事故」长得一模一样，是比崩溃更难查的失败）。宁可当场抛一句说清原因
的错误。

> 模块文档里原本写着「110 条记录, 8 页, **96 篇事故调查报告 + 14 篇挂牌督办**」。
> `count=110` 与接口自报一致；但「96 + 14」这两个数没有核算过，已删去。

##### 四个「不用改」也是结论

这轮四个源没有一个需要动生产逻辑：**「不改」如果是查过之后下的判断，和「没查」
是两回事**。第六轮之所以把它们列成待查，正是因为光看代码读不出结论——
`beijing_em` 的 `start_page` setter 写着 `pass # 单页无分页`，`ln_em` 的注释
写着「单页 20 条记录」，这些注释和它们声称的事实之间，此前没有任何一次核对。

`hebei_em` 也归入这一类，但过程不同：它被误判过一次，改动随后全部回滚。留下的
唯一改动是让失败信息指得到原因。**代价是一次真实的教训——「健康检查说没事、
我的手动测试说有事」时，先怀疑测法，而不是先改生产代码。**

##### 本轮补的测试

两条：

1. `test_列表接口的编码错误要翻译成能定位的话`——先断言 `resp.json()` 在匿名
   路径上确实抛 `UnicodeDecodeError`（钉住前提），再断言 `_decode_json()` 抛的
   是带「cookie」字样的 `RuntimeError`；
2. `test_河北源不许再用resp_json`——AST 扫描，防「顺手改回标准写法」。

### 2.5.9 第八轮：给「没进库的那些去哪了」补一栏（2026-10-01）

由头是待决项 B′ 的「还剩一步」。第六轮加的「列表」栏回答得了「这个源一共有多少篇」，
回答不了**「没进库的那些去哪了」**——列表 110 条、只收到 3 条，那 107 条是被初筛
排除的，还是压根没处理？这一轮补上。顺带撞出三件事，其中两件是**这一栏自己带的
毛病**。

| 项 | 结果 |
|---|---|
| **闭环栏**（本轮新增） | 判定 10 个源，**全部 `✓`、`差 N` 为 0**——列表条目进了循环就都落到了去向，管线内部没有丢条 |
| `hub_em` / `jl_em` / `jx_em` | 从「空」改判为「**没连上**」。三种毫不相干的故障（412 反爬 / DNS 解析失败 / SSL 老式重协商被禁），此前在表上**逐格相同** |
| 「条数」栏 | 加 `*` 标记。不早停的源这里是跑到底的**真实候选数**，早停的源是 `--limit`——两者此前混在一栏里 |

##### 判据：`列表条目数 == 收录 + 审核 + 排除`

三类计数器在循环里是逐条累加的：每处理一条列表条目，恰好给其中一个 +1。
所以跑到底时这个等式**必然成立**，一旦对不上就说明有条目进了循环却没落到
任何一个去向。实测 10 个源全部相等。

命名有两套，**必须对齐口径再相加**：

| 族 | 列表 | 收录 | 审核 | 排除 |
|---|---|---|---|---|
| TRS 基类（12 个源） | `_total_listed` | `_collected` | `_review` | `_filtered_title` ＋ `_filtered_classify` |
| 独立实现（6 个源） | `_total_list` / `_total_records` | `_collected` | `_review_count` | `_filtered_out` |

TRS 把「排除」拆成初筛与分类两段，独立实现合成一个。**只读 `_filtered_title`
不加 `_filtered_classify`，12 个源的差额会恰好等于初筛排除数**——一个看起来
非常像「丢了这么多条」的数字，而它只是少加了一项。

##### 这个判据自己带的两个毛病

**毛病一：`0 == 0 + 0 + 0` 是恒真的。** 这一栏刚加上时，任何完全抓不到的源都会
得到 `✓`——列表 0、收录 0、审核 0、排除 0。**一个恒真的判据和恒假的判据一样
没用**（这个项目里已经栽过一次：`?page=2` 对 7 个源都返回 200，于是它什么也
判不了）。补一个 `空表` 取值，专门表示「列表解析出 0 条，这一栏对它没有信息量」。

**毛病二：早停会让它必然不成立。** 早停在任意一条上截断循环，两边停在同一个
位置，差额恰好是「还没来得及处理的条目」——这个不成立**没有信息量**，但看上去
和「真的对不上账」一模一样。所以探针改了一处：**列表条目数 ≤ 60 的源不早停**，
让它跑到底（这类源的候选比例约 15%，跑完只要十几秒；实测 `ln_em` 跑到底反而比
早停的旧测法**更快**，因为省掉了早停前的重试等待）。更长的源照旧早停，这一栏
如实显示 `早停`。于是这一栏有四个取值，**只有两个是结论**：

| 取值 | 含义 |
|---|---|
| `✓` / `差 N` | 跑到底的真实对账结果——**结论** |
| `早停` | 列表超过 60 条，没跑到底——不适用 |
| `空表` | 列表 0 条，等式恒真——不适用 |
| `—` | 6 个源根本没记这几个计数器（`esafety` / `mem` / `mohurd` / `news_aggregator` / `open_gov` / `safehoo`）——不适用 |

四种取值混着数，会得出「十几个源闭环失败」这种自己吓自己的结论。所以小结那行
把四类分开报数，并且在打印时逐类解释。

##### 三个「空源」是哪一种空

把日志打开重跑，答案很直白：

```
jl_em   请求失败 (尝试 1..3): ... - [Errno -2] Name or service not known
        [jl_em] 列表共 0 篇文章          ← DNS 解析不了
jx_em   请求失败 (尝试 1..3): ... - [SSL: UNSAFE_LEGACY_RENEGOTIATION_DISABLED]
        [jx_em] 列表共 0 篇文章          ← TLS 谈不成
hub_em  （同上，HTTP 412）              ← 反爬
```

`_fetch()` 重试耗尽后返回 `None`，`collect()` 里 `if html:` 跳过，于是列表 0 条、
整轮「正常完成」、任务报成功。**这与「站点通了、栏目确实没内容」在每个计数器上
都相同**——同一个静默降级的模子，只是位置从 §2.5.8 那次的服务端响应换到了
客户端异常处理。

处置：TRS 基类加 `_fetch_failed`，**只数重试耗尽**。404/410 不算——那是「这一页
不存在」，与「没连上」都返回 `None`，但一个是正常结果、一个是故障；混在一起数，
判据又会两头都真。「结果」栏据此把 `空` 拆成 `空` 与 `没连上`。覆盖 12 个 TRS 源；
其余源（如 `esafety` 的「未配置 Token」）仍只有 `空` 一种，它不走 HTTP。

##### 「条数」栏为什么加星号

不早停的源会跑到底，于是 `cq_em` 收到 13 条、`sx_em` 收到 23 条、`hain_em` 12 条
——**这一栏的含义跟着变了**：短列表源是真实候选数，长列表源仍是 `--limit`。
拿 `cq_em` 的 13 和 `sh_em` 的 3 直接比是错的，后者列表 94 条、只是按设计停在了 3。
带 `*` 的是被早停截断的那些。

##### 本轮补的测试

新增 `tests/test_collector_health.py`，14 条，**不联网**：

1. 两族命名的对齐（TRS 的排除要加两段；独立族取 `_filtered_out`；`_total_records`
   也认）——**回归钉子**，只读 `_filtered_title` 会让差额看起来像丢了条；
2. `_closure_cell` 的五个取值，重点是 `列表 0 → 空表` 而不是 `✓`；
3. `_status_of` 把 `空` 与 `没连上` 分开，且没有 `closure` 时**退回 `空`、不猜**；
4. `_count_cell` 的星号；
5. `_fetch` 的三条路径：重试耗尽要计数、404 不计、缓存命中不发请求。

全量 **394 → 408 passed**。

**闭环这一栏至此可以结案**：判定 10 个源、全部对得上。剩下的是它够不着的
14 个（早停 5 ＋ 空表 3 ＋ 无此判据 6），各有各的原因，都写在上面的取值表里。

### 2.5.10 第九轮：正文在 PDF 里，而「解析」那条路够不着（2026-10-01）

前八轮修的都是「抓不到」——列表是 JS 壳、链接拼错、分页漏抓、错误被吞。
这一轮的两个源**一直「有数据」**：健康检查判绿、条数不是 0、正文中位也不为 0，
可**正文从来没取到过**。

#### 住建部：一个源，三处静默失败

`mohurd` 在表上此前是「空 / 0 条」。三处入口各有一种失败，共同点是
**HTTP 200、页面看着正常、一个 `<a>` 都没有**：

| 入口 | 现状 | 处置 |
|---|---|---|
| `/gongkai/zc/wjk/` | JS 异步渲染。静态 HTML 5 KB、`<title>` 正确、`<a>` **0 个** | 改走 JPaaS 接口拿 JSON，见 `MOHURD_JPaaS_API` |
| `zlaq.mohurd.gov.cn` | HTTP 521 + JS 反爬挑战页 | **不接**。要过它得执行 JS 换 cookie，属浏览器渲染一档，本项目不做；常量留着标注原因，不许再往 `collect()` 里挂 |
| `/gk/sgcc/`（应急部） | JS 跳转页，正文只有 `window.location.href="./sggpdbqk/"` | httpx 不跑 JS，停在那一行。入口换成 `tbzdsgdcbg/` |

第三条的换法有依据：主库 3 条 `mem` 记录的 URL **全在 `tbzdsgdcbg/` 下**。

JPaaS 接口有几处只能照抄的地方：`parseType` 的值拼作 `bulidstatic`
（站方原样，不是 `build`）；每页服务端硬上限 99 条；`data` 里**没有 total
字段**，翻到底只能靠「这一页没有链接了」判断。实测 60 页 5,940 条标题、
覆盖 2018 年至今要 93 秒，默认取 30 页。

#### 标题过滤：三段式，缺一不可

只按「房屋市政工程」筛会怎样——实测 60 页里 23 条命中，**其中 16 条是政策
文件**：《有限空间识别及施工安全作业指南》《生产安全重大事故隐患判定标准》
《施工安全监督人员培训考核大纲》《安全生产治本攻坚三年行动》。它们标题里
恰好有「房屋市政工程」，可拿去抽「死亡人数」「事故类型」是抽不出来的。

改成同时满足三段的判据（含「事故」+ 含文书类型词「通报/督办/调查/分析」
+ 含建筑行业词），剩 30 条，逐条看过全部是事故文书。**放进下游是污染，
比漏掉更麻烦，因为它在计数上看起来是成功的**。

一个反直觉的后果：「房屋市政工程生产安全较大及以上事故查处督办通知书」
这个标题实测出现 22 次，**每一份对应一起不同的事故**，事故本身只在正文里。
所以同名不等于重复——去重必须按 URL。

#### 正文抽取：判「有无」还是判「长短」

原写法逐个试选择器，一旦 `select_one` 命中就赋给 `content`，然后「有内容就
不再回退」。而 `.text` 在住建部详情页上命中一个 **24 字**的元素，`content`
被填满，回退分支从此不执行，最后卡在 `len(content) < 100` 上返回 `None`。

后果是**列表抓得到、正文永远抽不出**——两个环节各修一半，合起来还是 0 条。
判据得看长短，不能看有无。

#### 真正的根因：PDF 一直在盘上

上面几处修完后，住建部出得来 708 字的督办通知书正文，应急部却每条只有
**32 字**——`[PDF待解析] 标题`。

`_handle_pdf` 原本有一段「调 MinerU 直接解析」的代码，是**死代码**：

    settings.MINERU_API_TOKEN                —— Settings 上没这个字段
    construction_agent.input.pdf_processor   —— `input/` 目录是空的

而且那行 `if s.MINERU_API_TOKEN:` 写在 `try` **外面**，属性不存在时直接抛
`AttributeError`，函数整个崩掉——连上面那句「存 PDF」都执行不到。调用方没
有 try，异常冒泡到采集循环里被 `logger.debug` 吞掉。所以**住建部的通报
（PDF）从来没进过库**。

取掉死代码、改成「只存不解析、落一条 `needs_parsing` 占位」之后，链路通到
「下载附件」为止。但这仍然不对，因为**解析器就在同一个包里**：

    construction_agent/collector/pdf_text.py 的 extract_pdf_text()
    —— PyMuPDF，本地、免费、无 token、无网络
    —— henan_em / beijing_em / ln_em / nmg_em / hebei_em 一直在用它

|---|---|---|
| 泉州欣佳酒店“3·7”坍塌事故调查报告 | 51 | **37,618** |

两份都是**文字版**，不需要 OCR。而它们当时在库里是 50 字和 248 字。

#### `mem.py`：同一个病，写得更明白

`registry` 把 `mem` 这个 key 映射到 `mem.py::MemCollector`，`mohurd` 才映射到
`MohurdCollector`——所以应急部要改的是前者。它的两处入口都把正文推给一个
不存在的 MinerU：

    _handle_pdf_link          注释直说「不做正文提取，仅记录元数据供后续 MinerU OCR」
    _crawl_detail_article     抽到 PDF 链接就记 needs_ocr=True，从不下载

`needs_ocr` 那一行的写法也与全项目相反。其他五个源一直是：

    henan_em.py:278   "needs_ocr": bool(pdf_url) and not combined_text
    nmg_em.py:170     "needs_ocr": bool(pdf_url) and not detail_text
    hebei_em.py:246   同上
    ln_em.py:280      "needs_ocr": is_pdf and not detail_text

「有 PDF **且正文没抽到**才需要 OCR」。而 `mem.py` 写的是
`len(pdf_urls) > 0`——只要挂了 PDF 就喊需要 OCR，不管正文早在不在手上。
偏离惯例的那一个，恰恰是唯一没接解析器的那个。

#### 改动与实测

两处都改成「下载 → 落盘 → `extract_pdf_text` → 提出文本就用它」：

  采样的取舍会漂移且无从对账

第二条判据有实测对照：凤凰县堤溪沱江大桥那条，HTML 页正文已是全文 3,572 字，

#### 顺带查出：`_NO_CLASSIFY` 挂了一个构造器不认识的参数

`registry` 给 5 个省级源挂了 `_NO_CLASSIFY = (("enable_classify", False),)`，

对不上。`build()` 对不认识的参数只记一行 `logger.debug` 就丢掉：

```python
accepted = {k: v for k, v in kwargs.items() if k in sig.parameters}
dropped = set(kwargs) - set(accepted)
if dropped:
    logger.debug("[%s] 忽略构造器不接受的参数: %s", key, sorted(dropped))
```

不报错、不警告、测试照过。实测 `registry.build("beijing_em")` 拿到的实例：
`_enable_pdf_classify is True`——**「已经关掉分类」是个假象。**

其余 4 个源（`hebei_em` / `henan_em` / `ln_em` / `nmg_em`）参数名都是
`enable_classify`，确实生效了。已加一条遍历全部 24 源的断言，让任何新的
错配当场现形：

```python
@pytest.mark.parametrize("key", sorted(registry.SOURCES))
def test_每个源的build_kwargs都被构造器接受(key):
    unknown = set(dict(registry.get(key).build_kwargs)) - params
    assert not unknown
```

不指望把 `build()` 改成抛错——有些源本来就不接受 `data_dir`，静默跳过是
有意的。改成逐个核对更稳。

#### 那要不要给它补上参数名？——不要，而且 `_NO_CLASSIFY` 的理由本身写错了

`_NO_CLASSIFY` 的注释原先写着：

> 在采集器里跑一遍等于同一批文本被分类两次，**多花一次模型调用**。

查 `collector/classifier.py`：`classify_v2` 是个 **242 行的纯关键词规则
函数**，没有一处网络或 LLM 调用（`grep -nE 'anthropic|openai|httpx|requests|
api_key'` 零命中）。**它省不下任何模型成本。**

对 `beijing_em` 还多一层：它的 `enable_pdf_classify` 管的是**两件事**——
下载 PDF 提正文、拿正文分类，而**这个源的正文只存在于 PDF 里**（列表页
那段 HTML 只有标题、发布单位和附件路径）。挂上 `_NO_CLASSIFY` 等于把
正文来源一并关掉。

所以这一条是**摘掉**，不是补名字。摘掉不改行为，只是把既成事实写实。

其余 4 个源保留 `_NO_CLASSIFY`，但注释里的理由改了：真实代价是没有二级
筛选判据、条目一律落 `status=review`（人工审核队列变长）；换来的是
**不丢数据**——`classify_v2` 判「高置信度非建筑」时各源直接 `continue`
丢弃整条，规则误判不可逆。

## 三、目标架构

### 3.1 核心原则

> **适配器只负责「抓 + 解析」。存储、判断、计数，全部上收到存储层与分类层。**

这一条同时消解 2.2 的三个问题：目录不再散（统一落表）、状态机不再复制 18 份（统一在库里）、并发不再丢数据（SQLite 事务）。

### 3.2 工作库：`caiems_staging.db`

落实用户阶段③「临时数据库 → 人工审核 → 最终数据库」的要求，采集与提取的中间态全部进**独立工作库**，与最终库 `caiems_v2.db` 物理分离：

| 库 | 路径 | 角色 | Web 连接方式 |
|---|---|---|---|
| **最终库** | `data/caiems_v2.db` | 已审核并入的正式数据 | **只读**（`mode=ro` + `query_only`） |
| **工作库** | `data/caiems_staging.db` | 采集原始 + 提取暂存 + 审核状态 | 读写（WAL 模式） |

分离的收益：展示层永远不可能因代码缺陷污染正式数据；工作库可整库丢弃重建；备份策略不同。

### 3.3 采集层四张表

```sql
-- ① 源登记：把 24 个适配器的元信息从代码里搬到表里
CREATE TABLE collect_sources (
    source_key      TEXT PRIMARY KEY,        -- 'safehoo' / 'sh_em' / 'mohurd'
    display_name    TEXT NOT NULL,           -- '安全管理网' / '上海市应急管理局'
    source_group    TEXT NOT NULL,           -- 'national' | 'province' | 'literature' | 'academic'
    track           TEXT NOT NULL,           -- 'network' | 'literature' —— 对应论文两轨
    entry_url       TEXT,
    crawl_delay     REAL DEFAULT 2.0,        -- 秒，政府站建议 ≥5
    enable_classify INTEGER DEFAULT 1,       -- 是否走自动闸门
    is_active       INTEGER DEFAULT 1,
    last_run_at     TEXT,
    last_run_ok     INTEGER,                 -- 上次成功与否
    last_error      TEXT,
    total_raw       INTEGER DEFAULT 0,       -- 累计抓取
    total_promoted  INTEGER DEFAULT 0,       -- 累计进入提取
    notes           TEXT
);

-- ② 采集任务：一次运行 = 一条，取代内存字典 _collect_tasks
CREATE TABLE collect_tasks (
    task_id       TEXT PRIMARY KEY,          -- uuid4 hex[:12]
    source_keys   TEXT NOT NULL,             -- JSON 数组，支持多源一次任务
    params        TEXT,                      -- JSON: {since, until, limit, keywords}
    status        TEXT NOT NULL,             -- pending|running|paused|done|failed|cancelled
    created_at    TEXT NOT NULL,
    started_at    TEXT, finished_at TEXT,
    cursor        TEXT,                      -- JSON: 断点续跑位置（每源一个游标）
    stats         TEXT,                      -- JSON: {per_source:{collected,cleaned,kept,dup}}
    error         TEXT
);

-- ③ 原始事故文本：采集层的唯一数据表
CREATE TABLE raw_accidents (
    raw_id        TEXT PRIMARY KEY,          -- md5(source_url)[:12]，沿用 base.py 既有算法
    source_key    TEXT NOT NULL REFERENCES collect_sources(source_key),
    task_id       TEXT REFERENCES collect_tasks(task_id),
    title         TEXT,
    content       TEXT,                      -- 清洗后纯文本
    raw_html      TEXT,                      -- 原始 HTML（≤50KB，便于二次解析）
    source_url    TEXT NOT NULL,
    fetch_time    TEXT NOT NULL,             -- ISO
    publish_date  TEXT,
    -- 三层去重键（base.py 既有设计，入库时算好）
    url_hash      TEXT NOT NULL,
    fingerprint   TEXT,                      -- 事故指纹（年月+城市+伤亡+类型）
    title_hash    TEXT,
    -- 规则预提取字段（field_extractor 填充，base.py:36-49）
    ext_date TEXT, ext_province TEXT, ext_city TEXT,
    ext_deaths INTEGER, ext_injuries INTEGER,
    ext_accident_type TEXT, ext_severity TEXT,
    confidence_overall REAL,
    -- 闸门与人工裁决（取代 18 份复制品）
    gate_verdict      TEXT,                  -- confirmed | rejected | review | NULL(未判)
    gate_reason       TEXT,
    gate_stage        TEXT,                  -- rule | llm | manual
    gate_confidence   TEXT,                  -- high | low
    gate_at           TEXT,
    -- 生命周期
    status        TEXT NOT NULL DEFAULT 'new',  -- new|gated|promoted|archived
    promoted_at   TEXT,
    stage_id      TEXT,                      -- 指向提取暂存记录（阶段②③）
    extra         TEXT,                      -- JSON
    UNIQUE(url_hash)
);
CREATE INDEX idx_raw_status   ON raw_accidents(status, gate_verdict);
CREATE INDEX idx_raw_source   ON raw_accidents(source_key, fetch_time DESC);
CREATE INDEX idx_raw_fp       ON raw_accidents(fingerprint);
CREATE INDEX idx_raw_task     ON raw_accidents(task_id);

-- ④ 关联资产：PDF / 图片 / 附件从文件系统路径登记进表
CREATE TABLE raw_accident_assets (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    raw_id       TEXT NOT NULL REFERENCES raw_accidents(raw_id) ON DELETE CASCADE,
    asset_type   TEXT NOT NULL,              -- pdf | image | attachment
    url          TEXT,
    local_path   TEXT,                       -- 相对 data/ 的路径
    bytes        INTEGER,
    ocr_status   TEXT,                       -- pending|done|failed|skipped
    ocr_text     TEXT
);
```

> **状态机语义（唯一版本，替代 18 份复制品）**
> `status`（生命周期，4 值）与 `gate_verdict`（判定结论，3 值）**正交**：
> `new` 未判 → `gated` 已判 → `promoted` 已送提取 → `archived` 人工归档。
> 这样「已确认」不会再被写成 `new`（旧 `stores/__init__.py:244` 的语义冲突从根上消失）。

### 3.4 适配器协议归一

**按 §2.3 的实测修订，这里比初稿简单得多。**

初稿设想的是「4 个合规 + 21 个鸭子类型」，所以要一套 `LegacyAdapter` 配字段映射表。实测 24/24 都符合 `BaseCollector` 契约、都返回 `list[RawAccidentText]`，那层适配**不需要存在**。

不改动 24 个适配器内部的抓取逻辑，只做三件事：

**① 统一出口：`RawItem` 就是 `RawAccidentText` + 源标识。**不新造数据类型——`RawAccidentText` 已经带 `generate_url_hash` / `generate_fingerprint` / `generate_title_hash` 三层去重键，重造一个只是把它们抄一遍。

```python
# construction_agent/collector/adapter.py（新增）
def collect_items(collector: BaseCollector, *, limit: int | None = None,
                  should_stop: Callable[[], bool] | None = None,
                  ) -> Iterator[RawAccidentText]:
    """把任意 BaseCollector 的 collect() 产出变成可迭代、可中断的流。

    24 个源都是「一次性返回整个 list」，没有流式产出，所以这里拿到的
    是完整列表再逐条 yield。中断粒度因此是「一条事故处理完」，不是
    「一个网络请求」——取消一场正在跑的采集，最坏要等当前这条抓完。
    这是既有适配器结构的限制，改它要动 24 个源的 collect()，不值。
    """
    for item in collector.collect():
        if should_stop and should_stop():
            return
        yield item
```

**② 掐掉落盘通路：改 `RawAccidentStore`，不在 21 个调用点上各改一遍。**

21 个源调的是同一个类的同一个方法（9 个源直接调、12 个经 `TrsCmsCollector`）。给这个类加一个**不落盘的构造模式**，比在源里逐个找调用点稳得多：

```python
# construction_agent/collector/stores/__init__.py（改）
class RawAccidentStore:
    def __init__(self, filepath: Optional[Path] = None, *, sink=None):
        # sink 给了就只走回调、不碰文件系统；filepath 与 _save 全部失效。
        # 采集产出从 M2 起只落工作库的 raw_accidents 表（蓝图 01 §3.3），
        # 文件系统那条路留着只会又长出一份散落的 data/<源名>/ 目录。
        self.sink = sink
        ...
    def _save(self):
        if self.sink is not None:
            return          # 由 sink 接管，磁盘不动
        ...原有逻辑...
```

`sink` 由采集任务在执行前注入（`collector.raw_store.sink = task_sink`）。**加 `sink` 参数是纯增量改动，不改任何源文件**；`_save()` 与 `add_batch()` 的行为对源而言完全不变。

**③ 掐掉目录创建：`data/<源名>/` 不再产生。**

`TrsCmsCollector.__init__` 的 `self.data_dir.mkdir(...)`（`trs_cms_base.py:127`）与另外 10 处 `mkdir` 都要停。做法同 ②：`data_dir` 已经是可以传进来的构造参数（`TrsCmsCollector(site_config, data_dir=None)`），传一个 `tempfile` 下的临时目录即可，**不改基类源码**。这样 PDF 落到临时目录、随任务结束清理，而 `data/<源名>/` 永远不出现（本蓝图 §8 验收第 10 条）。

> **取消初稿的 `NullSink` 替身方案**：初稿设想「实现各适配器各自期望的 `_save()` / `cache_path` 接口」——但实测 21 个调的是同一个 `RawAccidentStore`，不存在"各自期望的接口"。②③ 两条把这件事收进两个构造参数，比注入替身少一层间接。

**文献轨**（`input/` 目录的 PDF）：`LiteratureAdapter` 包 `pdf_processor` + `llm_splitter`，一条书页 = 一条 `RawAccidentText`。**是否纳入在线管道待用户裁决**（见蓝图 07 第七节）。

> ### 3.4′ 实现后的事实修订（2026-09-30）
>
> 上面三件事在 M2 落地时各有一处与设计不符，**以实现为准**：
>
> **① 没有 `adapter.py`，中断粒度是「源级」而不是「一条事故」。**
> 该文件最终没有建。`collect_items()` 那种「逐条 yield、在 yield 处检查取消标志」的形态**在这 24 个源上不存在**——每个源的 `collect()` 都是一次性 `return` 整个列表，中间没有任何可插入检查点的位置。所以取消只能做到：置任务为 `cancelling`，**当前这个源跑完**再停，不再启动下一个源（`executor._run_source()` 开头的取消检查）。接口层把这个限制如实回给用户：`POST .../cancel` 的 200 与 409 两条分支都带 `note` 字段说明这一点，页面上也照写。
>
> **② `sink` 是 `attach()` 方法，不是构造参数。**
> 设计里写的是 `RawAccidentStore(sink=...)`，但采集器内部是**无参**构造它的（源里写 `self.raw_store = RawAccidentStore()`），执行器拿不到构造时机。改成事后注入：
>
> ```python
> # construction_agent/collector/stores/__init__.py
> store = getattr(collector, "raw_store", None)
> if store is not None and hasattr(store, "attach"):
>     store.attach(sink)      # 挂上之后 add() 多出一条写库通路，内存行为不变
> ```
>
> `attach()` 里会清空 `_data` / `_url_index`，并让 `_save()` 短路——磁盘那条路到此为止。
>
> **③「24 个源文件一行不改」不成立，实际改了 7 个。**
> `beijing_em` / `hebei_em` / `nmg_em` / `henan_em` / `ln_em` / `mem` / `safehoo` 这 7 个源把落盘目录**硬编码**成 `settings.DATA_DIR / "<源名>"`（不是从构造参数进来的），各加了一个可选参数：
>
> ```python
> def __init__(self, ..., data_dir: Optional[Path] = None):
>     # data_dir=None 时落 settings.DATA_DIR/<源名>（旧行为）。在线采集传一个
>     # 临时目录进来，data/<源名>/ 就不再产生——采集产出自 M2 起只落工作库。
>     self.data_dir = data_dir or (settings.DATA_DIR / "<源名>")
> ```
>
> 执行器为每个源建 `tmp_root/<source_key>`，任务结束 `shutil.rmtree`（PDF 几十 MB，不删就是残留）。`esafety` 与 `gd_em` 本身不建目录，不需要这个参数。`TrsCmsCollector` 那 12 个源走的是既有的 `data_dir` 构造参数，未改动。
>
> **④ 附件 URL 登记进 `raw_accident_assets`（初稿漏项）。**
> 省级站的通报常常把正文挂在 PDF 附件上（页面本身只有一行标题）。采集器把附件 URL 塞在自定义字段里，键名不统一，执行器按实测出来的一张表去认：`pdf_urls`（唯一定义在 `RawAccidentStore` 契约里的键）、`image_urls`、`attachment_urls`、`attachments`。只登记 URL 与 `ocr_status='pending'`，**不下载**——下载与 OCR 是阶段②的事。认不出的键不猜：宁可少登记一条，也不要把普通链接当附件去下载。
>
> 登记只针对**本次真正新插入**的 `raw_accidents` 行。`INSERT OR IGNORE` 之后 `total_changes` 只给总数、分不出被唯一键拦下的那些，所以写库前先查一次 `SELECT raw_id ... WHERE raw_id IN (...)` 取差集，否则每重跑一次采集，同一批 PDF 就再登记一遍。

### 3.5 调度与并发

| 项 | 方案 |
|---|---|
| 执行模型 | 任务进程内线程池（`ThreadPoolExecutor`，默认 3 并发），**不用 Celery**（无 Redis 依赖，2,623 条规模下线程足够） |
| 断点续跑 | `collect_tasks.cursor` 存每源游标（适配器已有的 checkpoint 语义上收）；任务重跑时从游标继续 |
| 限速 | 每源读 `collect_sources.crawl_delay`；同源串行、跨源并行 |
| 超时 | 单源总超时 30 min，单请求 30 s；超时记 `last_error` 并跳过该源，不中断任务 |
| 取消 | `POST .../cancel` 置状态 + 协作式退出。**实测修订**：适配器里没有 `yield` 检查点（见 §3.4′ ①），粒度只能到源级——当前源跑完就停，不再启动下一个源 |
| 失败重试 | 单源最多 3 次，指数退避；三次失败置 `failed` 并写 `last_error` |

## 六、技术选型与理由

| 选择 | 理由 |
|---|---|
| **SQLite 工作库**（非 JSON 文件） | 事务保证原子性、WAL 支持读写并发、SQL 可直接筛选分页、进程崩溃不丢数据。JSON 全量覆盖的三个缺陷（`stores/__init__.py:80-85`）从根上消除 |
| **线程池而非 Celery** | 无 Redis/RabbitMQ 依赖；24 源 × 单源串行的真实并发需求不超过 3。任务状态落库，进程重启可恢复 |
| **保留 `RawAccidentText` 的三层去重键设计** | `generate_url_hash` / `generate_fingerprint` / `generate_title_hash`（`base.py:54-94`）已考虑「同一事故多源报道」——这是采集层最难得的既有设计，原样保留 |
| **HTTP 客户端统一 httpx** | 项目已装（适配器在用）；支持超时、重试、连接池 |
| **解析统一 BeautifulSoup + lxml** | 适配器在用，无新增依赖 |
| **不引 scrapy** | 25 个站点已有手写解析器，引入框架等于重写全部适配器，收益为负 |

**必须遵守**：`robots.txt` 检查（政府站允许抓取详情页）、请求间隔读 `crawl_delay`、UA 标注项目身份与联系邮箱、`raw_html` 截断 50 KB。
