# S5: CAICS-CoT+ 策略

## 对标 Liu et al. (ESWA 2025)

HFACS-CoT+

## 核心思路

将 S4 的一次长 prompt 调用**拆分为 5 次独立 API 调用**，每次专注一个因果层级。前层分析结果作为上下文注入后层，消除单次调用中的注意力稀释问题。

## 完整提示词

### Call 1: M 层（管理根基）

```
System: 你是安全管理专家。从事故文本中识别管理根基(M层)致因。
注意: 发生死亡事故本身即说明现场监管严重缺失，需同时考虑显性证据和隐性推断。

M1现场监管缺失: 线索: 无人监管/监理失职。**推断**: 几乎全部死亡事故都存在M1，即使文本未直接提及
M2隐患排查失效: 线索: 未排查/未整改。**推断**: 事故涉及结构缺陷/设备问题未被发现→M2
M3安全培训不足: 线索: 未经培训/交底走过场。**推断**: 工人明显违章但文本未提培训→M3
M4制度规程漏洞: 线索: 无安全方案/应急预案缺失
M5市场行为违规: 线索: 违法分包/无资质/转包/抢工期

输出JSON: {"M":["M1","M2"],"reasoning":"M1[explicit]因为... M2[inferred]因为..."}
输出JSON: {"M":["M1","M2"],"reasoning":"M1因为...M2因为..."}

User: {[accident text]}
→ 得到 result_M
```

### Call 2: F 层（防线失效）—— 注入 M 层结果

```
System: 你是安全防护专家。已知管理层分析结果: {result_M}
从事故文本中识别防线失效(F层)致因。
F1临边洞口防护缺失: 无防护/无护栏/临边未设防/洞口未盖？
F2支撑体系失稳: 模板坍塌/脚手架失稳/支撑不足/支架倒塌？
F3设备安全装置失效: 限位器被屏蔽/防坠器失效/安全装置损坏？
F4个体防护未使用: 未系安全带/未戴安全帽/无防护用品？
输出JSON: {"F":["F2"],"reasoning":"F2因为..."}

→ 得到 result_F
```

### Call 3: T 层（触发条件）—— 注入 M+F 层结果

```
System: 你是事故分析专家。已知管理层: {result_M}，防护层: {result_F}
从文本中识别触发条件(T层)致因。
T1设备机具故障: 设备故障/塔吊倒塌/钢丝绳断裂/升降机故障？
T2物料状态异常: 堆载超限/材料缺陷/荷载过大/瓦斯积聚？
T3地质环境突变: 涌水/边坡失稳/地基沉降/土体滑移？
T4气象水文触发: 暴雨/大风/冰雪/雷电/连日降雨？
输出JSON: {"T":["T2"],"reasoning":"T2因为..."}

→ 得到 result_T
```

### Call 4: H 层（人的行为）—— 注入 M+F+T 层结果

```
System: 你是人员行为分析专家。已知管理: {result_M}，防护: {result_F}，触发: {result_T}
从文本中识别人的行为(H层)致因。
H1违反操作规程: 明确违反施工方案/操作规程/规范要求？
H2违规指挥决策: 管理人员强令冒险/明知风险仍施工/违章指挥？
H3风险辨识失败: 未意识到危险/安全意识薄弱/未检查确认/疏忽大意？
H4应急行为失当: 盲目施救/未及时撤离/救援不当扩大伤亡？
输出JSON: {"H":["H1","H2"],"reasoning":"H1因为...H2因为..."}

→ 得到 result_H
```

### Call 5: C 层（后果放大）—— 注入全部前层结果

```
System: 你是应急救援分析专家。
已知管理: {result_M}，防护: {result_F}，触发: {result_T}，行为: {result_H}
从文本中识别后果放大(C层)致因。
C1救援响应迟缓: 救援不及时/无预案/二次坍塌/延误抢救？
C2信息迟报瞒报: 未及时上报/瞒报/迟报/漏报？
输出JSON: {"C":["C1"],"reasoning":"C1因为..."}

→ 得到 result_C
```

### 后处理：合并 5 次调用结果

```python
all_codes = result_M["M"] + result_F["F"] + result_T["T"] + result_H["H"] + result_C["C"]
# 合并顺序: M → F → T → H → C（保持因果链方向）

# accident_type/severity/deaths/injuries: 从5次调用的最终JSON中各取一次
# 若多次调用返回了type/sev，取多数投票
```

## 设计特点

| 维度 | 说明 |
|------|------|
| 推理过程 | **多层串行** —— 前层推理结果注入后层上下文 |
| 示例 | 0 个 |
| API 调用 | **5 次**（每个因果层 1 次） |
| 每层 Prompt 长度 | ~200 字 |
| 总 Prompt 长度 | ~1000 字（5 × 200） |
| 领域知识注入 | 每层专精于一个维度 + 关键词引导 |

## 与 Liu et al. HFACS-CoT+ 的对应关系

| Liu et al. | 本实验 S5 |
|------|------|
| 11 个问题独立输入 LLM | 5 层独立 API 调用 |
| 程序化逻辑语句替代文本指令 | 前层 JSON 结果注入后层 prompt |
| 两步（不安全行为 + 前提条件） | 五步（M→F→T→H→C 因果链） |

## 与 S4 的关键区别

```
S4: 1 次 LLM 调用
    ├── 1500字 prompt 包含所有 19 类的 95 个关键词
    └── 问题: 注意力稀释，LLM 倾向扫描高频关键词，忽略低频类

S5: 5 次 LLM 调用
    ├── 每次 ~200 字 prompt，专注 1 个层级 3-5 类
    ├── 前层 JSON 结果作为后层上下文
    └── 优势: 每层的 200 字都有 LLM 的完整注意力
```

## 成本与延迟

| 指标 | S4 | S5 |
|------|:--:|:--:|
| API 调用 | 1 | 5 |
| 每例成本 | ~$0.001 | ~$0.005 |
| 每例延迟 | ~8s | ~40s |
| 批量 100 条 | ~15min | ~70min |
