# Golden Standard 数据集：300 条优质事故 + S1′ 标注结果

用于构建 CAICS 致因标注的**标准答案**：先筛出优质事故，再由强模型做特征提取与致因标注，
最后人工审核核对，冻结为评测用的标准数据集。

## 目录内容（4 个数据文件 + 本说明）

| 文件 | 内容 |
|---|---|
| `golden_candidates.jsonl` | **300 条输入**。每条含 `raw_text` 全文 + 元数据 + 筛选指标（tier/score/来源/事故类型/死亡人数…） |
| `S1_golden_results.jsonl` | **300 条结果**。每条含 `parsed`（**基础特征 31 字段** + **`codes` CAICS 5 层 19 类编码**）+ token/耗时 |
| `S1_golden_review.csv` | **人工审核表**。逐条：编码 + 基础字段 + 原文节选（前 600 字） |
| `S1_golden_review_vs_db.csv` | 审核辅助：与库内既有 `caics_causes`（主管道产出）的逐条编码差异（**差异信号，非真值**） |
| `S1_vs_db_diff.html` | **可视化逐条差异**：一致度分档、19 类编码逐类差异、300 条逐条对照（可搜索/筛选/排序，展开看 5 层编码全景与原文）。生成：`scripts/golden_s1/analyze_vs_db.py` |
| `S1_pro_vs_flash.html` | **pro vs flash** 跨模型逐条对照（同一提示词、同一样本，只有模型不同） |
| `basic_features_flash_vs_pro.html` | **基础特征 GT 裁决表**：31 字段 × 300 条，flash/pro/库内三方并排，默认只显示分歧字段 |
| `pro/` | **同 300 条的 pro 结果**，结构与本目录一致（结果 jsonl + 审核表 + vs 库内对照 CSV/HTML） |

筛选中间态、首轮含多事故合并块的版本等过程文件已全部删除；需要时用下方脚本重跑生成
（`screen_golden_candidates.py --select` 的过程文件会写进 `_process/` 子目录，不污染本层）。

## 数据来源与筛选

从 `data/caiems_v2.db`（2601 条）筛出 300 条。**只用书籍来源**——实测网页来源不可用：
`esafety` 是扫描件 OCR 双栏交错且截断在 ~3200 字；各地应急局 `*_em` 尾部带「(共N字)」标记，
原文均 7883 字而实际仅得 ~3066 字。书籍来源完整洁净：

| 来源 | 条数（入选） |
|---|---|
| 《建筑施工重大伤亡事故800例(樊锡仁)》 | 121 |
| 《建筑施工安全事故案例分析(住建部扫描版)》 | 88 |
| 《建筑施工安全事故案例分析(住建部)》 | 49 |
| 《建筑施工生产安全事故案例分析(住建部)》 | 42 |

**筛选判据**（`scripts/screen_golden_candidates.py`）：
1. 来源池限含官方原因认定者（排除新闻报道）
2. **正文含原因认定段落**为硬性闸门（剔除目录行干扰，避免目录里的"事故原因……8"蒙混通过）
3. 洁净度：先剥页码/目录点线/抓取元信息/**网页导航壳**再算碎片率，识别扫描件 OCR 交错
4. 单事故完整性：按**不同案例编号**计数；800 例另有专用判据——`发生(事故)?[简高]况`
   是该书**每起事故一条**的字段标签，出现 ≥2 次即多起事故
5. 致因丰富度打分：原因段陈述句条数 0.30 + 跨层关键词覆盖 0.25 + 篇幅/字段/层级/枚举

**入选集画像**：T1_core 160（≥1200 字 + 直接/间接原因齐全）+ T2_short 140（500–1200 字带原因标签）；
篇幅 p10 537 / 中位 1338 / p90 2624 字；原因段陈述句 p10 3 / 中位 9 / p90 27；
事故类型：坍塌 110、起重伤害 68、高处坠落 45、土方坍塌 31、触电 20、其他 26。

## S1′ 标注方案（S1 FewShot + 基础特征）

S1 原提示词的输出只有 6 个字段，本方案把 schema 扩成【基础特征 31 字段 + CAICS 编码】，
**不改动 S1 的策略内核**：

| 组成 | 来源 |
|---|---|
| CAICS 5 层 19 类定义 + 3 个少样本示例 + user 前缀 | `experiment3/runner.py` 的 `STRATEGIES["S1_FewShot"]`，**按文件路径加载**（走包导入会被主仓库已缓存的 `construction_agent` 遮蔽），不手工转录 |
| 基础特征 31 字段定义（含全部枚举与判定规则） | `step1_basic_extractor.py` 的 `STEP1_TOOL` 直接渲染，保证与主管道 Step1 口径一致 |

参数：`deepseek-v4-flash`，temperature 0，**max_tokens 16384**（DeepSeek 思考块占预算，2048 会返回空文本），
并发 4，原文整段送入不截断，逐条落盘支持断点续跑。

```bash
# 需用 /home/suntianhao/construction_agent/.venv/bin/python3
.venv/bin/python3 scripts/golden_s1/run_S1_golden.py --workers 4      # 全量
.venv/bin/python3 scripts/golden_s1/run_S1_golden.py --only-ids ids   # 指定 id 补跑
.venv/bin/python3 scripts/golden_s1/repair_S1_golden.py               # 补跑异常条
.venv/bin/python3 scripts/golden_s1/analyze_S1_golden.py              # 出审核表 + 打印统计
```

## 基础特征 GT 敲定：flash vs pro 逐字段一致性

脚本 `scripts/golden_s1/analyze_basic_features.py` → `basic_features_flash_vs_pro.html`
（31 字段 × 300 条的 flash/pro/库内三方逐条对照，默认只显示有分歧的字段）。

**没有任何一条事故的 31 个字段全部一致；292/300 条存在至少 1 个硬冲突**，
典型条目一致 23–27 个字段。

### 可自动采纳（有效一致率 ≥95% 且冲突 ≤10）——12 个字段

`severity`(100%) `deaths`(100%) `injuries`(100%) `direct_economic_loss`(100%) `date`(99.3%)
`accident_time`(99.6%) `location`(98.7%) `city`(97.5%) `fall_height`(96%) `district`(95.2%)
`developer`(100%) `supervision_company`(100%)
—— 后两个的 100% 是"双方都判为空"导致的虚高（非空样本仅 87 / 8 条），采纳时要留意。

### 取库内元数据，不要让模型抽 —— 1 个字段

`report_type`：冲突 85 条（第二高）。它是**来源属性不是提取任务**，库内 300 条统一为"教材案例"，
两个模型却按行文风格去猜，纯属自找分歧。

### 自由文本，需先定书写规范 —— 7 个字段

`summary`(有效一致 46.3%) `direct_cause`(54.7%) `accident_location_detail`(48.3%)
`project_name`(80%) `title`(81.7%) `contractor`(94.4%) `weather`(52.4%)
—— 严格一致率普遍为 0，必须规定"照抄原文 / 允许概括 / 长度上限"，否则无法判定对错。

### 需人工逐条裁决 —— 11 个字段

按硬冲突数排序：`work_task` 40、`worker_type` 49、`equipment_involved` 41、`material_involved` 41、
`construction_phase` 31、`contractor_type` 25、`project_type` 18、`accident_type` 14、
`collapse_subtype` 14、`building_structure` 5、`trapped_count` 30。
`accident_type` / `collapse_subtype` 虽一致率 95%+，但各 14 条冲突，建议优先手工过一遍。

> 附注：库内 Step1 存在零星字段错位（300 条中 1 条 `supervision_company` 取了"教材/案例"、
> 2 条 `contractor` 取了"总包/无资质挂靠"这类承包类型取值），作第三参考时需留意。

## 结果

- **300/300 全部成功**，JSON 解析失败 0，schema 违规 0
- CAICS 编码 **6.93 条/事故**（min 2，max 13），**19 类全覆盖**
- 命中率高：H1 违反操作规程 95%、M1 现场监管缺失 89%、M2 隐患排查失效 80%
- 命中率低且合理：C2 迟报瞒报 1%、C1 救援迟缓 2%、H4 应急行为失当 6%
- 基础特征：core 字段 100% 填充；低填的正是书籍案例本就不写的（监理单位 1.3%、天气 9%、坠落高度 13%）
- 质量核验：死亡人数与库内字段 **300/300 一致**、严重程度 300/300；与库内既有编码 Jaccard 中位 **0.750**，无一条零交集

### 与库内既有编码的差异（详见 `S1_vs_db_diff.html`）

库内编码来自主管道 Step2，**不是真值**；差异说明两套标注不一致，判定需回原文。

- 一致度：**完全一致仅 22 条（7.3%）**；高度一致(0.8–1) 99 条、中等(0.6–0.8) 122 条、较大差异(0.4–0.6) 52 条、严重分歧(<0.4) 5 条
- 编码数：S1′ **6.93** 条/事故 vs 库内 **7.69** 条 —— S1′ 比库内少打 168 条、多打 54 条
- 仅库内有的编码 **448** 个，仅 S1′ 有的 **221** 个
- 分歧最集中的类：**H3 风险辨识失败**（库内有 104 条 S1′ 没打，一致率仅 50.4%）、F2 支撑体系失稳（56 个仅库有）、M4 制度规程漏洞（44）、H2 违规指挥决策（34）、T2 物料状态异常（32）
- S1′ 更倾向打的类：M2 隐患排查失效（49 个仅 S1′ 有）、T2、H2、T1

### 两个模型档位对照（同一提示词、同一样本）

| | flash | pro |
|---|---|---|
| 编码数/事故 | 6.93 | **6.54** |
| 耗时 | 14.7 s/条 | **91.9 s/条** |
| 输出 tokens | 80 万 | **200 万** |
| vs 库内 Jaccard 中位 | 0.750 | 0.721 |
| vs 库内 完全一致 | 22 (7.3%) | 19 (6.3%) |
| vs 库内 仅本方有 / 仅库有 | 221 / 448 | 187 / 532 |

**pro 与 flash 相互一致度 0.833（完全一致 69 条，23%）**——比任一方与库内的一致度都高。
pro 比 flash 编码更少、与库内分歧更大；两档在 H3 风险辨识失败上的分歧最突出
（pro 一致率仅 36.6%，flash 50.4%）。这意味着**档位选择会系统性改变标注结果**，
冻结标准答案前需要固定一个档位。
