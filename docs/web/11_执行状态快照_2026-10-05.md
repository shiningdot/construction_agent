**同日再补第五格：读方法的入参面**：`scripts/check_2582_query_params.py` ——
§2.5.80 核的是**写方法**的入参（POST body），§2.5.81 核的是写方法的出参，**读方法（GET）
的入参**这一半一直空着。**GET 的 query 与 POST 的 body 是同一个病的两种形态**：前端拼
`?type=single`、后端读 `text_type` ⇒ **筛选静默失效**（页面照常渲染、数字照常返回，只是

## 四、本次查出的真缺陷：503 建库提示静默失效（已修）

**现象**：`e2e_collect.py` 96/1、`e2e_extract.py` 126/1，两个脚本各挂同一条断言——

```python
check("503 里给出建库提示", "create_staging_db" in body.get("message", ""))
```

**因果链**（靠 git 补齐）：

| 时间 | 提交 | 动作 |
|---|---|---|
| 10-01 00:33 | `1922bd7` | e2e 脚本落盘。此时 `POST /api/collect/tasks` 的 503 响应是 `{"ok": False, "error": "staging_db_missing", "message": BUILD_HINT}`——**message 就是建库提示本身**，断言成立 |
| 10-01 14:53 | `ca41bc4` | 新增 `dberr.py`（256 行），把不可用拆成分档的 `{error, message, hint}`：**`message` 只说「哪里不对」，「下一步动作」移到 `hint`**。该提交改了 collect/extract/review/staging_db/db 五个文件，**没有改 e2e** |

于是断言查的键里不再有建库提示——**但它不会报错，只是恒为 False**。e2e 平时不跑，
一直没暴露，直到 2026-10-05 复跑。

**修复两处，两处都有独立的理由**：

1. **实现（`construction_agent/web/dberr.py` 的 `_hint`）**：`database_not_found` 这一档
   **按 `kind` 分岔**。
   - `kind="staging"`：hint 改为「工作库还没建：跑 `scripts/create_staging_db.py` 建表（幂等…）。
     若库文件在别处，用环境变量 `CAIEMS_STAGING_DB` 指定」。理由是**同一档在两种库上的下一步
     动作不同**——工作库本来就是空的，建它是安全动作，而原 hint 只说「用环境变量指定库文件」，
     把**第一次打开页面**的用户引去设一个他并不需要设的环境变量。
     **这处漏掉的正是该文件自己的注释所推理的**（「『文件不在』与『零张表』都能靠
     `create_staging_db.py` 修」）——注释说了、代码没做。
   - `kind="final"`：**保持原样**，仍只说「用环境变量 `CAIEMS_DB` 指定」。主库是数据资产，
     不存在说明环境指错了，引用户去 `create_db_v2.py` 只会建出一个空的主库——**比不提示更费事**。

2. **断言（两个 e2e 脚本）**：改为 `"create_staging_db" in (message + hint)`。这不是"为了让测试
   通过而改测试"——`dberr.py` 立下的契约就是把动作放 `hint`，旧断言是**契约变更后没跟上的过期判据**。
   合并两键查、不依赖动作放哪一栏，契约再调整时这条也不会二次失效。

**复跑**：`e2e_collect.py` 97/0、`e2e_extract.py` 127/0，其余全部 e2e 与核验脚本复跑无回归（§1 表）。
