## 一、功能目标与用户场景

### 目标
把 CAIEMS 的四阶段工作前端化：**在线采集 → 审核与提取 → 暂存与人工确认 → 展示与分析**。研究者不必进命令行，就能完成从"发现一条事故新闻"到"它成为结构化数据"的全过程。

### 四类用户场景

| 场景 | 用户动作 | 系统行为 | 对应模块 |
|---|---|---|---|
| **补采** | 打开采集页，勾选若干名单网站，点「开始采集」 | 后台跑爬虫 → 清洗 → 结构化 → 落原始池 | `01_在线采集` |
| **审核** | 在待审列表逐条判定「单个事故 / 多事故 / 通报」 | 三分类分流；合格者进提取队列 | `02_审核与提取` |
| **提取** | 粘贴一段事故文本，点「分析」 | 走 CAICS 链路 → 特征提取 + 致因编码 → 落暂存表 | `02_审核与提取` |
| **确认** | 在暂存区审阅提取结果，勾选后点「并入主库」 | 事务写入 `accidents` + `caics_causes` | `03_暂存与人工审核` |
| **查阅** | 打开展示页，按地区/等级筛选，点进详情看证据链 | 直连 SQLite 查询，服务端分页 | `04/05/06 展示` |

### 一句话定位
**展示层只读主库；采集与提取层只写暂存区；人工确认是两者之间唯一的闸门。**

## 二、架构总览

```
① 在线采集            ② 审核与提取              ③ 暂存与人工确认        ④ 展示
─────────────      ──────────────────      ─────────────────      ─────────────
名单网站清单         原始池 → 三分类审核        extraction_staging      caiems_v2.db
   ↓ 爬虫              ↓ single 合格            （与主库同构）           （只读连接）
清洗四器              step1 特征提取              ↓ 人工逐条/批量审阅        ↓ SQL 查询
   ↓                  step2 CAICS 编码            ↓ 事务写入              筛选/分页/可视化
原始池 RawStore         ↓                       accidents              证据链展示
                   （配额与成本控制）            caics_causes
```

**贯穿全线的两条纪律**
1. **单一口径**：全项目只有 CAICS 5 层 19 类一套致因理论，只有主库 9 表一套 schema。HFACS-CS 与 V1 四维度退出生产路径（见第六节）。
2. **只读→只写暂存**：展示层不碰写接口；提取层不碰主库。要让数据进主库，必须经过人工确认。

### 3.1 数据库定位与路径解析

主库：`data/caiems_v2.db`（27.4 MB，SQLite，9 表）

**路径解析优先级**（新代码必须实现，理由是 worktree 与主仓库的 `data/` 是两份）：

### 3.2 连接策略

```python
con = sqlite3.connect(f"file:{db_path}?mode=ro", uri=True)
con.row_factory = sqlite3.Row
con.execute("PRAGMA query_only = ON")   # 双保险
```

三项要点：

1. **只读 URI**：展示层用 `mode=ro`，从物理上杜绝误写。
2. **`PRAGMA foreign_keys = ON` 必须显式开启**（仅写入路径需要）。实测三张子表的建表语句**都声明了** `REFERENCES accidents(id) ON DELETE CASCADE`：
   - `caics_causes.accident_id`、`source_urls.accident_id`、`image_files.accident_id`
   
   但 SQLite **默认不强制外键**。2026-09-23 清理掉的 1,041 行孤儿外键，根因就是「表声明了外键 + 连接没开 PRAGMA + 子表用裸 `INSERT` 而主表用 `INSERT OR REPLACE`」。**新代码的写入路径必须开 PRAGMA，并对子表用 `INSERT OR REPLACE` 或先删后插**，否则孤儿会再次产生。
3. **连接生命周期**：展示层每请求短连接（SQLite 打开成本极低）；写入路径用显式事务 `BEGIN IMMEDIATE`，避免并发写冲突。

### 3.3 索引方案（必须补）

**实测现状：索引严重不足。**

| 表 | 现有索引 |
|---|---|
| `accidents` | 仅 `sqlite_autoindex_accidents_1`（主键 id） |
| `caics_causes` | **无任何索引**（`accident_id` 非主键，16,323 行全表扫描） |
| `image_files` | `idx_image_files_accident`（唯一一个有价值的） |
| `source_urls` / `enum_definitions` / `pipeline_metadata` | 仅 autoindex |

**根因（实测）**：索引不是"从未设计"，而是**设计了但从未生效**。`scripts/create_db_v2.py:66-70` 声明了 5 个 `accidents` 索引（type / severity / date / city / deaths），`:84-85` 声明了 2 个 `caics_causes` 索引，共 **7 个**。但该脚本 `:165-167` 有 `if os.path.exists(db_path): os.remove(db_path)` 的破坏性行为，**从未在真实库上执行过**——真实库是另一个版本的表结构所建。同一脚本还留下更硬的漂移证据：`:10` 注释写「事故主表 (55列)」，同文件 SCHEMA 实际 52 列，真实库 **48 列**（少 `lighting`/`day_of_week`/`season`/`time_period`/`is_night_shift` 五列，多 `work_task_enum`）。**脚本、注释、真实库三者互不相同。**

> 这条漂移是本项目数据层最需要警惕的一类问题：**建表脚本不是 schema 的真相来源，`PRAGMA table_info` 才是**。凡涉及列名与类型，一律以真实库为准。

**必须补齐**：**命名一律沿用 `create_db_v2.py` 的既有风格**，不另起一套（后续所有 SQL 与本文件、蓝图 03 引用同一批名字）。

```sql
-- create_db_v2.py:66-70 声明过的 5 个
CREATE INDEX IF NOT EXISTS idx_acc_type     ON accidents(accident_type);
CREATE INDEX IF NOT EXISTS idx_acc_severity ON accidents(severity);
CREATE INDEX IF NOT EXISTS idx_acc_date     ON accidents(date);
CREATE INDEX IF NOT EXISTS idx_acc_city     ON accidents(city);
CREATE INDEX IF NOT EXISTS idx_acc_deaths   ON accidents(deaths);
-- create_db_v2.py:84-85 声明过的 2 个
CREATE INDEX IF NOT EXISTS idx_cause_acc    ON caics_causes(accident_id);
CREATE INDEX IF NOT EXISTS idx_cause_code   ON caics_causes(code);
-- 展示层需要、脚本未声明的 2 个
CREATE INDEX IF NOT EXISTS idx_acc_province   ON accidents(province);
CREATE INDEX IF NOT EXISTS idx_cause_quality  ON caics_causes(evidence_quality);
```

### 3.5 `accidents` 表的字段口径（48 列）

**关键结论：web 展示的唯一权威字段清单就是这 48 列。** 项目历史上有过多个不一致口径——JSON 快照 41 字段、`step1` tool schema 30 属性、模块 docstring 写 23。**以本表为准**，蓝图 04–06 的字段呈现以此为依据。

**填充率口径（重要）**：「填充率」这个词在本项目里被用过三种互不相同的算法，前两种都会得出误导性的结论，必须先钉死用哪一个。本节一律采用 **口径③「有值率」= 非 NULL 且非空串**（分母 2,623）。

| 口径 | 写法 | 在 `deaths` 上 | 在 `publish_date` 上 | 问题 |
|---|---|---:|---:|---|
| ① 非零率 | `WHERE col > 0` | 86.9% | — | **不是填充率**。`deaths=0` 是「原文未提及伤亡」的有效语义，不是缺失 |
| ② 非 NULL 率 | `COUNT(col)` | 100% | 100% | `COUNT()` 把空字符串也算作有值，会漏掉 907 条空 `publish_date` |
| ③ **有值率（本节口径）** | `COUNT(col) WHERE col IS NOT NULL AND col != ''` | **100%** | **65.4%** | 唯一能反映「这列在页面上能否显示出东西」的口径 |

三种口径在 `publish_date` 上差 **34.6 个百分点**（907 条空串），在 `deaths` 上则是「100% 有值 vs 86.9% 非零」的语义之别。**任何页面上的覆盖率标注都必须写明用的是哪一种。**

按**有值率**分四档：

**A 档 · 必显（≥ 90%，30 列）**

满值 100%（22 列）：`id` `title` `source_url` `source_name` `crawl_date` `project_type` `construction_phase` `deaths` `injuries` `trapped_count` `collapse_subtype` `report_type` `text_type` `classification_verdict` `classification_confidence` `source_count` `raw_text` `search_performed` `pipeline_version` `step1_duration_ms` `step2_duration_ms` `created_at`

近满值（缺失仅在个位数，但**确实存在**，渲染须兜底）：

| 列 | 有值率 | 缺失 | 列 | 有值率 | 缺失 |
|---|---:|---:|---|---:|---:|
| `severity` | 99.96% | 1 空串 | `province` | 99.47% | 14 NULL |
| `direct_cause` | 99.89% | 3 空串 | `date` | 98.86% | 30 NULL |
| `summary` | 99.81% | 5 空串 | `city` | 96.07% | 103 NULL |
| `accident_type` | 99.77% | 6 空串 | `accident_location_detail` | 91.88% | 213 NULL |

> `severity` 的 1 条空串与 `accident_type` 的 6 条空串，正是第 2.2 节分布图里「空 1」与「空 6」的来源。注意它们与 `province` 的 14 条**不属同一类**：后者是真 NULL，前者是空字符串——**查询时 `IS NULL` 抓不到空串**，两个条件都得写。

**B 档 · 有则显示（60%–90%，7 列）**

`project_name` 89.25% · `work_task` 83.95% · `accident_time` 82.77% · `worker_type` 72.63% · **`publish_date` 65.42%**（907 条空串，位列本档末位） · `search_enriched_text` 62.37% · `district` 62.33%

**C 档 · 折叠（40%–60%，5 列）**

`material_involved` 55.85% · `contractor` 54.78% · `equipment_involved` 52.34% · `direct_economic_loss` 41.56% · `contractor_type` 40.56%

> `work_task_enum`（58.64%）原列本档，现按 1.0 残留列弃用，不再计入字段分档——当前口径的 `work_task` 在 B 档。见 §3.7。

**D 档 · 高级折叠（< 40%，5 列）**

`developer` 35.30% · `fall_height` 14.22% · `building_structure` 13.69% · `supervision_company` 10.22% · `weather` 7.93%

> **`deaths` / `injuries` / `trapped_count` 的口径**：三列均 `NOT NULL DEFAULT 0`，**有值率 100%，一条空缺都没有**。0 的含义是「原文未提及」（S3 的 prompt 规则为「未提及填 0，不编造」）。因此 `SUM(deaths) = 5,894` 是全部 2,623 条的完整总和，**不需要**「基于有记录的 N 条」这类限定。若需「有死亡记录」的口径，用 `deaths > 0`，实测 **2,280** 条（`injuries > 0` **1,227** 条，两者至少其一非零 **2,474** 条）。

> **`caics_causes` 的文本列也有空串**：`evidence` **8 条**、`inference` **11 条**（均无 NULL）。证据链展示时这两列都要做占位符兜底，不能假定有编码就有证据文本。

**过程审计列**（默认隐藏，可展开）：`report_type`、`text_type`、`classification_verdict`、`classification_confidence`、`source_count`、`search_performed`、`search_enriched_text`、`pipeline_version`、`step1_duration_ms`、`step2_duration_ms`、`raw_text`、`crawl_date`、`publish_date`、`created_at`

> `raw_text` 是原始正文，可能很长（上限 50,000 字符），**默认不随列表返回**，仅详情页按需取。

### 3.7 日期与枚举口径

- `date` / `publish_date`：`'YYYY-MM-DD'` 字符串 → 按年份/月份筛选可直接用 `substr(date,1,4)` / `substr(date,6,2)`，也可 `BETWEEN`
- `crawl_date` / `created_at`：ISO 时间戳 `'2026-07-14T06:42:56'`
- 枚举字段（`work_task` / `equipment_involved` / `material_involved` / `worker_type` / `building_structure`）存的是**编码**（如 `WT06` / `EQP01` / `WKR01`），**中文名要查 `enum_definitions` 表**（57 行，含 `enum_type` / `code` / `name` / `definition` / `version` / `parent_code` / `is_active`）

> ⚠️ **`work_task_enum` 不是可用的枚举列，已裁决弃用**（2026-09-30）
>
> `accidents` 表确实同存两列，但它们不是「同一体系的两种写法」，而是**两套编码体系**：
>
> | 列 | 有值 | 取值 | 与 `enum_definitions` 的关系 |
> |---|---|---|---|
> | `work_task` | 2,202 | `WT01`–`WT10` + `WT99` | **11 条逐项吻合**（`sample_count` 与该列的分布一致） |
> | `work_task_enum` | 1,538 | 含 `WT11`–`WT15` | 其中 **703 条编码在枚举表里根本不存在** |
>
> 两列同时有值的有 1,538 条，其中 **1,392 条互相矛盾**。
>
> 裁决依据是 `pipeline_metadata.work_task_enum_version`（迁移日期 2026-07-28）：`total_categories=11`、`key_merges` 含 `"WT11+WT14→WT05"`、`new_category` 为 `WT10 辅助作业与场内运输`。即 2.0-llm 迁移把旧编码合并进新体系后，**产物写在 `work_task` 列**；`work_task_enum` 是 1.0 旧体系的残留。
>
> **陷阱**：该元数据的 key 名是 `work_task_enum_version`，指的是「work_task 枚举的版本」，**并不指 `work_task_enum` 这一列**。照 key 名去取列，恰好会取到旧值——这正是它容易被误用的原因。展示与并入一律只用 `work_task`。

## 四、API 基座规范

所有模块共用的约定，蓝图 01–06 只声明各自的业务端点。

### 4.1 响应顶层约定

**先说实话**：顶层形状**不统一**——23 个 GET 实测下来只有 7 个是教科书式的
`{ok, data}`。蓝图初稿写的是「统一结构 + 两条例外」，与实现不符；实现走的是另
一条路，而那条路更清楚。本节按实现重述，不再声称统一。

| 形状 | 个数 | 用在 | 例 |
|---|---:|---|---|
| `{ok, data}` | 7 | 结果就是全部内容 | `framework`、`images/stats`、`timeline`、`extract/pending` |
| `ok` + 平级元信息 + `data` | 11 | 结果之外还有可用性 / 本页范围 / 计数 / 标签表要说 | `collect/raw`（`available`+`meta`）、`causes/distribution`（`scope`+`filter`）、`review/queue`（`counts`+`by_warning`+`labels`） |
| 无 `ok`，统计块直接铺顶层 | 4 | 整页一次取全的大盘 | `overview`、`accidents`（`{items, meta}`）、`filters`、`province/audit` |
| `ok` + 诊断键，无 `data` | 1 | 健康检查 | `health` |

共用的是下面三条，**不是外壳形状**：

1. **能有 `ok` 就给 `ok`**。四个大盘接口不给：它们的顶层本来就是一组统计块，
   插个 `ok` 只是噪音。
2. **「这块数据没准备好」一律用 `available: false` 表达**，不报错、也不给空壳
   数据。采集 / 提取 / 审核三组的接口在工作库未建时都走这条。
3. **`data` 只装「这一次查询的结果」**；可用性、筛选回显、分页、计数、标签字典、
   提示语一律平铺在 `ok` 平级。塞进 `data` 会让前端分不清「是结果还是元信息」。

**失败响应——这里是真的没统一**（实测，三处各有一个毛病）：

| 模块 | 实测响应体 | 毛病 |
|---|---|---|
| 展示 | `{ "error": "accident_not_found", "message": "事故 x 不存在" }` | 不给 `ok` |
| 采集 | `{ "ok": false, "error": "raw_not_found", "message": "…" }` | —— |
| 审核 | `{ "ok": false, "message": "找不到这条暂存记录" }` | 少数分支不给 `error` 码 |

> 这三种形状**故意不画成 json 块**：`check_api_contract.py` 把「接口标题下的 json
> 块」当成**那一个**接口的响应样例，而这里是三个接口各一条，画成块会变成
> 「归属不明」挨一记警告。表格里的行内 code 不参与归属判定。

三处不一致各记一笔：① 展示模块不给 `ok`；② 审核模块少数分支不给 `error` 码；
③ 蓝图初稿把 `error` 画成对象 `{"code":…, "message":…}`——**实现里 `error` 一直是
字符串码**，`message` 另给。**新增端点按第二种写**（`ok` + `error` 码 + `message`），
它是多数派。

**没有全局 `errorhandler`**：只有 `DatabaseNotFoundError` 被单独接管（503 + JSON）。
所以打到不存在的路由（`/api/nope`）拿到的是 **Flask 默认 HTML 404 页**，不是
JSON——蓝图初稿写的「任何异常都以 JSON 返回」目前**不成立**。列在 §八 待决项。

> `scripts/check_api_contract.py` 逐字段核对文档样例与真实响应；它比的是**键名**，
> **比不出层级归属**——把 `data` 里的键平铺写，脚本照样判「文档写了」。本节这张
> 表是靠人核出来的，脚本护不住。

### 4.2 分页与筛选一律下推 SQL

旧版反例（不得重演）：
- `db.get_all()` 无缓存调用 10 次，每次都全量物化 2,623 条
- `/api/dataset` 一次吐 **21.5 MB**
- `dataset.html` 前端逐条 `JSON.stringify(r).toLowerCase().includes(q)` 搜索
- 仅两处分页，且在内存里 `per_page=20` 切片

新规范：
- 列表端点必须接受 `page` / `size`（默认 1 / 50，上限 200）
- 筛选条件拼成 `WHERE` 子句，`LIMIT/OFFSET` 由 SQL 执行
- 总数用独立的 `COUNT(*)` 查询
- 关键词搜索用 `LIKE`，必要时接 SQLite FTS5（**待决项**，2,623 条规模下 `LIKE` 足够）

### 4.3 参数与降级

- 所有筛选参数可选，缺省即不过滤；非法值（如 `page=abc`）降级为默认值而非报错
- 空值统一：DB 的 `NULL` 在出参中保持 `null`，**由前端负责显示兜底**（旧 `dataset.html` 的教训：模板里 `{{ r.location[:10] }}` 遇到 `None` 直接 500，而同一份数据的 JS 重渲染路径却有 `|| ''` 兜底——**统一在服务端出口做空值规范化，模板侧一律用 `|default('-', true)`**）

### 4.4 静态资源

`web/static/` 实测为空。新方案把内联样式外置到此目录（`app.css` / `app.js` / 图表库），好处是三页共用、可缓存、可统一 token。**不引 CDN**，保证离线可用。

### 4.5 `GET /api/health`（库连通性与结构自检）

启动时打开一次即可确认环境配置正确，也是排查「页面全空」的第一站。返回三样：

- `db_path` —— 实际解析到的库文件路径。库路径由环境变量 `CAIEMS_DB` 决定，
  不确认这一项就无法排除「读错了库」。库文件不存在时返回 **503** 并附上
  `CAIEMS_DB=/…/data/caiems_v2.db` 的示例
- `counts` —— 每张表的行数（`SELECT COUNT(*)`），一眼看出表在不在、是不是空壳
- `indexes` + `missing` —— 展示层最依赖的三个索引 `idx_cause_acc` /
  `idx_acc_province` / `idx_acc_date`。缺了**不报错**（索引是性能问题不是可用性
  问题），但列表页会慢两个数量级：实测 `has_causes` 筛选 **1.8 ms → 3,541 ms**

三个索引的建法见 §3.3。

## 五、管线统一方案（阻塞项，对应任务 #33）

### 5.1 问题

| | 产出主库数据 | 项目正式入口 |
|---|---|---|

### 5.2 处置

3. **`DatasetManager`（JSON 版）退出生产路径** —— 注意 `web/app.py` 与 `scripts/` 中多个脚本仍在用它。
4. 每个入口切换后**必须跑通一条端到端样本**，比对产出与主库现有记录的字段结构。

### 5.3 保护清单（不可动）
