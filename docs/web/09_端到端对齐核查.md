# 端到端对齐核查（2026-10-01）

> 落实蓝图 07 的验收项「端到端对齐检查」，以及项目硬性要求**每个 web 部分要实现端到端的完美对齐**。
> 复跑：`.venv/bin/python3 scripts/check_web_alignment.py` —— 退出码 `0` = 完全对齐，`1` = 有缺口（可直接接进 CI）。

## 一、查什么

「对齐」落到代码上是两件不能有的事：

| 缺口 | 形态 | 后果 |
|---|---|---|
| **孤儿端点** | 后端实现了、前端从不调用 | 数据层有、展示层缺。功能上「有」，用户够不到 |
| **幽灵调用** | 前端在请求、后端没有这条路由 | 点下去就是 404 |

核查范围是四个 API 蓝图（`api` / `collect` / `extract` / `review`）的全部路由，与
`static/*.js`、`templates/*.html` 里全部 `/api/...` 调用点。

## 二、判据：为什么第一版是错的

第一版脚本用的是**静态段顺序查找**——把路由的静态段按序在前端源码里找，
段落在别处偶然出现过就算「有调用」。它给 42 条路由报了 **0 条孤儿**。

这个结论是假的。`/start`、`/cancel`、`/rerun` 这几个后缀在前端源码里到处都是
（按钮文字「取消」、状态映射 `cancelling: '取消中'`、`// 启动` 注释、模板里的
`id="rerunBtn"`），判据只看「字符串出现过」，自然全部命中。真有一条孤儿，
是手工 grep 调用路径才挖出来的。

改用**路径形状匹配**：把两侧的变量段与 query string 都归一成 `<>`，再做集合运算。
难点在前端拼接——`'/api/extract/tasks/' + t.task_id + '/start'` 在源码里是三个字面量
夹两个表达式，所以从 `/api` 那串起贪心地吃后续的 `+ expr + '...'` 片段。

两个起初踩到的坑，一并记下来免得重蹈：

1. **蓝图前缀**：装饰器里写的是蓝图内相对路径（`/tasks`），完整路径要加上
   `Blueprint(url_prefix=...)` 的前缀（`/api/collect/tasks`）。漏了这步，
   41 条路由会全部对不上，报出一大片假孤儿。
2. **正则捕获的是 `api_bp` 不是 `api`**：前缀映射的键必须带 `_bp` 后缀。

## 三、结果

```
后端 API 路由 41 条（36 种路径形状）
前端调用点   44 处（36 种路径形状）

✓ 后端每条路由都有前端调用点
✓ 前端每个调用点都有后端路由

两侧完全对齐。
```

44 > 41 是正常的：同一端点被多处调用（如 `/api/health` 在 3 处），且部分调用
共享同一路径形状（query 参数不同）。

## 四、处理掉的那一条孤儿

`GET /api/accidents/<id>/images`（原 `api.py:80`）— **已删除**。

它是**真孤儿**：前端 0 个调用方，详情接口已经内联了 `images` 数组。删它有两条依据：

1. **它自己的定位不成立**。蓝图 06 §4 写的是「既然详情接口已返回 `images` 数组，
   此端点供画廊单独刷新或分页使用」——「刷新」靠 F5 就能做到，「分页」则被数据
   否掉：实测单事故最多 **7 张**，≥10 张的 **0 个**（559 个有图事故的完整分布见
   `check_web_alignment.py` 同期的 `img_dist` 查询）。
2. **它的实际成本是双份逻辑**。这段取数（取清单 → 取可疑哈希 → 逐条打 `shared`
   标记）在 `api.py` 与 `detail.py` 里是**逐字重复**的两份，一旦漂移，同一事故经
   两条路拿到的标记就不一样。

取数已收敛到单一出口 `images.for_accident_marked()`，`detail.py` 改调它，测试的
5 处断言改走**详情接口**——测的正是前端真正走的那条路。

顺带清掉的过时内容：

- `api.py` 里 `GET /api/images/stats` 的 docstring 还写着「覆盖率只有 7.4%」（单版口径），
  已改为三版合并口径 21.3% 并说明 `accidents_with_images_legacy_only` 的含义
- `detail.py` 的注释还在说「`image_files` 的 `local_path` 三版混存，按它拼 URL 会大面积
  404」——这条论断已被 08 的复核推翻，改为「旧登记与磁盘真源差 123 张 / 83 个事故」

## 五、顺带发现的第二类不对齐：数据口径落后于代码

核查路由时发现工作库的 `image_manifest` 停在**旧口径**：226 行 / 193 事故，
版本分布只有 `v3`。

代码已经把取材范围放开到三版，库里却还是单版——**代码对了、数据没跟上**，
这同样是端到端断裂：页面上会照常显示图片，只是少了 725 张、少了 366 个有图事故，
而且不报任何错。

重建后的实际值与代码口径一致：

| | 旧（库内） | 新（重建后） |
|---|---|---|
| 行数 | 226 | **951** |
| 有图事故 | 193 | **559** |
| 版本分布 | v3: 226 | **v1: 263 / v2: 462 / v3: 226** |
| 内容非图片被剔除 | — | **2**（`imageV2/` 下两个 `.webp`，内容是 HTML 与 MP4） |

重建命令（图片在主仓库、工作库在 worktree，所以要显式给 `--data-dir`）：

```bash
/home/suntianhao/construction_agent/.venv/bin/python3 scripts/build_image_manifest.py \
  --data-dir /home/suntianhao/construction_agent/data \
  --report /tmp/img_report.json
```

> 不加 `--data-dir` 时脚本会用 worktree 自己的 `data/`，那里**没有图片目录**
> （`.gitignore` 忽略了），结果会是「扫描到 0 张」——不是数据没了，是找错了地方。

## 六、已知未覆盖的对齐维度

本次核查只覆盖**路由 ↔ 调用**这一个维度。以下维度尚未做机器化核查，属于后续工作：

- **字段级**：接口返回的字段名与前端读取的属性名是否一一对应（前端有 `|| ''` 兜底，
  拼错的字段不会报错，只会静默显示为空）
- **页面可达性**：四个页面之间是否有导航路径，有无孤立页面
- **蓝图 ↔ 实现**：文档里描述的接口与实际注册的路由是否一致（本次已顺手修掉
  蓝图 06 §4 的 `/media` 描述与 `accidents/<id>/images` 小节）
