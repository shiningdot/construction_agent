## 一、查什么

「对齐」落到代码上有四件不能有的事，**本节脚本**（`check_web_alignment.py`）覆盖
其中前两个维度。渲染、字段名、交互三个维度各有自己的脚本，见 §六 / §七 / §八。

**路由维度**（静态分析，不需要数据库）

| 缺口 | 形态 | 后果 |
|---|---|---|
| **孤儿端点** | 后端实现了、前端从不调用 | 数据层有、展示层缺。功能上「有」，用户够不到 |
| **幽灵调用** | 前端在请求、后端没有这条路由 | 点下去就是 404 |

核查范围是四个 API 蓝图（`api` / `collect` / `extract` / `review`）的全部路由，与
`static/*.js`、`templates/*.html` 里全部 `/api/...` 调用点。

**页面维度**（起 app 打真实请求）

| 缺口 | 形态 | 后果 |
|---|---|---|
| **打不开的页面** | 路由在、请求报 500 | 蓝图 07 验收第 1 条直接不过 |
| **没有入口的页面** | 能打开，但从任何页面都点不到 | 只能手敲 URL 进，等于不存在 |

## 二、判据：为什么第一版是错的

第一版脚本用的是**静态段顺序查找**——把路由的静态段按序在前端源码里找，
段落在别处偶然出现过就算「有调用」。它给 42 条路由报了 **0 条孤儿**。

这个结论是假的。`/start`、`/cancel`、`/rerun` 这几个后缀在前端源码里到处都是
（按钮文字「取消」、状态映射 `cancelling: '取消中'`、`// 启动` 注释、模板里的
`id="rerunBtn"`），判据只看「字符串出现过」，自然全部命中。真有一条孤儿，
是手工 grep 调用路径才挖出来的。

改用**路径形状匹配**：把两侧的变量段与 query string 都归一成 `<>`，再做集合运算。
难点在前端拼接——`'/api/extract/tasks/' + t.task_id + '/start'` 在源码里是三个字面量
夹两个表达式，所以从 `/api` 那串起贪心地吃后续的 `+ expr + '...'` 片段。

两个起初踩到的坑，一并记下来免得重蹈：

1. **蓝图前缀**：装饰器里写的是蓝图内相对路径（`/tasks`），完整路径要加上
   `Blueprint(url_prefix=...)` 的前缀（`/api/collect/tasks`）。漏了这步，
   41 条路由会全部对不上，报出一大片假孤儿。
2. **正则捕获的是 `api_bp` 不是 `api`**：前缀映射的键必须带 `_bp` 后缀。

1. **导航不在源码里**。导航写的是 `url_for('views.xxx_page')`，`templates/` 与
   `static/` 里没有 `/collect` 这样的字面量——拿字面量去源码里找，6 个页面的
   入口数全是 0。只能起 app、打真实请求、解析**渲染后**的 HTML。
2. **入口要算两路**。列表页的详情链接是 JS 拼的（`overview.js:470`
   `href: '/accident/' + encodeURIComponent(it.id)`），服务端 HTML 里没有。
   只数渲染后 HTML 的 href，详情页会被误判成「谁也链不到」——它其实正是唯一
   那个叶子页，1 个入口恰恰说明结构是对的。所以入口 = 渲染后 href ∪ 该页加载的
   JS 里的路径字面量。

## 四、处理掉的那一条孤儿

`GET /api/accidents/<id>/images`（原 `api.py:80`）— **已删除**。

1. **它自己的定位不成立**。蓝图 06 §4 写的是「既然详情接口已返回 `images` 数组，

## 七、字段级：前端读的名字 ↔ 后端返回的字段

到这里还剩一类错配看不见：**后端返回 `death_count`、前端读 `deaths`**。页面不
报错、控制台干净、数字对账也全对，只是那一格永远显示「—」。出错的不是值，是
**名字**。

`scripts/check_field_alignment.py` 把两侧的名字对账：起 app 打真实请求，把 JSON
递归展平成字段路径；再读 `static/*.js` 与 `templates/*.html`，抽出全部 `.属性`
读取。前端读的每个名字落到四层之一就放过：

| 层 | 个数 | 是什么 |
|---|---|---|
| 后端运行时返回过 | 117 | 名字确实在 JSON 里——最强证据 |
| JS/DOM 白名单 | 24 | `.length`、`.classList`、`.dataset`，以及 `dom.js` 导出的 `el` / `num` / `blank` |
| 前端自己构造 | 4 | `on` / `accent` / `color` / `dev_pct`，每个都在代码里注明了出处 |
| 后端源码里出现过 | 126 | 兜底：库空时端点上没有元素可展 |

264 个读取全部有归属，**未归类 0 个**。

### 7.1 判据是怎么定下来的

第一版把 JSON 展开成字段路径、与前端 `.属性` 直接做差集，报了 156 个候选，绝大
多数是噪音——前端内部工具函数的属性（`add` / `clear` / `createElement`）跟后端
字段名混在一起。这次逐个查清了两类假信号：

1. **注释里的文件名**。`/* … overview.js 里还有一份… */` 会被当成 `.js` 属性读取。
   先剥注释。
2. **赋全局那几行**。`global.num = num` 里的 `.num` 是**定义**，不是读取。排除
   「点号后面跟单个等号」的位置（`==` 不算，那是比较）。

修完这两处，候选从 156 降到 4，而那 4 个也都查清了：`on` / `accent` / `color` 是
前端配置对象的键（`opts.on` 是事件表、`c.accent` 决定要不要加样式、`cfg.color(r)`
是取色回调），`dev_pct` 是 `usage()` 给后端的 `deviation_pct` 起的别名——查过后端
`extract.py:207`，那个字段确实返回，链路是通的。

同一批里还验过一次**反向**的：`/api/extract/tasks` 返回的 `usage` 对象，前端读
`tokens` / `est_tokens_so_far` / `deviation_pct` 三个名字，后端的 `extract.py:202-208`
逐个对得上。这类字段最容易在改名时单边漂移——后端改了 `deviation_pct`，前端还读
旧名，两边都不报错。

### 7.2 这一维的边界

**没被兜住的部分**：18 个端点的数组是空的，元素字段核不到。脚本会把它们连同空
数组的位置一起打出来，例如：

```
/api/review/queue            data
/api/collect/tasks           data
/api/accidents/<id>          data.images
/api/collect/stats           data.by_source data.funnel
```

这些字段能过四层里的一层，**是因为别处见过，不是因为在元素上核过**。这与 §五 的
空工作库是同一条边界：采集 / 提取 / 审核三组的表是 0 行，只在这三处出现的字段，
静态判据认不出、运行时也展不出。第 45 项全链路验证（起真实任务跑一遍）覆盖的正是
这一段，但那次是一次性的，没有固化成可复跑脚本——**库里灌了数据后重跑本脚本才算数**。

### 7.3 同一条脚本的反方向：`accidents` 的列 ↔ 详情页四档

上面这一半只查「前端读了什么」。缺口还有另一种形态，它天生查不出来：**后端表里
有值、页面上从未出现**。前端不会去读一个后端没下发的名字——它读不出来，也就永远
不会出现在「前端读取」那个集合里。7.1 里那套判据再准也看不见它。

所以同一条脚本又做了一件事：把 `accidents` 的**每一列**拿去对
`detail.CONTENT_TIERS` ∪ `META_FIELDS`，两边都不在的必须进 `DETAIL_NOT_SHOWN`
并写明理由（目前两项：`raw_text` 在响应顶层单独下发、`work_task_enum` 是 1.0 残留列）。

一查就查出三列：

```
── 不在任何档里：5 列 ──
  project_type               有值  2623 / 2623
  construction_phase         有值  2623 / 2623
  collapse_subtype           有值  2623 / 2623   ← 其中 1320 行是哨兵「不适用」
  raw_text                   有值  2623 / 2623   （单独下发，前端读了 ✓）
  work_task_enum             有值  1538 / 2623   （1.0 残留列，有意排除 ✓）
```

`project_type`（工程类型）与 `construction_phase`（施工阶段）**有值率 100%**、
在 `accidents` 里排第 7/8 位，列表页有「工程类型」列、概览页有这两维筛选，**唯独
详情页看不到**。`collapse_subtype` 同理。

**根因在文档，不在代码**：蓝图 05 §2.1 的分档表只列了 43 个列名，而顶层标题写着
「48 列实测分档」——五列的去向没人交代（其中两列还是 100% 有值的核心分类）。实现
忠实照抄表格，缺口就从文档进了代码。这与 §8.2 是同一种病：**蓝图里的表格比声称
的范围少了几项，实现照着表格做，文档的漏项变成了代码的漏项**。

三列的处置：前两列进 A 档（与 `accident_type` 同类），`collapse_subtype` 进 C 档。
后者还带出一个数据侧的问题——`step1_basic_extractor.py` 给「仅某类事故才填」的
字段约定了一个字面量**「不适用」**做哨兵（「仅坍塌/土方坍塌类填写，非坍塌类填
'不适用'」）。列里 2,623 行全部非空，但 **1,320 行就是这个哨兵**。不归一的话，
1,320 条非坍塌事故会各显示一行「坍塌子类：不适用」，C 档的 `available` 也会被顶成
满值。`detail.py` 读它时归一成缺失，真实有值 1,303 / 49.68%。

**这条判据反向验证过**：在内存里把 `project_type` 从 A 档挖掉，脚本报
`['project_type']`；再挖 `collapse_subtype`，报两列。挖一列报一列，不是恒过。

**这一维的边界**：它只认 `accidents` 的列，`caics_causes` / `enum_definitions` 等
其余八张表不查——那几张表的值进页面要走聚合与查表，列名与展示名不是一对一，
「没展示」与「不该展示」分不开。另外它判的是**列有没有归宿**，不判**归宿对不对**：
`trapped_count` 进 D 档而它有值率 100%（值几乎全是 0），档位是否合适由 §2.1 的分档
理由说了算，脚本管不着。

## 八、交互：点下去之后页面对不对

前四个维度验的全是**首屏**——路由通不通、页面开不开、渲染坏没坏、名字对不对。
用户在页面上做的事——勾筛选、翻页、粘贴链接、重置——一层都没验过。接口对账
（`e2e_verify_main.py` 那 45 项）验的是 API 层，也管不到「按钮绑没绑上」。

`scripts/check_web_interaction.py` 用无头浏览器真点一遍，看**页面自己说的话**
跟**点完之后的结果**对不对得上。十七条：

| 断言 | 观察到的 |
|---|---|
| 初始加载 | 分页器有总数，且是多页 |
| **概览页维度齐全** | chips 的 `data-key` 集合 == `/api/filters` 的五维（见 8.3） |
| **致因页维度齐全** | 同一判据，同一份 `/api/filters` |

| 列表真的只剩该省 | 首行确属该省 |
| 再点一次取消 | 总数回到初始，hash 里 `province` 已清空 |
| 翻到第 2 页 | 页码变了、首行换了、总数不变 |
| 粘贴链接能复原 | 新开页与当前页首行一致、chip 无残留选中 |
| **过期链接自愈** | 过期的省份值被清掉，列表回到全部 |
| 关键词搜索 | 总数变小，且首行标题确实含该词 |
| 重置 | 回到初始总数与首行 |
| **详情页折叠能真点开**（§8.4） | 12 个折叠逐个真点：开合翻转、文字量两头都对 |

**断言为什么能自洽、不写死数字**：概览页每个 chip 的 `title` 里就写着
「辽宁省：137 条」——那是后端 `/api/filters` 算的计数。点下去之后分页器的
「共 N 条」应当**等于**它。两个数出自不同代码路径（筛选器计数 vs 列表查询），
相等才算对齐。所以脚本里没有 `2623` 这种常量，数据变了照样跑。

### 8.1 途中挖出的缺口：`meta.filters` 回显的是假话

第 9 条「过期链接自愈」是在前八条之后补的，起因是实测：

```
GET /api/accidents?province=北京        （库里只有「北京市」，没有「北京」）
  → total = 2,623     全部条数，没筛
  → meta.filters.province = ["北京"]    声称筛了
```

`province.filter_clause` 对未识别的键是**静默忽略**的（刻意的：前端传了过期的
键不该让页面崩），但 `ListParams.normalized()` 把传入值原样回显。于是响应一半
在说「我按北京筛了」、另一半返回全部——前端拿到的是假话，也无从知道筛选没生效。

修法是**一份判断的两半**，放在同一个文件里共用 `raw_values`，避免分头实现漂移：

- 后端 `province.effective_keys()`（`province.py`）——回答「最后到底筛了什么」，
  `normalized()` 改用它。空值桶 `__empty__` 总生效（它筛的是 `IS NULL OR
  TRIM = ''`，与库里有几条无关，`raw_values` 对它返回空列表，不能拿它当判据）。
- 前端 `pruneUnknown()`（`overview.js`）——拿到 `/api/filters` 后，把 state 里
  库中已不存在的值摘掉、`writeHash()` 重写 URL、重查列表。用户看到的是自洽的
  状态，而不是「URL 说筛了、列表却是全部」。

其余多值字段（`severity` / `accident_type` …）不需要这一步：它们直接进
`IN (...)`，未知值筛出 0 条——条件确实生效了，回显原值是对的。

配套测试三条（`tests/test_web_m1.py`）：剔除库外省份、空值桶总生效、以及
**「生效键与过滤条件不漂」**——对五种键组合断言
`bool(filter_clause(keys)[0]) == bool(effective_keys(keys))`。这条是防漂移的锁：
两半各自演化时，它先红。

### 8.2 后端给了五维筛选，概览页只画了三维

这一轮做界面审美核查（截图探针只能看出「破图 / 空白 / 报错」，看不出「少了一组筛选」）
时，对着致因页的筛选区读数，读到两件事：

**第一件：标签串了维度。** 致因页把 `construction_phase` 标成「**施工工序**」，值却是
地基与基础 / 主体结构 / 装饰装修 / 拆除——那是**施工阶段**。`step1_basic_extractor.py`
里这个字段的描述原文就写着「或**施工阶段**(主体结构/装饰装修)」。而真正的「施工工序」
在库里是另一列：`work_task`（WT01–WT99，施工作业类型 11 类 LLM 枚举，蓝图 05 §57 定名
「**作业任务**」）。两个独立维度撞了同一个中文名，且取值还有个刻意的近似
（「主体结构」vs「主体结构工程」），串了名读起来完全通顺。

实测坐实了这一点：致因页筛选区的计数（主体结构 1,064 / 装饰装修 363 / 地基与基础 290）
与 `construction_phase` 分组**逐项一致**，而 `work_task` 分组（WT02 主体结构 397）对不上。

三处标签原本各叫各的：

| 文件 | 字段 | 原名 | 改后 | 依据 |
|---|---|---|---|---|
| `causes.js` | `construction_phase` | 施工工序 | **施工阶段** | `step1` 字段描述、`review.js` 已用此名 |
| `accident.js` | `work_task` | 施工工序 | **作业任务** | 蓝图 05 §57、`review.js` 已用此名 |
| `review.js` | 两个 | 施工阶段 / 作业任务 | 不动 | 本来就对 |

蓝图 04 §256 的筛选条线框里也写着「[工序▾]」——误名是从蓝图抄进代码的，一并更正为
「[施工阶段▾]」，并在 04 §4.2 写明两个维度不得互串。

**第二件是个更大的缺口：`/api/filters` 返回五维，概览页只渲染三维。** 后端给的
`province` / `severity` / `accident_type` / `project_type` / `construction_phase` 里，
`overview.js` 的 `MULTI_KEYS` 只列了前三个，`renderFilters()` 里还**另外字面重写了一遍**
同一个三元数组——`project_type`（工程类型）与 `construction_phase`（施工阶段）的值就
在接口里躺着，用户筛不到。而蓝图的筛选条线框（§256）明确画了「[工程类型▾]」。

这类缺口**没有任何症状**：不报错、不空白、控制台干净。原先的交互核查也测不出来，
因为 `check_web_interaction.py` 用 `#filterChips label.chip` 的 `.first` 定位——永远打
第一组，chips 区有几组它根本不知道。

修法与防复发：

1. `renderFilters()` 里那句字面副本删掉，直接用 `MULTI_KEYS`（原先是两处各写一遍，
   改一处漏一处）。
2. chips 容器加 `data-key` 属性，让核查脚本能**按维度**取集合而不是按位置。
3. 交互核查加两条断言（概览页 + 致因页）：`chips 的 data-key 集合 == /api/filters
   里非空列表键的集合`。两页共用一套判据函数，避免各写一遍再漂移。
4. **反向验证过**：把 `MULTI_KEYS` 临时改回三维，脚本如期报
   「后端给了 [...] 这几维可筛，页面只画了 [...]」并以退出码 1 结束——不是一条
   恒真的假断言。

### 8.3 这一维的边界

- **本脚本只覆盖概览页**。中段三页另有脚本，而且是自带数据的：

  | 页面 | 第三层（headless 真点击） |
  |---|---|
  | 提取页 | `scripts/e2e/e2e_click_m3.py`——从勾选到成本弹层到抽屉证据链 |
  | 审核页 | `scripts/e2e/e2e_click_review.py`——专验三处「前端先行拦截 + 后端兜底」的前半 |
  | 采集页 | `scripts/e2e/e2e_click_collect.py`——13 段，勾源 → 任务自己走完 → 表格自己刷出 → 裁决 → 筛选 → 翻页 |

  三页都造假采集器 / 假 pipeline，但落库、闸门、幂等、进度回填全是真的，库是临时库。
  所以此前记的「中段三页交互待数据具备」是**错的**——**能自己造出的条件，不该记成
  待办**。采集页这个脚本补齐后，三页的第三层齐了。
- **不做视觉回归**。断言的是文本与计数，不比对像素；样式改坏了这十七条不会响。
- **维度齐全只在概览页与致因页有断言**。中段三页（采集 / 提取 / 审核）的筛选是另一套
  形状，没有 `/api/filters` 那种「可选值接口」可比，这条判据套不上。
- **时序靠 `wait_for_timeout`**。900–1500ms 的等待在慢机器上可能不够——失败时
  先怀疑这里，再怀疑功能。
- **端口要各占一个**（约定见 `scripts/e2e/README.md`）。本脚本默认 **5100**，
  第一版写的是 5098——那个端口是「主库对账」的，两套脚本同时跑会撞。

### 8.4 详情页的真实点击（2026-10-05 补，四条）

前十一条**全在列表页**，详情页一条没有。§2.5.68 补折叠时用的是

```js
page.evaluate("() => document.querySelectorAll('details').forEach(d => d.open = true)")
```

——**程序式给 DOM 赋值**，跳过了「click 事件 → 浏览器默认行为」这条真实链路。两者
**不等价**：页面上一旦有 JS 在 `summary` 上 `preventDefault()`，程序式照样把 `open`
置上、那条判据照样报绿，而用户怎么点都展不开。§2.5.69 用注入实测了这张表：

| 方式 | 注入前 | 注入 `preventDefault` 后 |
|---|---|---|
| 真点 `locator.click()` | 开了 | **没开** ← 用户遇到的就是这个 |
| `d.open = true` | 开了 | **照样开** ← 上一版那条判据的处境 |

所以后四条一律走 `locator.click()`：**折叠真点**（12 个逐个，开合翻转 + 文字量两头
都对）、**「展开全文」按钮**（三点闭合：点前字数 + 按钮自称还剩的 == 接口全文 ==
点后字数）、**图片灯箱**（点开 / 下一张 / Esc，外加 `aria-hidden` 跟着翻）、
**列表→详情→返回**（真实导航链）。

**样本是两条，不是一条**：`raw_text` 超 5,000 字的 13 条图数**全是 0**（都是文献轨），
而图最多的那条正文只有 512 字——「展开全文按钮」与「图片灯箱」在库里**没有任何一条
记录能同时触发**。分别挑（`pick_samples()` 查库选，不写死 id）。

**两处坑**：①灯箱是**懒建**的（`open()` 里才 `build()`），进页面时 DOM 里根本没有
`.lightbox`，第一版把「点击前不存在」当成断言，报了一次假红；②`inner_text()` 对
**不可见**元素返回**空串**，「展开全文」按钮在闭合的 `<details>` 里，读它的文案必须用
`text_content()`。

### 8.5 键盘路径：鼠标点得开不等于键盘打得开（2026-10-05 补，两条）

第 12–15 条虽然走的是真事件，但走的是**鼠标**事件链；键盘走「focus + keydown →
浏览器激活语义」。两条链各有各的断法、且**互为盲区**：

| 断法 | 鼠标 | 键盘 | 只有点击的判据看得见吗 |
|---|---|---|---|
| 捕获阶段吃掉 `keydown` 的 JS | 照常 | Enter 失效 | 看不见 |
| 按钮被移出 Tab 序（`tabindex="-1"`） | 照常 | 真实 Tab 到不了 | 看不见 |
| 声明 `aria-modal` 却不做焦点陷阱 | 照常 | 焦点跑到背景上 | 看不见 |

第三种是**实测到的真缺陷**（`accident.js` 的灯箱）：`role="dialog"` +
`aria-modal="true"` 写得齐全，静态读代码读不出问题，实跑 Tab **一次**就从
`.lb-next` → `<body>` → 背景导航链接。屏幕阅读器会照着 `aria-modal` 把背景整个
隐藏掉，用户于是以为对话框已关、实际焦点在背景里。第二个缺陷是**关闭后焦点不归还**
（Esc 之后落在 `<body>`，键盘用户要从页首重新 Tab 一遍）。两处已修：`open()` 记
`lastFocus`、`close()` 带 `document.contains()` 守卫地归还，keydown 里加首尾循环的
Tab 陷阱（`focusables()` 用 `offsetParent !== null` 滤掉单图时 `display:none` 的
`prev`/`next`）。

**键盘路径本身没有缺陷**（实测）：Tab 遍历可达缩略图与折叠、`summary` 按 Enter/Space
真开合、闭合的 `<details>` 内部按规范不进 Tab 序、「展开全文」聚焦后按 Space 把
5000 字换成 43,124 字。

第 16 条的可达性**必须真实 Tab 遍历**，不能拿 `.focus()` 代替——那等于先假设"已经能到"
再去用。**两处坑**：①判据基准要取**前一次**状态而非初始值（`<details>` 能来回翻转，
拿初始值当基准时「Space 把 True 翻回 False」会被误判成"没翻转"）；②「按钮看不看得见」
要用 `is_visible()`，**不能用 `count()`**——按钮在 DOM 里一直都在（只是被闭合的
`<details>` 藏着），`count()` 恒为 1。两处都是**假红**，都是"选到了测不出这件事的那个
API"（与 8.4 的 `inner_text()` / `text_content()` 同族）。

**边界**：只测"焦点在不在灯箱内"，不测焦点顺序好不好；不管视觉焦点环
（`:focus-visible` 的对比度、可见性）；读屏软件本身不在射程内；`tabindex="-1"`
那格注入是**合成**的（今天源码里 `.img-tile` 就是普通 `<button>`）。

### 8.6 文字对比度：配色 token 从未按可访问性标准核过（2026-10-05 补）

§8.4/§8.5 把「够不够得着」（鼠标 / 键盘）补齐了，但那是**第三个**问题。同一族的
第四个问题一直没人问：**看不看得清**。前三层全绿而这一层是红的，用户照样读不出来
——而且它比前三层更容易机器化，WCAG 2.1 的 1.4.3 给了明确数值（正文 ≥ 4.5:1、
大字 ≥ 3:1），不需要人"看着办"。

`scripts/check_contrast_a11y.py`：起真服务、无头 Chromium 逐页取**每个有文本的
元素**的 computed `color` 与实际背景色（向上找第一个不透明祖先），按 WCAG 公式算
比值。**首次跑：六个页面 1,869 处可见文字里 757 处（40.5%）不达标**，最低 1.96。

归并后 61 种形态，根子在 **8 个 `:root` token**——`--muted`（`#8A827A`，在三种底色
上分别只有 3.78 / 3.56 / 3.39，撑起绝大部分）、`--sev-3`（**2.91，最差，而它是
「较大事故」等级徽章**）、`--ev-weak`（2.65）、`--layer-T`（3.68）、`--sev-4`（3.80）、
`--sev-2`（4.08）、`--brand`（4.37）、`--layer-C`（4.40）。处置：**只改 `:root` 那
一段的 8 个色号**（沿 HSL 的 L 轴压暗，色相饱和度不动），不动任何规则、任何组件
——重跑 **757 → 0**。

**两处方法论**：①**贴边取值等于没改**——求解器给出 `--brand: #0D7A69`（标称 4.50），
浏览器实测 **4.48**，HSL↔RGB 往返的舍入差把结果推到线下；改用留余量的 `#0D7867`
（4.60）。②**整棵子树的 `opacity` 必须折算**——否则 `.is-off { opacity: .45 }` 这类
整行压暗会漏报；折算公式 `eff_fg = mix(bg, fg, opacity)` **忽略"元素自身背景色也被
冲淡"这一层**，误差方向是高估对比度（偏保守）。C 段第二例注入 `opacity: .45` 就是
为这条判据存在的：删掉折算它会转绿。

**边界**：`opacity` 是近似（见上）；**背景只认不透明色**，半透明层与渐变、图片上的
文字不合成（六页各有 6 处背景链含半透明层，登记为已知近似）；半透明**文字**直接
跳过（实测六页均 0）；判据管不了"这个颜色好不好看"，达标是下限不是目标；只测无头
Chromium（容器内取不到 PingFang SC / 微软雅黑，回落字体与用户实际看到的不同）；
**色盲（1.4.1）与缩放（1.4.4）不在本节**——`--sev-*` 四色与 CAICS 五层色都同时带
文字标签，故不靠颜色单独传达信息，但这是**读代码得到的**、不是核过的。

**判据边界的一处特殊**：`.pager button:disabled`（「上一页」1.96）按 WCAG 1.4.3
明文豁免「非活动用户界面组件」。豁免取**结构性依据**（DOM 上真有 `disabled` /
`aria-disabled`）而非一张文字白名单——§2.5.67 的教训是白名单只写理由就永远不复核；
并加一条**后门判据**：断言被豁免的类名集合 ⊆ `{BUTTON}`，防"给任意元素加个
`aria-disabled` 就让它从判据里消失"。

细节见 01 §2.5.72。

## 九、蓝图 ↔ 实现：文档规定的接口，实现了吗

前面几维比的是**代码内部**两边（路由 ↔ 调用、名字 ↔ 字段）。这一维比的是
**文档 ↔ 代码**，问一个更靠前的问题：蓝图写下的接口规格，实现跟上了吗？实现了
的接口，写回蓝图了吗？

`scripts/check_blueprint_alignment.py` 对账两侧：蓝图（`docs/web/00`–`08`）里
的接口与 `construction_agent/web/*.py` 真正注册的路由。

### 9.1 判据：只有标题算「规定」

蓝图里出现 `/api/xxx` 有两种语义，混在一起判会立刻出错：

1. **接口设计章节的标题**（`### `GET /api/collect/sources``）——这是**规格**
2. **正文里的一笔带过**——可能是举的例子，也可能是**在说旧实现怎么错**。蓝图 02
   写「旧实现 `POST /api/process`（`web/app.py:326-350`）同步调用，40 秒的请求
   必然超时」，是在陈述**已废弃**的东西；蓝图 06 写「原有一个
   `GET /api/accidents/<id>/images`，2026-10-01 删除」，是在记录**删掉了什么**

把正文也算规定，这两条就会被报成幽灵接口——而它们恰恰是文档最该有的交代。所以
只取标题行；正文提及单独列出，并用否定词（删除 / 旧实现 / 原有 / 已废弃 / 移除 /
不再）把「对照提及」与「漏写」分开。

**踩过的坑**：第一版把每行 `[:90]` 截断后再存，`/api/process` 那行的「旧实现」
正好落在 90 字之外，否定词过滤看不见它，一条正常的对照提及被报成了缺口。改成
**存完整行、显示才截断**。

反向也要求为 0：实现了却没写进蓝图的端点，下一轮就可能被当成冗余删掉——蓝图是
后续会话唯一的施工依据。

第一版报幽灵 **0** 条、未写进蓝图 **6** 条。逐条读实现核实，**没有一条是实现

### 10.3 过程中修掉的两个「吞缺口」的 bug

这两处都是**判据写错**，会把真缺口咽下去，比不查还坏：

1. **`available` 用 `not v` 判**。`available` 这个名字在同一个响应里有两层意思：

   `images` 明明有 4 张图，却被标成「未判定」。改成 `v is False` 修好。
2. **多次采样用 `or` 合并**。`blocked = blocked or blocking_flag(body)` 让「五条
   里一条没数据」升级成「整个接口没数据」，于是真缺口不报。改成收集 `blocks`

人数）单条覆盖不全，会把它们误报成缺口。修好后打 5 条，93 个键名。

### 10.4 未判定为什么不算缺口

「未判定」有两种，都不该记成实现的问题：

- **整个接口展不开**：工作库未建，或本次响应的列表**全空**。空表时元素字段一个
  也展不出来，比下去全是假缺口
- **字段住在空数组里**：文档把 `token`、`backup_path` 画在 `promote_history` 里，
  而这次 `promote_history` 返回 `[]`。脚本把样例里的**数组键 → 数组内键名**解

  直接抛），再看该字段归属的数组**是不是全空**。只要有一个非空，元素结构就摆在
  那儿，照记硬缺口

第二条是本维度最费劲的一处：`/api/review/stats` 曾有 10 个字段被判硬缺口

## 十一、枚举取值：schema 注释声明的码 ↔ 前端标签表的键

### 11.1 缺口长什么样：页面上冒英文

工作库各表状态列的取值域写在 `staging_schema.py` 的列注释里：

```sql
status        TEXT NOT NULL,            -- pending|running|cancelling|done|failed|cancelled
```

前端另有一张「英文码 → 中文」的表把状态翻成「取消中」这类词。两侧一旦不同步，
症状是**页面上出现英文**——因为写法是 `TASK_LABEL[s] || s`（`collect.js:66`）。
这是**有意**的兜底（宁可见到 `paused` 也不要见到空白），代价是漏一个键就静默漏
一次翻译：不报错、不空白、控制台干净，只是那一格显示英文。

它与 §8.2 是同一个问题在两个层面上的形态：**后端能产出 N 种取值、前端只认 M 种**。
8.2 查的是「后端给了几维筛选 ↔ 页面画了几维」，这一维查的是「后端会产出哪几种
取值 ↔ 前端翻得出哪几种」。

### 11.2 判据：三个集合

对每组「表.列 ↔ 前端标签表」取三个集合：

| 集合 | 出处 | 取法 |
|---|---|---|
| **S** 声明 | `staging_schema.py` 的列注释 `-- a\|b\|c` | 正则，带表名归属（`status` 在四张表里都有） |
| **F** 前端 | `static/*.js` 的 `var XXX_LABEL = {...}` 的键 | 按变量名整块抠 |
| **B** 后端写入 | 代码里真正写这一列时的字面量 | 只认 `col = 'x'` / `col="x"`，且要带语境 |

两条断言：

1. **F == S**。不相等就报，两侧差集都打出来——**差集本身不指明谁对**：可能是注释
   多写了一个永不产出的值，也可能是前端少认了一个真实存在的值。
2. **B ⊆ S**。代码里写了 `status="cancelling"` 而注释没列它，说明**注释是谎话**——
   下一个照注释写前端的人必然漏掉这个状态。这一条是给第 1 条定方向的。

`B` 的取法要带语境，见 §11.4。

### 11.3 跑出来的三处，两种方向各占一边

十组映射里有三处不一致，正好演示了判据的两个方向各能抓到什么：

| 位置 | 形态 | 判定依据 | 处置 |
|---|---|---|---|
| `collect_tasks.status` | 注释写着 `paused` | 全项目 grep `paused` **只命中这行注释自己**，没有任何代码产出它 | 从注释删掉 |
| `extract_tasks.status` | 注释缺 `cancelling` | `staging_executor.py:592` `_update_task(task_id, status="cancelling")`，代码真会写 | 补进注释 + 两行语义说明 |
| `raw_accident_assets` 的 `asset_type` / `ocr_status` | 前端**没有标签表**，直接拼原值上屏（`'OCR: ' + a.ocr_status`） | 同段的 `asset_type` 也是裸值，同一类问题 | 新建 `ASSET_TYPE_LABEL` / `OCR_LABEL` |

第一行是「注释说了谎」（多写），第二行是「注释漏了话」（少写），第三行是「前端
根本没打算翻译」。三种形态都被这一条判据收在同一张表里——这是把 F、S、B 三个集合
摆在一起看的结果，只比 F 与 S 看不出第二行的方向。

### 11.4 第一版判据的两个错

两处都不是实现 bug，是**判据设计错**，记在这里因为它们各自代表一类容易写出的假判据：

**错一：正则卡在逗号上，一条也匹配不上。** 第一版写
`\s*([a-z_]+)\s+TEXT\b[^,]*?--`，想用 `[^,]*?` 限定「TEXT 到注释之间没有逗号」。
但列声明几乎都有 `NOT NULL,` 这个逗号，于是 15 个枚举列一个都没解析出来，输出
「schema 注释里的枚举列 0 个」、十组全部报「schema 没声明」。**它当时报错了**，
只是报的是全部——一个恒假的判据和一个恒真的判据一样没用。改成单行内 `.*?` 即可。

**错二：按文件抓写入，把别的表的列算到这张表头上。** 第一版 `WRITERS` 配的是
「哪些文件写这张表」，然后在文件里按列名抓字面量。结果 `web/collect.py` 里
`UPDATE raw_accidents SET ... status = 'gated'` 被算成 `collect_tasks.status`
的写入，报出 `gated` / `new` / `promoted` 三个假阳性——**`status` 这个列名在三张
表里都有**。实际 `web/collect.py` 只**读** `collect_tasks`（只多一条 `DELETE`），
真正写它的是 `collector/executor.py`。

修法是给每条写入规则加语境，两种抓法：

- `("sql", 表名)`：取 `UPDATE <表名> ... SET <子句>` 里 `WHERE` **之前**的部分。
  卡到 `WHERE` 是因为 `SET status='gated' WHERE status='new'` 里后一个是**读取**
- `("call", 函数名)`：取 `<函数名>(...)` 调用里的关键字参数。更新语句的列名在 SQL
  里是变量拼的（`SET {sets}`），字面量只出现在调用点

第一版的错法会让判据**朝假阳性方向偏**——报得越多越像在干活，实际是噪声。

### 11.5 反向验证：三个方向都得能报出来

判据写完要能说明它**不是恒真的**。在 `/tmp` 副本上挖三个不同环节的洞（不碰源文件）：

| 洞 | 期望 |
|---|---|
| 前端标签表少一个键 | 报「前端缺 skipped」——这些值会原样显示成英文 |
| 前端标签表多一个键 | 报「前端多 queued」——这张表没有产出的路径，标签永不生效 |
| schema 注释删掉一个真值 | 报「写入未声明 cancelling」——注释是谎话 |

三条都报出且退出码为 1。中间还有一个插曲：第二例原本设计成「往注释里加值」，
跑出来报的是「前端缺 queued」——与第一例同向。**这是我的用例写错了，不是判据
漏了**：往注释加值本来就是「声明了、前端没有」。改成往前端加键才落在另一个方向上。

三条覆盖的是判据三个集合两两之间的差：S−F、F−S、B−S。

### 11.6 这一维的边界

- 只查 `staging_schema.py` 里**以列注释形式声明**的枚举。`work_task`（WT01–WT99）
  这类走 `enum_definitions` 表的编码不在此列——它们的真值是库里的表，不是注释
- `PAIRS`（哪张表哪列对应前端哪张标签表）与 `WRITERS`（谁写这一列）都是**写死的
  映射**。改了前端标签表的变量名、或把某个写入点搬到新文件，都要同步改脚本
- **B 只覆盖状态类列**。分类列（`project_type` 等）的值来自 LLM 输出，代码里没有
  可抓的字面量——「后端会产出哪些取值」对它们是个开放集合，注释本来就只能是参考
- 判据比的是**集合相等**，不比**翻译对不对**。`failed: '失败'` 改成 `failed: '出错了'`
  它不会响——那是文案问题，不是对齐问题

## 十二、编码列的中文名：库里的码 ↔ 页面上的字

复跑：`check_enum_alignment.py` 的第三节（与前两节同一个脚本），**要连库**——
跑之前确认 `CAIEMS_DB`（主库）与 `CAIEMS_STAGING_DB`（工作库）指向想看的那两个。

### 12.1 为什么 §十一 的三集合判据套不上这一类

§十一 是围绕「取值域写在**列注释**里」这一族枚举设计的。`work_task` /
`building_structure` / `equipment_involved` / `material_involved` / `worker_type`
五列不属这一族，两条都套不上：

| | §十一 那一族（状态列） | 这一类（编码列） |
|---|---|---|
| 取值域在哪 | `staging_schema.py` 的列注释 | 主库 `enum_definitions` 表（57 行，5 个枚举） |
| 有几行 | 3–6 个 | 7–13 个，且随库改 |
| 失效长什么样 | 页面上冒英文（`paused`） | 页面上是一串**看不出对错的码**（`WT04`） |

第二行是关键。`paused` 一眼就知道不对；`WT04` 看着像模像样，页面上不刺眼，没
人觉得哪里出了问题——只是审核员核不了「S3 判的 WT04 对不对」，只能先背下 11 个
WT 码。**这类缺口没有视觉症状**，所以只能问接口，不能靠人眼扫源码。

§十一 的第三集合（后端写入字面量）在这里也没用：这些列的值来自 S3（DeepSeek V4），
不是代码里的字面量。

### 12.2 判据：单向，三个页面

**接口在下发的每条记录上，凡编码列有值，就要给对应的中文名。**

| 页面 | 接口 | 判什么 |
|---|---|---|
| 详情页 | `/api/accidents/<id>` | `data.fields[col]` 有值 → `data.fields[col+"_label"]` 必须在 |
| 列表页 | `/api/accidents` | 凡 `*_code` 有值 → 配对的 `*_label` 必须在 |
| 审核页 | `/api/review/items/<id>` | `enum_labels` 的键覆盖「`ENUM_COLUMNS` ∩ `EDITABLE_FIELDS`」 |

与前两节的**方向性**不同：§十一 的差集不指明谁对（可能注释多写了、也可能前端少
认了），这里没歧义——接口没给中文名就是漏了。脚本的收尾提示也据此分头给。

列表页那条**不写死 `work_task`**，判的是「凡 `*_code` 键有值就得有 `*_label`」，
列表页以后多带一个编码列会自动跟上。

详情页的样本是**逐级降级**挑的：要求五个编码列同时有值，挑不到就退到四个、三个……
主库实测填充率差得远（`work_task` 2,202 条 / `building_structure` 只有 359 条），
随手挑第一条往往只验得到两个列——**判据看着绿，七成没验**。现在挑到的样本
（`ae16d12d2c7f`）五列全覆盖，验不到的列会在输出里点名。

### 12.3 跑出来的那一处

**审核页把五个编码列渲染成可编辑输入框，值就是码，一个中文名都不给。**

而详情页**早就翻了**（`detail.py` 的 `_label_of`，`fields[col+"_label"]`），列表页
也翻了 `work_task`（`accidents_query.decorate`）。**同一份数据在三个页面，两个翻
一个不翻。**

之所以说这是审核页的硬伤、而不只是「少点提示」：这五个字段在 `EDITABLE_FIELDS`
里，是审核员**要动手改**的字段。让他对着 `WT04` 判断该不该改成 `WT09`，等于要求
他把码表背下来。

依据不是新立的规矩，是蓝图 03 §4.2 自己写的（当时是给告警码定的）：

> `labels` 是告警码→中文名的全表，一次下发……少了 `labels`，遇到一个没见过的码
> 就只能显示裸码

修法与 §十一 的三处一样是**两个方向都补**：后端 `review.py` 在详情接口里一次下发
`enum_labels`（五个枚举合计 57 条，比一次请求本身大不了多少），前端 `review.js`
在编码字段的输入框下渲染中文名，并且**跟着输入实时更新**——改完码提示还停在旧值上，
比没有提示更误导。查不到的码**原样亮出来**（`WT42（枚举表里没有这个码）`，用告警色），
不吞掉也不换兜底词：异常编码该自己冒头。

### 12.4 判据自己犯的两个错

**错一：照着上一个接口的包装抄，静默查不到东西。** 三个接口三种 JSON 包装——
详情是 `{"ok":..., "data": {"fields": ...}}`、列表**没有 `data` 层**（`api.py:60`
直接把 `{"items","meta"}` 发出去）、审核队列的 `data` **就是记录数组本身**。第一版
全按 `data.items` 取，结果列表页和审核页两组一个都没查到，却**不报错**——只是
`items` 为空，判据当成「没数据」跳过。这类错不会红，只会绿得可疑；跑完必须看
输出里的 `·` 行，确认每组都真的验到了。

**错二：反向验证的副本里没有主库。** 挖洞探针跑在仓库副本上，副本 `data/` 里
没有 `caiems_v2.db`，第三节整节退化成「跳过」，**挖的洞根本走不到**，跑出来一片绿。
补上 `CAIEMS_DB` 指向真库后才验出洞（挖掉审核页的 `building_structure` 一列 →
报「没下发对照表」、退出码 1）。这一条本身就是 12.4 错一的同一个教训：**跳过长得
跟通过一样绿**，反向验证必须确认被测的那条路径真的执行了。

### 12.5 这一维的边界

- **依赖库里真有条目**：主库没有编码列有值、或工作库没建，对应的组会跳过并在输出
  里用 `·` 说明。判「跳过」与判「通过」的区别只有这一行文字，看漏了就等于没跑
- 列表页目前只带 `work_task` 一个编码列，判据是通用的、覆盖的列是当前这一列
- 审核页判的是「对照表**键**在不在」，空表只记提示不报缺口——空表说明库里这个枚举
  没有 `is_active` 行，那是数据问题，该在数据侧查，不该让前端判据报
- 与 §十一 一样，判的是**有没有翻译**，不判**翻译对不对**（`WT04` 的中文名写错字
  它不响）
- 不判**该不该翻**：`accidents` 之外的表（`caics_causes` 等）的码不在 `ENUM_COLUMNS`
  里，加进来要连同页面一起改

## 十三、查询计划：筛选有没有真的下推到索引

复跑：`.venv/bin/python3 scripts/check_query_plan.py`，退出码 `0` = 带筛选的查询
全部走了索引（豁免项除外）。

### 13.1 为什么这条也得打接口，不能读源码

蓝图 07 §四 M1 的验收条目写的是「列表筛选下推到 SQL，`EXPLAIN QUERY PLAN` 显示走
索引」。这条**读源码判不了**：SQL 是 `build_where` 拼出来的，「拼得对」与「SQLite
真用上了索引」是两件事——列名对、条件也对，但只要写法上有一层函数包裹（`substr`、
`lower`），索引就白建了，而源码里看着毫无问题。

做法与 §十二 一致：给 `db.query` / `db.scalar` 打补丁，**抓真跑出来的 SQL**，再逐条
`EXPLAIN QUERY PLAN`。不照抄源码里的拼法——那样 `run()` 改了脚本不会跟着改。

### 13.2 判据：`SEARCH` 才是验收条目里那个词

| 计划里的样子 | 含义 |
|---|---|
| `SEARCH t USING INDEX x (col=?)` | 索引查找 ← **验收要的就是这个** |
| `SCAN t USING COVERING INDEX x` | 全**索引**扫描（扫全部索引项） |
| `SCAN t` | 全**表**扫描 |

后两行都是「扫」不是「查」。容易搞混的是中间那行：`SELECT COUNT(*) FROM accidents`
走最小的覆盖索引扫一遍**正是最优计划**（没有条件可用，不扫完就数不出总数），把它
判成问题是假阳性。

只看**带筛选的用例**，且这个「有没有筛选」取自**用例名**（脚本自己构造的），不看
SQL 文本——原因见 13.4。致因分析页与排序用例只打印计划不计分：前者是三张全量聚合
（按 `substr(code,1,1)` 分组就得把 16,323 行过一遍），后者没有筛选条件
（`SCAN a USING INDEX idx_acc_date` 配 `ORDER BY date`，索引有序、取前 20 条即停）。

### 13.3 查出来的两处：两个筛选维度一直没索引

```
列表·项目类型  ✗ 加了筛选却仍是扫描：SCAN a
    SELECT COUNT(*) FROM accidents a WHERE (a.project_type IN (?))
列表·施工阶段  ✗ 加了筛选却仍是扫描：SCAN a
    SELECT COUNT(*) FROM accidents a WHERE (a.construction_phase IN (?))
```

`MULTI_FIELDS` 里有五个多值筛选维度，`severity` / `accident_type` 有索引，
`project_type` / `construction_phase` **没有**——`add_indexes.py` 当初漏了这两个。

这类缺口**没有任何症状**：页面照常出结果，只是慢。实测（2,623 条）：

| | `project_type` | `construction_phase` |
|---|---|---|
| 未建索引 | 1.458 ms（`SCAN a`） | 1.445 ms（`SCAN a`） |
| 建索引后 | 0.012 ms（`SEARCH … idx_acc_project`） | 0.027 ms（`SEARCH … idx_acc_phase`） |

两个索引已补进 `scripts/add_indexes.py`（连同理由），建完共 11 个。

> **这一条现在退 `1` 是预期的**：脚本改好了，索引还等着在主仓库执行
> `scripts/add_indexes.py`（`10_待执行清单.md` 第 4 步）。建完复跑转绿——`0.012 ms`
> 那一列就是这么量出来的。**别把这个退 `1` 当成核查坏了**，它正指着待办；
> 哪天它转绿了，说明索引真的落到主库上了。
>
> **但它报几条，取决于它连的是哪张库**（见 §13.7）。上表那两个数字是在
> **worktree 那份预建过 9 个索引的副本**上量的；连**真主库**（一个自建索引都没有）
> 跑，报的不是 2 条而是 **5 条**——省份 / 严重程度 / 事故类型 / 项目类型 / 施工阶段
> 全缺。后者才是用户还没跑第 4 步时的事实，也是脚本默认该看的那张库。

### 13.4 判据写废了两版，都是设计错

**第一版：按表名匹配计划里的 `SCAN accidents`。恒真。** 展示层的 SQL 全都
`FROM accidents a`，计划里写的是别名 `SCAN a USING COVERING INDEX …`，一条也匹配
不上，「条件没走上索引」永远是空集。验法：挖两个洞——把筛选列改成 `lower(col) IN`、
清空豁免表——**跑出来一模一样**，判据对任何写法都点头。

这与 §11.4 那个「正则卡在逗号上」是同一类错：判据自己不报错，只是**恒真**。区别是
那次表现为恒假（报全部），这次表现为恒真（报没有）。

**第二版：改成「带 `WHERE` 就不许出现 `SCAN`」，靠 `" WHERE " in sql` 判有无筛选。
过严，而且仍然错。** 子查询里也有 `WHERE`：

```sql
SELECT … FROM accidents a
ORDER BY a.date DESC LIMIT ? OFFSET ?
-- 里面嵌着 (SELECT COUNT(*) FROM caics_causes c WHERE c.accident_id = a.id)
```

于是**排序用例**（压根没有筛选）被判成「带 WHERE 却是扫描」，一次出九条假阳性。

**第三版**：判据只问一句「这个用例加了筛选，计划里出现 `SEARCH` 了吗」，而「有没有
加筛选」取自用例名。子查询、别名、函数包裹都骗不到它。三个洞（`lower(col) IN`、
清空豁免、还原）都能如实反映。

### 13.5 一处「看着该优化、改了会算错」的

年份筛选写成 `substr(a.date, 1, 4) >= ?`，函数包裹列使得索引只能是**全索引扫描**。
改成字符串范围比较（`a.date >= '2015-01-01'`）实测快 11 倍（0.138 → 0.012 ms/次），
**但不能改**：

| 库里的值 | `substr` 口径 | 范围口径 |
|---|---|---|
| `'2008'`（纯年份，2 条） | 算 2008 ✓ | **丢掉**（`'2008' < '2008-01-01'`） |
| `'1986-01'`（年月，8 条） | 算 1986 ✓ | **算成 1985**（`'1986-01' < '1986-01-01'`） |

0.126 ms 的差别没人感知得到，3 条记录归错年份是实打实的数据错。**这一处不改是决定，
不是遗漏**——所以它进了脚本的 `EXEMPT`（带理由），哪天有人"顺手优化"成范围比较，
脚本会把这层因果重新摆到面前。

### 13.6 这一维的边界

- 认的是**形态**不是**语义**：`SEARCH` 只说明用上了索引，不说明这个索引合适——
  选错索引（比如该走 A 却走了 B）它看不出来
- 覆盖的是**列表查询 + 致因三端点**。详情页、审核页、采集/提取任务页的查询没纳入；
  那些页面的查询各有各的形态（按主键取一条、按状态取任务），套同一条判据意义不大
- `EXEMPT` 五条各带理由（关键词无 FTS、年份 `substr` 两处、`EXISTS` 无可用索引、
  省份计数的 `GROUP BY`）。**豁免要经得起看**——往里塞不好解释的东西，这条判据
  就退化成筛子
- 与 §十二 一样**依赖真库**：跑的是实际数据量下的计划。SQLite 会在数据量变化时换
  计划（比如小表干脆全扫），所以结论有时效性

### 13.7 连哪张库：同一份判据、两张库、两套结论

这一维是十四维里**唯一一条结论会随「在哪个目录下跑」而变**的。根因是项目里有两套
库路径解析，在 worktree 中指向不同的文件：

| 解析方式 | 落在哪 | 谁在用 |
|---|---|---|
| `_common.main_db_path()` | 上溯到 `.git` 目录 → **主仓库** `data/caiems_v2.db` | 字段、契约、截图、交互、主库对账五条 + `e2e_verify_main.py` |
| `settings.DATA_DIR`（`config.py` 的上两级 + `/data`） | worktree 自己的 `data/caiems_v2.db` | 应用本体（web 读的那张）、`add_indexes.py` |

worktree 的 `data/` 下确实**有**一份主库的副本（早前会话为了让 e2e 在 worktree 里
跑起来复制的）。两张库实测的关系是——

- **数据逐表相同**：9 张表行数逐张相等（2,623 / 16,323 / 57 / 282 / 1,037 / 580 /
  45 / 1,636 / 7），`pipeline_version` 都是 `caics_v1.0`，`quick_check` 都是 `ok`
- **索引不同**：主库只有 1 个自建索引（`idx_image_files_accident`），副本有 **9 个**
  （这份 1.1 MB 的差额就是它们，也是两个文件大小差别的全部来源）

所以「连错库」这件事**只在本维有后果**：其余各维比的是**数据**，数据一样，看哪张都对；
本维比的是**索引与查询计划**，两边不一样，于是同一份判据给出两套结论——副本报 2 条缺、
真库报 5 条缺。**连副本会把「主库还没建索引」这件事整个掩盖掉**。

本脚本原先用的是 `settings.DATA_DIR` 那一套（唯一一个这么写的），已改成
`main_db_path()`，并把库路径**打印出来**（连错库时结论会反，不该靠猜）。想故意核副本：

```bash
.venv/bin/python3 scripts/check_query_plan.py --main-db data/caiems_v2.db
```

> 顺带说明 `add_indexes.py` 为什么仍用 `settings.DATA_DIR`：它是**写**脚本，第 4 步
> 就是在主仓库里跑（那时两套解析指向同一个文件），而显式传 `CAIEMS_DB` 时以它为准
> ——`e2e_verify_main.py` 缺索引时给的那行提示正是 `CAIEMS_DB=<主库> python3
> scripts/add_indexes.py`，所以照着提示执行是安全的。**在 worktree 里裸跑它会建到
> 副本上**，那是本维要避免的。

## 十四、杀进程：状态与数据各自去哪了

蓝图 01 §8 验收第 5 条：「任务运行中杀进程（`kill -9`），重启后该任务状态为
`failed`，已入库的 `raw_accidents` **不丢不坏**（事务保证）」；
蓝图 02 §8 验收第 5 条对提取侧提了同一件事，还多要求一条：「**可续跑且不重复**」。

这条与前面每一维都不同：**它比的是「同一个东西在事故前后的两个状态」**，不是两侧
集合的关系，也不是实现与契约的关系。两个执行器各一个脚本：
`scripts/e2e/e2e_restart_collect.py`（17 项）与
`scripts/e2e/e2e_restart_extract.py`（24 项），都退 `0` 才算过。

为什么是两个脚本而不是一个参数化的：采集的验收点在**事务**（写进去的算不算数），
提取的验收点比它多一层——**续跑**（重跑一遍会不会把已经花掉的 LLM 调用再花一遍、
会不会插出第二条暂存记录）。前者只跑一趟，后者要跑三趟（被杀的那趟、补跑那趟、
全量重跑那趟），共用的只有「起子进程 + 等某一行输出 + 库外看现场」这几个工具函数。

### 14.1 为什么必须跨进程，以及为什么必须两个进程

pytest 里有 `test_reconcile把僵死任务标为中断`：往库里插一条 `running` 行，调
`reconcile_stale_tasks()`，断言它变成 `failed`。它验的是**函数改得对不对**，
验不到两件事：

- **进程真被杀掉时事务会怎样**——插入一条库里的假行，跟 SQLite 的崩溃恢复没有关系
- **新进程会不会真的去调那个函数**——`views.py` 的 `_reconcile_once()` 是**进程级**
  一次（模块级 `_reconciled` 标志）。同进程里再打一次 `/collect` 什么都不会发生，
  所以「重启后有清理、重启前没有」这句话，**只有起两个真进程才有内容**

### 14.2 判据：把「事务保证」四个字变成可执行的场景

「不丢不坏」不能靠数行数来验——那样随便怎么写都能过。脚本换掉的是
`_run_source`（假采集器，不碰外网），但换进来的东西**照样用真的
`staging_db.write_tx()` 写库**，只是分两笔：

| | 写法 | 杀进程后应该是 |
|---|---|---|
| 第一笔 | 写 3 行，**提交**，打印 `READY` | 3 行都在，逐列完整 |
| 第二笔 | 写 3 行，**不提交**，`sleep(300)` | **一行都不落地** |

父进程看到 `READY` 后确认状态是 `running`，然后发 SIGKILL——**杀在悬挂事务上**。
没有第二笔，整条验收就退化成「数一数行数」；两笔都提交，验的又只是「文件还在不在」。
实测：3 行提交的留下、3 行悬挂的随进程回滚，`PRAGMA integrity_check` 为 `ok`，
杀前杀后逐列相等。任务则是 `running`（被杀时）→ `failed`（重启后由 `/collect`
这个页面入口清理），`error` 写着「进程重启，任务中断」。

### 14.3 第一次跑是红的，红得有价值

第一版探针忘了 `import time`，第二笔 `time.sleep(300)` 抛 `NameError`。后果不是
脚本报错，而是**任务当场正常地 `failed` 了**（`run_task` 把源级异常收进
`stats.per_source[...].error`，任务级 `error` 留空）——于是「杀之前任务状态是
running」这条断言失败，脚本继续往下跑，后面所有断言都在验一个**已经结束的任务**，
毫无意义。

两处据此改了脚本：其一，断言链上游失败会让下游全部失去意义时**主动打住**
（`READY` 没出现就直接 `return 1`，并说明后面的断言无意义）；其二，失败信息要能指路
——第一次是靠现场库里那条 `stats` 才找到 `NameError`，脚本原样保留临时目录并把它
打印出来。**任务级 `error` 为空而源级有值**这件事本身不是缺陷：采集页会把
`stats.per_source[].error` 展开显示（`collect.js:393`）。

### 14.4 反向验证：挖两个洞

- **洞 A**：把 `views.py` `collect_page()` 里的 `_reconcile_once()` 去掉 →
  「僵死任务被标为 failed」「失败原因写明了是进程重启」两条报出，退 `1`
- **洞 B**：让第二笔也提交（模拟事务边界写错）→ 「悬挂事务的 3 行一行都没落地」
  等 5 条报出，退 `1`

两个洞都改源码/脚本本身，跑完即还原。**判据对真实缺陷有反应**，不是恒真。

### 14.5 提取侧：多验的那一件事是「续跑」

`scripts/e2e/e2e_restart_extract.py` 起**三个**子进程，走完一条完整的生命史：

| 进程 | 干什么 | 停下来时库里的样子 |
|---|---|---|
| A（被杀） | 单并发跑 6 条原文，第 4 条上停住 | 3 条暂存行已提交、任务 `running` |
| B（重启） | 只访问一次 `/extract` | 任务转 `failed`，暂存行一条没少 |
| C（续跑） | 看队列剩几条 → 用队列新建任务补完 → 再把 6 条全量重送一遍 | 仍是 6 条，`stage_id` 一个没变 |

**第 4 条上停住**用的是环境变量开关（`HALT_ON_HIT=1`），只有进程 A 带着它。这个开关
是踩出来的：第一版停车条件只看标题，续跑那趟第 4 条又停在那儿等 300 秒，脚本超时——
**探针自己没长记性，却被读成了「产品跑不完」**。同一趟里还红了一条：队列返回
`["rr6","rr5","rr4"]`，而断言写的是 `["rr4","rr5","rr6"]`。队列按 `fetch_time DESC`
排，那个先后是我自己造种子数据造的——**把探针的种子顺序当成了产品契约**，改成比集合。

三个判据点，各自防一类写法：

- **续跑的正确入口是队列，不是重跑任务**。`start_task` 只在 `pending` 时可启动，
  `failed` 任务点不动。C 从 `/api/extract/pending` 取剩下的（实测恰好 `rr4/rr5/rr6`
  三条，已提取的没被列出来）新建任务——这条覆盖的是
  `pending_raws(only_unstaged=True)` 的 `NOT EXISTS` 子查询
- **不重复是 UNIQUE 拦的，不是靠先查再写**。全量重送 6 条时 `run_one` 走
  `inserted == 0` 那一支：不写致因、不重复回填生命周期、`status` 记 `duplicate`。
  实测暂存区仍是 6 条、致因 12 条（6 × 2），**`stage_id` 逐条相等**——`stage_id` 相等
  才算真的没重写，光数行数分不出「没插」与「插了又删」
- **「数据不重复」不等于「不重复烧钱」**。`MODEL_CALLS=9` = 续跑 3 条 + 全量重送 6 条。
  暂存区拦住了重复落库，但 `_load_raws` 不过滤已 staged 的原文，**已经在库里且
  `stage_id` 不变的那 3 条，第二次仍然真调了一遍模型**。这不是缺陷（除非用户主动重送，
  否则走不到这条路），但它是「不重复」这四个字的边界，所以写成一条断言摆在那儿——
  哪天有人把 `_load_raws` 改成只取未暂存的，这条会变成 `MODEL_CALLS=6` 而报红，提醒
  改的人回来改判据。

反向验证同样挖两个洞，都报红（各 2 项），跑完即还原：

- **洞 C**：拿掉 `views.py` `extract_page()` 里的 `_reconcile_once()` → 任务停在
  `running`，「僵死任务被标为 failed」「失败原因写明了已完成条目不受影响」两条报出
- **洞 D**：把 `pending_raws` 的 `only_unstaged` 过滤改成恒不生效 → 队列列出全部 6 条，
  「队列恰好剩第 4–6 条」报出，且 `MODEL_CALLS` 从 9 涨到 **12**（补跑把 3 条老的
  也重跑了一遍）——同一个洞被两条断言分别看见

### 14.6 这一维的边界

- **只覆盖执行器，不覆盖同步写入**。闸门裁决（`collect.py` 的
  `POST /api/collect/gate`，人工把原文标 confirmed / rejected）看着像同族，其实
  不是：它是一条 **HTTP 请求里的同步 UPDATE**，包在 `staging_db.write_tx()` 里，
  没有「跑一半」的状态可留——请求断了事务自己回滚，pytest 那层已经覆盖。
  **这一维管不着它，不是缺口**（曾误记为待补，2026-10-01 查清）
- 假 `_run_source` / 假 pipeline 意味着**适配器层与真实模型调用都不在覆盖范围内**：
  验的是两个执行器的状态机、事务边界与去重判据，不是「爬虫抓得对不对」或「模型判得准不准」
- 杀的是 SIGKILL。用户按 Ctrl+C（SIGINT）走的是另一条路径，不在本维
- 与 §十二/§十三 一样**必须先有库**；它连库都不只是读——会真起进程、真杀、真写

那些字段，缺的只是「前端愿不愿意渲染」。

与"够不够得着"，它问的是**看不看得清**——前三层全绿而这一层可以是红的，用户照样
读不出来；它也是**唯一一个有国际标准可依据**的一维（WCAG 2.1 AA 的 1.4.3 给了

§8.7 补的**配色的单一定义源**是**第十四个**（2026-10-05）：它问的不是"颜色对不对"，

但 JS 里另抄了一份十六进制且已与 token 分叉，于是同一页同一语义两种颜色。前十三维
比的都是**两个对象是否一致**（前端↔后端、文档↔实现、库↔页面），这一维比的是
**一个语义的 N 个实现之间是否一致**——N 是多少，得先去数（改前实测 9 个色值字面量
里 7 个已分叉）。它也是**唯一一条会随"别人改 CSS"而无声变红**的一维：没人动
`causes.js`，只要 `app.css` 的 token 挪一下，它就该报红。
§8.7 同一轮顺带补的**非文本对比度**（WCAG 1.4.11）算**第十五个**且**与第十三个共用
一个脚本**（`check_contrast_a11y.py` 的 F 段）：标准族相同、量法相同，但**查的是
不同的 success criterion**——1.4.3 问"字读不读得出来"，1.4.11 问"控件辨不辨得出来
（边框/底色达不达 3:1）"；两者可以一个全绿一个红（实测就是这么回事：文字 0 违规，
<input> 边框 1.34:1 违规）。同轮还按 Tab 真走了一遍**焦点外观**（2.4.7 满足），
并**更正了一个条款号**：先前笔记把"指示面积 ≥2px 周长"记成 2.4.11，实际 **2.4.11
是 Focus Not Obscured（本条未测）**、"面积与对比度"是 **AAA 级的 2.4.13**。
§7.3 补的「`accidents` 的列 ↔ 详情页四档」是**第十二个**，与第十一个同族但走反方向：
前十个都从「页面上有什么」出发，这一个从「库里有什么」出发，找的是**后端有值而页面
从未显示**的那一类。所有维度里，只有 §十一 用了「后端写入字面量」这个第三集合——
其余比的都是两侧（前端 ↔ 后端接口 / 文档 ↔ 后端 / 库 ↔ 页面）。**§十二 与 §十三 是
仅有的两条必须先连库才能跑的一维**：前十一维比的是源码与文档里的集合关系，它们问的
是**运行时的实际输出**——「注册了路由」与「这条记录真的带了这个字段」、「写了
WHERE」与「SQLite 真的用上了索引」，都是两回事。§十三 还与其余的**方向**不同：它比
的是「实现 ↔ 性能契约」，不是「两侧是否一致」；它也是唯一一条**结论会随「在哪个目录
下跑」而变**的——项目里两套库路径解析在 worktree 中指向不同文件，而这一维看的是索引
与计划（§13.7）。

§十四 又是另一种：**它比的是同一个对象在事故前后的两个状态**（杀进程之前 / 之后、
重启之前 / 之后），而其余各维比的都是同一时刻的两侧。它对时间点敏感，所以必须是
跨进程的——同一进程里根本构造不出「重启前」。它也是唯一**覆盖两个执行器**的一维：
采集侧验到事务为止，提取侧还要往下验一层**续跑**（§14.5）。

§2.5.74 补的**取值域**是**第十六个**（2026-10-05）：比的是**提示词声明的取值域 ↔
库里已落地的值**（`scripts/check_value_domain.py`）。它与 §十一 最像（都问"取值合不
合法"），但**对象完全不同**：§十一 查的是**工作库/前端标签**那套枚举（`collect_tasks
.status`、`staging_accidents.text_type` 等），而这一维查的是**主库 `accidents` 表那
12 个枚举列的实际值**——`check_enum_alignment.py` 的三方（论文表 2 ↔ 生产提示词 ↔
主库**落库类名**）只覆盖 CAICS 那 19 类，这 12 列不在其中，此前**没有任何脚本管**。
它也是唯一**把"缺失"本身当作核查对象**的一维：缺失在本库有**四种**表示（`NULL`、
空串 `''`、字符串哨兵 `未知`/`不适用`、数值哨兵 `0`），前两种 §2.5.65 查过，后两种
是"写在值里的缺失"，`IS NULL OR TRIM=''` 一条都抓不到——`construction_phase='未知'`
在分布图里会作为一个**正常类目**和"主体结构"平起平坐。首查即出一条真缺陷：
`report_type` 声明 `教材/案例`、库里 895 条（34.1%）是 `教材案例`，同一语义在库里
分裂成两个值。**这一维的判据有个结构性缺口**：C 段只能发现**声明了 enum 的列**，
没有 enum 的列（文本列、`weather` 这类裸值列）完全不可见——所以那部分只能靠
**人工登记台账**（E2 四条），漏登记抓不到。

§2.5.75 补的**焦点遮挡**是**第十七个**（2026-10-05）：问的是**键盘焦点落到的元素有
没有被页面上的东西盖住**（WCAG 2.4.11 Focus Not Obscured, AA，
`scripts/check_2575_focus_obscured.py`）。它与已有的两维**正交**：§八 8.3 与
§2.5.69/§2.5.70 问"能不能操作到"，§2.5.68 问"读没读到、看不看得见"，而这一维问
"**拿到了焦点、却被另一层盖住**"——十七维里唯一一个**同时依赖元素位置与渲染堆叠
顺序**的判据。首查即出两条 AA 级硬违规：顶部吸顶区（顶栏 55px + 吸顶表头 39px）与
底部批量条（`fixed`，距底 18px、高 56px），键盘用户 Tab 到的按钮会**整条被盖住**
（5 个采样点全被挡）。修法是标准的 `scroll-padding-top` / `scroll-padding-bottom`。

**这一维最大的教训在判据自己身上**：纯 Tab 遍历**永远绿**——浏览器把焦点交给元素时
本来就会把它滚进视口，"把视口外的元素滚进来"这个动作压根不发生，而 sticky 遮挡**只在
这个动作里**发生；必须复现**先滚动、后 Tab**（v1/v2 探针走到 76/98/20 步仍全绿，v3
改了遍历形态立刻抓到）。底部批量条则**只能靠 `focus()` 全扫**：工作库是空的
（`/api/collect/raw` 实测 `total=0`）⇒ 采集页无行可勾 ⇒ 批量条不出现 ⇒ Tab 遍历**从
原理上**看不到它。**判据边界**：只判**完全**遮挡（AA 的定义），部分遮挡在这一档合规、
只打印不判红；且 `elementFromPoint` 是渲染性判定，`opacity: 0` 这类会判成"可见"。

§2.5.79 补的**响应类型**是**第二十一个**（2026-10-05）：补的是 §10.5 三条「比不出来」的

`"size": "50"` 在这层看着一样"）。它与第十个维度（响应契约，问**键名在不在**）、第十九个
（响应面，问**列名有没有作为键进过响应**）、第二十个（响应结构，问**层级对不对**）同族，
但问的是第四件事——**形状**：键名对而类型错（`"count": "12"` 让前端 `+1` 拼成 `"121"`）、
层级对而值错（`ok: false` 配 HTTP 200）都落在这三位的盲区里。

**它是二十一个维度里唯一主动放弃一半核查对象的一个**：`"值与类型"`被拆成两件事，**只核
类型、不核值**。放弃的理由在判据自身的健全性上——样例里的值是**示意值**，`"accidents": 2623`
是写作那天抄的快照，明天库里多一条它就该变，而**文档没有义务跟**；把示意值当判据核，等于
要求文档每改一次数据就重抄一遍，那是快照不是契约，而且是会过期的快照。§2.5.77 立过的
"**判据在多数样本上恒真就等于没有**"在这里同样成立，值面判据正是这个病。**类型不一样**：
它属于契约且**不随数据变**。

值面因此只留一格能核的——**`ok`**。它是布尔**断言**不是数据：文档画 `"ok": true` 说的是
"这个接口成功时给 true"，而它永远不该是 false（false 意味着失败，那时要么状态码不该是 200、
要么得有个错因字段，不能靠前端读 `ok` 猜）。这一格今天 14 条接口全绿；**它的价值不在今天**，
在于实现某天把失败当成功返回时能抓住。

**互斥设计承 §2.5.78 的教训**：A2（文档同一路径声明了不止一种类型）命中即**跳过** A1，
否则"文档自己矛盾"会同时触发两档、红的集合分不清是哪条判据抓到的；B1（文档只写 null/
占位）与 A1/A2 也互斥。于是**每条公共路径恰好归入 A1/A2/B1/通过 之一**——这条恒等式本身
是元判据（实测 `0+0+23+366 = 389`）。首查**零缺陷**：389 条公共路径里 366 条声明了类型、
类型矛盾 0；**23 条（5.9%）只写 null/占位、无从比对**——把豁免面量出来是要紧的，若它占
九成，"类型零矛盾"这句话就只是"我没比"。

**这一维的自证要接两个面**：C 段 4 例注入里**源码面 2（改实现类型 / 改 `ok` 取值）+ 文档面
2（改文档字面量类型 / 让同一路径两种声明）**。文档面那两例是**必须的**——只做源码面的话，
"判据真的在读文档侧的类型"这件事一次都没被验证过。其中第四例在首版**没打中**：把
`"一般事故"`（string）改成数字只是把一种类型换成另一种、**仍是一种**，落到 A1 而非 A2；
改对之后声明才成为 `{string, number}` 两种。**是"红的恰好是哪几条"这条断言把这个错抓出来
的**——只看退出码，两种改法都是红的（§2.5.68 立的规矩再次生效）。

**边界**：①核的是"文档声明的类型在真实里**出现过没有**"，**不是**"真实只有这一种类型"
（真实同时给 number 与 null 时，文档声明 number 就算通过，"可空"归 B2 提示）；②**样本
依赖**——真实侧类型是每个接口**单打一次**的并集，某字段这条样本上恰好是 null 就展不出类型
（实测 22 条这样的路径）；单次采样让判据**更严而不是更松**（真实类型集合越小，`dec ⊆ rts`
越难过），但它仍只是采样面；③**值面除 `ok` 外一概不判**——别把它读成"值已经核过了"。

§2.5.80 补的**写操作入参面**是**第二十二个**（2026-10-05）：结的是 §10.5 三条「比不出来」
的**第三条——POST 接口**（原文「它们写库，只读核查不打，如实列在『未比对』里。这批的错误
只能靠人核」）。**本节第一步是把「打不了」与「不能核」分开**：前半句是只读核查的**能力**
限制（打了就改数据），后半句却成了**结论**（因此一条判据都没有）。可写接口的**入参面**
完全能静态核——契约两端都在磁盘上，一端是调用方 `static/*.js`、另一端是被调用方
`web/*.py`，**全程不发一个请求**。

**基准取前端而不是文档样例**，理由是实测出来的：**文档 POST 样例把请求体与响应体画在
同一个 ```json 块里**，读者分不清哪个是入参——`/api/review/items` 的 7 个键里只 3 个是
入参（`action`/`edits`/`note`），`/api/review/promote` 的 24 个键里也只 3 个。这不是笔误，
是这批样例的**普遍形态**（03 号那处 §10.6 已记过）。而**前端发的键是运行时真发出去的**，
不随文档漂移，且「前端发了、后端不读」是一种真实的静默失败：用户点了按钮、界面提示成功、
字段被悄悄丢掉。

**口径比 09 号原文宽一格**：写路由 = **POST + DELETE**（同一批写操作里还有 2 条 DELETE
前端也在调，同一个病、同一个判据）。

**三档硬 + 两档定量**：A1 前端**发**而实现**不读**的键（静默丢弃）／A2 每条写路由**至少
有一个前端调用点**（死接口）／A3 每个前端调用点**须绑到一条真实路由**（打空）；B1 body
**解不出**的调用点（**不进 A1、也不算通过**——否则"不透明"会变成静默豁免）／B2 实现读而
前端从不发的键（可选参数）。**A2 与 A3 是一对反向判据**，闭式因此写成"有调用点的路由数 +
无调用点的路由数 = 写路由总数"并当场断言。

实测：**13** 条写路由（POST 11 + DELETE 2）、**14** 处前端写调用点、**绑定 14 对全部绑上
真实路由**、**A1/A2/A3 三档全绿**、闭式 `13 + 0 = 13`。进 A1 判定的是 **8** 处（14 减 6 处
无 body），逐条发了什么都列在 01 号 §2.5.80 第五节。**B1 6 处（42.9%）全部是"确实没有
body"**（参数在 URL 里：`task_id`/`stage_id`），**是设计不是盲区**——但判据分不出"没有"与
"解不出"，故脚本**逐条打印**，靠人眼区分。**B2 一条**：`extract.api_create_task` 读
`concurrency` 与 `enable_split` 而前端从不发，而 `02_审核与提取.md:372` 的样例**把它们画成
了入参**（三个键里前端只发 `raw_ids`）——`enable_split` 前端不传即落到默认 `False`，而样例
画的是 `true`。**不是缺陷**（都是带默认值的可选参数），但它是"文档 ↔ 前端不一致"的一处
实证；另注 `staging_executor.py:23` 自己写着「`enable_split` 参数会落库，但**当前不生效**」
——「有名无实」这次落在**函数入参**上（§2.5.65 是列、§2.5.66 是配置项）。

**本节的工作量主要在解析器上，两个坑把首版骗过去了**：①**`or {}` 让 `get_json()` 不是
赋值右值本身**——三个文件一律 `body = request.get_json(silent=True) or {}`，`or {}` 把它
变成 `BoolOp`，按"右值是 `Call`"判会**一条都解不出**，于是 A1 把前端发的**每一个键**都报成
"实现不读"（红的是一片不是一格）；②**同名函数跨文件覆盖**——`api_create_task` 在
`collect.py` 与 `extract.py` **各有一个**，首版只用函数名做 key，`extract` 那份把 `collect`
的**盖掉了**，报出"`collect.js` 发的 5 个键实现不读"而其实那个函数确实读。**两个文件里各
有一个同名函数是对的，一个文件里有两个是错的**——这是 §2.5.66「同名不同物」在解析器里的
复现。key 改为 `模块.函数`。前端侧另有三个封装（`send`/`req`/`post`）、四种 body 构造形态、
拼接式 URL（按顶层 `+` 切分后与 `<x>` → `[^/]+` 匹配），取 `fetch` 第二实参**必须括号配对**
（非贪婪正则会在 `headers: {…}` 的 `}` 处提前停下，把三处带 body 的 POST 全报成"无 body"）。

**自证七例、两个注入面都接**（源码面 5 + 文档面 2），断言的是"红的**恰好**是哪几档"：
改 `verdict` 键名 → `{a1}`；实现多读一个前端不发的键 → **∅**（落 B2）；一条 `promote`
调用点指向不存在的路由（另一条仍在）→ `{a3}`；把 `/api/collect/tasks` 的调用点改成 GET
