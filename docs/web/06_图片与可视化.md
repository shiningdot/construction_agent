## 一、功能目标与用户场景

### 目标
两件事：
1. **让事故现场图片可见**——详情页里图文对应，而不是只有一个崩溃的占位框
2. **让全站图表风格统一**——四份蓝图里出现了金字塔、条形图、热力图、折线、漏斗、徽章，需要有统一的规范与实现方式

### 两条用户路径

| 路径 | 动作 | 系统行为 |
|---|---|---|
| **看现场** | 打开事故详情页 | 图片画廊（缩略图网格）+ 灯箱放大 + VLM 分析结论 |
| **看趋势** | 打开致因分析页 / 概览页 | 统一的图表渲染（同一套配色、字号、刻度规则） |

### 设计约束
图片资产经过**三轮迭代**（`images/` → `imageV2/` → `imageV3/`），最终版是 `imageV3/`。数据库登记表 `image_files` 却把三版的路径**混在一起存**，且**没有指向最终版的完整映射**。本蓝图要解决的是「以最终版为唯一真源，重建登记」，而不是修补旧路径。

## 二、现状诊断

### 2.1 图片登记表与磁盘实际状态

**`image_files` 表（1,037 行，涉及 476 个事故，11 列）**：

```sql
id, accident_id, local_path, source_url, source_page_url,
file_size, width, height, mime_type, download_status, created_at
```

`local_path` 实测**三版混存**：

| 一级目录 | 条数 | 说明 |
|---|---:|---|
| `imageV2/` | **550** | 中间版 |
| `images/` | **276** | 初版 |
| `imageV3/` | **211** | **最终版** |
| 合计 | **1,037** | |

全部记录的 `download_status` 都是 `'downloaded'`——**该字段不可信**：三条路径指向的目录内容并不一致，标注"已下载"不等于文件真的在那。

**磁盘实际状态**：

| 目录 | 目录数 | 文件数 | 说明 |
|---|---:|---:|---|
| `data/images/` | — | 263 | 初版 |
| `data/imageV2/` | — | 464 | 二版 |
| `data/imageV3/` | **427** | **226** | **最终版**（168 jpg + 55 png + 3 webp） |
| `data/clip_test/` | — | 317 | CLIP 阈值判读样本（非数据） |

### 2.2 「少注册 15 条」的确切含义

CLAUDE.md 记载的「imageV3 少注册 15 条」实测确认：

```
imageV3 实际文件数                    : 226
image_files 中指向 imageV3/ 的记录数  : 211
                                差值  : 15
```

**这 15 个文件存在于磁盘但不在登记表里**，因此永远不会被前端展示。这正是需要重建登记的直接理由。

### 2.3 目录与事故的对应关系（实测）

`imageV3/` 的目录名 = `accident_id`（12 位十六进制，与 `accidents.id` 格式一致），实测 **427 个目录全部能在 `accidents` 表中找到对应**——**目录命名规则是可靠的**。

| 关系 | 数量 |
|---|---:|
| `imageV3` 目录总数 | 427 |
| 其中**非空**目录 | **193** |
| 其中**空**目录 | **234** |
| `image_files` 涉及的事故数 | 476 |
| `imageV3` 与 `image_files` 两边都有 | 229 |
| **仅 `image_files` 有（无目录）** | **247** |
| **仅 `imageV3` 有目录** | **198** |
| `imageV3` 非空目录 ∩ `image_files` | **178** |

**读法**：三个数字说明现状不可修补——247 条登记找不到目录，198 个目录不在登记里，只有 178 个非空目录是两边都能对上的。**任何"按 local_path 直接取图"的展示方案都会大面积 404。**

### 2.4 VLM 分析结果

`image_analyses` 表 **282 行**，记录了多模态分析结论（阶段一场景观察 + 阶段二上下文融合）：

```sql
id, accident_id, local_path, source_url,
phase1_scene_type, phase1_objects, phase1_people, phase1_damage, phase1_weather,
phase1_raw_response,
phase2_consistency, phase2_confidence, phase2_new_info, phase2_raw_response,
vlm_model, duration_ms, created_at
```

- 默认 `vlm_model = 'qwen-vl-max'`（建表 SQL 硬编码，`create_db_v2.py:116`）
- 但项目文件地图记载 VLM 使用 **GLM-5V-Turbo**（`worktree/construction_agent/extraction/vlm_analyzer.py`，两阶段盲观察 + 上下文融合）
- **模型名与实际调用不一致**，需核实（待决项 C）
- `image_analyses` 与 `image_files` 通过 `local_path` 关联——**同样受 2.1 的路径混存问题影响**

## 三、路径对齐方案

### 3.1 原则：以文件系统为真源，重建登记

**不做**的事：
- ❌ 不修改最终库的 `image_files` 表（会污染论文数据，且改动无法验证）
- ❌ 不按 `local_path` 做字符串替换（三版混存，替换规则无法统一）
- ❌ 不删除 `images/` 与 `imageV2/`（属可清理项，需作者确认，见文件地图第十一节）

**做**的事：
- ✅ 扫描 `imageV3/` 生成**新的登记表**，放在**工作库**（`data/caiems_staging.db`）
- ✅ 从旧 `image_files` / `image_analyses` **尽力回填** `source_url` 与 VLM 结论（能对上就填，对不上留空）
- ✅ 最终库的 `image_files` 保持原样，作为历史审计留痕

### 3.2 新表：`image_manifest`（工作库）

```sql
CREATE TABLE image_manifest (
    id           INTEGER PRIMARY KEY AUTOINCREMENT,
    accident_id  TEXT NOT NULL,              -- 目录名，= accidents.id
    rel_path     TEXT NOT NULL,              -- 相对 data/ 的路径，如 'imageV3/<acc_id>/5eb976418594.png'
    filename     TEXT NOT NULL,
    ext          TEXT NOT NULL,              -- jpg | png | webp
    bytes        INTEGER,
    sha1         TEXT,                       -- 内容哈希，用于识别跨目录重复
    -- 尽力回填（来自旧登记，可为 NULL）
    source_url   TEXT,
    source_page_url TEXT,
    width        INTEGER, height INTEGER,
    -- 尽力回填（来自 image_analyses）
    phase1_scene_type TEXT, phase2_consistency TEXT,
    phase2_confidence TEXT, vlm_model TEXT,
    analyzed     INTEGER DEFAULT 0,
    -- 溯源
    version      TEXT NOT NULL DEFAULT 'v3',
    manifest_at  TEXT NOT NULL,
    UNIQUE(rel_path)
);
CREATE INDEX idx_manifest_acc ON image_manifest(accident_id);
```

### 3.3 重建脚本 `scripts/build_image_manifest.py`

处理步骤：

1. **扫描** `data/imageV3/` 下全部文件（`226` 个），每个文件记录 `accident_id`（父目录名）、`filename`、`bytes`、`ext`
2. **校验** `accident_id` 是否存在于 `accidents` 表——实测 **427/427 全部存在**，若有例外记入报告
3. **算内容哈希** `sha1`，识别同一张图出现在多个事故目录的情况
4. **回填 `source_url`**：用 `(accident_id, filename)` 去 `image_files` 匹配——匹配率预计有限（因 2.3 的关系表），**匹配不上就留空，不猜**
5. **回填 VLM 结论**：同上，用 `local_path` 与 `image_analyses` 匹配
6. **生成报告**：文件数、目录数、空目录数、回填成功率、无法归属的事故 id
7. **写工作库**（`INSERT OR REPLACE`，`UNIQUE(rel_path)` 保证幂等）

**空目录处理**：`imageV3/` 有 **234 个空目录**。扫描时忽略，但报告里列出来——它们代表"曾计划为这些事故配图但最终没有可用图片"，是有价值的过程信息。

### 3.4 展示层用法

详情页请求 `/api/accidents/<id>` 时，服务端：

```sql
SELECT rel_path, filename, ext, phase1_scene_type, analyzed
FROM image_manifest WHERE accident_id = ? ORDER BY filename
```

- 有记录 → 画廊展示
- 无记录 → **显示「该事故无现场图片」而非空白区域**（427 个事故有目录，但只有 193 个是非空的，所以"有目录无图"是常态）
- 图片文件由 Flask 的静态路由按 `rel_path` 提供，**必须校验路径在 `data/` 之内**（防目录穿越）

## 四、接口设计

### `GET /api/accidents/<id>/images`
既然详情接口已返回 `images` 数组（见蓝图 05），此端点供画廊单独刷新或分页使用。

```json
{ "ok": true, "data": {
  "accident_id":"0008d0662525",
  "count": 2,
  "items": [
    { "rel_path":"imageV3/0008d0662525/5eb976418594.png",
      "url":"/media/imageV3/0008d0662525/5eb976418594.png",
      "filename":"5eb976418594.png", "ext":"png", "bytes":627616,
      "analyzed": true, "phase1_scene_type":"在建建筑外立面",
      "source_url":"http://…" } ] } }
```

### `GET /media/<path>`
图片静态服务。

- 白名单根目录：`data/imageV3/`（仅最终版）
- 校验：`os.path.realpath` 后必须仍在根内，否则 403
- 缓存头：`Cache-Control: public, max-age=86400`（图片内容不变）
- **不提供 `images/` 与 `imageV2/`**——它们不是最终版，展示旧版会让同一事故出现重复图片

### `GET /api/images/stats`
图片覆盖统计（供概览页）。

```json
{ "ok": true, "data": {
  "files": 226, "accidents_with_images": 193,
  "accidents_total": 2623, "coverage": 0.0736,
  "by_ext": [ {"ext":"jpg","count":168}, {"ext":"png","count":55}, {"ext":"webp","count":3} ],
  "analyzed": 282, "empty_dirs": 234,
  "backfill": { "source_url_matched": 0, "vlm_matched": 0 } } }
```

> 图片覆盖率仅 **7.4%**（193/2,623）。这个数字**必须显式呈现**——它是采集完整性的真实反映，不是缺陷。

## 五、页面结构

### 5.1 详情页图片画廊

```
┌─ 图片（2 张）──────────────────────────────────────┐
│  ┌────────┐ ┌────────┐                             │
│  │ 缩略图  │ │ 缩略图  │   ← 网格，自适应列数          │
│  │  ▣ 已分析│ │        │                             │
│  └────────┘ └────────┘                             │
│  场景：在建建筑外立面 · 一致性：一致                  │
└────────────────────────────────────────────────────┘
（点击缩略图 → 灯箱：大图 + 左右切换 + 来源链接 + VLM 结论）
```

**交互**：
- 缩略图按需加载（`loading="lazy"`）
- 灯箱支持键盘（`←`/`→`/`Esc`）与点击遮罩关闭
- VLM 分析结论**只在灯箱内展示**，不占列表空间
- 无图时：显示「该事故无现场图片」+ 图标，**不留空白区**
- **不显示 `clip_test/` 的内容**（那是阈值判读样本，不是事故图片）

### 5.2 图表规范（全站统一）

四份蓝图共出现 6 类图表，统一规范如下：

| 图表 | 用在哪 | 实现 |
|---|---|---|
| **横向条形** | 概览五图、致因 19 类、漏斗 | CSS 宽度百分比（`width: {pct}%`） |
| **五层金字塔** | 致因分析页 | 四层横条堆叠 + 层标签（不用 SVG 多边形，CSS 更简单且响应式友好） |
| **堆叠条** | 证据三级分布 | 单行 flex，三段宽度按比例 |
| **热力矩阵** | 编码共现 | 内联 SVG 网格，色阶 5 档 |
| **折线** | 年代趋势 | 内联 SVG `polyline`，**缺口处断线** |
| **徽章** | 类型 / 等级 / 证据等级 | CSS 圆角标签 |

**统一配色**（沿用旧模板暖色 token）：

## 七、验收标准

1. `scripts/build_image_manifest.py` 扫描 `imageV3/` 后，`image_manifest` 行数 = **226**（磁盘文件数），无遗漏
2. `image_manifest` 的 `accident_id` **全部**存在于 `accidents` 表
3. 重复执行脚本，`image_manifest` 行数不变（`UNIQUE(rel_path)` 幂等）
4. 全部 226 个文件的 `rel_path` 拼接后指向真实存在的文件（脚本内自检）
5. `GET /media/imageV3/<acc_id>/<file>` 返回 200 且 `Content-Type` 正确（jpg/png/webp）
6. `GET /media/../config.py` 或任何逃逸路径返回 **403**（目录穿越防护）
7. `GET /media/images/...`（旧版路径）**不提供服务**（仅最终版可访问）
8. `GET /api/images/stats` 的 `files = 226`、`accidents_with_images = 193`、`coverage = 7.4%`
9. 对无图事故（2,623 − 193 = 2,430 条）详情页显示「该事故无现场图片」，**不出现空白区或 404**
10. 有 VLM 分析的事故，灯箱内正确显示场景类型与一致性结论
11. 全站无 CDN 引用；断网环境下页面图表正常渲染
12. 深色模式切换后，五层配色与证据三级配色对比度可辨（不出现同色相邻）
