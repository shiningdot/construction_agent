## 三、错因

三版图片目录是**迭代产物**（`images/` → `imageV2/` → `imageV3/`），蓝图
把「以最终版 `imageV3/` 为唯一真源」当成了正确目标，于是：

1. 只检查 `imageV3/` 内部一致性（登记 211 vs 磁盘 226 vs 目录 427）；
2. 发现对不上，得出「三版混存，替换规则没法统一」；
3. 由此推断「按 `local_path` 取图会 404」——**跳过了"另外 826 条指向的目录也在磁盘上"这一步验证**。

「最终版」是**采集策略**上的概念（最新一轮爬取结果），不等于「唯一有效的图片」。
旧版目录里的图片**一直躺在磁盘上、也一直在数据库里登记着**。

## 四、影响

### 4.1 web 丢掉 73% 的图片

`web/images.py:27` `MEDIA_ROOT_DIRNAME = "imageV3"`，`web/views.py:83` 的
`/media` 路由同样只认 `imageV3/`。重建的 `image_manifest` 扫的也是
`imageV3/`（`scripts/build_image_manifest.py`）。后果（**磁盘真源口径**，
数字由三版重建实测得出，非估算）：

| 指标 | 只服务 imageV3 | 三版合并 | 差 |
|---|---|---|---|
| 可展示图片 | 226 | **951** | +725 |
| 覆盖事故数 | 193 | **559** | +366 |
| 覆盖率（÷ 2,623） | 7.4% | **21.3%** | 2.9 倍 |

其中 **366 个事故（占 559 的 65%）一张最终版图都没有**——只服务
`imageV3/` 时，它们在界面上就是「该事故无现场图片」。

> 口径说明：这里数的是**磁盘目录**；本文第二节数的是 `image_files` 的
> **登记行**，同一件事给出 476。两者都对，差 83 个事故，见 §八。

### 4.2 「覆盖率」统计被低估 2.9 倍

`web/images.py:166` 把覆盖率注释为「采集完整性的真实反映」：

> 覆盖率只有 7.4%（193/2,623）。这个数字**必须显式呈现**——它是采集
> 完整性的真实反映，藏起来才像缺陷。

但 193 是 `image_manifest`（只含 `imageV3`）的事故数。三版合并是 **559**，
即 **21.3%**。**这个数字当时不是"采集完整性"的反映，而是截断的产物**——
比注释担心的"藏起来像缺陷"更糟：它把一个偏高的事实显示成了偏低。

### 4.3 去重的理由与实际代价不成比例

`web/images.py:25` 的原始顾虑：

> 只服务最终版。`images/` 与 `imageV2/` 不给——三版里同一事故可能有重复
> 图片，放出来读者没法判断哪张是最终采用的。

实测重复规模（**磁盘真源口径**，按 sha1 逐条比对）：

| 项 | 数量 |
|---|---|
| 跨版本都有图的事故 | 84 / 559（15%） |
| **同事故 + 同内容 + 跨版本（真重复）** | **19 组 / 38 张**，冗余 **19 张** |
| 为规避这 19 张而隐藏的图片 | **725 张** |
| 由此在界面上「无图」的事故 | **366 个（65%）** |
| **代价 / 收益** | **38 倍** |

（本节原先写「13 张重复 / 558 张唯一图 / 43 倍」，是登记口径下的估算。
三版重建后用 sha1 逐条比对，真重复是 19 组、38 张，冗余 19 张。）

而且这个顾虑**有更直接的解法**：保留三版并**显式标注来源版本**，读者就能
自己判断哪张是最终采用的——比隐藏更符合「让数据说话」。

## 五、修复方案（已实施，2026-10-01）

原则：**不改最终库**（论文数据），只改展示层的取材范围与标注。

1. ✅ **`scripts/build_image_manifest.py`**：`--version-dir` 改为可给多个
   目录名（默认三版全部），每条记录按 `VERSION_DIRS` 显式映射写版本短名
   （`images→v1`、`imageV2→v2`、`imageV3→v3`）。原先从目录名推短名的
   `replace("image", "")` 对 `images` 会得到 `s`——一个谁也认不出的值。
   另按文件头魔数剔除内容非图片的文件（§六的 2 个）。
2. ✅ **`web/images.py`**：`MEDIA_ROOT_DIRNAME` 改为白名单
   `MEDIA_ROOT_DIRNAMES`；`media_root()` 上提到 `data/`（`rel_path` 自带
   版本段，不再往版本目录里下沉一层）；`rel_path` 校验改为「不含 `..`
   → 第一段在白名单内 → `realpath` 落在某个版本目录内」三道。第三条不能
   省：只查前两条挡不住符号链接，只查 realpath 又挡不住
   `imageV3/../imageV2/x` 这种绕出去又落回白名单目录的写法。
3. ✅ **`web/views.py`** 的 `/media` 路由同步放开。
4. ✅ **展示层**：`for_accident` 按 `v3 → v2 → v1` 排序，每条带
   `version_badge`；`accident.js` 给非最终版打「历史版本」角标（`.is-version`，
   暖褐而非告警红），灯箱里显式标出版本。
   **未做同 sha1 自动去重**——真重复只有 19 组 / 38 张，去重的收益很小，
   而代价是抹掉「这张图从 v2 一路用到 v3」这个事实。角标已足够让读者
   判断，藏起一条不如摆出来。
5. ✅ **覆盖率口径**：`accidents_with_images` 已合并三版（559/2,623 =
   21.3%）；新增 `accidents_with_images_legacy_only`（366），把截断会丢掉
   的规模显式暴露出来；`accident.js` 里写死的「193 条 / 7.4%」已删除——
   它不但是硬编码，取数还只算了最终版。
6. ✅ **更正蓝图**：本文即为 `06` 的更正；`06` 顶部已加指向本文的提示。

## 九、重建脚本：空扫描也退 `0` 的那个坑（2026-10-01）

第 3 步（`build_image_manifest.py`）在本次空跑复核时暴露了两个问题，一个口径、一个判据。

**口径**：`--data-dir` 默认取 `settings.DATA_DIR`，而它解析的是 `config.py` 的上两级
——**在 worktree 里就是 worktree 自己的 `data/`**。那里只有一个空的 `images/`
（没有 `imageV2` / `imageV3`），于是扫描结果是一份 **0 张**的清单。同一个坑
`check_query_plan.py` 也踩过（见 `09` §13.7），只是那次的后果是结论反过来。现在默认
改为**主仓库根**（上溯 `.git`），与七条只读核查同一口径；真图片资产在真仓库里，
脚本就该往那儿看。

**判据**：`--data-dir` 指向空目录时，脚本原先**退 `0`**——目录存在、一张图没扫到，
它会安静地走完全程，把一份空清单写进工作库。原来的防线只拦「三版目录都不存在」
（退 `2`），拦不住「目录在、里面是空的」，而这两件事对使用者是同一件事：**扫错了
地方**。空清单不是重建成功，现在扫到 0 张直接退 `2`，并把「真资产在主仓库 data/ 下」
写在报错里。

> 这条与 `09` §13.4（判据两版写废）、§11.4（正则卡在逗号）是同一族：**判据自己
> 不报错，只是恒真**。「0 张也成功」和「全表扫描也算走了索引」一样，两头都真等于
> 没有判据。

顺带，这次空跑把第 3 步**真验了一遍**（此前从未跑过）：951 张 / 559 个有图事故 /
剔除 2 个假图片，与 `10_待执行清单.md` 第 3 步承诺的数字逐个一致。

两者的关系（逐条比对，可重跑）：

| 项 | 数量 |
|---|---|
| 磁盘有、登记无 | **123 张 / 83 个事故** |
| 登记有、磁盘无 | **0** |
| 两边都有 | 830 张 |

- **「登记有、磁盘无」为 0**，再次印证 §二：`local_path` 全部有效。
- **「磁盘有、登记无」123 张 / 83 个事故**是旧登记漏登的规模。CLAUDE.md
  记的「imageV3 少注册 15 条」只算了 `imageV3/` 一个目录，把另外两版的
  漏登漏掉了。
- **展示层与验收一律用磁盘真源口径**（`image_manifest`）——那才是读者
  能看到的东西；旧登记只是审计留痕。

§2.2 说「唯一文件路径 830」指登记行去重后的文件数；磁盘上另有 123 个

## 十、平铺池接入（2026-10-01）

### 10.1 一直没进清单的那 3,701 个文件

`data/images/` **顶层**躺着 3,701 个图片文件（273.2 MB），不属于任何事故
子目录。它们是初版管线「按件落盘」的产物——文件名形如
`<事故标识>_<序号>.<ext>`——从未进过 `image_manifest`，因此网页上一张都
不显示。§五 的三版重建只扫了**子目录**（目录名 = `accident_id`），顶层
文件从头到尾没被看过。

与三版子目录的内容比对：**重复 0 个**，是完全额外的资产。内部去重后
1,323 个唯一 sha1（重复率高，初版管线一张图按多个来源页各存一份）。

### 10.2 标识形态与三道归属桥

| 标识形态 | 种数 | 归属办法 |
|---|---|---|
| 8 位 hex（旧库 `accident_id` 形态） | 1,838 | 标题桥 / id 前缀桥 |
| 中文事故名 | 5 | 手工表 3 条 + 明确排除 2 条 |
| **合计** | **1,843** | 归属 412 种 / 751 张 |

**① 标题桥（语义证据）**——旧库 `accidents.title` 归一化后与主库标题唯一
相同。279 种命中，是三条路里最大的一股。

**② id 前缀桥（结构证据，本次新发现）**——主库 12 位 `accident_id` 的
**前 8 位就是旧库那个 8 位 id**（`018e3f8e` → `018e3f8e82c6`）。实测：

- 主库 2,623 个 id 的前 8 位**零碰撞**（去重后仍 2,623 种）→ 前缀唯一命中
  不可能挂错
- 与标题桥重叠的 51 种**结论零冲突** → 互为旁证
- 旧库 1,178 条里只有 139 条落在主库前 8 位内（11.8%）——两套 id 体系
  大部分不同源

它救回的正是标题桥够不着的那批：**旧库标题被改写**（「武汉在建长江大桥
引桥发生坍塌事故」→「武汉天兴洲大桥引桥钢梁断裂坍塌事故」）**或为空**
的记录。新增 130 种 / 260 张。

**③ 手工表**——3 种中文标识，主库标题与它既不相等也不构成子串，
逐条写明依据后写死在 `FLAT_MANUAL_OWNER`。手工表指向不存在的事故 id
时脚本直接报错退出，不静默降级。

### 10.3 留空不猜

- **明确排除**：`7_22广州塔吊倒塌事故`、`广州7_22塔吊倒塌事故` 共 6 张。
  主库 2,623 条里含「广州」的 28 条、含「塔吊」的 10 条，**没有一条**是
  这两组标识描述的事故。理由与计数写进 `FLAT_DENIED`，报告里点名。
- **无归属线索 668 种**：第三套 8 位 hex 体系，既不在旧库 `accidents`
  表，也不在主库 id 前缀里。
- **两桥都不通 761 种**：前缀落在主库之外（旧库独有、未进主库的事故）。

**同一事故内按 `sha1` 去重**：平铺池 3,701 个文件只有 1,323 个唯一 sha1，
不去重会让详情页出现十张一模一样的图（实测齐齐哈尔 5 张里有 2 张同内容）。
**跨事故的重复保留**——那是 `cross_accident_duplicates` 要统计的，前端会
打 `shared` 标记。

### 10.4 结果

| 项 | 重建前 | 重建后 |
|---|---|---|
| `image_manifest` 行数 | 1,020 | **1,771** |
| 有图事故 | 578（22.0%） | **805（30.7%）** |
