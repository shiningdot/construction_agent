## 三、错因

三版图片目录是**迭代产物**（`images/` → `imageV2/` → `imageV3/`），蓝图
把「以最终版 `imageV3/` 为唯一真源」当成了正确目标，于是：

1. 只检查 `imageV3/` 内部一致性（登记 211 vs 磁盘 226 vs 目录 427）；
2. 发现对不上，得出「三版混存，替换规则没法统一」；
3. 由此推断「按 `local_path` 取图会 404」——**跳过了"另外 826 条指向的目录也在磁盘上"这一步验证**。

「最终版」是**采集策略**上的概念（最新一轮爬取结果），不等于「唯一有效的图片」。
旧版目录里的图片**一直躺在磁盘上、也一直在数据库里登记着**。

## 四、影响

### 4.1 web 丢掉 73% 的图片

`web/images.py:27` `MEDIA_ROOT_DIRNAME = "imageV3"`，`web/views.py:83` 的
`/media` 路由同样只认 `imageV3/`。重建的 `image_manifest` 扫的也是
`imageV3/`（`scripts/build_image_manifest.py`）。后果（**磁盘真源口径**，
数字由三版重建实测得出，非估算）：

| 指标 | 只服务 imageV3 | 三版合并 | 差 |
|---|---|---|---|
| 可展示图片 | 226 | **951** | +725 |
| 覆盖事故数 | 193 | **559** | +366 |
| 覆盖率（÷ 2,623） | 7.4% | **21.3%** | 2.9 倍 |

其中 **366 个事故（占 559 的 65%）一张最终版图都没有**——只服务
`imageV3/` 时，它们在界面上就是「该事故无现场图片」。

> 口径说明：这里数的是**磁盘目录**；本文第二节数的是 `image_files` 的
> **登记行**，同一件事给出 476。两者都对，差 83 个事故，见 §八。

### 4.2 「覆盖率」统计被低估 2.9 倍

`web/images.py:166` 把覆盖率注释为「采集完整性的真实反映」：

> 覆盖率只有 7.4%（193/2,623）。这个数字**必须显式呈现**——它是采集
> 完整性的真实反映，藏起来才像缺陷。

但 193 是 `image_manifest`（只含 `imageV3`）的事故数。三版合并是 **559**，
即 **21.3%**。**这个数字当时不是"采集完整性"的反映，而是截断的产物**——
比注释担心的"藏起来像缺陷"更糟：它把一个偏高的事实显示成了偏低。

### 4.3 去重的理由与实际代价不成比例

`web/images.py:25` 的原始顾虑：

> 只服务最终版。`images/` 与 `imageV2/` 不给——三版里同一事故可能有重复
> 图片，放出来读者没法判断哪张是最终采用的。

实测重复规模（**磁盘真源口径**，按 sha1 逐条比对）：

| 项 | 数量 |
|---|---|
| 跨版本都有图的事故 | 84 / 559（15%） |
| **同事故 + 同内容 + 跨版本（真重复）** | **19 组 / 38 张**，冗余 **19 张** |
| 为规避这 19 张而隐藏的图片 | **725 张** |
| 由此在界面上「无图」的事故 | **366 个（65%）** |
| **代价 / 收益** | **38 倍** |

（本节原先写「13 张重复 / 558 张唯一图 / 43 倍」，是登记口径下的估算。
三版重建后用 sha1 逐条比对，真重复是 19 组、38 张，冗余 19 张。）

而且这个顾虑**有更直接的解法**：保留三版并**显式标注来源版本**，读者就能
自己判断哪张是最终采用的——比隐藏更符合「让数据说话」。

## 五、修复方案（已实施，2026-10-01）

原则：**不改最终库**（论文数据），只改展示层的取材范围与标注。

1. ✅ **`scripts/build_image_manifest.py`**：`--version-dir` 改为可给多个
   目录名（默认三版全部），每条记录按 `VERSION_DIRS` 显式映射写版本短名
   （`images→v1`、`imageV2→v2`、`imageV3→v3`）。原先从目录名推短名的
   `replace("image", "")` 对 `images` 会得到 `s`——一个谁也认不出的值。
   另按文件头魔数剔除内容非图片的文件（§六的 2 个）。
2. ✅ **`web/images.py`**：`MEDIA_ROOT_DIRNAME` 改为白名单
   `MEDIA_ROOT_DIRNAMES`；`media_root()` 上提到 `data/`（`rel_path` 自带
   版本段，不再往版本目录里下沉一层）；`rel_path` 校验改为「不含 `..`
   → 第一段在白名单内 → `realpath` 落在某个版本目录内」三道。第三条不能
   省：只查前两条挡不住符号链接，只查 realpath 又挡不住
   `imageV3/../imageV2/x` 这种绕出去又落回白名单目录的写法。
3. ✅ **`web/views.py`** 的 `/media` 路由同步放开。
4. ✅ **展示层**：`for_accident` 按 `v3 → v2 → v1` 排序，每条带
   `version_badge`；`accident.js` 给非最终版打「历史版本」角标（`.is-version`，
   暖褐而非告警红），灯箱里显式标出版本。
   **未做同 sha1 自动去重**——真重复只有 19 组 / 38 张，去重的收益很小，
   而代价是抹掉「这张图从 v2 一路用到 v3」这个事实。角标已足够让读者
   判断，藏起一条不如摆出来。
5. ✅ **覆盖率口径**：`accidents_with_images` 已合并三版（559/2,623 =
   21.3%）；新增 `accidents_with_images_legacy_only`（366），把截断会丢掉
   的规模显式暴露出来；`accident.js` 里写死的「193 条 / 7.4%」已删除——
   它不但是硬编码，取数还只算了最终版。
6. ✅ **更正蓝图**：本文即为 `06` 的更正；`06` 顶部已加指向本文的提示。

## 八、口径对照：磁盘真源 vs 旧登记

同一条"有图事故"在两个口径下差 83 个，跨文档引用时极易混淆，单列一节。

| 口径 | 计数对象 | 图片数 | 有图事故数 |
|---|---|---|---|
| **磁盘真源** | `data/{images,imageV2,imageV3}/<事故目录>/` 下的图片文件 | **953** | **559** |
| **旧登记** | `image_files` 表里的行 | 1,037 行 / 830 个唯一文件 | 476 |

两者的关系（逐条比对，可重跑）：

| 项 | 数量 |
|---|---|
| 磁盘有、登记无 | **123 张 / 83 个事故** |
| 登记有、磁盘无 | **0** |
| 两边都有 | 830 张 |

- **「登记有、磁盘无」为 0**，再次印证 §二：`local_path` 全部有效。
- **「磁盘有、登记无」123 张 / 83 个事故**是旧登记漏登的规模。CLAUDE.md
  记的「imageV3 少注册 15 条」只算了 `imageV3/` 一个目录，把另外两版的
  漏登漏掉了。
- **展示层与验收一律用磁盘真源口径**（`image_manifest`）——那才是读者
  能看到的东西；旧登记只是审计留痕。

§2.2 说「唯一文件路径 830」指登记行去重后的文件数；磁盘上另有 123 个
文件没被登记，合计 953。

三版重建的实测输出（`python3 scripts/build_image_manifest.py --dry-run`）：

```
  images    : 263 张（空目录 0）
  imageV2   : 462 张（空目录 0，剔除内容非图片 2 个）
  imageV3   : 226 张（空目录 234）
  图片文件 : 951
  归属校验 : 730 个事故目录（含 234 个空目录），不在 accidents 表的 0 个
```

（`imageV2/` 的 464 → 462 是 §六 那两个坏文件被剔除。**按扩展名数磁盘是
953 个**，剔除内容非图片的 2 个后是 **951 个可展示**——§八 的对照表用 953
是因为它数的是「登记与磁盘的文件集合关系」，坏文件也在集合里。）

`730` 是「有图目录 559 ∪ 空目录 234」的并集——**两者有 63 个重叠**
（在 `imageV3/` 里是空目录、在旧两版里有图）。直接相减会得到 496 这个
不存在的数。
