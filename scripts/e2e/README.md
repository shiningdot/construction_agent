# 端到端验证脚本

这组脚本按**验证金字塔**的三层来组织，每层专治上一层看不见的东西。

## 三层金字塔

| 层 | 手段 | 能看见什么 | 看不见什么 |
|---|---|---|---|
| ① `tests/test_web_m3.py`（pytest） | Flask test client，进程内 WSGI | 接口契约、边界、事务回滚、SQL 正确性 | HTTP 栈、真实文件锁、浏览器 |
| ② `e2e_*.py`（本目录，无 `click`） | `werkzeug.make_server` + `urllib`，两个真文件库 | 真 socket 往返、SQLite 写锁、备份落盘、`mode=ro` 与写连接并存 | DOM 构造、事件绑定、合成事件语义 |
| ③ `e2e_click_*.py`（本目录） | headless Chrome（playwright）真点击 | 选择器、事件绑定、点击后 DOM 是否真变、控制台报错 | 数据规模下的性能 |

**为什么必须有第三层**：M4 的五个缺陷全部是第③层抓到的，前两层一个都看不见。
其中「`el()` 不认顶层 `id`」和「合成 `change` 事件不翻转 `checked`」这类问题，
在 API 层完全无痕——接口 200、数据正确、页面却是空的或被反着操作。

## 脚本索引

| 脚本 | 阶段 | 覆盖 |
|---|---|---|
| `e2e_collect.py` | ① 在线采集 | 源清单、采集任务、队列、分页夹取 |
| `e2e_click_collect.py` | ① 在线采集 | 同上的浏览器真点击版：勾源 → 任务自己走完 → 表格自己刷出 → 裁决 → 筛选 → 翻页 |
| `e2e_extract.py` | ② 审核与提取 | 闸门、任务编排、成本预估、暂存结果 |
| `e2e_click_m3.py` | ② 审核与提取 | 同上的浏览器真点击版 |
| `e2e_review.py` | ③ 暂存与审核 | 漏斗、队列筛选、单条审核、批量通过、并入、回滚 |
| `e2e_click_review.py` | ③ 暂存与审核 | 同上的浏览器真点击版 |
| `e2e_pipeline.py` | ①→④ **全链路** | 用主库一条真实事故走完全程，再把并入结果与主库原文**逐列**比对 |
| `e2e_verify_main.py` | ④ 展示 · 验收 | **在主库上**对账：每个端点的数字 vs 直接 SQL、分页整本翻完查重复/遗漏、三级证据数 |

`e2e_pipeline.py` 与上面几个的区别在**段与段之间谁搭桥**：那几个各测一段，
跨段的桥由脚本手工架（直接 INSERT 一条 raw / staging 行）；这个不架桥，只走
HTTP 与真库，最后把落回新库的那一行与主库里的**同一条**逐列比对——蓝图 07
的验收标准「产出与主库同构、可无缝并入」只能这样验证。比对差异分两类：
**已知口径差异**（两侧设计上就不同，脚本里逐条列了依据）与**其余全部**
（必须相同，不同就是映射写错）。

## 跑法

```bash
source .venv/bin/activate        # 或直接用 .venv/bin/python3
python3 scripts/e2e/e2e_review.py          # ② 层
python3 scripts/e2e/e2e_click_review.py    # ③ 层（需 playwright + chromium）
```

全部**自带服务**（各自起在独立端口）与**独立临时库**，不碰主库；
并入这类真写动作也只会写进临时目录里的副本。跑完打印通过/失败数并以退出码反映。

## 另有一组只读核查脚本（在 `scripts/` 根下，不在本目录）

上表那几个会**造数据、真写库**（临时库）。另有一组**只读**的核查脚本，跑在真实
主库与工作库上，验的是「做出来的东西对不对」而不是「流程走不走得通」：

| 脚本 | 查什么 | 端口 |
|---|---|---|
| `scripts/screenshot_web.py` | 六个页面逐张截图，报破图 / 空白 / 控制台报错。详情页样本两级挑，工作库没建好也照样截 | 5099 |
| `scripts/check_web_interaction.py` | 概览页真点击十一条（两页维度齐全 / 筛选 / 翻页 / 分享链接 / 过期链接自愈 / 搜索 / 重置） | 5100 |
| `scripts/check_field_alignment.py` | 前端读的名字 ↔ 后端返回的字段；**反向**：`accidents` 的列 ↔ 详情页四档 | 不起服务（`app.test_client()`） |
| `scripts/check_blueprint_alignment.py` | 蓝图规定的接口 ↔ 代码注册的路由 | 不起服务（纯静态分析） |
| `scripts/check_api_contract.py` | 蓝图画的响应样例 ↔ 真实响应的**字段** | 不起服务（`app.test_client()`） |

五条都只读不写，跑几次都行。它们的结论与判据记在
`docs/web/09_端到端对齐核查.md`（§六 渲染、§七 字段〔含 §7.3 反向那一半〕、§八 交互、
§九 蓝图↔实现、§十 响应契约）。

`check_api_contract.py` 跟上面四个各管一头：字段核查问「前端有没有人读它」，
蓝图核查问「路由在不在」，**中间空着「文档写了这个字段、实现给没给」**——这一格
由它补。退出码 `0` = 没有硬缺口、`1` = 有，可直接接 CI。想连采集 / 提取 / 审核
三组一起比，加 `--staging-db` 指向测试工作库：

```bash
.venv/bin/python3 scripts/check_api_contract.py --verbose
.venv/bin/python3 scripts/check_api_contract.py \
    --staging-db .claude/worktrees/classifier-mod/data/caiems_staging.db
```

## 两个约定

- **端口各占一个**，别改重复：采集 5091 · 采集点击 5092 · 提取 5093 · 提取点击 5094 ·
  审核 5095 · 审核点击 5096 · 全链路 5097 · 主库对账 5098 · 截图 5099 · 交互核查 5100。
  （踩过：交互核查第一版默认 5098，正好是主库对账的端口，两套同时跑会撞。）
- **`e2e_verify_main.py` 跑的是真主库**（只读，不写）。它慢不慢取决于主库有没有
  索引：实测无索引时整本翻页 2,590 ms/页、`?has_causes=1` 要 3.6 秒；补上
  `scripts/add_indexes.py` 的 9 个索引后是 6.1 ms/页 与 3 ms。跑之前先看它开头
  有没有那行缺索引警告。
- **主库路径由 `CAIEMS_MAIN_DB` 决定**，默认解析到 worktree 上两级的 `data/caiems_v2.db`。
  主库只被读（取 CAICS 类名与枚举口径），不被写。若默认路径解析不到，提取会**静默**
  拿到空分类体系——所有编码都判不出来却不报错，所以路径要显式。
